# Charts — design notes (Phase 1)

The Charts section of `AGENTS.md` carries the contract. `@glyphcss/charts` renders a declarative mark spec through the existing cell canvas; it never uses a camera, mesh, depth test, DOM layout, or the 3D rasterizer. Phase 0's canvas remains unchanged.

## Spec and pipeline

Constructors return plain marks. The renderer accepts a mark, marks array, complete spec, or numeric array (line shorthand). Numeric data defaults each missing axis independently to `x = index`, `y = identity`; explicitly supplied channels win. Records require x/y channels for cartesian quantity marks. Arcs require only the value channel `y` (`arc-missing-value` if absent); their category is `fill`, falling back to `label`, then the row index. Numeric arc arrays use the element as value and the index as category. Dates infer time, strings infer bands, numbers infer linear. Categorical y is supported by dot marks and paints at the band's centre.

The fixed order is validation and channel materialization → transforms → one d3 scale per axis → budgeted layout → fills → axes → lines/dots → labels → encoding. A chart's marks share their scales. Titles, legends and axis gutters reserve their cells before geometry is painted. Arc/text-only charts skip cartesian axes; tiny positive integer viewports omit axes when no room remains.

`width` and `height` are positive integers. Zero, negative, fractional and non-finite sizes reject with `bad-size` before layout or canvas allocation, including values forwarded by the page and CLI.

## Quantities, domains and stack bounds

A zero bar/rect has no painted cells. Bar extent excludes the baseline and includes its nonzero value endpoint after rounding: positive and negative bars extend on opposite sides of the same unpainted baseline. Coincident rounded endpoints produce no cells. Cell heights approximate the values within one cell; inclusive endpoints would invent one cell of quantity per bar. All-zero pies paint no cells and record an `empty-total` ledger entry. Negative pie values contribute zero to the nonnegative total.

### Ledger entries read like a sentence, not a log line

`report.ledger` is `GlyphChartLedgerEntry[]` — `{ code, message, detail? }`. Early versions pushed free-text lines like `layout: x ticks thinned 13 -> 7 (every 2th tick before collision thinning)`: an internal log format (a `layout:` prefix, an arrow, and a broken ordinal — "2th" instead of "2nd") that read fine to the person who wrote the string and as noise to everyone else. `ledger.ts` is now the ONE place a ledger string is authored: every producer (`layout.ts`'s axis-tick thinning/duplicate-drop/title-drop/legend-drop, `paint.ts`'s series-dodge degrade/empty-pie/dropped-slice, `labels.ts`'s abbreviate/drop) calls a typed constructor that returns a stable kebab `code` (`ticks-thinned`, `label-abbreviated`, `label-dropped`, `legend-dropped`, `title-dropped`, `series-dodge-degraded`, `empty-total`, `slice-dropped`, `double-diagonal-solid`, `tick-duplicate-dropped`) plus ONE plain-English `message` with no colon, no arrow, and no bare ordinal — `ticks-thinned`'s counts and stride live in `detail`, never spliced into an "every Nth tick" clause, which is what made the ordinal bug possible in the first place. The shared cell canvas's own free-text "double style has no diagonal analogue" note (`GlyphCanvasReport.ledger`, `string[]`, shared with `@glyphcss/diagrams`) is parsed once at the render boundary (`chartLedgerEntryFromCanvasMessage`) into the same `double-diagonal-solid` shape, since it is the only message that source ever produces. `renderGlyphChartJson` serializes the structured form as-is. The website's `/charts` page shows NO ledger readout at all — `report` stays in the API and the CLI (`glyphcss chart`) only, for callers that actually consume it as data rather than prose to skim.

Bar, rect and area inferred y domains include zero. An explicit numeric domain excluding zero rejects with `bar-domain-excludes-zero`. Rect uses the same baseline rule as bar. Degenerate linear domains expand to avoid division by zero. `scaleLog` and `scaleSqrt` handle the corresponding requested scale types; neither is substituted with linear. Log domains must exclude zero and retain one sign (`log-domain`), so zero-anchored marks need a zero-capable scale. A singleton log domain expands multiplicatively. `nice: true` uses d3's nicening; omitted/false preserves domain endpoints.

JSON time domains accept calendar-valid ISO strings. Validation returns a normalized spec containing parsed Date domains, which the renderer reuses. Time scale resolution caches each distinct data value's conversion. Malformed dates reject with `bad-time-domain`; no untagged `getTime` exception reaches the caller. Time tick labels use d3's multi-scale formatter, preserving hour/minute distinctions within a day.

The minimal transforms are `bin`, `stack`, `group`, `normalize`, and `window`. Stack accumulates each input row at its x, emitting `y0` and `y1`. Stack and group key Date values by their timestamp, so distinct objects for the same instant share a stack/bucket; group retains the first original x value to preserve time-scale inference. Bar and area paint those bounds. Area connects each stack layer independently; without an explicit series, the kth occurrence at each x belongs to the kth layer. Both lower and upper boundaries interpolate between adjacent x positions. Filling to original y or connecting different stack layers would leave a false sloping gap. Bin uses equal-width x buckets and yields a count per bucket; tests assert the distribution, not only its total.

## Series, styles and shading

Categorical `fill` or `stroke` splits line/area/dot (also bar/rect) into independently painted series. `fill` takes precedence when both channels are categorical. One grouping function supplies painting, `meta.series`, and the legend, with shared identities across composed marks. Numeric heatmap fill and pie quantities are not series identities. Arc categories (`fill`, then `label`, then index) use this same series/metadata/legend path; repeated categories sum into one slice. Nonpositive arc values occupy no angle and have no legend entry, preserving the empty all-zero pie. A supplied mark name identifies an otherwise ungrouped mark.

With colour enabled, named series get distinct palette colours. Without colour, lines and area boundaries cycle the canvas's solid, dashed, dotted and double line styles; dots cycle `● × + ◆` or ASCII `o x + *`. Legends include their names and matching swatches. Canvas styles retain their existing semantics: dashed/dotted runs use gaps, and a double diagonal falls back to solid with the canvas's ledger entry. This is a frozen canvas limitation, not a chart-specific replacement glyph. `size`, `shape`, and `curve` are removed from public types and schema and reject when supplied; Phase 1 does not advertise those unused APIs.

The legend row shows whenever at least ONE series is named — not more than one. The threshold used to be `names.length > 1`, so a single-mark chart with a `name` (the shipped tray presets: "Revenue", "Sales", "Visits", "Traffic", "Activity") built a legend entry in `meta.series` but never painted the row, because nothing distinguishes "one named series" from "one unnamed series" until the row itself renders the name. `>= 1` is the only threshold under which "every mark constructor accepts `name?`" and "a named mark gets a legend entry" are the same sentence.

**Braille-tier fills are `blocks`' own quadrant glyphs, not braille dot patterns.** `fillRect` (bar/area/rect/cell — anything painted as a region rather than traced as a curve) on `braille` used to reuse `subGlyph`, the SAME mask-to-glyph function `line()`/dots use, which meant a solid bar read as `⣿` (the braille full-block codepoint) rather than `█`. A fill is DENSITY, not a curve, so it gets its own table entry (`tiers.ts`'s `fillSubGlyph`, `undefined` on every tier but `braille`, where `canvas.ts`'s `fillRect` consults `fillSubGlyph ?? subGlyph`) pointing at the exact function `blocks` already uses — never a parallel table, so a braille bar/area/heatmap is pixel-identical to the same chart under `blocks`. `line()`'s own dots are untouched (still `subGlyph`), so a braille line chart still reads at genuine sub-cell resolution; a chart mixing a filled area with a braille line reads as a solid region next to a dotted curve, which is the whole point.

Arcs paint all categories against one shared total, never one full disc per grouped series. Slice styles cycle `█ ▓ ▒ ░` for box/blocks/braille and `# % + .` for ASCII, with the closing slice advanced if it would match the first. The shade cycle stays active with colour enabled, so removing colour downstream preserves the picture. Slice and legend share the same shade; coloured output adds the matching series palette colour to both. These categorical full-cell shades use `canvas.text`, since the frozen canvas's continuous `fillRect` shading would instead produce subcell occupancy on blocks/braille. This leaves the continuous heatmap ramp unchanged.

Cell shading shares one value domain across all cell marks. Mixed signs ramp each side independently from zero (blank) out to its own extreme (full ink) — blank means "no signal" and is reserved for exactly zero, never for the domain's most extreme value: an earlier mapping anchored blank at the most-negative value and a medium shade at zero instead, so a gains/losses heatmap's biggest loss read as missing data while zero (genuinely nothing happening) read as visible ink — exactly backwards. Same-sign data use one sequential ramp including zero, where the domain minimum alone is blank and a `GLYPH_CHART_CELL_MIN_INK_SHADE` floor keeps every other value visibly inked. The ordered ramp preserves sign and never takes `Math.abs(value)`: `[-10, 0, 10]` produces full ink, blank, full ink rather than two identical extremes collapsing under an absolute-value fold. The cell canvas owns each tier's shade-to-glyph conversion.

## Text and axis labels

All chart strings are measured through `canvas.text` on a scratch row and painted through `canvas.text` on the output. This uses the canvas's actual grapheme folding and cell widths. For ASCII, NFD input exercises the canvas's accent fold; the chart then restricts remaining single-cell Unicode to printable ASCII. Minus is `-`, ellipsis is `...`, and all three dots count against the budget. Output labels, titles, text marks, and tick formatting share this policy; no direct grid writes bypass it.

`glyphChartLabelLayout` owns abbreviation, viewport placement and collision handling. Numeric overflow first uses two-significant-digit SI (`1234567` → `1.2M`); a numeric label that still doesn't fit after SI abbreviation is DROPPED entirely, never truncated with an ellipsis — cutting characters off a formatted number produces a different, plausible, wrong one, where a category label can safely elide with `…`. Every abbreviation (and every drop) is recorded. Axis labels use this same policy: band labels abbreviate within their slots, y labels within the gutter, numeric/time labels within the viewport. Painting uses the measured left edge, so the canvas never clips either end. Band labels too crowded for useful abbreviations retain every kth category; all axes additionally thin collisions and record what was removed. Time tick formatting is multi-scale, not one date format repeated across intraday ticks.

## Axes: tick marks, requested counts, integer data, titles, grid

`spec.axes?.{x,y}: { ticks?, tickMarks?, title?, grid? }`, default ON for `tickMarks`. The tick-mark glyphs (`┤`/`┴`/`└`) are not a new table: they are the box tier's own JUNCTION table, read at the exact bit combinations that already mean "up+down+left", "up+left+right" and "up+right" for a route drawn through the cell canvas. Reusing that table rather than inventing a parallel one is what makes `ascii`'s tick glyph (`+`) free — its junction table already collapses every multi-stem combination to `+`, so no ascii-specific tick logic exists at all. `tickMarks: false` on an axis reverts it to the ORIGINAL two-`canvas.line()`-call sweep (the whole-cell rule this feature replaced), byte-identical to the feature not existing, rather than a third code path that happens to look the same.

`ticks` is a REQUESTED count, fed straight into `scale.ticks(n)` in place of the auto-fitted budget (label width × available space) the layout otherwise computes — it does not bypass the existing collision/stride thinning underneath it, so a request larger than what fits still degrades to an evenly-spaced subsequence rather than overlapping labels.

Integer/index data (every value the axis actually plots is a whole number — checked against the RESOLVED ROWS, not the scale's domain) never shows a fractional tick. d3's own "nice" ladder reaches for half-steps well before it runs out of room on a small domain (`[0,3].ticks(6)` returns `0, 0.5, 1, ..., 3`), which reads as real data on an axis whose only legitimate values are whole numbers — this is what the shipped `bar`/`README` examples on a `[3, -5, 2, 8]` index domain used to show. The fix filters the resolved tick set to integers post-hoc (never re-deriving a different tick algorithm) and falls back to the unfiltered set if filtering would empty it, so a genuinely fractional domain is never forced to show nothing.

`title` defaults to the axis channel's own field name — read off `mark.channels[axis]` when it is a plain string, never an accessor or literal array, which has no name to report — and is suppressed by an explicit `title: ""`. This default reaches EVERY chart whose x/y channel names a real field, which is deliberately wide: a record-shaped chart almost always has a meaningful field name and almost never had an axis title before, so this is a visible layout change (one more reserved row) for a large fraction of existing charts, not an edge case. The x title sits centred under its own tick-label row (reserved BELOW that row, so both survive together or the title alone drops first on a short chart); the y title sits top-left ABOVE the axis, because a rotated column of glyphs has no character-grid analogue — there is no "vertical title" option to build.

`grid` (default `false`) paints faint gridlines at tick positions — `┈` (horizontal, at y-tick rows) and `┊` (vertical, at x-tick columns), `.` on ascii for both. Painted FIRST, before any fill/line/dot mark and before the axis itself, so a gridline sits strictly behind the data it exists to help read.

## Validation and JSON Schema

Rule IDs and repair hints are explicit. Schema and runtime share mark/channel/transform/scale vocabularies and ISO calendar syntax. The schema enforces non-empty data, required x/y for cartesian records and y alone for arc records (`arc-missing-value`), known transforms, non-null marks, supported options, explicit numeric/time domain constraints and zero inclusion for explicit quantity domains. Runtime checks also inspect materialized/accessor-produced data and inferred scale domains; those data-dependent operations cannot be expressed generally in standard JSON Schema. Functions and Date objects are native-only representations; JSON uses field/array channels and ISO strings.

Ajv is a devDependency of charts only. Tests run the real draft-2020-12 evaluator over all shared positive fixtures and each designed bad spec, comparing its verdict with runtime validation. Render-size tests validate an independent integer-size schema because width/height are render options rather than spec properties. Non-finite values reject with `non-finite-data` before inference or painting. Every rule has a separately authored failing input rendered through the public entry and checked for its exact code and table membership; deleting a rule cannot pass a circular annotation-only test.

## Targets, page and CLI

Defaults are exported once as `GLYPH_CHART_TARGET_DEFAULTS`: chat is 72×24 box/no colour, terminal 80×24 braille/truecolor, web 96×32 braille/CSS — braille is the default wherever a sub-cell tier is safe. **`chat` stays `box`, REVERTED from an earlier braille default**: a chat client's own fenced code block renders in whatever monospace stack its own CSS picks (SF Mono, Menlo, Consolas, JetBrains Mono, ...), a choice this package cannot make on the visitor's behalf, and none of those stacks reliably carries the braille block (U+2800-28FF) — a braille chart pasted into chat therefore misaligns rather than merely losing a junction glyph, where `box` degrades no data at all (it is `line`/`dot`/an area's own whole-cell fallback tier). ANSI also never survives a paste, hence `color: "none"`. The bare `renderGlyphChart(x)` call (no `options` at all) defaults to `target: "web"` — a reader who hasn't chosen a target yet is almost always looking at a browser or an agent transcript rendered in one, and `web` is the one target this package can guarantee a complete font for (below). Braille uses the canvas's box-style axes and strokes with subcell fills. Render `text` remains the requested encoding: plain text for none/CSS, SGR for ANSI16/ANSI256/truecolor; CSS additionally provides escaped HTML. `NO_COLOR`/`FORCE_COLOR` are read from the explicit environment option only. Colour suppression also selects monochrome series styles, so series remain distinguishable after ANSI is removed.

**The website ships its own font, "Glyph Mono"** (`website/public/fonts/glyph-mono*.woff2`, declared in `website/src/styles/glyph-demo.css` and put first in the `/charts`/`/diagrams`/`/maps`/`/synth` pages' own font stacks): a Cascadia Mono (OFL) subset covering ASCII/Latin-1, arrows, box drawing (U+2500-257F), blocks (U+2580-259F), geometric shapes and braille (U+2800-28FF) at ONE advance width, so `web`'s braille default never has to trust a visitor's system font to carry it — the exact failure `chat` opted out of above is the one `web` closes for itself instead of merely avoiding. The internal name table is rewritten with fontTools (`python3 -m fontTools`) so the subset carries its own family name rather than reusing Cascadia's, respecting the OFL reserved-name clause. `font-display: block` avoids a fallback-font flash mid-render reflowing an already-painted grid. The colour font-atlas path (`GLYPH_FONT_ATLAS`) is untouched — it pins its own family per `<pre>` and never reaches this stack.

**`TargetPreview`** (`website/src/components/TargetPreview/`, one component shared by the charts and diagrams workbenches) frames the SAME `<pre class="glyph-output">` differently per target rather than changing what gets rendered into it, so Copy ASCII/Copy ANSI/Download SVG — all of which read that exact node — are unaffected by which frame wraps it. `web` is unframed, byte-identical to the render before this component existed. `terminal` gets a dark terminal-window chrome with a title bar naming the command a real CLI call would use, and its SGR string is decoded into real `<span>` colour by a small standalone `ansiToSpans` module (16-colour, 256-colour, truecolor, fg+bg, full and per-channel reset) — a browser has no ANSI decoder of its own, so without this a terminal preview would either show raw escape bytes or silently drop colour; the module duplicates xterm's standard 16/256-colour RGB tables (not exported by the canvas's own ANSI encoder, which treats them as a private encoding detail) and is unit-tested with no DOM at all. `chat` gets an assistant-bubble frame around a fenced-code-block look, deliberately set in a ChatGPT-like font stack (`ui-monospace, SFMono-Regular, "SF Mono", Menlo, Consolas, "Liberation Mono", monospace`) INSTEAD OF Glyph Mono — showing what a real chat client's own font does to the output is the entire point of this frame, which is also why `chat`'s default charset stays `box` (above).

The page tracks explicit overrides per control, including a choice equal to the current default. Switching target applies defaults to untouched controls; Reset to target defaults clears all overrides. The browser frames chat/terminal/web previews as described above; it never inserts raw ANSI escapes into a pre (the terminal frame decodes them into spans instead). Copy as text always copies plain cell text; Copy ANSI copies the encoded string. Tests mount the component and exercise selectors, reset, presets, both clipboard actions, fractional inputs, and which frame renders per target.

`renderGlyphChartJson` is the string entry for MCP/skill wrappers and readers of the CLI's `<spec.json>` file format. The file-based CLI parses JSON and calls the renderer directly; there is no `--stdin` flag. `glyphcss chart` parses actual argv, reads the spec, and forwards dimensions without rounding. It defaults to ANSI on a TTY and plain output on a pipe, with explicit colour taking precedence. Chart errors preserve their rule ID and exit 1; a missing file also exits 1. Tests exercise parsing and the command boundary as well as injected TTY selection. Real PTY/browser-server interaction is outside these automated checks; no server is required.

**Each mark card's PRIMARY data view is a table**, not the JSON textarea (`website/src/components/ChartsWorkbench/ChartsMarkCard.tsx`/`chartsWorkbenchState.ts`). Columns are a record's own field names, or the single pseudo-column `value` for a plain numeric array; rows edit inline (a numeric-looking string parses to a number, a `Date`-looking string — `\d{4}-\d{2}-\d{2}...` — stays a string on purpose, since coercing it would silently change what a time-scaled chart reads). The table and the JSON tab are ONE state: every edit (`setCell`, `addRow`, `removeRow`, `addColumn`, `renameColumn`, `removeColumn` in this file's own naming convention) reads and rewrites the same `dataText` string a fresh `chartMarkTable()` call re-derives on the next render, so nothing is duplicated or can drift. Adding a column to a numeric-array table PROMOTES it to records on the spot (`value` becomes an explicit field alongside the new one) rather than discarding the shorthand or refusing the edit. Every one of those six operations, plus the pure derivation itself, is tested with NO DOM (`chartsWorkbenchTable.test.ts`); channel selects continue to populate from `chartMarkFields`, which already read the table's own columns before this feature existed.

## Round 3: the rendering diagnosis fixes

`CHARTS-RESEARCH/DIAGNOSIS-charts-rendering.md` measured the shipped `/charts`/`/diagrams` pages against the built package and found the renderer's own logic honest but its OUTPUT visibly wrong in four structural ways, plus a website-side font cascade defect. Fixed here; every finding below has a dedicated `roundFixes.test.ts` gate (plus updates to the pre-existing tests whose assertions had pinned the bug).

**B1 — bars/areas floated above the axis.** The x-axis LINE used to be a row reserved unconditionally BELOW the plot (`layout.ts`'s `xAxisLineRow = bottom; bottom -= 1`), so `scaleToRow(scale, plot, 0)` — the baseline every bar/area painter excludes from its own fill — landed on the plot's OWN last row, one row above the drawn rule. Reading from the axis (where the eye anchors), every bar was two rows taller than its value implied and never touched the line meant to anchor it. The fix removes that separate reservation: the axis line row IS now derived from the y-scale itself, via the exact same `scaleToRow`-style fraction→row mapping the painters already use — `plotForTicks.y1` (the plot's structural bottom) when 0 isn't in the domain, or wherever `toFraction(0)` actually lands otherwise, which for the ordinary all-nonnegative/zero-anchored case is the SAME row (`toFraction(0) === 0`), and for a mixed-sign domain is genuinely INTERIOR to the plot. No change to `paintBar`/`paintArea`'s own row arithmetic was needed — the "stop one row short of the baseline" half-open exclusion was already correct, it was just being fed a baseline that didn't match where the rule was actually drawn.

The interior case (B6a — a mixed-sign bar's zero row used to be blank, with the drawn axis rule sitting under the negative bars where it marked nothing) falls out of the SAME mechanism for free: `xAxisLineRow` can now be interior, `paintAxes` draws the rule and its tick marks there, and a positive bar stops one row above it while a negative one stops one row below — "the axis line row IS the y=0 row" turned out to mean literally that, not "in addition to it." Two consequences needed separate handling once the row could move: the y-axis's own VERTICAL rule must still span the full plot top-to-bottom (it used to stop at `xAxisLineRow`, which orphaned the negative region entirely), with its corner glyph promoted from a plain corner (`└`) to a T-junction (`├`) whenever the line is interior; and a `rule` mark whose own value happens to sit exactly on the axis's row must not draw a second, redundant dashed overlay on top of it (`paintRule` skips a row/column match against `xAxisLineRow`/`yAxisCol` — the axis is already there, and drawing over it only stomps its tick-junction glyphs where both would otherwise agree on a plain `─`). A line/dot touching the y-scale's own minimum can now legitimately share a cell with the axis line too; painting axes AFTER marks was tried as the fix and reverted (it silently ERASED the touching mark instead of merely blemishing the axis glyph beside it — see `paint.ts`'s own comment at the call site), so the accepted trade-off is the reverse: that one column may carry the mark's own sub-cell ink over the whole-cell axis glyph.

**B2/B6d — stacked/dodged series and heatmap cells were visually identical in monochrome.** A bar/rect/area fill was always `canvas.fillRect(..., { fill: "solid" })` regardless of series — `styleIndex` picked a colour when colour was on and picked NOTHING otherwise, so two stacked segments (or two dodged bars) rendered as one indistinguishable block of `█`, and the legend swatch for every region mark was a LINE style (`paint.ts`'s generic swatch branch), never matching what the bars themselves painted. The arc/pie painter already had the right shape (`seriesShade(tier, entry.shadeIndex)` through `canvas.text`) — bar/rect/area now do the same thing via a new `fillRegionShade` helper (one `canvas.text` call per row, the glyph repeated across the run) keyed on the series' own `styleIndex`, UNCONDITIONALLY (not gated on `colorEnabled`), so Copy ASCII stays readable whether or not colour carries the picture on screen. The legend swatch branch grew matching `bar`/`rect`/`area`/`cell` cases reusing the identical glyph. `fillRect` itself could not be reused for this: its own per-tier shading ramp (`ascii`'s 8-level `" .:-=+*#"`, `braille`/`blocks`' sub-cell occupancy) is a DIFFERENT vocabulary from `series.ts`'s categorical `SHADE_RAMPS` (`["#", "%", "+", "."]` for ascii) — there is no `shade: number` that reliably reproduces a literal `%` on the ascii tier, so the fix paints the exact character directly rather than asking `fillRect` to approximate it.

A `cell` mark (heatmap) is not a categorical series (its shade is a continuous VALUE, via `shadeFor`), so it keeps `fillRect` on `ascii`/`box` (unaffected, always correct there) but stops using it on `blocks`/`braille`: `fillRect`'s own sub-cell path derives its glyph from PARTIAL dot-occupancy coverage, which is right for a bar/area's fill (always full coverage, always reads as a solid block) but wrong for a continuous ramp — a partially-covered cell there picks a quadrant SHAPE (`▘ ▀ ▛`), so four shade LEVELS read as four different textures rather than four different darknesses, unlike `box`'s own monotone `" ░▒▓█"`. `paintCell` now quantises through that SAME 5-level ramp (`GLYPH_CANVAS_TIERS.box.shadeRamp`) on every tier and paints it via `canvas.text`, so a braille heatmap reads identically to a box one. Its legend swatch is the ramp's own top (full-ink) glyph, since a heatmap has no per-series cycle to show.

**B3 — the tick ladder's collision pass deleted an arbitrary rung instead of degrading evenly.** Two independent, additive causes. First, `yRowBudget`'s formula (`Math.floor((bottom - top + 1) / 2) + 1`) counted the plot's ROW count instead of its row-INTERVAL count (`bottom - top`, one fewer) — the min-2-row-spacing rule that bounds how many ticks fit is a function of intervals, not rows, so this over-asked d3 by exactly one tick at every height. That over-ask usually matched d3's own "nice" overshoot (`ticks(4)` returning 5 elements for a domain that only has a 5-tick or a 2-tick nice answer, nothing in between), which meant the pre-existing overshoot-STRIDE thinning in `axisTicks` (engaged only when `d3's returned length > requestedCount`) never triggered — both numbers were inflated by the same one, so the flat greedy collision loop underneath was left to arbitrarily drop whichever candidate happened to sort into a colliding slot, producing holes like `8, 6, 2, 0` (dropping the evenly-spaced `4`) instead of a coarser but genuinely even `8, 4, 0`. Fixing the formula alone re-enables the pre-existing stride mechanism correctly in the common case. Second, even a CORRECTLY-sized request can still return values that, after fraction→row ROUNDING, land closer together than the minimum spacing — a step that doesn't evenly divide the available rows. A new `fitTicksToRowSpacing` helper (auto-budget path only; an explicit `axes.y.ticks` count is a caller request, not a fitting heuristic, and skips it) re-derives the actual rows d3's ticks would land on and, if any adjacent pair is too close, re-asks for one fewer tick and retries — "re-ask d3 with a smaller count," exactly as the diagnosis's own proposed rule states — until the ladder fits on its own or bottoms out at 2. Together, a kept numeric y-ladder is now an evenly-spaced (arithmetic) subsequence at every height 8–24, for both a plain bar and a stacked one, gated by an exhaustive parametrized test.

**B4 — an auto axis title cost a row/column it couldn't always spare.** The default (from a mark's own field NAME, never an explicit `axes.*.title`) used to show unconditionally whenever the channel resolved to a plain string, which is exactly the regime B3's ladder broke in (a 40×14 bar chart spent 2 of its 14 rows on `value`/`month`, leaving only 8 data rows). It's now gated on genuine room — `rows >= 20` for the x title, `cols >= 60` for the y title — AND the field name being longer than two characters (a table's own single-letter columns, `v`/`m`, were never worth a whole row anywhere). An explicit title (including `""` to suppress the default) is unaffected by either threshold; it always shows because "explicit" means the caller decided, not a heuristic.

**B6b — a braille/blocks dot mark was a sub-pixel fleck.** A single sub-cell dot (or the old 2-dot "companion" pattern that gave monochrome multi-series dots a distinct SHAPE) measures ~1.9px in the website's own Glyph Mono at 13px — visible in a screenshot at 400%, invisible at reading size. "Sub-cell precision may position a mark, never shrink it below a whole cell of ink" is now the rule: every dot paints a full 2×2 cluster (4 of the cell's 8 dots — both columns, the pair of rows the point's own position falls into), regardless of series index or colour. This retires the old shape-cycling contract (a lone dot at styleIndex 0, a 2-dot pair otherwise) in favour of visibility; colour remains the identity channel for a multi-series dot chart under `braille`/`blocks`, exactly as it already is for every other mark type at whole-cell resolution.

**B6c — a band tick/label sat one column right of the bar it named.** `scale.ticks()`'s own continuous `start + bandwidth/2` fraction, rounded to a column independently of where the bar is actually painted, disagreed with `bandColRange`'s own `[fractionToCol(lo), fractionToCol(hi) - 1]` — the `-1` right-edge pull-in (needed so adjacent bands never share a boundary column) is invisible to a fraction computed without it. ## URL state

## Sankey and funnel

Both are non-cartesian marks, plumbed through the exact same seams `arc` already uses (`scales.ts` excludes them from x/y collection, `layout.ts` excludes them from the cartesian gutter, `series.ts`'s `chartSeries` groups their rows into per-node/per-stage `ChartSeries`), rather than a parallel pipeline — the only new code is `flowMarks.ts`'s own layout math and painter.

**Why cumulative rounding, not per-band rounding.** A sankey node's row height is proportional to its throughput, and each of its outgoing (or incoming) flows gets a share of that height proportional to its own value. Rounding each share independently (`Math.round(value / total * height)` per flow) does not generally sum back to the node's own integer height — verified on a hub with three equal-value outgoing flows at a 10-row budget: independent rounding gives `3, 3, 3 = 9` (one row short), while the SAME cumulative-rounding technique `paint.ts`'s own `dodgeColRange` already uses for series dodging (round the running SUM, take the difference from the previous rounded sum) gives `3, 4, 3 = 10` exactly. This is why `distributeCumulative` is one shared function used for a column's own node-height split AND every node's outgoing/incoming band split — three call sites, one guarantee. The real energy-flow dataset's own ratios happen to round cleanly at the sizes it's exercised at and would NOT have caught a regression here; `flowMarks.test.ts`'s adversarial fixtures (equal-value flows at row budgets not evenly divisible by the flow count) are what actually falsifies the "round independently" mutation, on all three call sites.

**Folding.** A flow whose row allocation, under the real cumulative split, computes to zero is not simply invisible — it is pulled out of the per-node list and its value is summed into one synthetic `(other)` entry, and the WHOLE list (kept flows plus the one aggregate) is re-split via the same cumulative function. This keeps the conservation guarantee (the source's total row count is unaffected by folding) while avoiding a silently-dropped flow; `sankey-folded-flows` names exactly which flows were combined. A folded band has no real target to route to, so it paints as a short stub (up to 3 columns, capped by the inter-column gap) rather than inventing a fake destination.

**Node columns and row order** come from `d3-sankey` itself (`computeNodeDepths`'s longest-path-from-a-source layering, and the library's own relaxed `y0` as a within-column sort key) — this module does no graph-layout math of its own, only the integer snap from d3-sankey's continuous output to a `cols × rows` grid. `d3-sankey`'s own cycle detection (`computeNodeDepths` throws once its layering pass exceeds the node count) is reused directly for `sankey-cycle` rather than a second, parallel graph walk that could disagree with it.

**Why `sankey-cycle` is not a `GLYPH_CHART_VALIDATION_RULES` entry.** Exactly the `mixed-x-scale` precedent (`scales.ts`): whether a graph is acyclic is a cross-row, data-dependent property with no declarative JSON Schema equivalent, so it is a runtime-only tagged code with its own `RUNTIME_REPAIR_HINTS` entry instead. `sankey-bad-value` IS a `GLYPH_CHART_VALIDATION_RULES` entry, but its schema-expressible half only covers channel PRESENCE (mirroring `arc-missing-value`'s own precedent) — schema has no way to know which record field a caller's `channels.value` string names, so it cannot check the field's actual sign; the deeper "finite and > 0" check runs once channels are resolved (`flowMarks.ts`'s `resolveSankeyRows`), under the same code.

**Funnel row/width split.** Every stage gets an EQUAL row band (never proportional — only a bar's WIDTH encodes its value), with a one-row gap between stages when the budget allows one (`plotHeight >= 2n - 1`). A stage's bar width is `round(value / max(all stage values) * innerWidth)`, centred in a fixed inner column band (a `labelGutter` reserved on each side for the stage name and the `value · NN%` readout) — verified proportional on a synthetic 1000/500/250 funnel (4:2:1): measured bar widths at 60×12/box were 34/17/9, i.e. within one cell of the exact 4:2:1 ratio at every step. `funnel-not-monotone` fires per adjacent pair where a later stage exceeds the one above it (rendered in the given order regardless — a funnel's row order is the caller's own, never re-sorted); `funnel-thin-stage` fires when a nonzero value's proportional width would round under one cell, and draws a one-cell stub instead of nothing. The `value · NN%` label is built by hand (not through `abbreviateChartText`) and is explicitly re-folded through `chartText` before painting — the only label in this package that constructs its own separator character (`·`, replaced with a plain `x` on the `ascii` tier). The stated reason this used to ship with ("the one spot a forgotten fold would leak a non-ASCII byte past the `chat` target's 7-bit gate") was WRONG (P3-3): `chartText`'s own ASCII path already ends with an unconditional `replace(/[^\x20-\x7e]/gu, "?")`, so a forgotten fold leaks a `?`, never a raw byte — confirmed by mutation (flattening the ternary to a bare `"·"` changes nothing across the suite, since the fold still catches it downstream). The `x` substitution earns its keep on LEGIBILITY alone: `?` reads as "something broke," `x` reads as a plain separator.

**Legend defaults.** Both group into `ChartSeries` (sankey by source node, funnel by stage — see "Round 7" below for why a funnel is keyed by ROW, not name) so an explicit `legend: true` lists them like any other series — but funnel's stage labels already sit right next to their own bars, so showing a legend by default would only repeat them below the chart; `resolveGlyphChartLegendOption` gained an `explicit` flag so `layoutGlyphChart` can default the legend OFF specifically for a funnel-only spec without changing any other mark's existing default-on behaviour. Dead until now — mutating the flag's own check (`m1` below) changed no test; a funnel-only default-legend/explicit-legend pair now pins it.

## Round 7: flow-mark review fixes (crossing routing, global scale, folding to a fixed point)

An adversarial review (`CHARTS-RESEARCH/REVIEW-flow-marks-opus.md`) found the sankey painter genuinely broken on its own flagship dataset and four silent-loss paths across both marks. Fixed at the root in every case; nothing here is a relocated symptom.

**Crossing bands erasing each other (P1-1) — SUPERSEDED, see "Round 9" below.** The two fixes tried here (a shared `mid` column, then a per-band lane with a two-pass leg/lane paint) were both later found to still erase a band's own connection to its border — the per-band-lane fix RELOCATED the defect rather than closing it (a wide leg still crossed a NEARER band's lane, and lanes spread across the whole gap made it worse, not better). Round 9 replaces the whole painter with one routed through the cell canvas's own edge/route/junction contract; this paragraph is kept only as the record of what didn't work and why.

**Band thickness not comparable across columns (P2-1) — see also Round 9's "monotone within one row" correction below.** Every column used to independently normalise its own node heights to fill the FULL available row budget, so a value of 150 alone in its own column stretched to claim the whole plot height while a 130 sharing a crowded column got a small fraction of it — the review's own measured case, `Natural Gas → Industrial` (150) drawing 3 source rows against `Electricity Generation → Industrial` (130) drawing 5. Fixed with ONE global rows-per-unit rate (`distributeByRate`), sized to the TIGHTEST column (`min` over columns of `capacity / total-throughput-in-that-column`) so every OTHER column has slack rather than any column ever overflowing — a lone node in its own column no longer stretches to fill it (measured: a 150-value lone node now draws ~12 rows at a 24-row budget, not 24). The honest trade, stated rather than hidden: a column whose nodes are proportionally smaller than the graph's biggest value now has genuine BLANK rows below its own content — comparability costs the old "always fills the column" guarantee, which was never something to promise in the first place once two nodes must be comparable.

**A 0-row node vanishing silently (P2-3).** Under the global rate a small node can still round to 0 rows; it is now bumped to 1 UNCONDITIONALLY and the row reclaimed from the TALLEST entry in its own column afterward — gating the bump on whether the column looked like it already had headroom (the first cut) was itself a bug: a column sitting exactly at capacity (one huge flow beside one tiny one, together summing to exactly the row budget) has a reclaimable row the tallest entry can give up, and refusing to even try left the tiny one at 0 despite that. Only when a column holds more REAL nodes than it has rows (reclaiming from every entry over 1 row still isn't enough — N nodes cannot show in fewer than N rows) does anything end up at 0, and the smallest-value entries lose that tie-break last, reported via `sankey-nodes-dropped`. `cursor` is proven never to leave the rect by construction (the no-trailing-gap fix below) and by a 60-seed property sweep over random skewed hub graphs at five heights.

**A deep sankey overflowing the plot (P2-2).** Even at the minimum node width (3 cells), enough columns still didn't fit the plot width, walking `colX0(col)` past `plot.x1` and, at extreme widths, clipping the last box mid-glyph. Fixed by folding the deepest columns onto the last one that fits (clamping `nodeDepthById` before column bucketing) when `numCols * MIN_WIDTH + (numCols - 1) * MIN_GAP > plotWidth`, reported via `sankey-columns-folded`; a link between two now-merged depths becomes a same-column band and is silently skipped by the painter's own `gapX1 < gapX0` guard (a real, reported degradation, never a crash). A trailing gap row after the LAST node in a column (the old code added one after every node including the last, wasting one row of the column's own accounted-for capacity) is also removed — it is what makes the rect-bound proof above exact rather than approximate.

**The fold not reaching a fixed point (P1-2).** `foldSankeyOutLinks` used to re-split ONCE after folding the first pass's zero-height flows into `(other)`; that re-split can itself hand a DIFFERENT survivor zero rows (`(other)`'s own bigger share can push a link just above the earlier threshold under it), and the reviewer's own repro (`Hub → Big 1000, T0..T5 3..8` at 60×20) showed exactly that. Fixed by iterating: keep folding newly-zero real links into the running `(other)` bucket and re-splitting until a full pass leaves every remaining real link at >= 1 row (bounded by the link count, since each round that continues strictly shrinks the kept set) — verified over a 40-seed property sweep at four heights. A converged `(other)` bucket can ITSELF still round to 0 (its own residual negligible against the kept links) — an invisible fold stub defeats the one thing it exists to show, so it steals one row from the source's tallest kept link when one has a spare row to give (`ensureFoldStubVisible`); the mutation this closes (`m14`: replacing the folded-stub paint condition with `if (false)`) previously passed the FULL suite untouched, since only the `sankey-folded-flows` LEDGER entry was ever asserted, never the painted cells.

**A typo'd channel name misreporting as a cycle (P2-8).** A missing/typo'd `source`/`target` field name still has a defined ACCESSOR (the string itself), so the structural "channel present" check passes; the accessor then resolves every row to `undefined`, which used to get stringified into a literal `"undefined"` node — and when BOTH endpoints did it, every row became a `"undefined" → "undefined"` self-loop, misreporting as `sankey-cycle` instead of naming the real mistake. Fixed by checking the RAW resolved value (before `String()`) for `undefined`/`null` and rejecting with `sankey-missing-channel` — a runtime-only tagged code, like `sankey-cycle`, since a field name that resolves to nothing is exactly as data-dependent as an acyclicity check.

**A 1–2-row node's label overwriting its own border (P3-4).** A 2-row box has no interior row — its only two rows ARE the top and bottom border — and `midRow = floor((y0+y1)/2)` lands on the TOP one for exactly that box height, so painting the label there overwrote its own corner glyphs (visible in the shipped tray thumbnail, `┌Coal┐`). Fixed by skipping the label (not the border) for any box under 3 rows tall and reporting `label-dropped`.

**Funnel stages past the row budget dropping silently (P1-3).** `if (rowStart > plot.y1) break` dropped the tail with no ledger entry (30 stages in 24 rows silently lost six). Fixed by keeping the first N-1 stages and folding the rest into one synthetic `"other (k more)"` stage, valued at the LARGEST folded value (the first, since stages are conventionally non-increasing) so the funnel's own monotone shape stays plausible through the fold; reported via `funnel-folded-stages`. Resolution itself (`resolveFunnelRows`) is untouched — the fold is a PAINT-time decision, so `meta.series`/the resolved row count still reflect every stage the caller supplied.

**A fabricated percentage when the reference stage isn't positive (P1-4).** `pct = stages[0].value > 0 ? … : 0` made EVERY stage print `0%` when the first stage was zero or negative — a stage worth 100 labelled `0%`, the exact failure mode `abbreviateChartText`'s "never truncate a number" rule exists to prevent, arriving by a different route (a manufactured number, not a truncated one). Fixed by omitting the percent entirely (labelling just the value) when the denominator isn't usable, reporting `funnel-bad-reference` once per render rather than per stage.

**The funnel accepting values it wouldn't draw (P2-5).** A negative stage used to draw no bar and log nothing; an all-negative or all-zero funnel drew nothing at all with no `arc`-style `empty-total` analogue. Fixed with the same `finite`/`sign` split `sankey-bad-value` already has: a NEGATIVE value rejects with `funnel-bad-value` (structurally, for the literal `number[]` shorthand the schema CAN see the sign of; at resolve time otherwise, exactly like sankey's own asymmetry) — non-finite values already rejected generically and earlier as `non-finite-data`, so this only needed the finite-but-negative gap closed. An ALL-ZERO funnel now shares `arc`'s own `ledgerEmptyTotal` (its message generalised from "this pie" to "this chart" to serve both) and draws nothing, rather than a zero-width bar with a label.

**Duplicate funnel stage names collapsing (P2-4).** `chartSeries` grouped a funnel by `String(row.x)` — the same key `sankey` uses to merge multiple links from one source node into one series, which is CORRECT there but wrong for a funnel, where every row is meant to be its own stage. Two stages sharing a label (two "Retry" steps) silently merged into one `ChartSeries` group, and `paintFunnelMark` reads only `g.rows[0]`, dropping the second row's value with no ledger entry. Fixed by keying a funnel's GROUPING by its own row index (unique per row, trivially) while keeping the DISPLAYED name/legend/colour identity keyed by the stage name as before (`displayNameByGroupKey`, a new map decoupling the two) — sankey's own by-source grouping is untouched.

**Funnel value labels vanishing at realistic widths (P2-6).** The fallback chain was `formatFunnelValue` (SI above 1000, `d3format("~s")`'s default SIX significant digits) → drop, with no plainer form ever tried — `12345` (5 chars) became `"12.345k"` (7 chars, LONGER than the number it replaced) and was then dropped at 30 columns because even the "abbreviation" didn't fit. Fixed with a three-step chain: a plain, exact, comma-grouped `d3format(",")` form FIRST (`"12,345"`), a 3-significant-digit SI form SECOND only when the plain form is too wide (`"12.3k"`), then drop (`label-dropped`) only when neither fits — tried with AND without the `· NN%` suffix, in that order, so a value can survive even when the full `value · pct` string can't.

**Five dead guarantees, mutation-verified (P2-7).** Each of these passed the FULL suite with the guarding code deleted or inverted; each now has a test that goes red on the same mutation (results recorded in the fix's own commit, not restated here since this file documents design, not a changelog): the funnel-legend `explicit` flag (`m1`), the `ascii` `x`-vs-`·` substitution (`m6`, see the "Funnel row/width split" section above for why the ORIGINAL rationale for keeping it was also wrong), the non-cartesian gutter exclusion (`m7`), the non-cartesian scale-domain exclusion (`m8`), the funnel thin-stage stub's actual PAINT (as opposed to just its ledger entry, `m11`), and the sankey fold stub's actual PAINT (`m14`, see above). A SIXTH mutation from the same review (`m12`, `series.ts`'s `canGroup` array widened to include `"sankey"`/`"funnel"`) was confirmed genuinely UNREACHABLE — the very next line's channel lookup already excludes both types unconditionally — and reverted rather than given a test, per the reviewer's own recommendation.

## Colours

**Why axes default to a muted grey, not the reader's own foreground.** Before this option existed, `paintAxes`/`paintGrid` passed no `color` at all, so an axis painted in whatever full-brightness colour the page's own text used — identical in weight to a data mark's own saturated palette entry, so the frame around a chart and the data inside it read as the SAME visual layer. A reader scanning for "what changed" has no way to tell the y-axis's vertical rule from a line series at a glance. `GLYPH_CHART_AXIS_DEFAULT_COLOR` (`"#7a7f8a"`, a neutral mid grey) demotes the axis to background structure, the same relationship a real chart's axis has to its data in every general-purpose plotting library — measured on HSL LIGHTNESS it sits roughly equidistant between the palette's own darkest and lightest entries (palette 0.427-0.651, mid 0.539; axis 0.510), but on RELATIVE LUMINANCE (the quantity contrast ratios are computed from) it is DIMMER than every palette entry (axis 0.2115 against a palette minimum of 0.2154, `#a855f7`) — the two statistics disagree on which is more extreme, and only luminance is the one a contrast claim can be built on. Measured contrast: 4.02:1 against white, 5.23:1 against black (AA for normal-size text is 4.5:1; 3:1 is the lower graphical-object threshold the rule/tick-mark/gridline glyphs clear either way) — the recolour reaches the axis TICK NUMBERS too, text a reader must actually read, so on a light chart surface it is marginally under AA and worth a deliberate call before leaning on it for body text; the constant is otherwise left as-is (no gate would catch a tuning, and the shortfall is small). It is a DEFAULT, not a forced value — `spec.axes.color`/`spec.axes.{x,y}.color` still let a caller paint the axis any colour, including matching the foreground exactly to reproduce the old look. Applying it required no new machinery: `layoutGlyphChart` already resolves every other axis option (`tickMarks`, `grid`, `title`) once per render into `GlyphChartLayout`, so `xAxisColor`/`yAxisColor` join that same resolution and `paintAxes`/`paintGrid` read them instead of omitting `color` — gated on `colorEnabled` exactly like every mark's own palette colour, so `color: "none"` output (the ASCII/plain-text exit) is untouched.

**Why a mark's colour override lives beside its `styleIndex`, not as a second resolution path.** `chartSeries` (`series.ts`) already assigns every painted series a `styleIndex` — the shared, cross-mark, first-appearance-ordered slot the palette (`SERIES_COLORS[styleIndex % length]`) and the shading cycle (`seriesShade`/`seriesDot`) both key on. Adding `ChartSeries.color` (a mark's own `options.color`, resolved at that series' PER-MARK position — `chartSeries`' pre-existing `sliceIndex` counter, reset per mark, never the shared `styleIndex`) and one `resolveSeriesColor(entry, enabled)` helper meant every one of `paint.ts`'s and `flowMarks.ts`'s existing `PALETTE[styleIndex % PALETTE.length]` call sites became a single substitution, with no new branch anywhere a series is painted, shaded, or legended — the legend swatch in particular falls out for free, since `layoutGlyphChart`'s own legend-item builder reads the same per-name colour map (`chartSeriesColors`) rather than re-deriving one.

**Why a series NAME resolves to one colour across marks, not per-mark position.** The per-mark `sliceIndex` resolution above is right for an UNNAMED series (it has no cross-mark identity to agree on), but a NAMED one does: two marks that both name a series "B" are, by `series.ts`'s own header ("one grouping drives geometry, metadata and legend: their identities must agree"), the SAME series, and its legend swatch was already keyed by name (`chartSeriesColors`, first-appearance order) while its painted ink stayed keyed by `sliceIndex` — so mark 2's "B" could paint a colour the legend never showed, silently, with nothing in `report.ledger` to say so (an adversarial review finding). `chartSeries` now runs a second pass after building every series entry: for each NAME, the first entry's resolved colour (override or palette default — exactly what `chartSeriesColors` already computed) becomes that name's ONE colour, reassigned onto every entry sharing it; a second, differently-coloured EXPLICIT override for the same name is dropped in favour of the first and logged as `series-color-conflict` (naming both colours) — a name whose first occurrence had no override at all is not a conflict, it simply adopts whatever that occurrence resolved to, same as the legend already did. `chartSeriesColors` itself now calls `resolveSeriesColor(s, true)` instead of re-deriving the same `s.color ?? SERIES_COLORS[...]` expression inline, since after this pass a named entry's `color` is never null and the two were always meant to be the one rule its own doc comment claimed.

**Why `cell` is the one mark resolved outside that mechanism.** Every other groupable mark type can have as many series as it has distinct `fill`/`stroke` values, so an override array's LENGTH is naturally checked against `groups.size` (the mark's own series count) to decide what's unused. A `cell` mark, however, is never split by name — its own row loop groups every row into ONE series regardless of channels (`paint.ts`'s `paintCell` doc) — so `groups.size` is always 1, which can't distinguish "one ink colour, fully used" from a diverging (mixed-sign) domain's legitimate SECOND colour (`[losses, gains]`). `chartSeries` therefore skips its own `mark-color-unused` check for `cell` entirely, and `paintGlyphChart`'s cell branch reports it instead, once `cellSigned` (computed once, across every cell mark in the chart) is known — comparing the override array's length against 2 slots on a diverging domain or 1 otherwise. The two colours themselves are resolved separately from the generic per-series field too: `paintCell` takes the mark's RAW `options.color` (never the single resolved `ChartSeries.color`, which can only carry one value) and reads `[0]`/`[1]` as loss/gain directly, falling back to the existing `GLYPH_CHART_CELL_LOSS_COLOR`/`_GAIN_COLOR` constants; a single string (or one-element array) broadcasts to both signs, since asking a diverging heatmap to distinguish gains from losses by colour ALONE (with no override) was never the design — the gain/loss RAMPS (two distinct glyph families) already carry that signal, colour is a reinforcement.

## Round 8: data layer review round 2 (curated-mapping fallback, URL cap enforcement, the recommender rewrite)

A second adversarial pass on the data layer (`CHARTS-RESEARCH/REVIEW-data-layer-opus-round2.md`) found five new defects, three of them the textbook relocation shape — a fix that closes a P1 by moving the same failure one seam over.

**A curated mapping applied against columns a pipeline had already deleted.** `topChartsRecommendation` returned a STOCK dataset's curated `recommended` field unconditionally, with no check that its `x`/`y`/`fill`/`label` names still resolve against the pipeline's OUTPUT columns — a `select`/`flatten`/`pivotLonger`/`pivotWider` step can rename or drop exactly those columns, and applying the mapping anyway rendered an empty chart with an empty `report.ledger` and no error at all. Fixed by validating the curated channels against the resolved `DataProfile` (`curatedChannelsResolve`) and falling back to the profiler's own top pick when any of them no longer exist, carrying a `fallbackNotice` ("Pipeline changed the columns; using recommended …") so the reader sees WHY the readout changed rather than a silent empty chart.

**The 256 KB custom-payload cap was enforced in one handler, not at the boundary.** `ChartsDataFolder.tsx`'s paste/upload handler refused an oversized payload before dispatching — but `onSelectDataset`'s "Custom…" branch dispatched `customText` unconditionally, so a paste-too-big → pick-a-dataset → pick-Custom-again round trip re-dispatched the SAME refused text with no size check on that path at all. Moved the enforcement into `chartsWorkbenchState.ts`'s `set-data-source` reducer case itself — the one place ANY action can install a custom source — so no dispatch path can bypass it; the paste handler's own check stays as immediate UI feedback, not as the guarantee.

**The link-size drop decided in the wrong dimension, and said nothing to the sharer.** `stateForUrl` dropped a custom source's `raw` from the `?c=` envelope when the RAW payload exceeded `CHARTS_URL_SIZE_WARN_BYTES` (8192) — but that threshold is sized for the ENCODED query string, and deflate compresses real CSV/TSV roughly 1.6:1, so a raw payload comfortably over 8 KB could still produce an encoded link comfortably under it and got dropped for no reason. Worse, dropping the payload SHRINKS the encoded link back under the threshold, so the page's only signal (`urlTooLong`) never fired for exactly the case that most needed telling the sharer their data didn't make it. `chartsUrlState.ts`'s `encodeChartsUrlStateInfo` now encodes once WITH the payload in full and only re-encodes with it dropped when THAT actual encoded size is over the threshold, returning `omittedCustomBytes` (the PRE-drop raw size) so the page can show "Custom data (N KB) isn't included in this link" independently of the (now-correct) "link is N KB" notice.

**The recommender's multi-numeric rule summed the wrong column and duplicated a channel.** `category + several numerics` used to recommend `bar { x: category, y: numbers[1], fill: category }` — silently dropping every numeric column but the SECOND, and binding `x`/`fill` to the identical channel (never a real grouping). Rewritten as a long-format reshape: a `pivotLonger` step (carried on the `ChartRecommendation` itself as an optional `pipeline`, applied on top of the already-resolved rows by `apply-data`'s reducer case before `buildDatasetMark`) melts every numeric column into one `measure`/`value` pair per row, so the chart becomes `bar { x: category, y: value, fill: measure }` — one series per measure, never one arbitrarily chosen. `arc` stays reachable only for a category + exactly ONE numeric column whose values actually read as a share/count (non-negative) — a signed quantity like a temperature change has no honest wedge-size reading. The `date + numeric + category` fill rule is capped at 8 distinct categories (`DATE_NUMERIC_CATEGORY_FILL_MAX_CATEGORIES`): past it neither the legend nor the 4-style line cycle stays distinguishable (measured: 12 categories reads as 12 identical truncated legend entries, 20 as one-character labels with the cycle repeated five times over), so the rule falls back to a plain unfilled line with a reason stating why, rather than silently degrading to an unreadable chart.

**Smaller fixes, same review.** `pivotLonger`/`pivotWider` (`dataPipeline.ts`) now read every column through the same `Object.hasOwn`-guarded `rowColumn` helper `filter`/`sort`/`parseDate`/`derive`'s "col" node already used, closing the same inherited-`Object.prototype`-member hole on the two step kinds that hadn't been switched onto it yet. `compileDateFormat` rejects a format with no `YYYY`/`MM`/`DD` token at all or one in the wrong case (previously silently nulled the whole column) and a repeated token (previously reached `new RegExp` and threw the host's raw "Duplicate capture group name" message verbatim). `isRolledCalendarDate` (`dataProfile.ts`) now also catches a rolled `SLASH_DATE` day (`"2/30/2024"`), not only the ISO shape. `dedupeHeaders` (`tabularParse.ts`) walks left to right tracking every name already committed rather than only how many times each ORIGINAL name repeats, so a generated suffix that happens to collide with a LATER column's own literal name keeps climbing instead of re-colliding (`"a,a,a_2"` → `"a,a_2,a_3"`, not a second silent drop). `coerceCell` no longer TRIMS a quoted field's padding — RFC4180 (and d3-dsv, and PapaParse) treat a quoted field's whitespace as literal, the one place the format lets an author say the padding is data. Round 3's R1 narrowed this further: quoting gates the TRIM only, never the TYPE — a quoted `"42"`/`"true"` still coerces to a number/boolean exactly like an unquoted one (none of those three authorities drop coercion for a quoted cell either), so a QUOTE_ALL export's numeric column still profiles as numeric.

**N10 — the F3 seed test defended the effect, not the seed; the footer row still failed `aria-required-children`.** The original F3 regression test asserted the paste box's value only AFTER mount, by which point the `useEffect` had already re-seeded it — reverting the lazy `useState` initializer back to a bare `useState("")` while keeping the effect left the test green. Fixed by rendering OUTSIDE `act()` and asserting synchronously in the same tick, before React's passive-effect flush has run, so only the initializer's own value can be observed. The table's footer row (`role="row"`, add-row/add-column) held two bare `<button>`s with neither `columnheader` nor `gridcell` — the exact `aria-required-children` violation the original F7 finding named and the commit that fixed the header/data rows didn't reach; both buttons are now wrapped in their own `role="gridcell"` `display: contents` element. One caveat stays documented rather than coded: the committed tests assert DOM structure under happy-dom, which cannot confirm a `display: contents` element with an explicit ARIA role survives into a REAL browser's accessibility tree — right in current Chrome/Firefox, but unverified here (no axe, no real-browser run), and WebKit has historically been the engine most likely to drop such nodes.

## Round 9: sankey band painter rebuilt on the canvas's own routing (round-2 review's P1-1, relocated twice)

A second re-review (`CHARTS-RESEARCH/REVIEW-flow-marks-opus-round2.md`) measured that round 1's fix (see "Round 7" above, now marked superseded) had RELOCATED P1-1 rather than closed it: per-band lanes plus a two-pass paint stopped one band's lane from being wiped out along its own length, but did nothing about a band's own LEG being erased by another band's LANE — and because lanes were spread across the whole gap, band-over-band overwrites went UP by an order of magnitude (the `A/B → X/Y` fan: 12 → 396 overwrites at 72×24; the energy dataset: `Electricity Generation → Commercial`, its tied-second-largest flow, painted touching NEITHER of its own node borders). The three round-1 gates couldn't see any of it — "every row keeps >= 1 cell of its own colour somewhere in the gap" is satisfied by a single 1-column lane, and the energy gate explicitly `continue`d past the one skip-level band that failed worst.

**The root cause both prior fixes shared: hand-painted rectangles, with no way to tell a real crossing from an accidental overwrite.** `packages/glyphcss/src/render/canvas/` already has that machinery — `canvas.edge(id, {from, to})` + `canvas.route(id, cells)` + `resolveJunctions()` decide, per cell, whether two routes JOIN, form a routine perpendicular CROSSING (silent), or are a genuine route CONFLICT (`report.routeConflicts`) — and `@glyphcss/diagrams` already builds its own edges on exactly this contract (`docs/design/canvas.md`'s "Junctions"). The sankey painter used none of it. It now does.

**The band, rebuilt as k routes.** A band of `k = max(sourceHeight, targetHeight)` rows is painted as k single-cell-wide polylines (`buildSankeyBandRowRoute`), one per row: `source-stub -> lane column -> target-stub`, clamped-mapped when the two ends' row counts disagree (`srcRow = sr0 + min(i, srcHeight-1)`, same for target) — a TAPER, and measured as the COMMON case, not an edge case: 10 of 52 bands across the fan and energy datasets at four sizes have `sourceHeight !== targetHeight` by exactly 1, and 3,978 of 12,922 bands (30.8%) across a 200-seed random-DAG sweep. Each row is registered as its OWN edge id, `{from: band.source, to: band.target}`, so `resolveJunctions()`'s route-coincidence test can tell two rows of the SAME band (which may legitimately converge when the ends taper) from two DIFFERENT bands crossing.

**Stub allocation is TARGET-COLUMN ORDER leaving a node, SOURCE-COLUMN ORDER entering one** (`layoutSankeyGraph`'s outgoing/incoming loops now sort by the OTHER end's already-settled node-box `y0` before assigning row ranges) — not the OLD declaration order. This is what makes non-crossing bands land on disjoint rows in the first place, rather than relying entirely on the painter to sort it out downstream.

**Lanes are a RIBBON, not one shared column, sized by INTERVAL-GRAPH COLOURING with WIDTH** (`assignSankeyLanes`): each bent band reserves `k` CONSECUTIVE columns (one per row) rather than one column all k rows share — the first cut of round 9 itself gave a band ONE shared lane column and measured that a multi-row band's OWN rows collide with EACH OTHER there just as often as two different bands' lanes used to (190+ same-band `"parallel"`/`"multi"` conflicts on the fan alone, since row i's vertical run `[srcRow_i, freeRow_i]` and row i+1's `[srcRow_i+1, freeRow_i+1]` genuinely share cells on one column). Placement is a "meeting rooms" packing: sort bands by vertical extent `[min(sr0,tr0), max(sr1,tr1)]`, assign the lowest SLOT whose occupant's extent has ended, size each slot to the widest ribbon ever placed there — two bands share a slot only when their extents never overlap. A gap narrower than the packed width wraps ribbon starts modulo the available width and reports `sankey-crossings-merged` (same code as round 1).

**Border cells are claimed with ABSOLUTE priority, independent of lane placement.** This is the fix for the specific reader-facing failure (a band touching neither of its own borders): a row's first cell (adjacent to its source) and last cell (adjacent to its target) are structurally UNIQUE to that row (row ranges partition a node's box without overlap), so no OTHER row can ever legitimately own them — what CAN reach one is a DIFFERENT band's transit merely passing through on its way to a farther lane (unavoidable once two bands' ribbons sit on opposite sides of one shared border column). `paintSankeyLayout` claims every row's own two border cells, across ALL rows, BEFORE painting any interior cell — so a later-registered transit arriving at an already-claimed border cell finds it occupied and draws nothing there, never the other way round. This is independent of, and more robust than, lane uniqueness: it is what keeps gate (a) below green even under the interval-colouring's own "shared lane column" mutation (measured — see below).

**Skip-level bands (target two-plus columns past source) route their pass-through at a PROVEN-FREE row**, never through an intermediate node's own box (`pickSankeyFreeRow` + an internal assertion in `paintSankeyLayout` that throws naming the offending node if a route ever lands inside a foreign box). This is what makes `Natural Gas -> Industrial` (passing behind `Electricity Generation`'s own column) fully connected instead of losing its whole lane under EG's box, which round 1 and 2 both left as a known defect (the round-7 paragraph's own "legitimately loses ONE cell... painted last by design" turned out to lose 15-27 cells and all its connectivity once measured). If no row clears every intermediate box (one of them spans the full plot height), it falls back to the top row — a documented, rare residual, not a silent one: the internal assertion is what would catch it if it ever fired on a real dataset, and it did not across the fan, the energy dataset, or 200 random DAGs.

**What the redesign proves, and what it does not.**

- **Gate (a) — every band's own row touches BOTH its node borders** (a cell adjacent to the source border, a cell adjacent to the target border, for every row 0..k-1), across the fan and energy dataset, four sizes, three tiers. Mutation-verified: disabling the border-priority pass, or reintroducing a shared lane column (ignoring `assignSankeyLanes`'s own map), both redden a dedicated test.
- **Gate (b)/(c) — zero silent overwrites.** One shared routing pass (`computeSankeyRoutedRows`, split out of `paintSankeyLayout` specifically so a test can inspect the SAME lane placements the real render uses — re-deriving lanes for one band in isolation would give it slot 0 every time, an incomparable placement) records every band's own cell set; a cell a band's own route claims but the combined render doesn't show must be claimed by some OTHER band's own route too (a genuine crossing), never lost to nothing.

## Round 10: data layer/website review round 3 (double-evaluated `&&`, unsafe-integer header dedupe, slider coordinate mismatch, negative log domains, Apply date normalization, URL double-copy omission)

A third adversarial pass over the website's own data layer and Dock controls (batch-3 review, two seats) found six correctness defects the library-level rounds above never touch — all in `website/src/lib/`/`website/src/components/ChartsWorkbench|InstrumentWorkbench/`, none in `@glyphcss/charts` itself.

**`derive`'s `&&` evaluated its own left operand twice, and the second copy was on the FALSY branch** (`op === "&&": truthy(evaluateNode(node.left)) ? evaluateNode(node.right) : evaluateNode(node.left)`) — `parseAnd` builds a LEFT-leaning tree for a chain of `&&`s, so every node's own left subtree is itself another such node, and a FALSY chain (the reported repro's bare `0`s — a quoted `"0"` is truthy under this evaluator's own `truthy()`, so only the unquoted numeric-zero shape triggers it) doubled the leftmost leaf's evaluation count at every level: 24 operands measured 16,777,215 (2^24-1) evaluations for one row, 40 exceeded a 1500ms limit outright. Fixed by evaluating the left operand once and reusing it for both the truthy test and the falsy return value — which also makes the operator properly short-circuit (a falsy left never touches `node.right` at all, matching real JS `&&`).

**`dedupeHeaders`'s numeric-suffix allocator could get stuck at `Number.MAX_SAFE_INTEGER` (2^53).** `requested + 1` and the allocator's own `n++` both stop advancing at that magnitude in IEEE-754 double arithmetic (`2**53 + 1 === 2**53`), so two columns literally named `col_9007199254740992` looped `nextFree` forever re-testing the same occupied name. **Apply recommended a date chart it could not itself render.** `dataProfile.ts`'s profiler recognizes date SHAPES the renderer's own `ISO_DATE_PATTERN` doesn't — a bare `YYYY-MM` or a slash date (`MM/DD/YYYY`) profiles as `type: "date"`, so `xChannelIsDate` set `scales.x.type: "time"` while the mark's own `dataText` still carried the un-normalized string, and rendering rejected with `bad-time-domain` on the exact one-click flow Apply exists for.
