# Render modes and output encoding — design notes

> Design notes moved out of `AGENTS.md` (the agent guide keeps the contract and points here).
> Covers: `ink` mode internals, `glyphPalette: "dense"`, `charMode` (braille/halfblock/quadrant), `wireframeJunctions`, `solidWeightRamp`, `hiddenLines` (wireframe and ink), `colorTolerance`, and `colorEncoding: "atlas"` (the COLR/CPAL font atlas, its two variants, palette quantization, pooling, readiness, and the sticky spans fallback).
> Cross-references to "above"/"below" that no longer resolve refer to sibling files in `docs/design/`.

`mode: "ink"` detects silhouette edges (adjacent triangles' front/back-facing sign flips, same screen-space convention `solid` mode's backface cull uses — view-dependent, correct under both ortho and perspective) and crease edges (dihedral angle beyond a fixed 35° threshold, always drawn independent of view), plus boundary edges on open meshes; an edge is only ever drawn when at least one adjacent triangle is front-facing. Kept edges are chained into a per-vertex screen-space tangent field via central differencing (most-anti-parallel neighbor pair at a junction), then smoothed with two passes of sign-aligned neighbor averaging — this is what turns per-triangle-edge stair-stepping into a tangent that reads as continuous along a sphere/torus silhouette. The smoothed tangent quantizes into four 45°-wide direction buckets (horizontal / `\` / vertical / `/`); the horizontal bucket further picks `‾`/`-`/`_` from the cell's fractional vertical position, and the vertical bucket mirrors that onto the column axis, picking `▏`/`|`/`▕` (LEFT ONE EIGHTH BLOCK / VERTICAL LINE / RIGHT ONE EIGHTH BLOCK — verified font-distinct, not invented) from the cell's fractional horizontal position; without this a stroke could wander within a cell while its glyph stayed fixed, reading as head-on wobble. The diagonal buckets (`\`/`/`) do not get sub-cell discrimination — no monospace font renders an offset diagonal variant, and a diagonal stroke already spans its cell corner-to-corner. Interior cells stay empty by design — hatching/texture fills are future effect-layer work, not baked into this mode. `charMode` and `wireframeJunctions` are wireframe-path-only concerns and are documented no-ops in `ink` (it always renders its own fixed oriented-glyph set as plain ASCII, independent of `glyphPalette` too). `hiddenLines: "hide"` IS wired in `ink` — see below. `ink` is a runtime-only render mode for now, same as `wireframe`/`solid`/`voxel`.

When two kept edges of EQUAL `rank` contest the same cell — the reported case being an extruded letter's own front-face silhouette and a farther extrusion side wall, both `rank: 1` — the winner is the NEARER one (camera-space depth, same "larger = nearer" convention `fillDepthTri` uses), not whichever segment happened to rasterize last. This is unconditional, not gated behind `hiddenLines` (which only drops an edge that fails a depth test along its ENTIRE length; two visible, un-hidden edges can still tie for a cell, and that's what this resolves). Depth is the same per-vertex `camera.project` result already computed for screen position, cached alongside it — no second projection pass — and lerped along each segment exactly like its tangent/color. Because this only changes which already-kept, already-visible stroke wins a contested cell, it cannot blank a cell the way the two per-sample hidden-line attempts recorded in `research/contour-first-text/decisions.md` did; the convex-mesh regression suite (cube, icosahedron, sphere subdiv 2 and 3) confirms identical inked-cell counts before and after.

`glyphPalette: "dense"` is the ramp for a cell smaller than ~2 device px, where glyph SHAPES stop resolving and only the fraction of the cell carrying ink survives as colour — a sparse glyph washes its cell to grey. Every step keeps ≥ ~25% ink (ordered by MEASURED alpha-weighted coverage in Menlo at the 0.606 cell aspect, the same measurement `@glyphcss/effects`'s `calibrateGlyphRamp` does), so a cell reads as its COLOUR at any size while the ramp still shades dark → bright. Every step is printable ASCII BY DESIGN — it is also the ramp for a hard ASCII-only output constraint (a terminal, a 7-bit pipeline, `fontAtlas: GLYPH_FONT_ATLAS_ASCII`), and that is what keeps it inside the 94-glyph ASCII atlas. Do not "improve" it with block/Unicode characters.

`charMode: "ascii" | "braille" | "halfblock" | "quadrant"` (scene option, default `"ascii"`) selects the character encoding used for rasterized output. `"ascii"` is the rule-glyph encoding above. `"braille"` (`wireframe`-only) packs a 2×4 subcell dot-coverage grid into each output cell as Unicode Braille Patterns (`U+2800`..`U+28FF`), giving up to 8 independent sub-cell "pixels" per glyph — visibly smoother diagonal/curved edges than a single ASCII rule glyph per cell. It runs the same `transformCells` post-rasterize hook as the ASCII path. `charMode: "braille"` is a documented no-op in `solid`/`voxel`/`ink` modes — braille dot coverage is binary and cannot carry a Lambert shade ramp, a voxel face-normal glyph, or ink's oriented direction glyph, so those modes always render ASCII regardless of this option.

`charMode: "halfblock"` (`solid`-mode-only) is the mirror trade-off: braille buys SHAPE resolution at one color per cell; halfblock buys COLOR resolution at coarse (block) shape — exactly where solid mode's shade ramp already loses per-subcell color by averaging supersampled subcells into one glyph. It reuses that same supersample pass (internally forcing an even supersample of at least 2 when the scene didn't already request one) and independently averages the TOP half and BOTTOM half of each cell's subcells, then picks a glyph from the resulting per-cell decision table: neither half covered → a bare space with no color and no background (a cell with no geometry never paints an opaque rectangle); both halves covered with the SAME resolved color → `█` (full block) with just `color` set, no `background-color` — cheaper markup, and the cell merges into a same-color run exactly like the ASCII solid path; both halves covered with DIFFERENT colors → `▀` with `color` = the top subcell's color and `background-color` = the bottom subcell's color; only one half covered → `▀` (top) or `▄` (bottom) with that half's color as `color` and no background, so the uncovered half shows the page/`<pre>` background instead of a painted rectangle. A run only merges consecutive cells when BOTH colors match (`encodeGlyphBuffersDual` in `render/cells.ts`, a sibling encoder to the single-color `encodeGlyphBuffers` — it does not extend the shared `CellGrid` contract, so the `transformCells` hook and the generic effect compositor stay exactly one-color-per-cell). `charMode: "halfblock"` is a documented no-op outside `solid` mode, and also a no-op alongside a `transformCells` hook or active `temporalBlend` reprojection — both already expect and produce the existing one-color-per-cell grid, and halfblock's two-color split has no equivalent there.

`charMode: "quadrant"` (`solid`-mode-only) generalizes `"halfblock"` from a 1×2 (top/bottom) subcell split to a full 2×2 split, buying BOTH shape and color resolution at the same two-colors-per-cell markup cost — half-block's `▀`/`▄` are two of the 16 masks this mode picks from (space, `▘▝▖▗▀▄▌▐▚▞█`, and the four three-quadrant glyphs `▛▜▙▟`, covering every possible binary 2×2 coverage pattern exactly, with no approximation). It shares halfblock's eligibility rule and forced even supersample (`≥2` in both axes, so each output cell splits into four TL/TR/BL/BR subcell regions), and the same never-paint-an-empty-region discipline. Per cell: no region covered → a bare space, no color, no background. 1-3 regions covered → the exact coverage-mask glyph (14 distinct partial silhouettes vs. halfblock's fixed top/bottom split — the shape win) with ONE coverage-weighted average color across the covered regions and no `background-color` (a background would have to paint an uncovered region, which this mode — like halfblock — never does); distinct true colors among the covered regions collapse into that single average. All 4 regions covered → the color win over plain solid-mode averaging: same resolved color on all four → `█` with just `color` set (the halfblock-style cheapest-markup case); otherwise the 4 regions split into a "high"/"low" luminance group by comparison against their mean (deterministic, not real k-means clustering) and render as the matching two-tone mask with `color` = the high group's average and `background-color` = the low group's — a genuine two-color split of the whole cell, since full coverage is the only state where a background can never touch an uncovered region. A degenerate split (every region on the same side of the mean) falls back to the same-color `█` case. What's lost vs. per-subcell-exact color: a partially-covered cell with more than one true subcell color still collapses to one average; a fully-covered cell with more than two true colors collapses to whichever two-group luminance split the mean threshold produces, not a globally optimal partition. Same `encodeGlyphBuffersDual` two-color encoder halfblock uses — `CellGrid`/`transformCells`/the generic effect compositor stay untouched.

Both `"halfblock"` and `"quadrant"` are documented no-ops outside `solid` mode, and no-ops alongside a `transformCells` hook or active `temporalBlend` reprojection — both already expect and produce the existing one-color-per-cell grid, and neither's two-color split has an equivalent there. Both are also no-ops alongside `solidWeightRamp` (neither's two-color-per-cell encoding has a font-weight span). Mirrored as `char-mode` on `<glyph-scene>` and `charMode` on the React/Vue `<GlyphScene>`. `charMode` is also reachable from the static path — `compileScene` and `GlyphSceneStatic` (React + Vue) accept and forward it, so braille/halfblock/quadrant output can be baked at build time, not just rendered at runtime.

`wireframeJunctions: boolean` (scene option, default `false`) is a `charMode: "ascii"`-only refinement, orthogonal to `charMode` itself: the default per-cell wireframe glyph is picked independently per edge (weight tier → random glyph from the active palette), so two edges meeting in one cell — a corner, a T-junction, a crossing — render whichever edge rasterized last, which visibly breaks at joints. When `true`, a second pass runs over the finished wireframe stamp: every near-axis-aligned edge accumulates which of a cell's four sides (N/E/S/W) carry a line into a per-cell mask, and any cell with a non-zero mask renders from the fixed `┌┐└┘├┤┬┴┼─│` box-drawing set keyed by that mask instead of the random pick — so a joint resolves to ONE glyph consistent with every edge touching it. An edge counts as "near-axis-aligned" when its two projected endpoints round to the same output row (near-horizontal) or the same output column (near-vertical) — under half a cell of perpendicular drift across the edge's whole screen-space length; this scales with edge length instead of a fixed angle constant. A diagonal-dominant edge contributes nothing to the mask, so its cells keep the existing slope-glyph behavior unchanged. It is a pure post-rasterize resolve pass over the same stamp (no geometry-pass change) and runs the same `transformCells` hook as the untouched path; `false` (the default) keeps `rasterize` byte-identical. Mirrored as `wireframe-junctions` on `<glyph-scene>` and `wireframeJunctions` on the React/Vue `<GlyphScene>`. Unlike `charMode`, it is runtime-only — `compileScene`/`GlyphSceneStatic` do not expose it.

`solidWeightRamp: { glyph: string; weight: number }[]` (scene option, `solid`-mode-only, default `undefined`/off) is a second density axis for solid-mode shading: CSS `font-weight`. A weighted ramp is a sequence of `(glyph, weight)` steps ordered darkest → densest by MEASURED ink coverage — `@glyphcss/effects`'s `calibrateWeightedGlyphRamp` crosses a glyph pool against candidate `font-weight` values through the same real-canvas measurement `calibrateGlyphRamp` uses, so this is never a hand-authored table. It cannot be expressed as the existing plain ramp string (`glyphPalette`'s `.solid: string[]`), since a plain ramp has no weight dimension — so it is its own option, and when set it REPLACES `glyphPalette`'s solid ramp entirely for that render (both the glyph sequence AND the weight lookup come from the steps). This is safe because bold measurably does NOT change monospace advance width in every tested stack (Menlo, Courier New, Monaco, Andale Mono, the gallery's `ui-monospace, "JetBrains Mono", "SF Mono", "Menlo", monospace` stack — including for a browser-SYNTHESIZED bold when a font lacks a real bold face), so a weight-bearing span can never desync the character grid; `encodeGlyphBuffers` starts a new run on a weight change alongside color, landing `font-weight` in the same `<span style="...">`. Measured payoff (Menlo, 10-glyph pool): glyph-only ramp reaches 10 steps / coverage 0.3295; the weighted ramp reaches 15 steps / coverage 0.4508 — more distinguishable shading buckets and a darker dark-end than glyph shape alone reaches. `undefined` (the default) keeps `rasterize` byte-identical — the per-cell `weight` buffer (`CellGrid.weight?: Uint16Array`, `0` = no override) is never allocated or written. Documented no-op outside `solid` mode, under `charMode: "halfblock"` or `"quadrant"` (both two-color-per-cell encoders have no font-weight span either), and during active `temporalBlend` reprojection (which blends the ramp index continuously across frames and has no notion of a parallel weight lookup) — same precedent as `charMode: "halfblock"`'s own no-op list. The `transformCells` hook and `rasterizeToCells`'s `CellGrid` both carry the live `weight` buffer when the option is active, so an effect can read or rewrite it like `color`. Mirrored as a `solidWeightRamp` JS property on `<glyph-scene>` (not an attribute — the ramp is data, the same "JS property, not attribute" rule `sceneManifest`/`dictionary` use) and `solidWeightRamp` on the React/Vue `<GlyphScene>`. Also reachable from the static path — `compileScene` accepts and forwards it (plain step data, no browser/canvas dependency at compile time, exactly like `charMode`), so a weighted-ramp render can be baked at build time too.

`hiddenLines: "show" | "hide"` (scene option, default `"show"`) is hidden-line removal for the `wireframe` render path, including `charMode: "braille"`. The wireframe path otherwise has no depth reference at all: edges rasterize in mesh/array order, and `drawLineToStamp` resolves a contested cell by edge WEIGHT (`if (stamp[idx] < val)`), not by which edge is actually nearer the camera — so a mesh's back side can paint its extrusion side walls over a front face, braille strokes from a farther stroke can bleed into a nearer one's dot pattern, and a darker `sideColor` edge can overwrite a brighter front-face color. `"hide"` depth-tests every wireframe stroke sample (per-cell for ASCII, per-cell for braille too — measured 777 vs 786 inked cells for 25% more cost at per-subcell resolution, not worth it) against a solid surface prepass — the same triangle-depth rasterizer `computeOcclusionIds`/cross-layer occlusion uses — with a slope-scaled depth bias: `allowed = bias + slopeScale * |local screen-space depth gradient|` (the standard shadow-map slope-scaled-bias technique). The gradient term is load-bearing, not cosmetic: a FLAT bias (`slopeScale = 0`) regresses every convex mesh at every magnitude tried (cube -11..-32, icosahedron -5..-44, sphere -12..-158 inked cells vs. ground truth), because a smooth surface's own silhouette lies ON the contour it outlines and needs an allowance proportional to the local depth gradient, not a constant one; `slopeScale ~0.5` converges within ~0-4% of analytic ground truth (cube 115→115, icosahedron 177→173-175, sphere 431→426-430) and is the shipped internal constant (bias 0.03, not a public option). Documented no-op in `solid` mode (already depth-buffered per cell via the normal scan-fill depth test).

`ink` also wires `hiddenLines: "hide"`, but with an IDENTITY-based occlusion test, not the wireframe margin-based one reused as-is. Two earlier bias-based attempts (flat, then slope-scaled, applied per-sample and then per-edge) both fought SELF-occlusion — a sphere's silhouette lies ON the sphere, so the surface occludes its own outline, and any margin large enough to prevent that ate 38-46% of the silhouette anyway (recorded as ruled-out attempts in `research/contour-first-text/decisions.md`). The fix excludes the caster from its own test, the same principle as shadow-map self-shadow exclusion: `buildInkOcclusionMap` rasterizes every ink triangle into a depth+id buffer (id = triangle index, reusing `fillDepthTri`, the same rasterizer `computeOcclusionIds` uses), and each kept silhouette/crease edge carries its own local vertex-topology neighborhood (`edgeOwnFaceIds` — the triangles touching either endpoint, one vertex-ring hop out) as an exemption set. A stroke sample is hidden only when a DIFFERENT, non-exempt triangle wins that cell and is nearer by more than a residual `depthGradient`-scaled allowance (the same screen-space depth-slope probe wireframe HLR uses, needed only to absorb the tiny chord-vs-curve discretization noise between a fine mesh's neighboring facets — not a self-occlusion margin, since identity already handles that). A flat constant residual was tried and rejected: it rescued one world scale and regressed a 10x-larger sphere in the same projection by up to -60%, reproducing the original failure one scale away — the gradient term is load-bearing because it scales with the mesh's own local screen-space depth variation. `INK_HLR_RING = 1` / `INK_HLR_SLOPE_SCALE = 2.5` are the smallest combination measured to hold cube/icosahedron/sphere (subdiv 2 and 3) to exactly 0 delta across five world-scale/projection combinations; because self-occlusion is handled by identity rather than margin, the test runs per-SAMPLE (not per-edge), so a wall edge only partly behind a cap now hides just the covered portion instead of the old rule's all-or-nothing whole segment. On the motivating extruded-text repro (`Glyph\nCSS`, depth 80, curveSteps 4, turn -38 tilt 0.2) this takes inked cells from 1152 (show) to 914 (hide, -20.7%), with the interior cross-letter/side-wall clutter visibly reduced — the previous per-edge design only reached -1.9% on the same repro. Mirrored as `hidden-lines` on `<glyph-scene>` and `hiddenLines` on the React/Vue `<GlyphScene>`. Unlike `wireframeJunctions`, it IS exposed by `compileScene`/`GlyphSceneStatic` — like `charMode`, it's a pure function of geometry + camera, and it fixes a genuine occlusion defect a static bake shouldn't reproduce.

`colorTolerance: number` (scene option, default `0` = off, byte-identical) merges adjacent same-glyph cells into one `<span>` while their colors stay within this redmean colour distance of a held run **anchor** — spans are what gate frame rate for colored output, and this directly minimizes span count for a given colour error. Range is `0`–`765`, not `0`–`255` (black↔white is 764.83 under redmean); the public surface validates at that layer — `NaN`/negative degrades to `0`, `+Infinity` merges every same-glyph run in a row. It is a **lever, not a flat multiplier**: `bench/color-tolerance.md`'s reproducible six-preset table (`node bench/color-tolerance.mjs`, matched to ~8 mean redmean error) measures a 1.2x–9.1x reduction in spans from unquantized to the best merge policy — Aurora 1.2x, Lava 1.3x, Nebula 1.5x, Menger 2.9x, Breathing gyroid 9.1x; Cube tiles (already flat, an `argmax` tiling) gains nothing at 1.0x, on purpose, and does not regress. An earlier hand-measured 1.6x–31x figure from a different, non-reproducible rig is superseded by this table — do not cite it. Flat, hard-edged output (per-face colour, carved solids) wins enormously; smooth noisy fields win modestly because their spans are dominated by genuine per-cell variation no merge policy can invent coherence around. Monotonicity (raising tolerance never raises span count) holds on every shipped preset measured but is **not a general guarantee** — greedy re-anchoring admits local non-monotonicity (a larger tolerance can let an early run swallow one more cell, moving the next anchor to a strictly worse centre for what follows); worst magnitude observed at grid scale is +5.4%. One exported comparison test, `colorRunExtends` (`packages/glyphcss/src/render/cells.ts`), backs all four coalescers glyphcss can emit colour from so they can't drift out of sync: `encodeGlyphBuffers` (single colour), `encodeGlyphBuffersDual` (`charMode: "halfblock"`/`"quadrant"`'s two independent channels, where a run requires *both* foreground and background to match), and `rasterize.ts`'s two DUPLICATE coalescers — `solidBufToString`'s unsafe branch (the common no-`transformCells` solid/ink/braille render path) and `stampToGlyphs` (the plain-`charMode: "ascii"` wireframe/voxel no-hook path) — neither of which calls `encodeGlyphBuffers` and would otherwise silently lack the feature. Routing either unsafe path through `encodeGlyphBuffers` itself was measured and rejected: its per-cell `assertGlyph`/`assertColor` validation costs ~90-100% more time per call at ~86k cells. Composes normally under active `temporalBlend` reprojection (a pure post-hoc merge over the same one-colour-per-cell grid TAA already produces — no structural conflict) and is a documented no-op under `glyphOutput: "semantic"` (semantic colours are exact class identifiers, not shaded appearance, so merging them would corrupt the lineage `scene.getGlyphSemanticCellFrame()` reads). Mirrored as `color-tolerance` on `<glyph-scene>` and `colorTolerance` on the React/Vue `<GlyphScene>`, and forwarded by `compileScene`/`GlyphSceneStatic` — like `charMode`/`hiddenLines`/`solidWeightRamp`, it is a pure function of geometry + camera reproducible at build time, though mechanically it alone operates on the already-rasterized cell grid rather than changing rasterization itself. None of the four reach `buildGlyphFramesExport`, `buildGlyphInteractiveExport`, or `buildGlyphFieldSynthStaticExport` — a `colorTolerance` set through the `/synth` page's UI persists to the URL but is silently dropped by that page's CodePen export.

`colorEncoding: "spans" | "atlas"` (scene option, default `"spans"`, byte-identical when unset) is a second, structurally different lever over the same four coalescers: instead of merging same-colour runs into fewer `<span>`s, `"atlas"` encodes `(glyph, colour)` as Private Use Area code points against a checked-in COLR/CPAL colour font, so the whole render becomes ONE text node with ZERO `<span>`s (`bench/color-font-atlas.md` on `spike/color-font-atlas` measured 2.7-9.4x FPS and 20,948 DOM nodes → 9 at equal visual output; raster got *cheaper*, not dearer, refuting the natural "more glyphs to rasterize" counter-hypothesis). `render/fontAtlas.ts` owns the mapping: `codePoint = puaStart + paletteSlot * glyphCount + glyphIndex` — the code point encodes a colour's POSITION in the caller-supplied `atlasPalette` array, never its value, so re-declaring what a slot resolves to (a `@font-palette-values`/`override-colors` swap, ~0.4ms measured) never touches already-encoded text; this is what lets a palette be held fixed, refreshed periodically, or selected from a precomputed bank (e.g. hue-rotated variants) without re-encoding a single cell. `atlasPalette` (an ordered `#rrggbb` array, ≤ the active atlas's `maxPaletteSize`) is the companion option, and is now OPTIONAL: it pins a fixed palette (a brand ramp, a reproducible bake), and `undefined` hands derivation to the scene's own pooled quantizer rather than disabling the atlas.

**Two atlas variants, and the glyph-vs-palette trade.** The BMP Private Use Area is a fixed 6,400-code-point budget and the mapping spends it as `glyphCount x paletteSlots`, so glyph coverage and colour resolution are the two ends of ONE lever (past the BMP PUA an atlas would need a plane-15/16 surrogate pair, which breaks the one-char-per-cell invariant everywhere). `GLYPH_FONT_ATLAS` is the universal set: 212 glyphs, 30 slots. `GLYPH_FONT_ATLAS_ASCII` (`assets/glyph-atlas/ascii-atlas.json`, family `GlyphCssAtlasAscii`) is printable ASCII minus space — 94 glyphs, **68 slots**, 2.3x the colour resolution for a scene that never uses the universal set's Greek/braille/box-drawing axis (a solid render on the `dense` ramp, say). `GlyphSceneOptions.fontAtlas` selects it PER SCENE and is **fixed at creation** — `setOptions` is deliberately inert for it, since a scene's `<pre>`s, readiness probe and `@font-palette-values` block are all pinned to one family for its lifetime. A frame needing a glyph outside the CHOSEN atlas falls back to the span encoder for that frame, the same whole-grid fallback the universal atlas applies to its own scope cuts. Nothing defaults to the ASCII variant. **Both variants share the same PUA range from `puaStart` 0xE000 with different `glyphCount` moduli**, so a code point does NOT identify a glyph without knowing which atlas produced it — and disjoint ranges cannot fix that (94 x 68 = 6,392 of the 6,400 points are already spoken for). The `font-family` the renderer pins on each output `<pre>` is the one per-element record of which atlas actually painted it, so it is the decoder's key: `glyphAtlasForFamily(fontFamily)` resolves it (parsing the stack rather than substring-matching, since `"GlyphCssAtlas"` is a prefix of `"GlyphCssAtlasAscii"`), and the clipboard chokepoint threads it PER `<pre>` — so one copy spanning two scenes on different variants stays correct on both. Payloads, `@font-face` `<style>` ids and per-document readiness are all keyed per variant, so each ships its own lazily-imported WOFF2 chunk and the other variant's is never fetched.

**Palette quantization (`render/paletteQuantize.ts`).** A render with more distinct colours than the atlas has slots is REDUCED to fit, never refused — refusing was what left the feature wired on eight pages and usable on almost none, since continuous Lambert shading routinely emits hundreds of colours (measured: 291 on `/examples/parthenon`, 2,495 on `/examples/image`, 358 on `/synth`). The reducer is median cut with three deliberate departures from the textbook rule, each measured rather than assumed: channel spreads are scaled by the redmean weights so the split decision lives in the same geometry as the error metric; boxes are ranked AND cut by weighted squared error (the exact 1-D optimum via prefix sums) rather than by extent or population, because a population median merges two well-separated clusters while bisecting a third — max redmean error 237 on a three-cluster histogram this rule keeps under 20; and per-cell assignment is nearest-palette-entry by redmean, not box membership. A frame with no more distinct colours than slots skips subdivision entirely and encodes EXACTLY, so a flat-shaded render (`/wordart` Ink, `/examples/city-lab`) stays lossless. `isGlyphAtlasEncodable` therefore no longer rejects on colour COUNT; what it still rejects is structural — a glyph with no outline in the atlas, or a non-blank cell with no `#rrggbb` colour — plus a palette outside `1..maxPaletteSize`. Its `palette` argument is optional: omitted, it answers the structural question alone, which is what a UI availability gate needs (`website/src/lib/glyphAtlasAvailability.ts`).

**Pooling and refresh.** `createGlyphAtlasPaletteQuantizer` is a CAUSAL pool: each resolved output's colours accumulate into a pending histogram, and a repool builds the next palette from the window that just elapsed, never from a future frame. A per-frame palette drifts badly under animation (`bench/color-font-atlas.md` §3: mean redmean 32.0 single-frame vs 5.1 pooled). Two gates must both pass to repool — **time** (≥ `refreshMs`, default 250, §6's most accurate measured interval) and **drift** (the window's drifted-cell fraction exceeds what this palette already scored on the window it was BUILT from). Measuring drift against that baseline rather than against zero is load-bearing: 30 slots can never cover a photo's thousands of colours, so a fixed fraction of cells is always past the threshold, and comparing against zero read that irreducible floor as staleness — measured at 10 repools over three motionless seconds on `/examples/image`, against the 1 a static scene should cost. The clock does NOT keep one frame's outputs on one palette, and an earlier claim that it made a mid-frame repool "structurally impossible" was wrong: the base `<pre>` resolves at the end of base rasterization and each detail `<pre>` at the end of its OWN raster pass, so they are a whole pass apart — routinely more than `refreshMs` in exactly the heavy-scene regime this feature targets. A repool landing between them leaves the base encoded against generation N while the scene publishes N+1 to the single `font-palette` ident every output SHARES, recolouring the base wholesale with no error and, on a static scene, permanently. `beginTransaction()`/`endTransaction()` on the quantizer close that: `createGlyphScene` brackets every render (full and effect-only) in one, the palette is LATCHED at the transaction's first resolve, and every later output of that frame gets the same one. Ingest is unaffected — every output's colours still pool, so the window a later repool trains on stays complete and causal, and the refresh is deferred by at most one frame. A caller that never opens a transaction (a one-shot bake) keeps the pre-existing per-resolve behaviour. Separately, the structural `isGlyphAtlasEncodable` test runs BEFORE the palette resolves at all four encode sites, so a permanently-unencodable render (`charMode: "braille"`, an out-of-atlas ramp glyph) never pools, never repools, and never publishes `@font-palette-values` for slots no `<pre>` will reference. `createGlyphScene` allocates the quantizer lazily (a `"spans"` scene never creates one and runs no quantization code at all), and republishes the palette to its `@font-palette-values` block after a successful commit only when the generation changed — a `<style>` write a few times a second at most, never a `<pre>` write, so the one-write-per-`<pre>`-per-cycle invariant is untouched. Quality gate against the span render on three real scenes: `bench/color-font-atlas-quantize.md`. **Convergence on a quiescent scene.** Both gates are evaluated only inside `resolveGlyphAtlasPalette`, i.e. only DURING a render — so a scene whose content streams in and then stops rendering could stay encoded against its bootstrap palette forever. Measured on `/maps` with `colorEncoding: atlas`: the palette bootstraps on the coarse relief backstop tier alone (exactly 11 colours, ten dark greens and one blue — `medianCutPalette` returns a histogram verbatim when it fits, so 11 in gives 11 slots out and `baselineDrift` 0), the mount storm carrying the real terrain ramp lands 101-151 ms later (always inside the 250 ms floor, so the clock gate refuses), and the page then goes still: idle 25 s, palette CSS byte-identical; one wheel notch at 9.1 s repools immediately to 30 slots. 4,769 of 8,820 ink cells (54%) were further than redmean 32 from any slot, mean error 71.5 — deep ocean collapsed onto the lone blue, mountain tans onto greens at error 156-315. The fix is a REPORT plus one settling render, never a lower floor (which would trade a wrong palette for churn through the mount storm and still lose the race on a slower machine): the quantizer's `repoolDeferredMs()` returns how long the clock gate still owes a repool the drift gate already demanded (`null` when nothing is owed), and `createGlyphScene` arms a single `setTimeout` for exactly that, on the same shape as `commitRender`'s existing `needsSettlingRender`. It is armed at most once per palette GENERATION, so a settling render that fails to clear the deferral (a blank grid, an output the atlas can't carry) cannot re-arm itself and the scene can never acquire a heartbeat; a static scene costs one `null` read per commit, a `"spans"` scene has no quantizer to ask, and a pinned `atlasPalette` cannot repool at all. Gate: `api/colorEncoding.paletteConvergence.test.ts`, which is deliberately SCENE-level on a frozen clock — the quantizer unit test hands it the very resolve the real scene never issues, and `colorEncoding.paletteTransaction.test.ts` advances its clock a full interval per raster pass, the opposite of the real cold-load timing; the load-bearing clause is that nothing between the bad frame and the assertion mutates the scene or calls `rerender()`.

Requires a palette to resolve — either pinned or derived; when the current render's GLYPHS aren't covered by the atlas, `colorEncoding: "atlas"` falls back to `"spans"` for that render — a WHOLE-SCENE decision (`isGlyphAtlasEncodable`, `render/cells.ts`), never per-cell, since a mixed encoding would still need spans for whatever fell outside the atlas and defeat the zero-span point. For `mode: "wireframe"`, that decision is NOT over the frame's realized glyphs: `wireframeGlyphForCell` draws a fresh `Math.random()` glyph per cell from its tier every render, so gating on the realized set made a partially-covered tier's atlas eligibility flip frame to frame (measured live: `runes` palette, 10x5 grid, zoom 4 — 82 encodability transitions, and 82 font-family pin flips, across 300 rerenders). `isWireframePaletteAtlasEncodable` (`render/rasterize.ts`) instead gates on the palette's POTENTIAL glyph set — `thin ∪ normal ∪ core`, plus the 11 junction glyphs when `wireframeJunctions` is on — computed from CONFIGURATION (the palette name + `wireframeJunctions`) alone, never from any one frame's draw, and memoized per (atlas family, name, junctions) since all three are page-scoped, not per-frame. A fully-covered palette (`default`, `ascii`, `detail`, `dense`, `dots`, `lines`, `solid`, `binary`, `hex`) atlas-encodes exactly as before; a partially-covered one (`runes`, `braille`, `blocks`, `stars`, `arrows`, `math` — each has at least one out-of-atlas glyph in a tier a plain wireframe cell can draw) now DETERMINISTICALLY renders spans on every frame instead of oscillating — the intended outcome, since it already spent most frames there, and reaching FULL coverage on every tier would cost palette slots a custom ramp still couldn't use. For content this potential-set gate structurally can't see in advance — an animated Glyph Effect layer's data-driven ramp, or a `transformCells` hook's arbitrary output, since `@glyphcss/effects` depends on `glyphcss`, never the reverse — `createGlyphScene` instead makes the out-of-atlas-glyph fallback STICKY per scene: once ANY output this scene renders (the base grid, a detail layer, or a retained effect layer) falls back to spans specifically because a glyph lacked an atlas outline (`RasterizeContext.atlasGlyphFallback`, set alongside `atlasEncoded` and cleared at the top of every `rasterize()` call; `hasGlyphOutsideFontAtlas`, `render/cells.ts`, is the equivalent check for the CellGrid-shaped retained-effect path), every LATER render of that scene stays spans — even once the data would otherwise re-qualify — until a `setOptions` call touches `colorEncoding`, `atlasPalette`, `mode`, or `charMode`. This sticky latch is never set for a colour/palette-only fallback reason (a missing/invalid per-cell colour, an oversized palette) — those are transient, not configuration problems — and it is a wholly separate mechanism from `atlasFontReady`'s "the lazily-loaded font hasn't arrived yet" fallback, which must keep flipping spans→atlas the instant the payload arrives regardless of whether this scene has ever latched; conflating the two would permanently disable the atlas the first time any scene rendered before its font arrived, since every fresh atlas scene spends at least one frame there. The checked-in **universal glyph set**, 212 glyphs (`packages/glyphcss/assets/glyph-atlas/atlas.json`, with the ASCII variant alongside it as `ascii-atlas.json`; both are generated by the sibling `build-atlas.py` — Python + fontTools, run by hand when the set changes, never by `pnpm build` or in the browser; the font ships as inlined base64 WOFF2, no separate request) covers full printable ASCII, the 24 Greek capitals, EVERY named `glyphPalette`'s solid ramp (including "dots"/"braille"/"runes" — a 22-glyph gap here silently fell back to spans for a number of revisions before being closed by sourcing those glyphs from two vendored fallback faces, see below), the "default"/"ascii" wireframe palettes' line-weight tiers, ink mode's 10-glyph set, and wireframe-junctions' 11 box-drawing glyphs — **not** `charMode: "braille"`/`"quadrant"`/`"halfblock"` (two-colour-per-cell or 255-glyph encoding needs its own atlas design) and not the `blocks`/`stars`/`arrows`/`braille`/`runes`/`math` palettes' non-solid tiers, so a render using one of those always falls back to spans. Every in-scope glyph now resolves from one of THREE source faces `build-atlas.py` tries in order — Menlo (a macOS system font, not vendored — still why building the font requires a Mac or a copy of Menlo.ttc), then DejaVu Sans (`assets/glyph-atlas/sources/dejavu/`, Bitstream Vera License), then Noto Sans Runic (`assets/glyph-atlas/sources/noto-sans-runic/`, SIL Open Font License) for the 22 glyphs Menlo lacks; a fallback outline is scaled into Menlo's em square and advance box and has its `hmtx` advance forced to Menlo's own so it can't desync the monospace grid, and an in-scope glyph resolving from none of the three is a hard build error naming the glyph, not a silent drop. Of the four coalescers: `encodeGlyphBuffers`-based paths (including `solidBufToString`'s `safe` branch, taken when a `transformCells` hook ran) and `solidBufToString`'s unsafe branch and `stampToGlyphs` are all atlas-eligible (single colour per cell); `encodeGlyphBuffersDual` (`halfblock`/`quadrant`) is a permanent no-op, same category as `solidWeightRamp`'s no-op there. Documented no-op wherever a `<span>`-per-cell representation is structurally required: `charMode: "halfblock"`/`"quadrant"`, an active `solidWeightRamp` selection (COLR/CPAL carries colour, not `font-weight`), `glyphOutput: "semantic"` (already documented to ignore every presentation option), and `useColors: false`. **The font artifact is two files, and the WOFF2 half is lazily imported.** `atlas.json` carries metadata only (family, glyph list, `puaStart`, `glyphCount`, `maxPaletteSize` — ~1.8KB) and is imported statically, because the PUA encode/decode formula needs it synchronously every frame and `decodeGlyphAtlasText` runs over plain `"spans"` output too. The base64 WOFF2 (~49KB) lives in `atlas-font.json`, whose ONLY importer is `render/fontAtlasPayload.ts`, which in turn is reached only through `import("./fontAtlasPayload")`; the ASCII variant repeats that shape exactly — `ascii-atlas-font.json` → `render/fontAtlasAsciiPayload.ts` → `import("./fontAtlasAsciiPayload")` — so a scene on one variant never pulls the other's chunk. That split is the lazy-load mechanism, not file cosmetics: when the payload was a field of the one manifest it sat in `dist/index.js` unconditionally — 18% of a 246KB bundle — for every consumer, including the "spans" default that can never use it. `tsup`'s `splitting: true` is load-bearing for the same reason (esbuild INLINES a dynamic import back into its importing bundle when splitting is off, silently undoing the whole thing); `render/bundle.atlas.test.ts` asserts the boundary against the BUILT output, since no source-level test can see it. Measured on `dist/index.js`'s transitive static-import closure: 246,256 → 204,417 bytes raw, 96,827 → 67,079 gzipped. **The async transition is spans-until-loaded**, never blocking, never a flash of PUA in a fallback face (which renders as tofu boxes): `createGlyphScene` keeps an internal `effectiveColorEncoding()` that stays `"spans"` while `options.colorEncoding === "atlas"` but the font hasn't arrived, and re-renders itself once it has. Readiness is `styles.ts`'s `ensureGlyphAtlasFontFaceStyles(doc, atlas?)` — idempotent and shared per (Document, atlas family) pair (ten scenes on one page and one variant await one promise; each payload import is memoized process-wide on top of that, keyed by atlas IDENTITY rather than family so a caller-built atlas reusing a shipped family name gets a loud "no payload registered" rejection instead of the wrong variant's glyph indices), resolving `true` only after the `@font-face` is injected AND `document.fonts.load` reports the face decoded for a real atlas code point. A failed load resolves `false`, warns exactly once, and pins that session to spans — never a broken render, never a retry storm. Readiness ALSO requires that the engine actually PAINTS COLR: every atlas base glyph is a deliberately empty outline with all its ink in a COLR layer, so a COLR-blind engine renders a blank grid and an engine that never applied the font renders tofu — neither visible to `CSS.supports("font-palette", …)`, which only asks whether the property parses. `ensureGlyphAtlasFontFaceStyles` therefore rasterizes one atlas code point to a 24x24 canvas with `fillStyle` pinned to black and requires a CHROMATIC pixel: blank isn't, tofu isn't, a real COLR paint is (its colour comes from CPAL, not `fillStyle`). It returns ready when it cannot conclude (no 2D context / no `getImageData`) rather than demoting a browser it merely failed to measure. That probe alone is NOT sufficient, and the readiness gate does not rely on it alone: the atlas's own baked CPAL palette is chromatic, so an engine that renders COLRv0 but ignores `font-palette` (Chrome 71-100, Firefox 26-106, Safari 12-15.3) paints a real chromatic glyph, PASSES the probe, and then renders the whole scene in the checked-in rainbow instead of the scene's colours — and canvas cannot observe `font-palette` application at all, so no probe tuning closes it. `ensureGlyphAtlasFontFaceStyles` therefore also requires `CSS.supports("font-palette", "--x")` (the dashed-ident form specifically), checked BEFORE the payload import so an engine that could only render the rainbow never fetches the 49KB chunk either, and returning ready when there is no `CSS.supports` to ask. This is the LIBRARY's guarantee, not the website's: the website's own `CSS.supports` gate decides a UI default, while a consumer setting `colorEncoding: "atlas"` directly previously had no guard at all. Every atlas function takes the atlas as a trailing argument defaulting to `GLYPH_FONT_ATLAS`, so a caller working with the ASCII variant must pass it consistently. `render/fontAtlas.ts` also exports `buildGlyphAtlasFontFaceCss(woff2Base64, atlas?)` — it takes the payload as an ARGUMENT rather than reading it off `atlas`, so a static/CodePen/SSR export cannot silently ship a `@font-face` with an empty `src`; it throws on an empty payload, and `loadGlyphAtlasFontFaceCss()` is the awaited convenience that loads and inlines it (rejecting, unlike the runtime path, because a build-time caller wants the loud failure). `loadGlyphAtlasFontPayload()` (shared, resolves `null` on failure), `glyphAtlasFontPayload()` (sync peek) and `glyphAtlasFontLoadState()` complete the surface. `render/fontAtlas.ts` also exports `buildGlyphAtlasFontPaletteValuesCss` (a pure CSS-text builder) and `decodeGlyphAtlasText`/`decodeGlyphAtlasCodePoint` (the copy/paste reverse map — `website/src/lib/asciiClipboard.ts`'s `extractAsciiFromPre` is the single chokepoint every page's "Copy ASCII" goes through, so decoding there covers all of them and is a no-op on ordinary `"spans"` output; a copy that also offers a COLOURED `text/html` flavour needs the palette too, since atlas output carries no per-cell colour in the DOM, and `glyphAtlasCellsFromPre` recovers glyph + colour together by resolving each slot through the scene's own injected `@font-palette-values` block — the gallery's and `/examples/image`'s coloured paste survive the atlas rather than degrading to plain text). `createGlyphScene` auto-injects the atlas CSS and manages `font-family`/`font-palette` on every output `<pre>` (base grid and each per-mesh detail layer) whenever `colorEncoding: "atlas"` is set — closing what was originally a manual-wiring footgun. The `@font-face` block is document-global and injected at most once PER VARIANT, the same idempotent-by-id shape `injectGlyphBaseStyles` already uses (`styles.ts`'s `ensureGlyphAtlasFontFaceStyles`; the universal atlas keeps the historical id `glyph-atlas-font-face` verbatim and any other variant suffixes its family, so two variants in one document inject two independent styles) — re-asserted on the cached path, since the `<style>` is ordinary DOM a consumer can remove; a scene's own `@font-palette-values` block is per-SCENE (never shared — a module-level monotonic counter, same "never aliasing across scenes" convention the mesh-id counter uses, allocates each scene's `--glyph-atlas-palette-N` custom ident), created lazily on first use and updated in place on a later palette edit, and torn down in `scene.destroy()`. The `<pre>`'s inline `font-family` prepends the atlas family ahead of the existing `monospace` fallback rather than replacing it, and is applied **per output `<pre>`, from the encoding that frame actually PRODUCED, not from the option** — `RasterizeContext.atlasEncoded` (an output field set by `rasterize()`) and `encodeCellGridOutput`'s `{ text, encoding }` return carry that answer up, and `commitRender` writes the family in the same transaction as the text it describes. Pinning it whenever the option is `"atlas"` is NOT safe, contrary to what this file used to claim: the atlas cmap covers `U+0020` as well as its own PUA range (`build-atlas.py`'s `cmap = {0x0020: "space"}`, which atlas frames need, since they write blank cells as literal spaces and those must come from the same face as the PUA cells), so a spans-fallback frame under a pinned family resolves its SPACES from the atlas and every other character from the platform `monospace` — one grid, two advances. Invisible on macOS, where `monospace` IS the atlas's Menlo source face, and measured broken elsewhere: 40 spaces 394.92px vs 40 "M" 393.67px in Chromium and WebKit, 389px vs 537px against a proportional fallback, ~9% drift per space where `monospace` maps to Consolas. The same cmap fact governs cell MEASUREMENT: both probes (`measureCellOf`'s hidden `<pre>` and `fitToHost`'s inherited `<span>`) probe with a PUA code point when the node they measure is atlas-pinned and with `"M"` otherwise, because `"M"` is not in the atlas cmap and probing with it measured the fallback font an atlas `<pre>` does not paint in — silently wrong `autoSize` fit, hotspot placement and detail-layer transforms. A pin flip invalidates the cached base cell, re-fits, and schedules one settling render; each detail layer's own pin is tracked independently too — `commitRender` compares every output node's pin from just before this commit against what it actually became, base and detail alike, and a flip on ANY of them (a mesh-targeted effect, or — via wireframe's unchecked `e.color ?? null` — a raw non-`#rrggbb` polygon color, can make just one detail grid unencodable while the base stays atlas) invalidates that layer's own cached cell and schedules the same settling render. The density path derives its cell straight from the base's own measured cell (`cw = cwB / density`) only while this layer currently shares the base's pin; once its own encoding diverges from the base's, that shortcut stops being valid (it is a property of ONE face) and it measures its own painted font stack directly instead, exactly like the explicit fontSize/lineHeight path already did. `setOptions` leaving `"atlas"` unpins every output eagerly and synchronously, ahead of the render it schedules — so `commitRender` never observes a flip for that transition — and invalidates the same cached metrics eagerly alongside the unpin instead. A `"spans"` scene (the default) never calls the injector and stays byte-identical and DOM-injection-free. Mirrored as `color-encoding` on `<glyph-scene>` (`atlasPalette` and `fontAtlas` are JS properties only, like `solidWeightRamp` — neither an ordered colour array nor an atlas manifest round-trips through a string attribute) and `colorEncoding`/`atlasPalette`/`fontAtlas` on the React/Vue `<GlyphScene>`, both of which get this injection for free through `createGlyphScene`. Because `fontAtlas` is fixed at creation, the bindings read it at MOUNT only and never forward a later change through `setOptions`; the element's setter records it for the next scene the element creates. `@glyphcss/react`/`@glyphcss/vue` re-export `GLYPH_FONT_ATLAS`/`GLYPH_FONT_ATLAS_ASCII` as values, since the prop takes a manifest and `glyphcss` is their own dependency rather than the consumer's. `compileScene`/`GlyphSceneStatic` (React + Vue) accept and forward `fontAtlas` alongside `colorEncoding`/`atlasPalette`, since it is pure configuration exactly like `charMode`. They remain the one path that still does **not** auto-inject: being DOM-less/pure they have no document to inject into, so a caller embedding compiled `"atlas"` output must include the CSS itself via the exported builders (`await loadGlyphAtlasFontFaceCss()` plus `buildGlyphAtlasFontPaletteValuesCss`) — passing the SAME `fontAtlas` it compiled with, since the two variants' code points mean different glyphs. **The WEBSITE defaults to `"atlas"`; the LIBRARY default stays `"spans"`.** `website/src/lib/glyphColorEncodingDefault.ts` is the single feature-detection chokepoint every page with the control shares: `CSS.supports("font-palette", "--x")` — the dashed-ident form specifically, since `font-palette: normal|light|dark` alone would leave every cell in the font's baked CPAL ramp — decides the default synchronously, because the value has to be settled before the first render and before the URL codecs read state. No user-agent sniffing. Where support is missing or unmeasurable the default is `"spans"` and the control stays ENABLED, so a user can still try it. `/synth`, `/gallery`, `/wordart` and `/examples/{flatmap,city-lab,loaders,parthenon}` take that default; **`/examples/image` deliberately does not** — it is a photograph at 2,495 distinct colours (~83x the slot budget) shipping `colorTolerance` 0, so it currently guarantees exact per-cell colour, and `bench/color-font-atlas-quantize.md` measures atlas costing it mean redmean 9.2 / p95 25.4 with 2.9% of cells past redmean 32, the only measured scene to cross that bar; every other page either already merges colour runs or has fewer distinct colours than the atlas has slots. The URL codecs keep `default: "spans"` as their OMISSION SENTINEL — a browser-dependent sentinel would make the same patch encode differently per engine, so a link shared from a supporting browser would decode wrong on one that isn't — and the detected default is applied at HYDRATION, from the decoded partial, so an explicit `?`-URL value always wins. A link that omits the token carries no preference and takes the detected default; that is the intended consequence of the flip, and there is no token that could distinguish a spans-era omission from a fresh one.
