# Per-mesh detail layers and cross-layer occlusion — design notes

> Design notes moved out of `AGENTS.md` (the agent guide keeps the contract and points here).
> Covers: `density`/`fontSize`/`lineHeight`, `transparent`, per-mesh `mode`/`glyphPalette`/`ambientIntensity`, `detailGroup`, the shared occlusion id-map and its sub-cell refinement, alpha-aware claims, `occlusionPriority`/`occlusionClaim`/`occlusionContourPx`, cross-scene occlusion, and meshless viewport overlays.
> Cross-references to "above"/"below" that no longer resolve refer to sibling files in `docs/design/`.

By default every mesh renders into that one shared base `<pre>`. A mesh can opt into **its own resolution** — set `density` (a multiplier: `density: 3` → 3× the scene's glyph resolution, cell = base ÷ density, isotropic, same on-screen size) or the low-level `fontSize` / `lineHeight` (which override `density`). Such a mesh "pops out" into its **own silhouette-fitted, CSS-translated `<pre>`** rendered at that cell size — so a hero mesh carries far more detail while the rest of the scene stays cheap in the shared grid. Browser-only (needs layout to measure cells); works with any camera (ortho / perspective / FPV) — detail meshes render **in place** (real world positions, scaled zoom, offset projection center), and the detail grid is clamped to the viewport so a camera near/inside a mesh can't blow up the render. This is **not** a group/tree concept — it's a per-mesh property on the flat mesh list.

`transparent: true` (default `false` = opaque) makes a mesh see-through (x-ray): it neither occludes nor is occluded. Because a mesh in the shared `<pre>` always occludes (one depth buffer), declaring `transparent` also pops the mesh into its own `<pre>` — separation happens for custom cell metrics **or** transparency.

**Per-mesh `mode`** (omitted by default = the scene's mode) separates a mesh for the SAME structural reason, applied to the render mode itself: the shared grid is rasterized in ONE pass under ONE mode, so a private mode needs a private layer. A mesh declaring only `mode` renders in its own `<pre>` at the BASE cell size. Unlike `glyphPalette`, separation is CONDITIONAL on the mode genuinely differing — `isDetailMesh` compares `t.mode !== options.mode`, so declaring the mode the scene is already rendering in keeps the mesh in the shared base grid, byte-identical and one pass. A mode is a small closed enum compared exactly, which is what makes that answerable; `glyphPalette` cannot answer it, since an unrecognized name silently resolves to the default ramp and two different strings can name one ramp. The comparison is re-made every render (the base/detail partition is rebuilt inside `doRenderTransaction`), so a `setOptions({ mode })` that matches lets the mesh rejoin the base grid on the next frame. Occlusion is UNCHANGED: a mode-separated OPAQUE mesh still claims its full footprint in the shared id-map (a geometry raster — it knows nothing about which glyphs the layer will paint), so an outline mode (`wireframe`, `ink`) blanks the base cells under its silhouette while painting only edges; `transparent: true` alongside it is the x-ray layering an outline usually wants. Each distinct mode in a scene is a full extra rasterizer pass — reach for it per LAYER, not per mesh (`base-raster` is ~99% of a full-screen `/maps` frame, `bench/maps-render`).

**Per-mesh `glyphPalette` and `ambientIntensity`** (both solid-mode, both omitted by default = the scene's value) separate a mesh for the same STRUCTURAL reason, not for resolution: the shared grid is rasterized in ONE pass against ONE ramp and lit in ONE pass under ONE ambient, so a private ramp or a private ambient needs a private layer. A mesh declaring only one of them renders in its own `<pre>` at the BASE cell size — a separate pass, no extra detail. `glyphPalette` is the solid ramp only (`charMode`, `wireframeJunctions` and `solidWeightRamp` stay scene-level, and an unknown name falls back to the library default exactly like the scene option); `ambientIntensity` substitutes `{ ...scene.ambientLight, intensity }` for that layer, so both its glyph choice (shade = clamp(light) x texel luma) and its texel colour tint follow it, while the ambient COLOUR and the directional key light stay scene-level.

**Shared detail outputs (`detailGroup`).** Every detail mesh naming the same `detailGroup` string renders into ONE silhouette-fitted `<pre>` — one grid, one rasterizer pass, one entry in the shared occlusion id-map — instead of one per mesh. It exists for CORRECTNESS at a shared edge, not economy: two abutting meshes in two separate detail outputs point-sample coverage on lattices fitted to two DIFFERENT silhouettes, so on a curved, foreshortened surface a sub-cell sliver along the edge they share can fall inside neither sample and nothing paints it. No occlusion refinement can close that (the cell was never claimed by either layer — see the sub-cell refinement below, which closes the *other* mechanism); one lattice has one sample per cell, and whichever member covers it paints it. Members also cannot occlude each other, since they are one layer id — within a group, ordinary per-cell depth decides, exactly as it does for two meshes sharing the base grid. Group names are scoped to the scene and STABLE: a group keeps its `<pre>` and its occlusion id across renders as members come and go (its id is drawn once from the same module-level monotonic counter mesh ids use, so it can never alias a mesh id), which is what lets a tile pyramid churn its meshes without recreating DOM. `detailGroup` NEVER separates a mesh by itself — `isDetailMesh` does not consider it — so setting it on meshes that aren't detail meshes (`density: 1`, nothing else declared) is inert and byte-identical. Because one output has one cell size, one render mode and one occlusion claim, every member must agree on `density`, `fontSize`, `lineHeight`, `transparent`, `glyphPalette`, `ambientIntensity`, `mode`, `occlusionPriority`, `occlusionClaim` and `occlusionContourPx`; a disagreement throws a `RangeError` naming the group and the field rather than silently taking one member's value. Per-polygon mesh ids are still each member's OWN (a mesh-targeted effect matches real mesh ids — a group is a rendering unit, not a mesh), and a grouped `<pre>` carries `data-glyph-detail-group` instead of `data-glyph-mesh-id`. `@glyphcss/maps`' raster layer is the reference consumer: it groups the tiles of each never-black TIER (`glyph-map-raster:<layerId>:fine|fallback|floor`), which removes the inter-tile seam while leaving cross-tier compositing to the id-map exactly as before — folding the tiers together instead would put two near-coincident surfaces built at different mesh resolutions in ONE depth buffer, which reads as speckle.

**Cross-layer occlusion.** Opaque meshes occlude each other across `<pre>` layers via a shared camera-depth pass: `computeOcclusionIds` rasterises all opaque geometry into one id-map (nearest layer per cell), and each layer's `rasterize` blanks cells a *different* layer owns (a layer never occludes itself). Integrated into `rasterize` (an `occlusion` `OcclusionMap` input) so it works for plain text **and** colored spans, and self-disables (zero cost) when no opaque detail mesh exists. Within the shared `<pre>`, meshes occlude each other for free via the normal per-cell depth buffer. The occlusion id-map is built at the **scene's supersample** resolution (same offset-scaling wrapper `rasterizeSolid` uses), so the world's supersampled silhouette and its id-map hole coincide subcell-for-subcell — no 1-cell seam at the world/entity boundary. **Detail layers still render at `supersample: 1`** (already high-res; coverage AA buys little and costs a full extra pass) and sample the supersampled id-map via an `×ss` cell affine. Both world-hole and detail-fill clip to the same id-map footprint, so they coincide (no black-hole, no seam). No-op when `supersample: 1` (id-map = output resolution, byte-identical to the non-supersampled path). **Ownership is decided per id-map cell, coverage per DETAIL cell**, and that mismatch is its own seam: where two adjacent opaque detail meshes SHARE an edge, the id-map cell straddling it is claimed by exactly one of them and the other blanks every detail cell it owns inside that cell — including the ones the winner does not cover, which nothing then paints. `@glyphcss/maps`' raster layer mounts one mesh PER TILE, so at `density > 1` that was a black line along every tile boundary in both axes (measured on the globe at density 1.4: a median 0.75 base cells over ~1,500 runs per frame, ~4% of the painted area, and identical at integer densities 2 and 3 — it was never a fractional-density effect). The fix is a SUB-CELL refinement, not a finer id-map: `computeOcclusionIds` now also hands back the nearest-depth buffer it already builds (`depthOut`), and `createGlyphScene` derives from it a per-map-cell local depth variation (`OcclusionMap.depth`/`gradX`/`gradY` — the largest absolute depth difference to a finite neighbour on each axis, then dilated by a 3x3 max, since a one-cell difference is the surface's AVERAGE slope across that cell and under-predicts the slope at the cell edge where a detail cell actually samples). A cell is blanked only when the owner is nearer by more than `(|dx|*gradX + |dy|*gradY) * 1.5`, with `dx`/`dy` the exact sub-cell offset between the detail cell and the map cell whose depth it read. Deliberately a RATIO of the map's own local depth variation rather than a flat bias, which fails across world scales for the same reason it fails for wireframe `hiddenLines: "hide"`; a detail cell near its map cell's centre gets an allowance near zero and blanks exactly as before, so only cells near a map cell's edge — where the seam lives — are affected. Skipped entirely, keeping the pure id-based claim, when any group sets `occlusionPriority` or `occlusionContourPx` (both are explicitly id-BASED claim overrides where the map no longer means "whose surface is nearest here", so refining them against depth would undo the feature), and never applied to the foreign-occluder sentinel (whose stamp overwrites the owner but not the depth). Cost measured on a 160x64 globe frame with 12 `<pre>`s: 43.97 → 44.48 ms/frame (+1.2%). This closes the id-map component, which was ~65% of it. The remaining ~35% was a second, independent mechanism — two abutting meshes each point-sample their own coverage in their own grid, so a sub-cell sliver at a shared edge can fall inside neither — and that one is removed by `detailGroup` above, not by any refinement here: the raster layer no longer mounts one `<pre>` per tile. Measured end to end on the globe fixture (`packages/maps/src/widget.tileSeam.test.ts`, subcell resolution, both axes, of 628 interior tile-boundary samples): one `<pre>` per tile dropped 296/291/322 at densities 1.4/2/3, the sub-cell refinement took that to 105/75/77, and one `<pre>` per tier takes it to 0/0/0.

**A blanked cell is not an empty one, and a painting hook has to be told which (`CellGrid.occluded`).** Blanking writes `" "` and `-Infinity` — byte for byte what open sky is — so a `transformCells` hook that PAINTS into the grid cannot tell "another layer owns this" from "nothing is here", and a grid's own `depth` never holds another layer's geometry to test against either. `rasterize` therefore records the cross-layer verdict per cell in an optional `Uint8Array` on the `CellGrid` (`1` = a DIFFERENT output layer owns it). It is an OWNERSHIP answer, not a "was erased" one: the loop's `myDepth === -Infinity` fast path skipped every cell this pass drew nothing in, and those are exactly the cells of a base grid whose meshes have ALL separated — so the flag is recorded before that check, and only when the buffer exists. Allocation is gated on a shared id-map AND a `transformCells` hook both being present, so a scene with no detail layer, and one with no hook, keep the original loop and allocate nothing.

**And the id-map has to describe the cells the paint pass will actually cover.** `CellGrid.occluded` is only as good as the shared id-map behind it, and three of that map's conventions disagreed with the paint rasterizer's. All three surfaced at once when `@glyphcss/maps` put a walker on the ground, as "the roads are on top of everything, the sky is also on top of everything" at a link whose OSM stack carried one row (`omt-buildings`) at density `1.7`.

1. **The sample point.** `fillDepthTri` tested coverage at the cell CENTRE `(x + 0.5, y + 0.5)` while `scanFillTriangle` tests it at the integer `(col, row)`. Half a cell, which is a WHOLE cell of disagreement along every bottom and right silhouette edge, in every projection and at every zoom: a face whose edge lands at `y = 32.2` paints row 32 and claimed only to row 31. Measured on a street-level fixture, that one row was the entire overlap between a road and the building it runs under (at eye height every ground point past a hundred metres compresses into the row or two above the horizon), so the road survived the ownership test along the whole base of the building. `fillDepthTri` already sampled its TEXEL at `(x, y)` "so the id-map's claimed set and the paint path's covered set read the same texel for the same cell" — the inside test simply had not been brought along. Aligning it left all 919 glyphcss tests green, which is the evidence that the old offset was a bug and not a load-bearing convention.
2. **The depth quantity.** `project()` returns a linear eye-space `cssZ` at `[2]` and a screen-space-linear z-buffer at `[3]`; `scanFillTriangle` — and therefore `CellGrid.depth` — is fed `[3] ?? [2]`, while `computeOcclusionIds` filled the retained `OcclusionMap.depth` with `[2]`. An ORTHOGRAPHIC camera omits `[3]` entirely, so the two were the same number for as long as glyphcss had only orbit cameras and nothing had to choose. Under a positioned perspective camera they are different quantities in different units, and the sub-cell seam refinement subtracts one from the other DIRECTLY: measured at the walk entry pose, a sky-dome cell read `myDepth = 267.44` (a z-buffer value) against the building's `ownerDepth = -7.8e-5` (a `cssZ`), so `ownerDepth > myDepth + allowed` was false at all 4,480 dome cells and the base grid was never blanked at all. That is the sky drawn over the buildings, and it is why the walk-mode `occluded` buffer only ever carried the cells where the base grid was already empty.
3. **The near plane.** `computeOcclusionIds` did not clip. A polygon with any vertex behind the eye projects to `NaN` and `fillDepthTri` drops the whole triangle, so under the walk camera the base layer claimed ZERO id-map cells out of 8,820 while painting 4,480 (1,338 of its 2,304 fan triangles projected to `NaN`, another 822 to an off-screen bbox from the reprojected garbage). An orbit camera looks at its scene from outside and this is unreachable; a street-level one stands INSIDE it — the ground under the walker and the dome around them both straddle the near plane by construction. `ProjectCamera` grew an optional `eyeDepth` and the loop clips exactly as `rasterizeSolid` does, UVs interpolated at the crossings so an alpha-aware claim survives it. An orthographic camera answers `+Infinity` and a camera that declines the probe is never clipped, so the whole branch is dead code on every scene that had one.

The retained-effect compositor was the fourth link in the same chain and the one that made the road fix from `a3b7c56` look like it had failed. `cloneCellGrid` did not copy `occluded`, so the immutable per-frame snapshot `retainGlyphEffectOutput` takes dropped it, and `composeRetainedGlyphEffectOutput` rebuilt the grid handed to the legacy `transformCells` hook without it — meaning the ownership test was inert for exactly the scenes that have an effect mounted. Walk mode always has one (the sky is a mesh-targeted appearance program), so entering it silently disabled the fix. The clone now carries `occluded` like every other optional buffer, and compose assigns it onto the working grid BY REFERENCE: unlike the buffers around it, this one is not the compositor's to own — the rasterizer allocates it fresh per pass, nothing here reads or writes it, and by-reference assignment sidesteps the pooled-scratch staleness `cellGridShapeMatches` guards for the copied fields (a pooled grid from a frame with no occlusion has no destination buffer to copy into, and would have silently dropped the data). It is deleted rather than left stale when the frame has none.

The compositor was the fifth link too, and this one was not about `occluded` at all: `runLegacyCellHook` called the hook with the grid ALONE, dropping the `GlyphTransformCellsLayer` second argument that `withTransformCellsLayer` binds on the direct path. So mounting any effect layer made a DETAIL grid indistinguishable from the base grid to a hook that reads it — and `@glyphcss/maps` (the reference consumer named in that type's own doc) then stamped its strokes through the IDENTITY affine into a grid `density` times finer, i.e. at `1/density` of their real position. That is the report `a3b7c56` and the four links above did not close: with `omt-buildings` alone at `1.7` in walk mode, every road in a street-level frame was redrawn across the buildings at roughly half its own height, in the buildings' own `<pre>` — which is why a fixture reading only the BASE `<pre>` measured the road cell-for-cell correct while the page was visibly wrong. Measured on the real page at the reported link, 48 base cells' worth of road ink sat in the buildings' detail `<pre>` at rows the unseparated render paints solid building; on the vendored Zürich tile at the same pairing, 265 base cells of road ink landed outside the road's own screen path. The tag now rides on `GlyphEffectOutputMetadata.transformCellsLayer` rather than on a render-scoped variable, because the hook runs on two paths — inside a full geometry render, and again on every retained recompose, which iterates outputs retained frames earlier and has nothing else left to say which grid each one is — and each construction site hoists ONE object that both the metadata and `withTransformCellsLayer` receive, so the two can never drift.

What that fix does NOT close, and is left as it is: a stroke stamped into a detail grid still paints unconditionally where that grid's own depth is `-Infinity` (the layer covers nothing there and the id-map awarded it the cell anyway, a silhouette-fringe artefact of the id map being coarser than the grid). Measured after the fix on the same tile: 77 of 7,324 stamp samples, all in the road's own row, all inside the one base cell of slack a change of resolution can move a stroke by. Gating them would remove road ink at a building's edge rather than leak any, so nothing is spent on it until something is actually seen.

Gates: `packages/glyphcss/src/render/rasterize.occlusionPerspective.test.ts` (claimed set == painted set, orthographic and perspective and across the near plane; id-map depth == `CellGrid.depth` cell by cell; ownership surviving retain + compose, and absent rather than stale), `packages/glyphcss/src/api/createGlyphScene.effectLayerIdentity.test.ts` (mounting an effect layer must not change what the hook is told about the grid it was handed — recorded per output with and without a layer mounted and compared field for field, `cellToSceneGrid` above all), `packages/maps/src/widget.walkDetailOcclusion.test.ts` (the reported density pairing end to end: separating the building into its own `<pre>` must not change which cells the base grid's sky and road paint) and `packages/maps/src/widget.walkStrokePlacement.test.ts` (the same pairing on the vendored OpenFreeMap tile, composited across EVERY `<pre>`: the road may only ink cells it actually runs through, measured with nothing in front of it).

`@glyphcss/maps`' `line` layer is the reference consumer and the reason this exists. Its stamp is an independent 3D object rather than an annotation of the winning surface, so it draws over empty cells by design — and with `omt-buildings` alone at `density: 1.7` and every other OSM row at `1` (a real reported `/maps` link), the buildings left the base grid for a `<pre>` of their own while the roads stayed in it, and every road cell inside a 60 m footprint drew over base cells reading `-Infinity`. Measured on the fixture in `packages/maps/src/widget.strokeDensityOcclusion.test.ts`: 23 of 23 footprint cells inked, identical at `781486f` and at its parent `2d27c55`, so no depth allowance was ever in the path. The rule the flag buys is that a stamp paints a cell only in the grid whose layer owns it — which loses nothing, because the composed hook runs over every grid the frame renders and the owning layer stamps there against its own real depth. A `contour` was never exposed: its `requireSurface` gate already skips a non-finite-depth cell.

**Alpha-aware id-map claims.** A polygon carrying a texture + UVs claims a cell only where its sampled texel is actually opaque (`a > TEXEL_COVERAGE_ALPHA_MIN` — the SAME coverage test `scanFillTriangle` applies, so the id-map's claimed set matches the paint path's covered set instead of the triangle's bounding geometry), resolved through the same sampler and the same fan-triangle UV assignment `rasterizeSolid` uses. Without it a sprite quad's transparent margin blanked the layer beneath, reading as a black halo around the artwork. A texture with no transparent texel at all skips per-cell sampling outright (checked once per sampler, cached), and frames before a texture decodes fall back to the pure-geometry claim. **This is not purely additive**: a pre-existing scene that has BOTH transparent-textured polygons AND opaque detail layers now renders differently — that difference IS the halo fix, and it is the intended change.

**Shaping an opaque detail mesh's claim.** Three per-mesh transform options, all `solid`-mode cross-layer machinery, all no-ops on a `transparent` mesh (which opts out of occlusion entirely), all defaulting to the pre-existing behaviour. `occlusionPriority` (default `0`) is an occlusion CLASS: a higher class claims a cell over every lower one REGARDLESS of depth and depth only breaks ties within a class, so `1` is a foreground layer scene geometry can never occlude and a negative class is a background layer any ordinary mesh occludes; an UNCLAIMED cell is claimable by any class, which is what keeps a negative class from claiming nothing at all. `occlusionClaim` (`"alpha"` default, `"geometry"`) opts a mesh back into the full-triangle-footprint claim — a filled plate under partial-alpha artwork. `occlusionContourPx` makes the claim COVERAGE-aware and is also the only way to buy fine artwork a small clean ground around its ink: the id-map is re-rastered at 4x per axis, any output cell containing this mesh's ink claims, and the value is a margin in SCREEN PX stamped around that ink in the fine map before reducing (`0` = the tightest possible claim), converting only base-layer or unclaimed cells — never stealing from another detail mesh. Because the margin is a screen-px reach rather than a count of whole cells, it stays visually uniform on an anisotropic cell (on an 8x16 cell one cell-height of margin buys one output row and two output cols), which is what a rejected earlier cell-counted dilation could not express — it grew twice as far vertically as horizontally, and a 2-cell pad became a ~20px square-kernel slab. The reduced map is still at output resolution, so the ground the layer beneath loses stays quantized to output cells — the map's hard floor. The margin's reach is capped at 24 fine cells per axis, i.e. `6 / supersample` output cells, so a margin wider than a few cells is out of range on a supersampled scene. Contour claims are the expensive one: the fine raster runs for EVERY group in the scene whenever ANY group carries the option, even at `0`, even while the contour mesh is entirely off-screen — measured 2.4-3.1x the plain id-map pass on a 120x48 grid with a ~2,000-triangle world, 7.5x at `supersample: 2`.

**Cross-SCENE occlusion.** Two scenes stacked over one host rect join a single occlusion domain through the scene handle: the producer publishes `getOpaqueCoverage()` (the last committed render's opaque per-cell coverage at OUTPUT resolution — cells owned by the base grid or an opaque detail layer, foreign stamps excluded so a chained consumer never relays an occluder it merely received) and the consumer takes it through `setForeignOcclusion(coverage | null)`, which stamps every covered cell of its own shared id-map with `GLYPH_FOREIGN_OCCLUDER_ID` (`-3`, never a real layer id). Every LOCAL layer then blanks under it — base grid, opaque detail layers, and `transparent` detail layers alike, the last via `OcclusionMap.foreignOnly`, which blanks solely on that sentinel and keeps ignoring every local owner, exactly as `transparent` promises toward its own scene. Grid resolutions may differ (mapped proportionally at cell centres); `covered.length !== cols * rows` throws `TypeError`; a re-publish of identical bytes costs one comparison, not a render, and the held coverage is a COPY so a producer reusing one buffer cannot alias the comparison. The whole mechanism is **`mode: "solid"` only** — it rides the local cross-layer machinery, which only the solid rasterizer reads, so in `wireframe`/`voxel`/`ink` a foreign mask is a silent no-op. A scene only builds an id-map when it has an opaque detail mesh or a foreign mask, so the most ordinary PRODUCER shape — a scene of plain base meshes — needs the `trackOpaqueCoverage` scene option (default `false`) to force a base-layer depth raster and publish anything at all; that map is base-only, which no local layer ever blanks on, so it changes no output and costs only the raster.

**Meshless viewport-wide overlay outputs.** `GlyphSceneHandle.setViewportOverlayDensities(densities: readonly number[])` requests one or more additional, transparent, FULL-VIEWPORT output grids — not silhouette-fitted like a per-mesh detail layer, since there is no mesh here to fit one to — each at `density`× the base grid's own resolution. Values are deduplicated and `1` (the existing base output) is ignored; an empty list removes every such output. This exists for a `transformCells` hook that wants its OWN resolution independent of every mesh's — a `line`/`contour` stroke layer in `@glyphcss/maps` (which has no geometry of its own to attach a `density` to) is the reference consumer: `widget.ts`'s `strokeLayerStampsIntoGrid` routes a stroke layer's genuine (`!== 1`) `density` through this call and stamps that layer ONLY into the matching overlay grid, never into the base grid or a mesh's detail grid too (which would otherwise duplicate the same stroke at a coarser resolution). Each requested density gets its own `<pre>` (`class="glyph-output glyph-output--detail"`, `data-glyph-overlay-density="<density>"`), rendered with zero polygons of its own — the ONLY way anything appears in it is the scene's `transformCells` hook, invoked with `{ detail: true, viewport: true, cellToSceneGrid, density }` (`GlyphTransformCellsLayer.viewport`), where `cellToSceneGrid` is `[1/density, 0, 0, 1/density, 0, 0]` (no translation — full-viewport, not offset like a detail mesh's bbox fit). Because a hook receiving a blank grid still needs to know what's occluding it, each overlay carries its OWN geometry depth pass at its own resolution — every base mesh plus every OPAQUE detail mesh's own transformed polygons (a `transparent` detail mesh never occludes, mirroring the shared id-map's own filter), via `buildSurfaceDepth` (the same `fillDepthTri` machinery `computeOcclusionIds` itself uses, exported for this) projected through the BASE grid's own unchanged metrics and scaled via its documented `sx`/`sy` output-multiplier mechanism (the `charMode: "braille"` subcell precedent) — never by independently re-deriving `cellWidth`/`centerCol`, which silently desyncs from the camera's own unmeasured-layout fallback (`BASE_TILE / cellAspect`, a constant `computeOcclusionIds`-style metrics scaling can't divide by `density` without reaching into the camera's internals). This is NOT the shared cross-layer id-map (`ctx.occlusion`) — that blanks a layer under a NEARER layer's ownership, which would blank an overlay's entire output since it owns no geometry itself; a hook instead reads the overlay `CellGrid`'s real per-cell `depth` directly. An overlay's depth pass is therefore SCENE-WIDE where a base or detail grid's is that pass's own; a stamp reaching a base/detail grid gets the cross-layer answer from `CellGrid.occluded` instead (see "Cross-layer occlusion" above), which is the half that was missing when this paragraph claimed the two were one contract. With no density requested (the default), `setViewportOverlayDensities` is never called and the render path returns before any allocation, depth pass, or `<pre>` — byte-identical to before the feature existed. This is a scene-handle capability, not a scene option, so React/Vue/custom-element consumers reach it through the handle they already expose — no wrapper component.

These options mirror across React/Vue `<GlyphMesh>` and the `<glyph-mesh>` custom element (`density`, `font-size`, `line-height`, `transparent`, `glyph-palette`, `mode`, `ambient-intensity`, `occlusion-priority`, `occlusion-claim`, `occlusion-contour-px`, `detail-group`; `<glyph-mesh mode>` ignores an unrecognized value rather than popping the mesh into a mode that doesn't exist); `trackOpaqueCoverage` mirrors as `track-opaque-coverage` on `<glyph-scene>` and `trackOpaqueCoverage` on the React/Vue `<GlyphScene>`, while `setForeignOcclusion`/`getOpaqueCoverage`/`setViewportOverlayDensities` are reached through the scene handle in every binding and need no wrapper component. **Static compile (`compileScene`, `GlyphSceneStatic`, the CLI/Vite plugin) and the interactive/CodePen export take a flat polygon list — they cannot represent per-mesh detail layers**, so per-mesh density/transparent is a runtime-only feature there (the gallery's scene-wide "Density" slider drives the render font-size instead, which *does* export).
