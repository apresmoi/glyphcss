## Why this is a new module, not an extension of `CellGrid`/`rasterize.ts`

`CellGrid` is the rasterizer's OUTPUT contract — the shape a 3D scene's projected, depth-tested, shaded geometry ends up in. A chart or a diagram never runs a 3D pipeline at all: there is no camera, no depth test, no shading. Reusing `CellGrid` as-is (via `buildCellGrid`) gives the canvas the exact same `char`/`color`/`depth`/`occluded` fields a `transformCells` hook already knows how to read — genuinely useful, since a Phase 3 fragment host can sample a canvas's grid the same way it samples a rasterized one — without adding a single field to the type `rasterize.ts` cares about. Everything the canvas needs that `CellGrid` doesn't have (`bg`, `sub`) is carried alongside it instead of grown into the shared contract; see "Why `bg` and `sub` are canvas-owned" below.

The module boundary is enforced by construction, not convention: nothing under `render/canvas/` is imported by `rasterize.ts` or `cells.ts`, and the reverse imports (`buildCellGrid`, `isSingleCellGlyph`, `inkGlyphForTangent`, `isQuantizableColor`) are all PURE, already-public helpers. A scene that never touches `createGlyphCanvas` pays nothing for its existence, and the byte-identity script in `bench/canvas-identity/` is the check that this stays true — not just "the tests still pass" (a test suite doesn't prove the existing render path is untouched; a digest of its actual output, before and after, does). That script now covers five fixtures across two packages (three `compileScene` renders, one `@glyphcss/maps` `compileGlyphMap` render, and one `rasterizeToCells` `CellGrid` capture), closing the gap the original three-`compileScene`-fixture version left — the ground rule this script exists to prove cites "every fidelity digest," and the original version never touched `@glyphcss/maps` at all.

## Why `bg` and `sub` are canvas-owned, not new `CellGrid` fields

A rasterized 3D scene has no concept of a per-cell BACKGROUND colour distinct from its foreground glyph colour — a solid-mode cell's "colour" already means the whole cell's paint. A chart legend swatch, a diagram node's fill, or a table-style layout all need the opposite: a background colour behind a glyph the FOREGROUND colour draws (an axis label sitting on a shaded band, an arrowhead on a tinted lane). Adding `bg` to `CellGrid` would mean every existing consumer of the type — the effect compositor, every render mode, every encoder in `cells.ts` — now has to reason about a field that is always empty for them, and the two real encoders that would need it (`encodeGlyphBuffers`, `encodeCellGrid`) are exactly the ones that must stay byte-identical for 3D scenes. Keeping it a canvas-owned parallel array instead means it's invisible outside `render/canvas/` and free everywhere else.

**Both encoders read `bg` UNCONDITIONALLY, independent of the glyph occupying the cell.** An earlier version suppressed `bg` on a blank (`" "`) cell using the same rule that (correctly) suppresses a blank cell's `color` — but a background is, definitionally, the thing a reader sees where there is no glyph. Suppressing it made the canvas's headline addition over `CellGrid` express only "a tint behind a character," which is the opposite of this section's own motivating example: an axis label sitting on a shaded band rendered as a band that existed ONLY under the label, and a legend swatch, an alternating-row background, or a plot-area fill all failed the same way. The fix is one line in each encoder (drop the `glyph === " " ?` guard on `bg` specifically, keep it on `color`) and is gated by painting a background under a space character specifically (`"a b"` over blue → three coloured cells in both exits), not merely under a filled glyph, which the original gate did and which cannot distinguish "reads `bg`" from "reads `bg` only where there's ink."

`sub` is the same argument at finer grain: a 2×4 sub-cell occupancy byte per cell exists only so the `braille`/`blocks` tiers can derive a fill glyph from partial coverage instead of a 1-D shade ramp. No 3D rasterize path has ever needed sub-cell occupancy as a *retained* buffer (the existing braille WIREFRAME mode computes its dot mask inline per edge and throws it away); inventing a general `CellGrid.sub` for one canvas feature would be exactly the kind of speculative surface `AGENTS.md`'s "No shallow work" section warns against.

**The 8 sub-cell dot bits fill in QUADRANT order, not bit order.** The dot layout is fixed (bit0..2 = left column rows 0..2, bit3..5 = right column rows 0..2, bit6 = left row 3, bit7 = right row 3 — see `GlyphCanvas.sub`'s doc comment), but the ORDER in which `shade`'s dot count lights them is a free choice, and it is what determines when the `blocks` tier's quadrant mask reaches "all four quadrants lit" (a full block) relative to the input shade. An earlier version filled bits in raw index order (`[0,1,2,...,7]`, effectively the braille bit order), which lights the four quadrants unevenly — one quadrant's second dot arrives before another quadrant's first — so a `blocks` cell reached a full `█` at `shade: 0.75`, meaning the top quarter of the input range was already indistinguishable from fully solid, and the render coverage sequence measured `0, ¼, ¼, ½, ¾, ¾, 1, 1, 1` across `shade` in eighths (a quarter of the *input* range renders as a *full* block either way this can go — see below). The fix orders bits by QUADRANT — both of top-left's dots, then both of top-right's, then both of bottom-left's, then both of bottom-right's (`[0, 1, 3, 4, 2, 6, 5, 7]`) — so `shade: 0.5` (4 of 8 dots) lands on EXACTLY "top-left and top-right both fully lit, bottom half untouched": the `blocks` quadrant mask is `TL|TR` → `▀` and the raw braille mask is bits `{0,1,3,4}` → literally the cell's top four dots. Both are the exact properties the "blocks/braille are sub-derived" gate requires (a designed half-fill must render precisely `▀`/`▄`, or the braille top-four-dot pattern — not merely "some 4-dot mask," which a shade-ramp substitute could fake). Full saturation now arrives at `shade: 0.875` rather than `0.75`; the two-cells-per-quadrant granularity means SOME early saturation is unavoidable at 4 discrete quadrant states over 8 sub-steps, but landing the boundary exactly on the required half-fill glyph — rather than merely reducing how much of the range saturates — is what makes the gate meaningful rather than approximate.

## Junctions: `edge()` + `route()`, resolved by ROUTE COINCIDENCE

The wireframe-junction pass `rasterize.ts` already has (`accumulateJunctionMask`, `JUNCTION_GLYPHS`) unions every edge's contribution into ONE mask per cell as it goes, because in that context every edge belongs to the SAME mesh's silhouette/crease outline and any two edges meeting at a cell are, by construction, meant to look joined. A diagram graph has no such guarantee: two independently ROUTED edges can legitimately cross in open grid space without ever being connected at a node, and a reader needs to be able to tell the two cases apart at a glance (a real junction vs. two wires that happen to overlap on a character grid, which has no way to draw one wire slightly in front of the other the way an isometric line drawing can).

`canvas.edge(edgeId, { from, to, priority? })` registers an edge's actual graph endpoints; `canvas.route(edgeId, cells)` then records its ORDERED cell polyline and throws (`RangeError`, naming the edge) if it was never registered — the join/crossing decision is undecidable without `from`/`to`, so silently guessing would reintroduce the exact defect this module exists to avoid. `route()` also throws if any two consecutive cells are not 4-adjacent: a route is a walk over the grid, not an arbitrary point set, and every mask this module derives depends on that adjacency holding.

### Round 1: masks are per-edge, not unioned at record time

The FIRST defect (closed in round 1, described for context because the fix that replaced it is round 2's own subject) was answering the join/crossing question from MASK SHAPE alone — "does some edge's mask at this cell have popcount 1 (a stub)" — on the theory that a terminating edge is always meeting something on purpose. That heuristic was wrong in both directions: a stub with no relationship to an unrelated transit it merely touched read as a real junction; two edges that legitimately shared a node but both ran straight through the shared cell read as an ordinary crossing and lost their join glyph; a corner losing an unrelated crossing was substituted with a hop oriented to an axis that had nothing to do with the turn; a third, unrelated edge merely stubbing into an existing crossing unioned all three into a false `┼`. Round 1's fix was to stop unioning masks at record time at all — keep each edge's own contribution separate per cell — and defer the union decision to `resolveJunctions()`, deciding it from the edges' declared graph endpoints instead of mask shape.

### Round 2: node-ID equality is still not local — the fix is ROUTE coincidence

Round 1's resolver asked, per cell: do the edges present here share a `from`/`to` string, ANYWHERE, transitively through however many bridging edges? That question has no reference to the CELL at all — it is a global fact about the graph, asked at a specific, local rendering decision. Two consequences, both found by round 2's independent reviews:

- **A fan-out from one hub drew a false `┼` however far its two legs' crossing point was from the hub.** Two edges `A(hub→x)` and `B(hub→y)` share `from: "hub"`, so round 1's resolver joined them at EVERY cell either was present at — including a cell seven-plus columns from the hub, where the two routes' legs happened to cross in open space after diverging. The round-1 test suite's own headline gate (`E|W` from one edge, `N|S` from another, both terminating at the SAME graph node) pinned this defect as a requirement: that mask shape is geometrically IMPOSSIBLE at a node either edge actually terminates at (an edge ending at a node has a stub or a corner there, never a full two-sided transit), so the configuration the gate demanded could only be produced away from the node — exactly the false-join shape.
- **Transitivity chained unrelated edges through a bridging third one.** `A(n1,n2)`, `B(n2,n3)`, `C(n3,n4)` sharing one cell (masks `E|W`, `N`, `S`) joined into one `┼` because `A.to === B.from` and `B.to === C.from`, even though `A` and `C` share nothing. The bridging node string `n2`/`n3` need not even be anywhere NEAR the cell in question — `edge()` records only two label strings, with no cell position attached to either.
- **A same-axis, non-perpendicular "crossing" escaped the conflict report.** Two `E|W` transits laid on top of each other (never sharing a node at all) passed round 1's "exactly two groups, both plain straight transits" test for a routine crossing — the check never verified the two axes were actually PERPENDICULAR, so a genuine overlap (two routes running along the identical cells without ever connecting) silently rendered as if it were the ordinary "wires cross in open space" case.

**The fix replaces node-ID equality with ROUTE COINCIDENCE, and removes caller-supplied masks entirely.** `route(edgeId, cells)` records the ordered polyline; every N/E/S/W bit a cell contributes is DERIVED from that edge's own neighbouring cells in the route (an endpoint contributes one bit, an interior cell one or two), never supplied directly — there is no longer a mask-shape input to get wrong. At resolution, for a cell `C` shared by edges `E1` and `E2`: they JOIN iff they share an endpoint graph node `n` AND the WALK of cells from `C` back to `n` is the IDENTICAL sequence for both edges (`pathToNode` in `junctions.ts`, walking forward through the route if `n` is that edge's `to`, backward if `n` is its `from`). Three concrete shapes fall out of one rule:

- **A real hub.** `C` already IS `n`'s own location for every edge that starts (or ends) there — the walk from `C` back to `n` is zero cells long, trivially identical for every edge present. This is the ordinary T/cross-join case (`┬`, `┼`, …), computed exactly as a hub with any number of spokes always was.
- **A merge into a common target.** Two edges approach `C` from different directions, then run along the IDENTICAL trunk of cells the rest of the way to a shared `to` node — the coincidence check walks that shared trunk forward and finds it byte-for-byte equal for both, so they join (rendering `┬`/`┴`/`├`/`┤` as the actual turn shapes dictate).
- **A fan-out from a common source.** The mirror image: two edges share the SAME trunk from a common `from` node, then diverge after `C` — the coincidence check walks BACKWARD toward the shared source and finds that side identical, joining at the split point even though the two edges' onward paths differ completely.

Sharing a node id with no such coincidence — the fan-out's DISTANT crossing, the `A`/`B`/`C` bridging-node chain, two edges that reference the same label without ever tracing the same cells — never joins, however many edges bridge the two on paper. This is what makes the rule LOCAL: the answer at cell `C` depends only on what happens AT and AROUND `C`, never on a fact about the graph elsewhere.

### The winner "keeps its glyph", and route conflict `kind`

Two or more groups (edges, or joined clusters of edges, that don't coincide with each other) at one cell is a CROSSING or a route CONFLICT. The highest-priority group (an explicit `priority`, ties broken by registration order — the earlier `edge()` call wins) is the WINNER and draws its own glyph, computed as if it were the only thing at the cell — unchanged from what it would draw alone, except that a PLAIN STRAIGHT TRANSIT mask (`E|W` or `N|S`) is upgraded to the tier's dashed `hop` glyph on the WINNER's OWN axis (never the loser's — orienting the hop to the losing edge's axis reads as a foreign mark breaking the winner's own line, the inverse of "the higher-priority edge reads as continuous"). Every other group draws nothing at that cell.

Exactly two groups, both plain straight transits, on PERPENDICULAR axes is the routine "two wires cross in open space" case and logs nothing — a router will manufacture this constantly. Every OTHER 2+-group shape is logged to `canvas.report.routeConflicts` as `{ edgeIds, col, row, kind }`, `edgeIds` in registration order:

- **`"parallel"`** — two (or more) groups whose masks are both plain straight transits on the SAME axis. This is what closes the "escaped the conflict report" defect above: two coincident, non-joining `E|W` routes are not a crossing at all (nothing routes through open space along the exact same line without meaning something), so this shape is never mistaken for the routine perpendicular case.
- **`"corner"`** — exactly two groups where at least one is NOT a plain straight transit (a corner or a stub meeting an unrelated transit, or another corner).
- **`"multi"`** — three or more mutually unrelated groups at one cell.

This is a genuinely new capability past what either round-1 review asked for verbatim — PLAN.md's original Phase 0 gate only forbade `┼` on an ordinary crossing — but it is the natural generalization the "keeps its glyph" rule needs once 3+-edge and irregular-shape crossings are handled by the same code path as the classic 2-edge case, and the `kind` field lets a later phase's router distinguish "route around this, it's genuinely overlapping" (`parallel`) from "this is an unavoidable incidental touch" (`corner`/`multi`) without re-deriving the shape itself.

**Priority is an explicit, optional field with registration-order fallback**, not a value threaded implicitly through call order alone. A caller who cares which edge wins a given crossing can say so directly (`priority: 10`); one who doesn't gets the same "route the ones you want in front, first" mental model, with no RNG and no wall clock anywhere in the path (`"same spec + same options = same string"` holds either way).

### Round 3: `resolveJunctions()` is a pure function of the registered routes, including on a second call

REVIEW-arc-density-search-opus.md (P2-1) found `resolveJunctions()` was correct for exactly ONE call per canvas and undocumented about it: every cell's GLYPH write (`grid.char[idx] = ...`) is an overwrite and so is trivially idempotent, but `report.routeConflicts.push(...)` — the ONE place anything writes that field (grepped) — is an accumulator with no matching clear. A second call with no new `edge()`/`route()` registration re-derives the exact same conflicts from the same `state` and pushes them AGAIN, so `canvas.report.routeConflicts` doubles (triples, …) on every extra call, silently. `@glyphcss/charts` (the one caller today) never hits this — it calls `resolveJunctions()` once per render, always against a fresh canvas — but the precondition was nowhere written down and nothing caught a violation, which is exactly the shape of bug a NEXT caller (the arc leader-line callout, which currently paints leaders through plain `canvas.line` calls for exactly this reason — see AGENTS.md's "Charts") would walk straight into the moment it tried routing through `edge()`/`route()`/`resolveJunctions()` instead.

Fixed at the top of `resolveGlyphCanvasJunctions`: `report.routeConflicts.length = 0` before the resolution loop runs, truncating the array in place (the same reference the canvas's own `report` object holds, so a caller who captured `canvas.report.routeConflicts` earlier sees the clear too, exactly like every other `GlyphCanvasReport` field). This makes the whole function a pure function of `state`/`grid`: calling it N times with the same registered routes produces the SAME report every time, not an N-times-longer one. Gated in `junctions.test.ts` (a two- and a three-edge conflict, each resolved twice/thrice and compared byte-for-byte) rather than merely asserted — a mutation that drops the clear reddens both.

## Why tiers are tables, not branches

`GLYPH_CANVAS_TIERS` exists so that "render this in braille instead of box-drawing" is a single lookup key change, never a rewrite of the painters. Every painter (`fillRect`, `line`, `arrowhead`, `resolveJunctions`) reads its glyph from `GLYPH_CANVAS_TIERS[canvas.tier]`. The four tiers share IDENTICAL keys at every depth for the same reason a discriminated union needs the same fields on every arm: a consumer generic over `GlyphCanvasTierName` (a chart rendering at `"chat"` vs `"terminal"` targets, per `PLAN.md`'s Phase 1) has to be able to treat them uniformly.

**"Never branches on the tier name" was true of every painter except `fillRect`'s sub-cell fill path, which round 2 fixed rather than merely re-described.** `fillRect` used to ask `tier === "blocks" || tier === "braille"` to decide whether to read `sub` at all, then `tier === "braille"` again to choose between the two sub-cell ENCODINGS (a raw braille codepoint vs. a quadrant-glyph table lookup) — both were branches on the tier's NAME, contradicting the very sentence that described this table. The fix moves both decisions into the table itself: every tier carries a `subcell: boolean` flag (`fillRect` reads `tierTable.subcell`, never `canvas.tier === "..."`, to decide whether a fill is sub-cell-derived at all) and, for the two tiers where it's `true`, a `subGlyph(mask: number): string` function (`fillRect` calls `tierTable.subGlyph!(mask)` uniformly, never asking WHICH sub-cell tier it's in). `ascii`/`box` carry `subGlyph` explicitly set to `undefined` — never simply omitted — so the tier-parity gate's own-key walk sees the identical key set on all four tiers; omitting it there would silently reintroduce a per-tier key mismatch for a key that is genuinely part of the table's shape.

`ascii` and `box` fill shaded regions from a 1-D `shadeRamp` because their glyph vocabulary has no sub-cell addressing — a single character IS the whole cell's ink level. `braille` and `blocks` instead derive their fill glyph from the canvas-owned `sub` occupancy buffer via `subGlyph`, because THEIR vocabulary is naturally sub-cell (a braille cell is eight independently-addressable dots; a quadrant block is four). Giving `braille`/`blocks` a `shadeRamp` entry too, even though `fillRect` never consults it for them, is what keeps the tier-parity gate meaningful rather than accidentally correct — it says "this is a real table with the same shape," not "these two tiers happen to both lack a field the other two have."

**`ascii`'s AND `box`'s shading ramps are both blank at `shade: 0`.** `ascii`'s dedicated ramp (`" .:-=+*#"`) was never the photographic `dense` wireframe ramp (`WIREFRAME_PALETTES.dense.solid`, `"%$EUKH#D80BM@N"`, which includes LETTERS and would make a solid ASCII bar read as text) — round 1's fix. Round 2 found the SAME "zero shade must be invisible" property missing from `box`'s own ramp (`"░▒▓█"`, no leading blank entry — `shade: 0` painted a visible light-shade glyph), which meant a zero-valued heatmap cell or stacked-bar segment gained ink purely from switching from `ascii` to `box`, even though "switching tiers is a data swap" (this section's own opening claim) says it should not. `box`'s ramp is now `" ░▒▓█"` (5 steps, blank at 0, full block at 1) — `blocks`/`braille` never needed this fix, since their sub-cell derivation already produces the tier's own zero-coverage glyph (a plain space for `blocks`, `U+2800` for `braille`) at `shade: 0` for free. `fillRect`'s `fill.shade` is additionally validated as a FINITE number in `[0, 1]` (`RangeError` naming the painter otherwise) — a continuous quantity a layout computes from a scale, exactly like `x0`/`y0`/`x1`/`y1`, and `NaN` (an all-zero series' `v / max`, a constant series' `(v - min) / (max - min)`) used to reach `ramp[NaN]` = `undefined`, written verbatim into `grid.char` and shortening the encoded row.

**Junction/hop/arrow line art (`edge()`/`route()`/`resolveJunctions()`, `arrowhead()`) has no sub-cell analogue worth inventing for `braille`/`blocks`**, so those three still reuse `box`'s glyphs verbatim — a route drawn in a "braille" chart is still legible as a route, and an arrowhead is a GLYPH (a fixed tip shape), not geometry, so there is nothing to rasterise at finer resolution. `line()` itself is the one exception, and it is a later addition to this document: see "`line()` in `braille`/`blocks`: sub-cell (dot) resolution" below.

## `line()` in `braille`/`blocks`: sub-cell (dot) resolution

The owner-reported defect: `canvas.line()` painted the SAME whole-cell slope glyphs (`/ \ ‾ ▔ ▏ ▕ - | _`, via `inkGlyphForTangent`) in every tier, so a line chart in `braille` or `blocks` was exactly as coarse as `box` — the `sub` occupancy buffer existed and was read only by `fillRect`. `line()` now branches on the active tier's `subcell` flag (the same flag `fillRect` already reads, never a `canvas.tier === "..."` name check): `ascii`/`box` take the UNCHANGED whole-cell walk (`walkGlyphCanvasLine`, `line.test.ts`'s fixtures pinned byte-for-byte); `braille`/`blocks` rasterise the segment directly into `sub` at DOT resolution and derive each touched cell's glyph from the tier's own `subGlyph(mask)` — the exact mask-to-glyph step `fillRect` already uses, so a line crossing a fill (or another line) MERGES into the existing occupancy (`sub[idx] |= bit`, never an assignment) instead of overwriting it.

**`opts.subcell` overrides the tier's own capability for one call, so the orchestrator decides which lines are DATA and which are STRUCTURE.** The first cut of this feature routed EVERY `line()` call in a `braille`/`blocks` chart through the sub-cell path, axes included — a chart's own axis frame (and `glyphChartRule`'s reference lines, and gridlines/tick marks) is not data, and rasterising it at dot resolution produced a wobbly, half-connected vertical/horizontal rule instead of a clean `│`/`─`. `@glyphcss/charts`' axis and rule painters now call `canvas.line(a, b, { ..., subcell: false })` explicitly; every other `line()` call in the charts package (line marks, area boundaries, the `dot` mark's degenerate-point placement) omits the option and gets the tier's own default. The contract is therefore "sub-cell DATA marks, whole-cell axes" under `braille`/`blocks` — never "everything sub-cell" — and it is the canvas that stays generic (it has no notion of "axis"; it only honours whichever capability the caller asks for).

**The sub-cell walk is a plain Bresenham, deliberately NOT `walkGlyphCanvasLine`'s supercover/DDA.** Supercover exists to avoid gaps at CHAR-cell resolution (a short, near-axis-aligned segment landing mid-cell at both ends must still ink the cell its interior plainly crosses — see this file's own `walkGlyphCanvasLine` section above). At DOT resolution that same "visit every cell the interior merely grazes" rule is actively wrong: a shallow diagonal can graze `2 + 4 - 1 = 5` of a single 2×4 cell's 8 dots, more than half a cell solid for what is supposed to be a single hairline stroke. Standard (thin) Bresenham — the technique every braille/sixel plotting library uses (`drawille` et al.) — visits at most `max(dx, |dy|) + 1` dots along a connected, 8-adjacent path, single-stepping the minor axis at most once per major-axis step. `subcell.test.ts` pins the concrete bound this was chosen against: a line from `(0,0)` to `(10,3)` on a 12×4 canvas never puts more than 4 of a cell's 8 dots down.

**Cell-space → dot-space is one affine map, applied per axis.** A `line()` cell coordinate already uses the convention "integer = cell CENTRE, half-integer = cell BOUNDARY" (see `walkGlyphCanvasLine`'s own doc). Recursed one level down — dot `k` of `DOTS` sits at cell-local offset `(k + 0.5) / DOTS - 0.5` — the map `DOTS * x + (DOTS - 1) / 2` sends every such offset, for every integer cell `x`, onto an INTEGER dot coordinate (dot centres on integers, dot boundaries on half-integers), which is exactly the framing plain Bresenham (rounding each endpoint once) needs. `DOTS` is `2` for columns and `4` for rows — `GlyphCanvas.sub`'s fixed layout, not a function of `cellAspect`: the lattice size is a property of what a braille/quadrant GLYPH physically has, not a runtime-tunable resolution, and splitting a cell 2-wide-by-4-tall (rather than, say, 2×2) is itself what "honours the cell aspect" — a terminal cell defaults to roughly twice as tall as wide (`cellAspect: 0.5`), so a 2×4 dot split is what makes each individual DOT come out roughly square, which is what keeps a geometrically 45-degree `line()` run looking like one.

**Style handling mirrors the whole-cell path one level down.** The dash/dot cadence advances per DOT visited (not per cell — the walk itself is finer, so the cadence is too), following the SAME "advance the pattern index before the occlusion check" rule the whole-cell path already established (an occluded cell/dot still consumes its place in the cadence, it simply isn't painted — no renumbering of everything downstream). `style: "double"` on a DIAGONAL sub-cell line keeps the EXACT SAME documented contract narrowing as the whole-cell path (solid + one `report.ledger` entry) — there is no more a clean single-dot perpendicular offset for an arbitrary slope than there was a doubled diagonal GLYPH. An AXIS-ALIGNED (horizontal/vertical) `style: "double"` sub-cell line, by contrast, is REAL support rather than a narrowing: a second dot-thin run exactly one dot away, perpendicular to the first — the lattice always has room for this on a straight run, so nothing degrades.

**`@glyphcss/charts`'s `dot` mark is the other consumer.** A whole-cell dot glyph (`seriesDot`'s `● × + ◆` / `o x + *`) would throw away exactly the resolution `line()` now has, so `paintDot` (`packages/charts/src/paint.ts`) places a `braille`/`blocks` mark via `canvas.line`'s own DEGENERATE (zero-length) case, which rasterises to exactly one dot, at the EXACT (unrounded) sub-cell position — `layout.ts`'s new `scaleToColExact`/`scaleToRowExact` carry that precision from the scale into cell space, where the existing `scaleToCol`/`scaleToRow` round to a whole cell first and would throw the offset away before the canvas ever saw it. Monochrome multi-series identity (previously a distinct whole-cell glyph per series) is preserved as a distinct 2-dot COMPANION shape one dot away from the primary — computed to land in the SAME cell as the primary via `paint.ts`'s own `primaryDotIndex`/`dotIndexToCoord` (replicating `line()`'s own dot-rounding rule), because simply adding "half a cell" in continuous coordinate space can cross into the NEIGHBOURING cell instead, depending on which half of the current cell the primary's own fraction happens to round into (found via a real test failure, not by inspection — `review.test.ts`'s own regression history). Colour, when enabled, carries series identity instead, and every mark collapses back to the single-dot shape (`paintGlyphChart` already zeroes `styleIndex` whenever `colorEnabled`).

Gates: `packages/glyphcss/src/render/canvas/subcell.test.ts` (monotone dot path, ≤4 dots/cell, OR-merge on crossing, box/ascii byte-identity, double/dashed/dotted, arrowhead unaffected), `packages/charts/src/paint.subcell.test.ts` and `review.test.ts` (a braille line has strictly more distinct glyphs than the same chart in `box` and never emits `/`/`\`; a dot mark never exceeds 2 dots in one cell).

**Diagonal (`line()`'s non-axis-aligned) glyphs are ALSO a tier table now**, keyed by the nine raw glyphs `inkGlyphForTangent` (`../rasterize`, the same tangent-based selector the `ink` render mode uses) can return for a sloped run: `‾ ▔ ▏ ▕ / \ - | _`. The reviewed version called `inkGlyphForTangent` directly from `line()`'s diagonal branch and wrote its result straight to the grid, with no tier indirection at all — box's own vocabulary happens to be exactly `inkGlyphForTangent`'s raw output, so this looked correct in the default tier, but an `ascii` canvas emitted the same non-ASCII glyphs (`‾`, `▔`, `▕`, `▏` are all outside `0x20-0x7e`), failing the Phase 1 gate ("`charset: "ascii"` matches `/^[\x20-\x7e\n]*$/`") on the exact mark (`line`) most likely to be diagonal in a real chart. `box`'s `diagonal` table is the identity map (it already IS `inkGlyphForTangent`'s vocabulary); `ascii`'s collapses the four horizontal offset levels to `-`, the three vertical offset levels to `|`, and keeps `/`/`\` as-is (both already ASCII) — the sub-cell offset detail is simply lost, not approximated by an out-of-set character. The degenerate zero-length case (`inkGlyphForTangent`'s `·`) isn't a `diagonal` table entry at all; it reuses `dot` directly, since `·` already IS `box`'s own `dot` glyph.

**The tier-swap gate itself was strengthened past what it verified before.** The reviewed version's membership loop only inspected cells where the two tiers' rendered glyphs DIFFERED (`if (b === a) continue`) — which is exactly blind to a painter that bypasses the table IDENTICALLY in both tiers (precisely what the un-fixed diagonal branch did, since `inkGlyphForTangent`'s raw output happens to already be ASCII-safe for horizontal/vertical near-axis cases). The fixed gate checks EVERY painted cell's membership in its own tier's table, with the sole documented exception of `text()`'s own cells (which are contractually NOT table-driven — `text()` writes literal, caller-supplied characters, by design, and that exemption is itself pinned by a separate "raw ASCII text is byte-identical across tiers" assertion). A second, exact-fixture test compares box/blocks/braille/ascii's FULL rendered strings for a small fixed script (a horizontal run, a vertical run, a diagonal) against each other and against a hardcoded expected string per tier — this is what "switching tiers is a data swap" means made concrete, rather than a membership property alone.

## Line styles: `"double"` on a diagonal, and dash/dot phase vs. occlusion

**`style: "double"` on a non-axis-aligned `line()` run is a documented CONTRACT NARROWING, not a bug to fix.** No font in this glyph set has a doubled diagonal — `inkGlyphForTangent`'s vocabulary (`‾ ▔ ▏ ▕ / \ - | _`) already varies by sub-cell offset, and there is no second, "doubled" variant of any of those nine glyphs to select between. Throwing would make an author's diagonal-heavy diagram unrenderable over a style choice that has no wrong answer to give; silently falling back to `"solid"` with no signal would look like the style was ignored. The chosen behaviour renders solid AND records exactly one `canvas.report.ledger` entry per `line()` call (not one per diagonal cell — a `loggedDoubleDiagonal` flag inside the call gates it), naming the style and the first affected cell. Both the docs and the test suite state this explicitly rather than leaving it to be inferred from the code: `AGENTS.md`, this file, and `canvas.report.ledger`'s own test assert the exact rendered bytes AND the ledger message.

**A `line()`'s dash/dot pattern phase advances per DISTINCT cell the walk visits, independent of whether that cell is paintable.** The pattern index used to increment only AFTER the occlusion guard — meaning a hidden cell was skipped entirely, including the increment, so every cell AFTER it read the pattern one step early. A period-3 dashed run of `"-- -- -"` (on, on, off, on, on, off, on) occluding only its second cell should read `"-  -- -"` (that one cell blanked, the rest of the phase untouched) but instead read `"- - -- "` — the occluded cell's missing increment silently renumbered the entire remainder of the line, showing ink where the unoccluded line would have shown a gap and vice versa, arbitrarily far past the hidden cell. The fix is one reordering: `patternIndex++` runs BEFORE the occlusion check, so an occluded cell still consumes its place in the cadence; it simply isn't painted. This mirrors the "throw immediately, never let a skipped step silently shift everything after it" discipline the shade/coordinate validation in the next section follows for a different input.

**`line()`'s walk is a supercover/DDA over cell BOUNDARIES (Amanatides–Woo), not a fixed sample count.** The reviewed version picked `steps = round(length)` evenly-spaced samples along the segment and rounded each one to its nearest cell — round 3's finding: a short, near-axis-aligned segment landing mid-cell at both ends (`(0.49, 0) → (1.51, 0)` on a 3-wide canvas) rounds to samples at cell 0 and cell 2 only, skipping the middle cell the segment's interior plainly crosses (`"- -"` instead of `"---"`); vertical and shallow-diagonal equivalents left the same kind of hole. `walkGlyphCanvasLine` (`canvas.ts`) instead steps from one cell boundary to the next in parametric `t`, visiting every cell the segment's interior enters — exact at any length, angle, or sub-cell endpoint, and a corner-exact 45-degree crossing (both axes' boundaries at the same `t`) advances both axes at once rather than visiting the two orthogonal neighbours a real diagonal never touches. `line()`'s own coordinate convention centres a cell on its integer coordinate (`Math.round` picks the containing cell), so the walk runs shifted by `+0.5` — putting cell boundaries on integers — and reports cells back unshifted. The per-cell dash/dot pattern and diagonal ink selection above are unchanged; each visited cell now carries the midpoint (in `t`) of its own traversal as the representative point for `subRow`/`subCol`, in place of the old fixed sample's coordinates.

## Stroke width: glyph substitution on `ascii`/`box`, real dot ink on `blocks`/`braille`

`line()`'s `width?: 1 | 2 | 3` option (default `1`, byte-identical when absent — the whole-cell path's `width >= 2` branch and the sub-cell path's `widthOffsetPos`/`widthOffsetNeg` variables are both dead code at `width: 1`, gated on the exact same condition every other optional-field default in this module uses) exists because `@glyphcss/charts`' `options.strokeWidth` needs it, and the two tier families have genuinely different amounts of resolution to spend on it.

**`ascii`/`box` have no per-cell sub-resolution, so "wider" means a HEAVIER GLYPH on the IDENTICAL footprint, never an extra cell.** This was a deliberate design constraint, not an oversight: `@glyphcss/charts`' `paintLine` already clips a segment to the chart's plot rect (`clipSegmentToPlot`) before handing it to `canvas.line()`, and that clip is computed once, from the mark's OWN footprint at width 1 — if width 2/3 grew the footprint by walking neighbouring cells, the clip would need to know the width too, coupling a canvas-internal glyph choice to a caller's own layout math. Reusing the tier's own `double` glyph (`═`/`║` for `box`, `=`/`#` for `ascii`) for a width-3 STRAIGHT run costs nothing extra — that field already exists for `style: "double"` — and falling back to the tier's own full-ink `shadeRamp` entry (`"█"` for `box`/`blocks`/`braille`, `"#"` for `ascii`) for every other case (width 2 on any run, width 3 on a diagonal, which has no `double` analogue any more than `style: "double"` does — see "Line styles" above) needed no new table field at all.

**`blocks`/`braille` add real sub-cell ink because they have DOT resolution to spend, and the mechanism is the SAME one `style: "double"`'s axis-aligned case already uses, generalized.** `style: "double"`'s existing sub-cell offset (`horizontal ? {x:d.x,y:d.y+1} : vertical ? {x:d.x+1,y:d.y} : (ledger, solid)`) only covers the two exactly-axis-aligned cases. Stroke width needed the same idea for an arbitrary slope, so the offset direction is derived from which axis the segment travels LESS along (`Math.abs(ddx) >= Math.abs(ddy)` in DOT space, computed once per `line()` call from the segment's own endpoints) rather than branching on `horizontal`/`vertical`/`else` — a near-horizontal run gains a dot below it, a near-vertical run a dot to its right, and a genuine diagonal (where neither axis obviously dominates) still gets a well-defined answer instead of `style: "double"`'s own ledger-and-solid fallback. Width 2 offsets by one dot in the POSITIVE perpendicular direction only; width 3 adds the NEGATIVE direction too (`widthOffsetNeg`), so the run reads as centred rather than shifted. Both offset arrays are computed once (per `line()` call, not per dot) and merged into `sub` via the SAME `plotDot`/OR-write path every other dot in the walk already uses, so a width-3 line crossing a fill or another line still merges rather than overwrites.

**`@glyphcss/charts`' own plot-rect clip needed a matching margin, and it is the CALLER's responsibility, not the canvas's.** A width>=2 dot offset can reach at most one cell over (a cell holds only 2 dot columns or 4 dot rows, so a dot at a cell's own outer edge steps into its neighbour on a single 1-dot offset) — but `canvas.line()` itself only bounds a walk to the whole GRID (`cols`/`rows`), the same limitation `paintLine`'s own `clipSegmentToPlot` doc already states for the unwidened case. Teaching `canvas.line()` about a caller's "plot rect" (a concept this module has never had — it doesn't know what a chart, an axis, or a legend even are) would be exactly the kind of consumer-shaped coupling `AGENTS.md`'s module-boundary discipline exists to prevent. `paint.ts`'s `strokeClipPlot` instead insets the PLOT rect by one cell on every side before `clipSegmentToPlot` runs, but only when the active tier is sub-cell AND `width > 1` — `width <= 1` (including every render before this option existed) is untouched. Measured: for an integer-cell-aligned segment endpoint sitting exactly ON a plot boundary, `toSubcellSpace`'s own `+0.5` rounding convention (`Math.round` rounds `.5` up) happens to land that endpoint's dot on the INNER of the two/four local positions on ONE specific edge of a boundary column/row, which can mask the defect for a hand-picked test case that only touches that one edge — the one-cell margin is a general bound independent of that per-case luck, not a fallback for when it fails.

## Why raw text, HTML and ANSI are three separate functions

Each exit has a genuinely different, mutually exclusive escaping/colour contract, and collapsing them into one function with a mode flag would make it possible to ask for the wrong combination (HTML entities in a value that's about to hit a terminal; SGR codes in a value about to be dropped into `innerHTML`) with only a runtime flag standing in the way. `encodeGlyphCanvasText` emits the cell buffer verbatim — including a literal `<`, `>` or `&`, because a consumer piping this into a terminal, a chat message, or a plain log line needs exactly the characters that were drawn, not their HTML-safe substitutes. `encodeGlyphCanvasHtml` escapes those three characters ITSELF (deliberately not delegating to `cells.ts`'s private `escapeGlyphHtml`, which has no reason to be exported for this) because a `text()` label can carry arbitrary caller-supplied content, unlike a rasterized 3D scene's glyphs which are drawn from a fixed, already-safe vocabulary. `encodeGlyphCanvasAnsi` is the only one of the three that needs a colour-distance metric at all (the 16/256-colour downgrade), so folding it into either of the other two would mean carrying palette-quantization machinery into code paths that never use it.

**The HTML encoder is SPANS ONLY in Phase 0 — the atlas-delegation optimization described in an earlier revision of this document was removed entirely, not merely made opt-in.** The reviewed version conditionally delegated to the existing colour-font-atlas encoder (`encodeCellGridAtlas`) whenever every glyph was atlas-covered and no cell had a `bg`, for a zero-`<span>` result "identical in spirit to a scene's own `colorEncoding: "atlas"`." Two things were wrong with this, both found independently by both reviews: (1) box-drawing glyphs ARE atlas-covered, so the branch fired for exactly the content this document's earlier revision claimed it would NOT — a chart's own axes and rules, the common case, not an edge case; (2) the atlas encoder returns PUA (Private Use Area) code points that mean something only against a specific palette, and the delegation computed that palette, handed it to `encodeCellGridAtlas`, and then DISCARDED it — the caller receives text with no way to recover which colour each code point meant, and no signal even indicating which encoding it received. `encodeCellGridOutput` (`cells.ts`), the existing 3D-scene equivalent, avoids exactly this by returning `{ text, encoding }` so a caller can tell and react (per-`<pre>` `font-family` pin, `@font-palette-values` CSS). Reinstating an atlas path correctly needs that same signal — real bindings/CSS surface, added deliberately in a later phase — rather than a silent "sometimes atlas, sometimes spans" toggle a caller has no way to detect from the return value alone. Phase 0 therefore ships spans, unconditionally; nothing about `GLYPH_FONT_ATLAS` is imported by `encode.ts` any more.

**The gap this closes for the escaping gate is real, not incidental.** With the atlas branch removed, "the HTML exit escapes `<`" can be exercised with a plain colourized label — no `bg` trick needed to force the span path, which is the ONLY path now. The reviewed version's escaping test could only reach its own assertion by setting a `bg` specifically (its own code comment said so), meaning the escaping guarantee was verified on a minority path; a bare `<`/`&`/`>` render (no `bg`) would have silently taken the broken, colour-discarding atlas branch and never exercised escaping at all.

## Why colour is validated at the PAINTER, not the encoder

`CellGrid` colours are contractually canonical `#rrggbb` everywhere else in glyphcss (`cells.ts`'s `assertColor`, enforced at every write into the shared buffer). The reviewed version let an arbitrary caller string reach `grid.color`/`canvas.bg` completely unvalidated, with two independent, reviewer-discovered consequences:

- **Silent divergence between exits.** A non-hex colour (`"red"`, `"steelblue"`) rendered correctly in the HTML exit (which interpolates the string directly into a CSS `color:` value, and CSS understands named colours) but as pure black in the ANSI exit (`packHexColor("red") ?? 0` — the `?? 0` fallback for an unparseable string silently became "black" with no error and no report). A Phase 1 chart spec carrying a CSS colour name would render correctly on the web and wrongly in a terminal, with nothing to say why.
- **HTML style-attribute injection.** The same unvalidated string, interpolated into `<span style="color:${runFg}">`, let a crafted colour value (`'#fff" onmouseover="alert(1)'`) close the `style` attribute and open a new one — turning `text()`'s "a label can carry arbitrary caller-supplied content" design premise (the very reason the HTML exit escapes `<`/`&`/`>` itself) into an actual injection vector once a colour reaches this module from untrusted JSON, which is exactly the shape Phase 1's planned `renderGlyphChartJson`/MCP entry point produces.

Both defects share one root cause (an unvalidated string reaching a shared buffer) and one fix: `fillRect`/`line`/`text`/`arrowhead` each validate their `color` (and `fillRect`'s `bg`) against the SAME canonical-`#rrggbb` test `cells.ts`'s own encoders already require (`isQuantizableColor`, already public), throwing a `TypeError` naming the specific painter the moment an invalid value is supplied — not later, not at encode time, and not silently. Once every colour that CAN reach `grid.color`/`canvas.bg` is provably canonical, no encoder needs its own validation or sanitizing step; the injection is refused before it exists, not sanitized after the fact.

**`isQuantizableColor` alone validates HEX, not CANONICAL hex — it is case-INSENSITIVE, matching `cells.ts`'s own `assertColor`.** Round 1 accepted anything it accepted, which meant `#FF0000` (and any other uppercase or mixed-case spelling) passed validation and was stored verbatim. Round 2 measured the consequence: both string encoders (`encode.ts`) coalesce adjacent same-colour runs by comparing the colour STRING for exact equality, so a design-token palette alternating `#3B82F6`/`#3b82f6` for the identical colour (uppercase hex is how Tailwind, Figma, and most style guides print it) produced one `<span>`/SGR run per CELL instead of one run for the whole span — 20 cells, one colour, alternating case measured 1 span → 20 spans, 55 bytes → 720 bytes of HTML. `assertCanvasColor` now additionally requires the STRICT canonical pattern (`/^#[0-9a-f]{6}$/`, no `i` flag) on top of `isQuantizableColor`, so uppercase, `#rgb`, `rgb(...)`, and incidental leading/trailing whitespace all throw `TypeError` here rather than silently defeating run coalescing three modules downstream.

`fillRect` additionally requires INTEGER cell coordinates, throwing a `RangeError` otherwise. A fractional bound (`fillRect(0.5, 0, 2.5, 1, …)`) used to clamp without rounding, producing a fractional index that silently painted NOTHING (a fractional array index is never read back by any integer loop) while leaving non-integer string keys sitting on the shared `CellGrid`/`bg`/`sub` buffers — the worst available failure mode for a bug a layout computing rects from continuous scales (exactly what Phase 1 does) would trigger constantly. Throwing immediately is louder but never silently corrupts shared state.

**`text()` and `arrowhead()` share that same check (round 3) — every painter that addresses ONE cell does.** Both took their `x`/`y` as a plain in-range check (`x < 0 || x >= cols`, …), which a fractional value passes; `y * cols + x` then either resolves to a DIFFERENT valid cell whenever `y_frac × cols` happens to be an integer, or adds a stray non-integer key to the shared buffers otherwise — a fractional `y` on `text()` silently displaced the label by `y_frac × cols` COLUMNS, sized by the canvas's own width, and could wrap it onto a different row entirely. `line()` is the deliberate exception: its endpoints are a documented sub-cell quantity (the previous paragraph's walk), and rejecting a fractional one would reject the feature rather than a bug.

**`fillRect`'s round-1 coordinate validation covered `x0`/`y0`/`x1`/`y1` but not `fill.shade` — the SAME class of continuous-scale input, left unguarded.** `resolveFillShade` clamped an out-of-range shade with `Math.min(1, Math.max(0, fill.shade))`, and `Math.min`/`Math.max` both propagate `NaN` rather than clamping it — `Math.round(NaN * (ramp.length - 1))` is `NaN`, and `ramp[NaN]` is `undefined`, written straight into `grid.char` with a non-null assertion hiding the gap. A `NaN` shade is not a contrived input: `v / max` on an all-zero series, or `(v - min) / (max - min)` on a constant series, both produce it, and either is a first-day charts input (a flat heatmap row, a constant-valued series). The corrupted cell shortened the encoded TEXT row by one character (misaligning every column after it) while the HTML/ANSI exits printed the literal string `"undefined"` — and handing the resulting `CellGrid` to glyphcss's own `encodeCellGrid` throws, because the canvas had produced a grid violating the very "one printable glyph per cell" contract it deliberately reuses (see "Why this is a new module" above). `resolveFillShade` now throws a `RangeError` naming the painter for anything that isn't a finite number in `[0, 1]`, exactly mirroring the coordinate check's "throw immediately, never silently corrupt shared state" rule.

**Round 2 also found `encode.ts`'s `?? 0` fallbacks around `packHexColor` were dead code standing in for a proof, not a guard.** `packHexColor` returns `undefined` only for a non-canonical string, and by the time a colour reaches `encode.ts` it has already passed through `assertCanvasColor` — a `?? 0` there is defensive code for a case that cannot occur, exactly what `AGENTS.md`'s "no defensive code for cases that can't happen" rule flags, and a real bug reaching this module some other way would have silently rendered as black instead of surfacing. The three call sites now go through one `packValidatedHexColor` helper that asserts non-null (`packHexColor(hex)!`) with a comment stating why the assertion is safe, rather than three separate silent fallbacks.

## Why `NO_COLOR`/`FORCE_COLOR` key on non-empty presence, not "is set at all"

Both <https://no-color.org/> and <https://force-color.org/> key on the variable's PRESENCE with a NON-EMPTY value — `NO_COLOR=""` and `FORCE_COLOR=""` do not count as set, but ANY non-empty value (including `"0"`) does. The reviewed version used `env.NO_COLOR !== undefined` (empty string counted as "set," disabling colour when the spec says it shouldn't) and gave `FORCE_COLOR` a special case exempting `"0"` from counting as "set" (again the opposite of what "any non-empty value counts, regardless of contents" means at this phase-0 layer — there is no numeric colour-depth parsing here, only "is colour forced/suppressed at all"). Both are fixed by one predicate (`value !== undefined && value !== ""`) applied identically to both variables; `FORCE_COLOR` still wins over `NO_COLOR` when both are non-empty, matching both specs' documented precedence.

## Why `text()` folds instead of throwing or silently dropping

Reusing `isSingleCellGlyph` (rather than inventing a second, canvas-specific single-cell test) means "will this glyph corrupt the character grid's column alignment" is answered by exactly the same function the rest of glyphcss already trusts for that question — a combining-mark sequence, a wide CJK character, or an astral emoji is exactly as disruptive to a chart's column alignment as it would be to a rasterized scene's. Throwing on the first unsupported glyph would make a chart's title unrenderable because ONE character in a user-supplied label happens to be outside the safe set; silently dropping it would shift every subsequent character in the line left by one column, corrupting the whole label instead of one glyph in it. Folding (NFD-normalize, strip combining marks — recovers a base letter from an already-decomposed grapheme like `"e" + COMBINING ACUTE ACCENT`, which is two UTF-16 units and fails `isSingleCellGlyph` on length alone even though the letter itself is perfectly renderable) or substituting (a small table for punctuation NFD can't fix — mainly FULLWIDTH forms, which are genuinely double-width and have no decomposition to fall back to) keeps the column budget intact and the label legible, at the cost of one character's exact identity. `?` is the last resort for what's left (a wide CJK character, most emoji), and `canvas.report.unsupportedGlyphs` records every occurrence so a caller — or a later phase's label-abbreviation policy — can decide whether that's acceptable for a given label rather than discovering it by eye. Every actual fold or substitution (as opposed to the terminal `?` case) is now ALSO recorded, in `canvas.report.foldedGlyphs` (`{ from, to, col, row }`), so a caller can audit exactly which characters were silently changed, not only which were lost outright.

**Input is split by GRAPHEME CLUSTER (`Intl.Segmenter`, code-point fallback), not by UTF-16 code point.** The reviewed version split with `Array.from(text)` — which iterates by CODE POINT, not by user-perceived character — so a decomposed grapheme like `"e" + COMBINING ACUTE ACCENT` was ALREADY separated into two independent code points before `resolveTextGlyph` ever saw either one. The base `"e"` on its own is already a valid single-cell glyph, so the NFD-fold branch NEVER RAN for this input: it was dead code, provably so (a brute-force search over the whole BMP found zero code points for which the raw form fails `isSingleCellGlyph` and the NFD-stripped form succeeds — the two failure conditions coincide exactly). Both reviews demonstrated this independently: deleting the fold branch entirely left all of that test file's assertions passing, and the actual rendered behaviour for `"éx"` (decomposed) was `"e?x"` — THREE cells, with the accent reported as a stray unsupported glyph, worse than either of the two failure modes this section's opening paragraph explicitly designed against (it shifted the label RIGHT by a column, and reported a combining mark as unsupported when it was, in fact, perfectly foldable as part of its own grapheme). Segmenting by grapheme cluster first means the decomposed pair is treated as ONE two-code-unit unit, which fails `isSingleCellGlyph` on length alone (correctly, since it cannot be laid out as a single cell as multiple code points) and THEN reaches the NFD-fold branch, which strips the combining mark and returns the single base letter — now genuinely exercised, and correct: `"éx"` (decomposed) occupies exactly two cells and renders `"ex"`, with one `foldedGlyphs` entry. `Intl.Segmenter` is available in every runtime this module targets (evergreen browsers, Node ≥ 16); the code-point fallback is exactly `Array.from`'s previous behaviour for a runtime that somehow lacks it, so nothing regresses where the API is unavailable — it simply loses the specific grapheme-cluster fix this section describes, same as before.

## `text({ scale })`: `@glyphcss/charts`' `textScale` web affordance

`scale?: number` (default `1`, integer `>= 1`, byte-identical when `1`) exists so `@glyphcss/charts`' Density control (`docs/design/charts.md`'s "Round 16") can keep chart TEXT off the same shrink a denser render grid puts on everything else, in ONE render — never a second grid or a second `<pre>`. Two new canvas-owned buffers, `textScale`/`textFiller` (parallel to `bg`/`sub` — see this file's own "Why `bg` and `sub` are canvas-owned" above), both all-zero and therefore inert unless a caller ever passes `scale > 1`.

**Layout is per-glyph, not per-call.** At `scale === 1` the original code path runs byte for byte (verified directly — `text.test.ts`'s own byte-identity case compares a `scale: 1` call against no `scale` option at all, cell for cell, including the two new buffers staying all-zero). At `scale > 1`, glyph `i` of a line lands at column `x0 + i*scale` (not `x0 + i`) and row `y0 + r*scale` for line `r` (not `y0 + r`) — the run's OWN pitch, generalizing the align formulas (`left`/`right`/`center`) by replacing every `width` term with `width * scale` (the run's actual box-width in cells), which is exactly `width` itself at `scale === 1`. Only the glyph's own ORIGIN cell (top-left of its `scale x scale` box) receives the real character and colour; the remaining `scale*scale - 1` cells are marked `1` in `textFiller` and explicitly reset to `" "`/`null` — clearing whatever an earlier mark painted there, since `@glyphcss/charts`' fixed pipeline order (fills → axes → marks → labels) means labels paint LAST and a filler cell must never show through in the plain-text/ANSI exits, which read `grid.char`/`grid.color` as-is and know nothing about `textFiller`.

**Every other painter refuses a `textFiller` cell**, mirroring the existing `occluded` refusal exactly (`isOccludedCell(grid, idx) || isTextFillerCell(textFiller, idx)` at every write site — `fillRect`, the whole-cell `line()` path, the sub-cell dot plotter via a threaded `textFiller` parameter, and `arrowhead`) — so a mark painted AFTER a scaled label (an unusual pipeline order, but not one the canvas itself should assume never happens) can't reach into its reserved box either. `text()` writing INTO another glyph's filler cell is refused the same way, at the per-glyph level: a glyph whose own origin cell is occluded or already-filler is skipped entirely (no partial box, no orphaned filler cells with no origin).

**The HTML encoder is the one exit that reads `textScale`.** `encodeGlyphCanvasHtml` skips a `textFiller` cell outright — no span, no blank character — so the ORIGIN glyph's own font-size-scaled advance width (a monospace font's glyph width is linear in font-size) is what fills that horizontal space; emitting a literal blank character there would double it. An origin cell (`textScale[idx] > 0`) becomes its own standalone `<span class="glyph-text" style="font-size:<s>em;line-height:calc(1 / <s>)">`, flushing whatever plain run was accumulating before it and resuming after — never nested inside the plain-run span, so its own `color`/`background-color` fold into the SAME style attribute rather than a parent/child pair. The `line-height` term is load-bearing, not decorative: an inline element's `line-height` sets the height of the WHOLE line box it sits in, and CSS's unitless-inheritance rule recomputes an inherited `line-height: 1` against THIS element's own (now `s`-times-bigger) font-size — so a naive span with no explicit `line-height` would grow its own row to `s` rows tall, pushing every later `\n`-separated row in the `<pre>` down by `s - 1` EXTRA rows on top of the `s - 1` already-blank filler rows the layout reserved below it, double-reserving vertical space. `calc(1 / s)` cancels this exactly (`(1/s) * (s * P) === P`), pinning the origin's own line to one normal row while the bigger GLYPH still paints `s` rows of ink, overflowing past its own (unchanged) line box — downward, via the consuming page's own `vertical-align: top` rule on `.glyph-text` (`charts-workbench.css`), into the space the already-blank filler rows reserve.

**`encodeGlyphCanvasText`/`encodeGlyphCanvasAnsi` read neither new buffer.** A filler cell holds a real `" "` (written by `text()` itself, not inferred by the encoder), so both plain exits see it as an ordinary blank — the origin glyph plus real single-cell gaps between letters (`"H e l l o"` at `scale: 2`, never `"Hello"` and never corrupted), matching the doc's own "a web-only affordance never reaches a CLI/terminal exit" rule with no special-case code in either encoder.

**Batch-4 review (codex P1-2): "skip every filler cell" is only correct on the ORIGIN'S OWN ROW.** `encodeGlyphCanvasHtml` used to skip EVERY `textFiller` cell unconditionally — but a filler cell on a row BELOW the origin (`dy > 0` of the `scale x scale` box) is not covered by the origin's own span at all: that span's bigger glyph merely overflows DOWNWARD in ink past its own line box (the `line-height: calc(1/s)` mechanism above), it never widens a LATER `\n`-separated row's own text. Skipping those cells too silently dropped them from that row's HTML string entirely (no span, no blank), shifting every later character on that row left by the filler width — a `"|"` character placed at column 8 on the row below a `scale: 2` origin rendered at column 6. The fix adds a second canvas-owned buffer, `textFillerBelowOrigin` (`1` only for `dy > 0` fillers, `0` everywhere else including same-row fillers), so `encodeGlyphCanvasHtml` can tell the two cases apart: same-row fillers are still skipped (the origin's own advance covers them); below-row fillers fall through to the ordinary per-cell path instead, emitting the real blank `text()` already wrote there — keeping that row's own column count exact.

**Batch-4 review (fable P3-1): the filler-WRITING loop itself had none of the guards every other write site does.** `text()`'s own filler loop (which marks the `scale*scale - 1` non-origin cells of a scaled glyph's box) blanked those cells UNCONDITIONALLY — no `isOccludedCell` check (every OTHER painter refuses an occluded cell; this one overwrote it) and no check for whether the target cell was ALREADY an ORIGIN of a different, earlier `text({ scale })` call. Two overlapping scaled runs (not reachable from `@glyphcss/charts`' own fixed pipeline today, where label runs never overlap by layout, but a contract hole in the canvas primitive itself) could therefore have a LATER run's filler cell silently ERASE an EARLIER run's own real glyph: `text(1,0,["A"],{scale:2})` then `text(0,0,["B"],{scale:2})` left `"B "` with `A` gone and no report entry, since cell `(1,0)` — run 1's own origin — sat inside run 2's filler box. The fix adds the same guard every other write site already has: `isOccludedCell(grid, fidx) || textScale[fidx] > 0 || isTextFillerCell(textFiller, fidx)` refuses the filler write, so an occluded cell, an existing origin, or an already-reserved filler cell from an earlier run all survive a later run's own filler pass untouched (at the cost of a partially-reserved box on the LATER run when it genuinely overlaps existing content — the only sane outcome, since a box can't be fully reserved without destroying what's already there).
