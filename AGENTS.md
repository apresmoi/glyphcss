## What this repo is

`glyphcss` is an ASCII polygon-mesh renderer for the DOM. It projects 3D meshes to 2D and rasterises them as monospace text inside a single `<pre>` element. No WebGL, no canvas-per-frame, no per-polygon DOM nodes.

Originally forked from polycss (a CSS-based polygon paint engine). The mesh math, OBJ/glTF/GLB parsers, scene composition tree, camera math, and input controls carried over intact. The paint backend is entirely new: the rasteriser walks all polygons, fills a `cols × rows` character grid, and writes one text string to `<pre>.textContent`.

Monorepo layout (pnpm workspaces):

| Package | npm name | Role |
|---|---|---|
| `packages/core` | `@glyphcss/core` | Pure math: Vec3, Polygon, scene, camera, mesh ops, parsers. Zero browser globals. (`project()`/`math/projection.ts` was removed with no BC shim — use each camera's own `.project()`.) |
| `packages/glyphcss` | `glyphcss` | Vanilla renderer + custom elements (`<glyph-scene>`, etc.). Owns the ASCII rasteriser, custom element definitions, and imperative API. |
| `packages/react` | `@glyphcss/react` | React components + hooks. Thin wrapper over core + glyphcss. |
| `packages/vue` | `@glyphcss/vue` | Vue 3 mirror of the React package. |
| `packages/compile` | `@glyphcss/compile` | Build-time static compiler: 3D mesh → static `<pre>` ASCII. Vite plugin, CLI, Node API. Node-only (fs); reuses `compileScene` (pure) from glyphcss. |
| `packages/effects` | `@glyphcss/effects` | Framework-agnostic spatial effect definitions and stock surface/scene effects. Depends on glyphcss's generic effect protocol; never owns the renderer or animation clock. |
| `packages/maps` | `@glyphcss/maps` | Geographic data → glyphcss. Raster `source → sample → classify → compile` pipeline, projections, relief meshes, TopoJSON/PMTiles/MVT providers, and `createGlyphMap` (the interactive widget with the full layer vocabulary). Root entry is pure/browser-safe; `@glyphcss/maps/node` carries fs-backed readers (never `gdal-async`). |
| `packages/fonts` | `@glyphcss/fonts` | Font/text → extruded polygon meshes. Emits Z-up meshes (world Z = letter height, Y = letter width, X = extrusion depth). | `website` | `@glyphcss/website` | Astro + Starlight docs site. Not published. |

Public API is **mirrored** across React and Vue. Adding a hook on one side without the matching composable on the other is not acceptable (see "Cross-package discipline").

### Three-like parity surface

The native API keeps glyphcss/voxcss conventions. For Three.js ports, explicit `*/three` subpaths exist:

- `@glyphcss/core/three` — pure Three-like math wrappers and transforms.
- `glyphcss/three` — the core Three-like surface plus `compileScene` and geometry helpers.
- `@glyphcss/react/three` and `@glyphcss/vue/three` — mirrored `GlyphThreePerspectiveCamera`, `GlyphThreeOrthographicCamera`, `GlyphThreeMesh`.

These subpaths use Three-compatible names and units (`Vector3`, `Euler`, `Object3D`, `PerspectiveCamera`, `OrthographicCamera`, `DirectionalLight`, `AmbientLight`; radians; Y-up; Three frustum semantics). They are adapters, not a Three.js dependency. Geometry converts to native coordinates via `transformPolygonsToGlyph` with the Y-up → Z-up axis map `[x, -z, y]` so winding and Lambert lighting stay right-handed. `DirectionalLight.toGlyphDirectionalLight()` converts Three's `target → position` vector into the native source-vector convention.

## Rendering model

**One render pass → one `<pre>.textContent` assignment.** On every camera or scene change the rasteriser walks all mounted meshes in scene order, projects vertices through the camera, fills a `cols × rows` grid (per-cell depth test, glyph picked by render mode), joins the cells into one string, and writes it exactly once. No per-polygon DOM, no CSS `matrix3d`.

**Post-rasterize cell hook.** A scene's optional `transformCells(grid, layer?)` runs after rasterization and depth testing but before stringification. It receives a `CellGrid` (in solid mode with requirement-gated `shade`/`worldPosition`/`normal`/`surfaceUv` buffers; `NaN` = unavailable) and a `GlyphTransformCellsLayer` (`{ detail, mesh?, density?, viewport?, cellToSceneGrid }`) identifying which output grid it was handed; the hook must tolerate `undefined` for the second argument (a direct `rasterizeContext` caller supplies none — a SCENE render always does, on the retained-effect path exactly as on the direct one, and a mounted effect layer never changes what the hook is told). Still one write per `<pre>`. A grid rendered under cross-layer occlusion also carries `occluded` (`1` where a DIFFERENT output layer owns the cell) — a hook that PAINTS needs it, because `char`/`depth` cannot tell a blanked cell from open sky and a grid's depth holds only its own pass's geometry. Allocated only when a shared id-map and a hook both exist.

**Per-cell textures.** A polygon carrying `uvs` + `texture` (and a sampler for that key) is sampled PER CELL in solid mode: the texel multiplies the cell colour AND folds its luminance into the `intensity` that picks the glyph, so a texture reads as character variety and survives `useColors: false`. `Polygon.textureWrap` is honoured per cell (`repeat` / `mirrored-repeat` / default `clamp-to-edge`), so a face's UVs can carry a real TILE COUNT and one small image tiles across it — `@glyphcss/maps`' building facades are the consumer, and it is the difference between 1 image and 101. A triangle CLIPPED against the near plane rebuilds its sampler context from the clipped UVs, so a textured surface the eye straddles (the road you are standing on) keeps its texture instead of falling back to flat colour. `scene.setTextureSamplers(map | null)` supplies decoded pixels directly, keyed like a `texture` URL and merged over anything the scene decoded itself — the path for a PROCEDURAL texture, with no fetch, no canvas, and therefore no browser requirement.

**Authored shading normal.** `Polygon.shadingNormal` (optional, unit) replaces the geometric normal a face's own vertices imply, in solid mode only — visibility is still the projected-winding back-face verdict, depth, the shadow map and the occlusion id-map read geometry, and a zero-length or non-finite value falls back to the geometry. It reaches the Lambert term AND the retained `CellGrid.normal` (so the `normal` effect input and the control tensor's normal channels), because that channel means "this cell's surface normal" and for such a face the authored vector is it; `CellGrid.objectNormal` stays geometric. A mesh transform MOVES it — rotated, inverse-transposed through a non-uniform scale, renormalized, never translated (`*/three` additionally applies the Y-up → Z-up axis map). It exists for a face whose PLANE is not the surface it stands for: triangulating a curved region in a flat parameter space emits near-collinear slivers whose plane is a great circle's, so their geometric normal is up to 90 degrees off and shading by it lights a real piece of surface as if lit from inside — the only alternative being to drop the face and leave a hole. `@glyphcss/maps`' vector `fill` on a globe is the reference consumer.

**Semantic output.** `scene.getGlyphSemanticCellFrame()` is an immutable base-grid snapshot of the depth-winning polygon → surface → instance → class lineage, derived from the rasterized winner buffer (never a second projection); `null` in visible mode; detail-layer cells excluded. The model-control tensor is a 17-channel NCHW keyframe (23 in temporal form); missing UVs are `NaN` in raw frames and zero + `surface-uv-valid = 0` in tensors.

**Retained Glyph Effects.** `scene.addEffectLayer(definition, options)` mounts ordered scene-root appearance programs with no extra DOM. The first geometry render retains an immutable `CellGrid` per output; changing `params`/opacity/blend/order/enabled recomposes from those grids without re-projecting. `params` has stable identity and schedules a coalesced transaction. Effects run before `transformCells`, and `CellGrid.occluded` rides ACROSS them (cloned into the retained snapshot, carried by reference onto the composed grid) — the hook's ownership answer must not depend on whether a scene happens to have an effect mounted. With no effect and no hook, the direct renderer is byte-identical and allocates nothing extra. Compositor supports `over`/`replace`, `"surfaces"`/`"viewport"`/mesh-handle(s) targets, and the requested inputs `baseColor`, `baseShade`, `depth`, `normal`, `worldPosition`, `objectPosition`, `objectExit`, `uv0`. Hard requirements are solid-mode-only; `optionalRequirements` and `dynamicRequirements(params)` degrade in wireframe/voxel. Scene-image sampling, scratch buffers, and static export of a mounted effect reject explicitly.

**Per-object targeting.** A `GlyphMeshHandle` or array target normalizes at mount to an immutable id set (`setOptions` with a different set throws — remove and re-add). Mechanism is per-cell `targetCoverage` from `CellGrid.winnerMesh` (solid-only; elsewhere the layer is inactive, never a throw). Later scene-wide layers composite over targeted ones by design. React/Vue diff array targets by id set.

**`program` / `colorProgram`.** Opaque definition-owned payloads on `GlyphEffectDefinitionLayerOptions`, forwarded unchanged, validated once at mount via the definition's `validateProgram`/`validateColorProgram`, immutable after mount (imperative `setOptions` throws; wrappers forward at creation only). glyphcss never interprets them — `@glyphcss/effects` depends on `glyphcss`, never the reverse.

**Stock effects (`@glyphcss/effects`).** Matrix rain, flow text, scan, wipe, scramble, glitch, noise dissolve, ripple, field synth; `GlyphRamps`. Package owns no clock — apps drive `time`. Field-synth is the large one: up to `SYNTH_VOICES = 9` voices (`fieldN`/`waveN`/`freqN`/`ampN`/`angleN`/`originU/V/WN`/`dutyN`/`phaseN`/`iterN`), three voice layers, `combine` incl. categorical `argmax`, `space: "auto" | "surface" | "scene" | "object"`, `subcellRes: "1x1" | "2x4" | "ink"`, `render: "paint" | "carve" | "xray"`, SDF voices (`gyroid`/`menger`/`sierpinski`, `step` wave), sphere tracing for qualifying SDF programs, and a public field-program IR (`buildGlyphFieldProgram`, `validateGlyphFieldProgram`, `evaluateGlyphFieldProgram`, `marchGlyphField`, `integrateGlyphField`, `glyphFieldStepCount`). Every `validateParams` throw carries a rule id from `GLYPH_FIELD_SYNTH_VALIDATION_RULES`. Schema key families are append-only (the `/synth` URL codec decodes positionally). The `/synth` website page is the front-end. Full semantics: `docs/design/effects.md`.

### Per-mesh detail layers

By default every mesh renders into the shared base `<pre>`. A mesh pops into **its own silhouette-fitted, CSS-translated `<pre>`** when it declares any of: `density` (multiplier, isotropic) or `fontSize`/`lineHeight`; `transparent: true` (x-ray: neither occludes nor is occluded); a `mode` that genuinely differs from the scene's; `glyphPalette` (solid ramp only); `ambientIntensity`. Browser-only; works with every camera; detail grids clamp to the viewport. This is a per-mesh property on the flat mesh list, not a group concept. Each distinct mode is a full extra rasterizer pass — reach for it per layer, not per mesh.

- **`detailGroup`** — detail meshes naming the same string share ONE `<pre>`/pass/occlusion id (removes the inter-mesh seam at shared edges). Never separates a mesh by itself. Members must agree on every layer-level option or a `RangeError` names the group and field. `@glyphcss/maps` groups raster tiles per tier.
- **Cross-layer occlusion** — opaque meshes occlude across `<pre>`s via a shared id-map built at the scene's supersample resolution (`computeOcclusionIds`); detail layers render at `supersample: 1` and sample it. A SAME-POINT ownership refinement closes the ownership-vs-coverage seam and is skipped when any group sets `occlusionPriority`/`occlusionContourPx`: the map retains, per cell, the owner's depth AND the winning triangle's own screen-space depth SLOPE, and a pass walks that plane from where the map sampled it to where its own cell actually sits before comparing against that cell's own depth. **Comparing two surfaces at the SAME point is what makes a mesh's `density` unable to change who occludes whom** — inside one triangle the walk is exact, so two halves of one continuous surface agree to the last bits (only `OCCLUSION_COINCIDENT_REL`, a float-noise tolerance, separates them) while a layer genuinely behind another is still blanked everywhere, including the ring of its own silhouette where it covers output cells but no map sample point. Two superseded forms both compared DIFFERENT points and had to choose between forgiving the difference or opening a seam on it: an allowance of the map's local depth GRADIENT (under a pitch that is the VIEW's depth ramp, not the surface's roughness, and it swallowed `@glyphcss/maps`' draped `fill`, then 10 m above the terrain — 32 of the terrain's cells at density 1.4 and 0 at 1.8, against 81 per base cell in one grid), and a strict comparison against the output cell covering the map's sample point, which is only the same point when the detail lattice contains the map's integers — a silhouette-fitted fractional origin never does, and it lost 28 cells at density 2 and 135 at density 3 along an 18-cell shared edge whose depth varied ALONG it (0 when it did not, which is why a coplanar gate could not see it). The residue it accepts is a FOLD: where the owner's surface bends within half a map cell of the boundary, the walk stays on the triangle that won the cell. Gates: `rasterize.occlusionSeam.test.ts` (flat AND sloped, both slope axes, densities 1.4/2/3), `createGlyphScene.foreignOcclusion.test.ts` (keep-when-uncovered reddens it), `@glyphcss/maps`' `widget.fillDrapeDensity.test.ts`. Textured polygons claim only opaque texels (alpha-aware). Self-disables at zero cost when no opaque detail mesh exists. **The id-map raster speaks the paint rasterizer's own conventions and none of its own**: it samples coverage at `scanFillTriangle`'s integer `(col, row)` with `scanFillTriangle`'s own exact-sign inside test (a cell centre is half a cell off, i.e. a whole cell of disagreement along every bottom/right silhouette edge; a normalized `-1e-6` tolerance is a hair off, measured as a whole 24-cell column claimed by a layer painting none of it); it BACK-FACE CULLS on the same `area2 > 0` verdict when the scene is single-sided (without it a back-facing quad claimed 75 cells and painted 0, blanking whatever stood behind it); it retains `project()[3] ?? [2]`, the quantity `CellGrid.depth` holds; it NEAR-PLANE CLIPS through `camera.eyeDepth`, or a polygon with any vertex behind the eye projects to `NaN` and drops out of the map entirely — which under a street-level camera, standing inside its own scene, is most of the frame; and it honours `Polygon.hidden`, the CONSUMER's own cull, which is the one of these that is a BLANKING defect rather than a coverage one — a hidden polygon paints nothing, so a cell it claims is a cell where its own layer shows sky and every other layer is punched out (measured: a base quad claimed all 64 cells of an 8x8 map with `hidden: true`, and the detail quad behind it lost 140 of its 238 painted cells to a hole nothing then filled). It also takes the SAME pre-projection cull runs the solid paint loop takes, per group (`cullChunks` on each id-map group; `createGlyphScene` supplies the base grid's merged list and one per opaque detail group, memoized the same way) — byte-identical, since a run whose box projects off THIS raster's grid claims no cell of it and a run whose every normal is back-facing is one `fillDepthTri` rejects triangle by triangle, and the back-face half is gated on `!doubleSided` exactly as `fillDepthTri`'s own verdict is. `occlusionContourPx` needs no exemption: its margin grows from the fine map's OWN indices, so a run with no claim inside the grid seeds none.
- **Claim shaping** (solid, opaque meshes only): `occlusionPriority` (class beats depth), `occlusionClaim: "alpha" | "geometry"`, `occlusionContourPx` (coverage-aware claim with a screen-px margin, expensive — fine raster for every group whenever any group sets it).
- **Cross-scene occlusion** — producer `getOpaqueCoverage()` → consumer `setForeignOcclusion(coverage | null)`; solid-mode only; a plain-mesh producer needs `trackOpaqueCoverage: true`.
- **Meshless viewport overlays** — `scene.setViewportOverlayDensities([...])` adds transparent full-viewport output grids at `density×` resolution, painted only by `transformCells` (`layer.viewport === true`), each carrying its own geometry depth pass in the Z-BUFFER depth every paint path fills `CellGrid.depth` with (`buildSurfaceDepth`'s `zBufferDepth`), never the linear `cssZ` the wireframe HLR prepass compares against — identical under an orthographic camera, incompatible units under a positioned perspective one. `@glyphcss/maps` stroke layers with `density !== 1` are the consumer.

All of these mirror on React/Vue `<GlyphMesh>`/`<GlyphScene>` and the custom elements (kebab-case attributes); scene-handle methods need no wrapper. **Static compile takes a flat polygon list and cannot represent detail layers.** Details and measurements: `docs/design/detail-layers.md`.

### Render modes

| Mode | How cells are filled |
|---|---|
| `wireframe` | Polygon edges rasterised as ASCII rules; glyph weight scales with edge prominence |
| `solid` | Filled cells; glyph picked from a `CharRamp` by Lambert-shaded intensity |
| `voxel` | Cube-aligned geometry; face normals drive glyph selection |
| `ink` | Silhouette + crease outline only; oriented glyph (`_ / \| \ - ‾ ▏ ▕`) traces the smoothed contour tangent |

All four are runtime modes. Scene options layered on top, each a documented no-op outside its listed modes:

- **`glyphPalette`** — named solid ramps; `"dense"` is printable-ASCII-only by design for sub-2px cells and ASCII-only outputs. Do not add Unicode to it.
- **`charMode: "ascii" | "braille" | "halfblock" | "quadrant"`** — braille is wireframe-only (2×4 dot mask); halfblock/quadrant are solid-only two-colour-per-cell encoders (`encodeGlyphBuffersDual`), no-ops with `transformCells`, `temporalBlend`, or `solidWeightRamp`. Reachable from `compileScene`/`GlyphSceneStatic`.
- **`wireframeJunctions`** — ascii-wireframe-only box-drawing resolve pass for joints. Runtime-only.
- **`solidWeightRamp`** — `(glyph, weight)` steps from `calibrateWeightedGlyphRamp`, replaces the solid ramp and adds `font-weight` to spans (bold never changes monospace advance). Reachable from `compileScene`.
- **`hiddenLines: "show" | "hide"`** — wireframe uses a slope-scaled depth bias against a surface prepass (bias 0.03, slope 0.5, internal); `ink` uses an identity-based test (`buildInkOcclusionMap`, own-neighbourhood exemption) — never a flat bias, which fails across world scales. No-op in solid. Reachable from `compileScene`.
- **`colorTolerance`** (0–765 redmean) — merges same-glyph runs within a colour distance; one `colorRunExtends` backs all four coalescers. Composes with TAA; no-op under semantic output. Forwarded by `compileScene`; not by the export builders.
- **`colorEncoding: "spans" | "atlas"` + `atlasPalette` + `fontAtlas`** — atlas encodes `(glyph, palette slot)` as PUA code points against a checked-in COLR/CPAL font (`GLYPH_FONT_ATLAS` 212 glyphs/30 slots, `GLYPH_FONT_ATLAS_ASCII` 94/68); zero spans. Library default is `"spans"`; the website defaults to `"atlas"` via `CSS.supports("font-palette", "--x")`. Palettes are median-cut quantized and causally pooled per scene with a transaction latch; a pooled palette also CONVERGES on a quiescent scene — the quantizer reports the repool its 250 ms clock gate refused (`repoolDeferredMs()`) and the scene arms ONE settling render for it, at most once per generation, so a scene whose colours stream in and then stops rendering is never left on its first frame's palette (`/maps` cold-loaded entirely green until the first wheel notch); readiness needs a real COLR paint probe AND `font-palette` support; the per-`<pre>` `font-family` pin follows the encoding a frame actually produced; out-of-atlas glyphs latch the scene to spans until a relevant `setOptions`. `fontAtlas` is fixed at creation. Compiled output must include the CSS itself (`loadGlyphAtlasFontFaceCss`, `buildGlyphAtlasFontPaletteValuesCss`). Breaks find-in-page; accepted.

Rationale, constants, and measurements for every option: `docs/design/render-modes.md`.

### Shadows

Opt-in: set `shadow: GlyphShadowOptions` on the scene, then `castShadow`/`receiveShadow` per mesh (both default false; `GlyphGround` defaults `receiveShadow`). Shadow-map technique, so self-shadowing is free. **A `hidden` polygon casts nothing** — it is excluded from the depth raster AND from the light-space volume the 256 texels are divided across, on the same rule the solid rasterizer already applies before any projection or shading. Excluding it from only one of the two is a distinct bug: a caster left in the fitted box makes every texel coarser and degrades the shadows that are on screen. `@glyphcss/maps`' per-frame wall cull is expressed exactly this way.

| Option | Type | Default | Description |
|---|---|---|---|
| `shadow.color` | `string` | `"#000000"` | Shadow tint hex color |
| `shadow.opacity` | `number` | `0.25` | Darkness 0..1 toward `color` |
| `shadow.lift` | `number` | `0.05` | EXTRA absolute-world-length depth bias, on top of the derived acne guard below. `0` is a valid and often correct answer |
| `shadow.maxExtend` | `number` | `2000` | **Declared but never read.** The light-space volume is fitted to the AABB of the caster vertices themselves (`buildShadowMap`), so this option has no effect on any render; the type and the `shadow-max-extend` attribute still accept it. Removing it is a public break and has not been taken. |

That volume's PAD is relative to the caster extent, not a fixed world length: 256 texels are divided across it, so an absolute term sets a smallest scene the shadow map can resolve at all.

**The caster set is the SCENE's, not the pass's.** A frame rasterizes the base grid plus one grid per detail layer, and the shadow map used to be built from whichever polygons the pass in hand held — so a mesh that separated for a reason with nothing to do with shadows (`density`, a private `mode`, `glyphPalette`, `ambientIntensity`, `transparent`) silently stopped casting, and one that separated stopped receiving. `castShadow` meshes are now collected once across every mesh in the scene (`GlyphShadowCasters`) and the built map is shared across the frame's passes through a `GlyphShadowMapCache` holder, so one light gives one light-space volume to all of them: a detail layer casts onto the base grid, the base grid casts into a detail layer, and two detail layers cast onto each other. A detail pass's `receiveShadow` is read PER MEMBER, not off the group's shared transform — it changes shading, not how the group rasterizes, so a `detailGroup` may legitimately hold a receiver beside a non-receiver. Both are supplied only when `scene.shadow` is set and something actually casts, so the shadows-off path is byte-identical and allocates nothing. Gate: `@glyphcss/maps`' `widget.shadowDensity.test.ts` (casting out of a detail layer and receiving into one are separate clauses, so neither can hide behind the other).

**A `transformCells` stamp cannot receive.** The shadow term is consumed inside `scanFillTriangle` when a cell's final colour is computed, and no per-cell occlusion fraction survives into `CellGrid` — the requirement-gated `shade` buffer is the LIGHT term, not the shadow one. Anything painted by the hook instead of by geometry (`@glyphcss/maps`' `line` and `contour` layers) therefore keeps its flat colour under a shadow that darkens the surface around it.

**The acne guard is derived, slope-scaled and internal** (`SHADOW_SLOPE_BIAS_TEXELS` = `1.25`, `rasterize.ts`). Self-shadow acne here is a POSITION quantization artefact, not a depth-precision one — the buffer is `Float64Array`; a receiver reads the map at `tu = lu | 0`, i.e. up to one full texel away in each light-space axis, so its own depth is compared against a copy of itself taken from up to `|dd/du| + |dd/dv|` away. One texel of each is the exact bound, so `1.0` is the smallest guard that provably closes it; measured, a lone self-receiving box goes from 450 of 450 lit roof cells claimed at `0` (`floor`, not `round`, makes the error systematic — it darkens almost uniformly rather than speckling) to 0 at `1.0`, and the first real shadow loss is at `1.5` (a 4 m building inside a 1.8 km caster AABB). `1.25` sits between the two bounds. `lift` stays the caller's own EXTRA absolute term; its `0.05` default is a room-scale assumption (`@glyphcss/maps` sets `0` because a map has no absolute length to offer, see its own section).

### Hotspots

3D anchors → positioned 2D hitboxes. The rasteriser projects `Hotspot.at` and returns a `HotspotCell` (col, row, depth, visible); the consumer positions its own `<div>`. The rasteriser never emits the DOM node. **`GlyphHotspotHandle.setAt(at)`** moves an anchor without touching the element — for a consumer that PLANTS its overlays on geometry arriving later (`@glyphcss/maps` anchors a map label at the ground under it, which moves when a finer terrain tier lands); remove-and-re-add is the alternative and it destroys the element, losing whatever the consumer wrote on it and restarting any CSS transition on it. Gate: `createGlyphScene.test.ts`.

The injected `.glyph-hotspot` rule defaults to `user-select: none` (`-webkit-user-select: none`), same as `.glyph-output` and for the same reason — the hotspot div sits `pointer-events: all` above the drag surface, so without this a drag on a hotspot's label selects its text instead of orbiting the camera. `.glyph-hotspot.glyph-selectable` re-enables `user-select: text`, mirroring `.glyph-output.glyph-selectable`. `pointer-events: all` is unchanged — hotspots must stay clickable; only selection was the defect.

### Cell canvas

`createGlyphCanvas({ cols, rows, cellAspect, tier })` (`packages/glyphcss/src/render/canvas/`) is a pure 2D authoring surface for `@glyphcss/charts`/`@glyphcss/diagrams` — storage and painters only, no layout/scales/routing. It owns a `CellGrid` (via `buildCellGrid`) plus two buffers the grid itself lacks: canvas-owned `bg` (both encoders read it UNCONDITIONALLY, independent of what glyph occupies the cell) and `sub`, a 2×4 sub-cell occupancy byte per cell for the `braille`/`blocks` tiers, filled in QUADRANT order so `shade: 0.5` lands on exactly `▀`/the braille cell's top four dots. Every colour a painter (`fillRect`/`line`/`text`/`arrowhead`) accepts is validated ONCE, at the point it is written, as CANONICAL lowercase `#rrggbb` — uppercase, `#rgb`, `rgb(...)`, and incidental whitespace all throw a `TypeError` naming the painter, since both string encoders coalesce runs by exact colour-string identity. `fillRect` additionally requires integer cell coordinates and a `fill.shade` that is a finite number in `[0, 1]` (`RangeError` naming the painter otherwise, in both cases); `shade: 0` is blank on every tier. `canvas.edge(edgeId, { from, to, priority? })` registers an edge's graph endpoints; `canvas.route(edgeId, cells)` records its ORDERED cell polyline (consecutive cells must be 4-adjacent, else `RangeError`) and throws if the edge was never registered — every N/E/S/W mask is DERIVED from the polyline's own neighbours, never supplied directly. `resolveJunctions()` resolves each cell by ROUTE COINCIDENCE, not by node-id equality: two edges at a cell JOIN only when they share a graph node `n` AND their walk from that cell back to `n` is the IDENTICAL cell sequence for both (a hub they both originate at, a shared trunk that later fans out, or several branches merging into one run) — sharing a node id with no such coincidence never joins, however many edges bridge the two on paper. Two groups whose masks are both plain straight transits on PERPENDICULAR axes is the routine, unlogged "wires cross in open space" case: the higher-priority group (an explicit `priority`, ties by registration order) keeps its own glyph, upgraded to the tier's dashed `hop` glyph on ITS OWN axis. Every other 2+-group shape is logged to `canvas.report.routeConflicts` (`{ edgeIds, col, row, kind }`; `kind` is `"parallel"` for two coincident same-axis transits, `"corner"` for a corner/stub in an otherwise two-group cell, `"multi"` for three or more mutually unrelated groups). `resolveJunctions()` is IDEMPOTENT — it truncates `report.routeConflicts` to empty before resolving, so calling it more than once against the same registered routes reproduces the identical report rather than duplicating every conflict onto it again (P2-1, `docs/design/canvas.md`'s "Junctions" Round 3). `GLYPH_CANVAS_TIERS` (`ascii`, `box`, `blocks`, `braille`) are parallel tables with identical keys — switching tiers is a data swap, never a code branch on the tier's name — including a `subcell` flag plus matching `subGlyph(mask)` function (what lets `fillRect` pick blocks'/braille's sub-cell-derived glyph without branching on the tier name itself), `diagonal` (the nine-glyph table a sloped `line()` run resolves through on `ascii`/`box`), and `ascii`'s/`box`'s own letter-free, blank-at-`shade:0` shading ramps. In `braille`/`blocks`, `line()` instead rasterises AT SUB-CELL (dot) resolution into the shared `sub` buffer via a plain Bresenham walk (never `walkGlyphCanvasLine`'s supercover, which over-fills a 2×4 cell for a shallow slope), so a diagonal reads as a smooth dotted stroke instead of one `/`/`\` glyph per cell — `ascii`/`box` are unaffected (`line()` never reads `sub` for them). `line()` takes an explicit `subcell?: boolean` option (default: the active tier's own `subcell` capability) so a caller can force the WHOLE-CELL path even on a subcell-capable tier — `@glyphcss/charts` passes `false` for axes/gridlines/tick marks and `rule` marks, so sub-cell data marks, whole-cell axes is the rule under `braille`/`blocks`: only `line`/`area`-edge/`dot` (the DATA marks) gain the finer resolution, never the axis frame around them. A `line()`'s dash/dot pattern advances per DISTINCT cell (or, in `braille`/`blocks`, per DISTINCT dot) the walk visits regardless of occlusion, so a hidden cell never renumbers the phase every later cell reads; `style: "double"` on a non-axis-aligned run has no diagonal analogue in this glyph set — it renders solid and records one `report.ledger` entry, a deliberate contract narrowing (kept, unchanged, for the sub-cell path too). `line()` also takes `width?: 1 | 2 | 3` (default `1`, byte-identical when absent) — `ascii`/`box` widen by GLYPH SUBSTITUTION on the identical walked cells (never visiting an extra cell): width 3 reuses the tier's own `double` glyph on a straight run, everything else (width 2 anywhere, width 3 on a diagonal) falls back to the tier's own full-ink `shadeRamp` glyph; `braille`/`blocks` widen in real sub-cell DOTS, offsetting the same Bresenham walk one dot perpendicular to the segment (two, one each side, at width 3) rather than re-walking at whole-cell resolution. `@glyphcss/charts`' line/area-boundary/rule marks are the consumer (their own `options.strokeWidth`, see "Charts"). `text()` never rasterises a rejected glyph: input is segmented by GRAPHEME CLUSTER (`Intl.Segmenter`, code-point fallback) so a combining-mark sequence folds as one unit instead of being split apart before `isSingleCellGlyph` ever sees it; a failure then folds (NFD + strip combining marks, then a small punctuation substitution table) or becomes `?`, with every fold recorded in `canvas.report.foldedGlyphs` (`{ from, to, col, row }`) and every `?` in `canvas.report.unsupportedGlyphs`. Three independent string exits: `encodeGlyphCanvasText` (raw, literal `< > &`), `encodeGlyphCanvasHtml` (escapes itself, emits `color`+`background-color` per run, spans only), `encodeGlyphCanvasAnsi` (fg+bg SGR, `colors: "16" | "256" | "truecolor"` bounding which escape family may appear, `NO_COLOR`/`FORCE_COLOR` read only from an explicit `env` option and keyed on NON-EMPTY presence per both specs — `"0"` counts, `""` doesn't). Every painter refuses a cell whose `occluded` byte is `1`, `bg`/`sub` included. Not imported by (and importing nothing private from) the existing render path — adding it changes no existing render byte. Full rationale, measurements and defect history: `docs/design/canvas.md`.

## Compilation (static & interactive)

`rasterize` is pure, so a scene renders at build time or on the server; the render *is text*.

- **`compileScene(opts)`** (`glyphcss`, pure) — polygons + camera + options → `<pre>` string, byte-identical to the runtime render for the same inputs. Foundation for every adapter.
- **`@glyphcss/compile`** — Node adapters: `loadMeshFromFile`, `compileFile`, Vite plugin (`?glyph`), CLI (`glyphcss`), `compileInteractive`. `writeGlyphControlMaps` defaults to the frozen `glyph-control-export/v1` contract; `appearanceRgb: "albedo-and-target"` opts into `v2`.
- **`GlyphSceneStatic`** (React + Vue) — SSR/SSG `<pre>`, no client runtime.
- **`buildGlyphFramesExport`** — turntable of `frameCount` full renders cycled by a pure-CSS `steps()` animation. Payload grows linearly with frames.
- **`buildGlyphInteractiveExport` / `glyphCodepenPrefill`** — self-contained CDN snippet; declared `interactions` drive both the wired control and the decimation budget; optional `effect: { id, params, blend?, timeScale? }` mounts a **stock** `@glyphcss/effects` layer from the CDN. The export path for a moving-camera or volumetric/carve/xray effect scene.
- **`buildGlyphFieldSynthStaticExport`** (`@glyphcss/effects`) — effect-only, static-camera field-synth scene → inlined-JS pen with zero runtime imports; verified byte-exact against the real renderer. Rejects `space: "object"`, carve/xray, `program`, and 3D-only voice params; `isGlyphFieldSynthStaticExportSupported(params)` is the matching predicate for UIs.

Mounted effects are otherwise runtime-only (no `compileScene`/frame-roll evaluation). Trade-offs and reject rules: `docs/design/compile.md`.

## Charts (`@glyphcss/charts`)

An Observable-Plot-flavoured chart spec rendered through the cell canvas (`packages/glyphcss/src/render/canvas/`), never through `compileScene`/`rasterize.ts` — a chart has no camera, no mesh, no depth test. Mark constructors (`glyphChartLine`, `glyphChartArea`, `glyphChartBar`, `glyphChartDot`, `glyphChartArc`, `glyphChartRect`, `glyphChartCell`, `glyphChartText`, `glyphChartRule`, `glyphChartSankey`, `glyphChartFunnel`) return plain `GlyphChartMark` values and all accept `options.name?: string` (a series/legend name — see "Series and shading"); `glyphChartPlot({ marks, scales?, axes?, title?, description?, legend? })` composes them into a `GlyphChartSpec`. `renderGlyphChart(input, options)` accepts a spec, a mark, an array of marks, or a bare `number[]` (sugar for `x = index, y = identity`, copying Observable Plot's own shorthand) — channel type inference copies Plot too: `Date → time`, `string → band`, `number → linear`. Stack/group key Dates by timestamp, retaining the original Date as output x. Transforms `bin`/`stack`/`group`/`normalize`/`window` are minimal, deliberately (PLAN.md Phase 1), not Plot's full vocabulary. The bare `renderGlyphChart(x)` call (no `options`) defaults to `target: "web"`.

**Pipeline, fixed order**: validate/materialize → transforms → one d3 scale per axis → budget-first layout → fills → axes → marks → labels → encode. `report.ledger` is `GlyphChartLedgerEntry[]` (`{ code, message, detail? }`) — a stable kebab `code` a caller matches on, ONE plain-English `message` written for the chart's reader (never a `layout:`/`arc:`-prefixed log line), and `detail` carrying the exact numbers; every producer goes through a constructor in `ledger.ts`. **The x-axis LINE ROW is the y=0 row whenever 0 is in the y domain** (an interior row for a mixed-sign domain, the plot's own bottom row for the ordinary all-nonnegative/zero-anchored case) **or the y-MINIMUM row when 0 isn't in the domain** — never a row separately reserved below the plot, which used to float every bar/area/line a full row off the line meant to anchor it (CHARTS-RESEARCH `DIAGNOSIS-charts-rendering.md` B1/B6a). A positive bar/area segment occupies the rows strictly above that row up to its value's row inclusive, a negative one the rows strictly below; a zero bar paints nothing; the y-axis's own vertical rule still spans the full plot height regardless of where the (possibly interior) x-axis line sits, and its corner glyph is a T-junction (`├`) rather than a corner (`└`) exactly when the line is interior. Zero bars/rects paint no cells. All-zero pies are empty with an `empty-total` ledger entry. Bar/rect/area inferred y-domains include zero; explicit numeric domains excluding zero reject with `bar-domain-excludes-zero`. Log/sqrt use `scaleLog`/`scaleSqrt`; zero-containing or sign-crossing log domains reject with `log-domain`. Calendar-valid JSON ISO time domains parse once into Dates (`bad-time-domain` on failure), and ticks use d3's multi-scale time format. Marks sharing an axis but disagreeing on inferred value type (numeric vs categorical vs date) reject with `mixed-x-scale` — a runtime-only tagged error, deliberately not a `GLYPH_CHART_VALIDATION_RULES` entry (the cross-mark, data-dependent check has no declarative JSON-Schema equivalent). Every mark's coordinate output is guarded before it reaches the canvas: a non-finite/non-integer value (an unresolved channel, a mismatched scale) throws `GLYPH_CHART_INTERNAL_COORD` naming the mark type, never the canvas's own untagged `RangeError`. Stacked bars/areas paint `y0`→`y1`, connecting area layers independently; UNSTACKED multi-series bars/rects dodge into equal, gapless sub-bands (Plot's `fx`-free grouping) instead of overwriting each other, degrading to the full band with a ledger entry when a series can't get even one cell. Band marks use the scale's own bounds, and a band's tick/label centre on the EXACT columns/rows the mark itself paints (re-derived from the same `bandColRange`/`bandPartitionRowRange` the painter calls, never an independently-rounded continuous fraction, which used to land a tick one column off at most widths). **`bandPartitionRowRange` never hands a band-y category the x-axis LINE row** — that row is always `plot.y1` for a band y-scale (a band never admits a zero fraction), so a category partition excludes it exactly like a bar's own fill stops one row short of the baseline; without this, a `cell` (heatmap) category whose whole chunk happened to be that one row had its ink unconditionally overwritten by `paintAxes` (which runs after `paintCell`), silently erasing the category. `line`/`area`/`dot`/`rect`/`bar`/`cell`/`arc`/`text` all clip to the plot rect, so an explicit domain narrower than the data never paints through the title, axis, or tick labels.

**Legend and title placement** (owner packet): `legend: boolean | { placement }` — `placement` is `"bottom"` (default, `true`), one of the four plot corners (`"top-left"`/`"top-right"`/`"bottom-left"`/`"bottom-right"`, painted INSIDE the plot rect, no chart row reserved, right-aligned swatch+name for the right corners; overlapping painted marks logs `legend-overlaps-marks` with the covered cell count), or `"title"` (shares the title's own row, after the title text; degrades to `"bottom"` with a `legend-placement-degraded` ledger entry when there's no title row or the entries don't fit beside it). `title: string | { text, align?, position? }` — a bare string is `{ align: "center", position: "top" }`, byte-identical to before either option existed; `position: "bottom"` reserves the chart's LAST row (claimed before the legend/axis rows, so it sits below them). Both spec fields and the matching `renderGlyphChart` options resolve through `resolveGlyphChartLegendOption`/`resolveGlyphChartTitle` (`layout.ts`); `options.legend`/an object title override `spec.legend`/`spec.title`. Invalid shapes reject with `bad-legend`/`bad-title`. The website Dock (`ChartsDock.tsx`) exposes target/charset/color/detail and both placements as icon-button toggle groups (`IconToggle`, shared with `/synth`) instead of `<select>` dropdowns, with the Output and Chart folders' own reset actions living on each folder's native lil-gui title bar (`InstrumentWorkbench/useFolderTitleReset`, shared with `/diagrams`'s own Output reset) rather than a separate button or header row.

**Series and shading**: `renderGlyphChart` accepts `legend` (default `true`); `false` omits the legend row without changing `meta.series`. categorical `fill` or `stroke` splits line/area/dot (also bar/rect) into independently painted series, shared by `meta.series` and the legend; a mark's own `options.name` contributes its own legend entry with its own swatch the same way — one named mark is enough (>= 1 named series shows the row, not > 1), so a single-mark chart like the shipped presets can carry a name ("Revenue") and still show a legend. Colour assigns per-series palette colours. A LINE/area-BOUNDARY series additionally cycles the canvas's solid/dashed/dotted/double styles when colour is off, so it stays distinguishable in `text`. **A REGION mark's fill (bar/rect/area/cell) instead carries series identity through its own GLYPH, `seriesShade(tier, styleIndex)` (`█ ▓ ▒ ░`/`# % + .`), painted through `canvas.text` — unconditionally, with colour on or off** (CHARTS-RESEARCH B2/B6d): a stacked/dodged chart's Copy ASCII must stay readable even when colour carries the picture on screen, so the fill glyph is never a flat `"solid"` `fillRect` call. Its legend swatch is that same shade glyph, never a line style — the arc/pie legend already worked this way and every region mark now matches it; a `cell` (heatmap) mark has no per-series cycle of its own (its shade is a continuous VALUE ramp, not a category), so its swatch is the ramp's own full-ink glyph. A `dot` mark's series identity stays a distinct whole-cell glyph (`● × + ◆`/`o x + *`) on `ascii`/`box`; under `braille`/`blocks` every point instead paints a full 2x2 SUB-CELL DOT CLUSTER (4 of the cell's 8 dots, positioned at the exact sub-cell coordinate) regardless of series or colour — a single dot measured ~1.9px and read as a stray fleck, not a plotted point (B6b); colour is the series-identity channel for dots at that resolution. Arc categories use `fill`, then `label`, then index (numeric arrays: element = value); positive categories sum into slices sharing one total, `meta.series`, and legend swatches. Shades cycle `█ ▓ ▒ ░` (box/blocks/braille) or `# % + .` (ASCII), also with colour on; the closing shade advances if it matches the first. Nonpositive slices have no swatch. Canvas double-diagonal fallback remains logged. `size`/`shape`/`curve` are removed from public types and reject rather than being ignored. Cell values use one shared monotone sequential ramp for same-sign values, or a diverging ramp around zero for mixed signs; never absolute magnitude — a same-sign value strictly between the domain's zero-anchored endpoint and its extreme always lands on the lowest INKED ramp level, never blank (blank is reserved for the domain minimum exactly), so a heatmap's smallest nonzero cell is never mistaken for a missing one. **A mixed-sign (diverging) `cell` domain also carries the sign in the GLYPH, not just the shade**: gains quantise through the ordinary solid-shade ramp (`" ░▒▓█"`/`" .+*#"`) and losses through a same-length HATCH ramp (`" ▖▞▚▙"`/`" ,x%@"`) — two distinct glyph families, so the biggest loss and the biggest gain are never confusable even in monochrome/`NO_COLOR` — and colour (when enabled) is a distinct hue per side (blue gains, red losses), never two shades of the same colour; both ramps still open on blank at exactly zero. Nonpositive arc slices are excluded from the total and logged as dropped. Categorical y dots paint on bands. **A `cell` mark's shade always quantises through `box`'s own monotone 5-level `" ░▒▓█"` ramp, on every tier** — `blocks`/`braille`'s usual sub-cell-occupancy fill (density, not a curve; still what a full-coverage bar/area/rect reads as `█` through) derives its glyph from PARTIAL coverage, which for a continuous value ramp picks a quadrant SHAPE (`▘ ▀ ▛`) rather than a darkness level and reads as texture, not monotone shading (B6d) — `paintCell` bypasses `fillRect`'s per-tier path entirely (painting through `canvas.text`, exactly like bar/rect/area's own fill glyph above) so every tier's heatmap reads the same monotone ramp `box` always has.

**`options.strokeWidth`**: `1 | 2 | 3` on `line`, `rule`, and an `area`'s own boundary line (the same monochrome-series `paintLine` call the paragraph above describes) — default `1`, byte-identical to the chart before this option existed (verified against a real build of the commit before it landed). Forwards straight to `glyphcss`'s `canvas.line({ width })` (see "Cell canvas"): `ascii`/`box` substitute a heavier glyph on the identical footprint, so a width>1 line never covers a cell width 1 didn't already clip to; `blocks`/`braille` add real sub-cell dot ink, clipped against the plot rect inset by one cell (`paintLine`'s own `strokeClipPlot`) so the extra dot can never land outside it. Style cycling is unaffected — a dashed wide line is still dashed — and the legend swatch (both the bottom-row and the four corner placements) paints at the same width. Any other value rejects with `bad-stroke-width`.

**Arc shape and callouts**: a pie/donut's radius is ONE shared value split into `rx`/`ry` by `canvas.cellAspect` (width/height, canvas default `0.5`), never fitted independently per axis — `colRadius = rowRadius / cellAspect`, so the disc is a circle on SCREEN AT THE TARGET'S OWN DECLARED ASPECT, not merely in cell counts. `renderGlyphChart` carries each target's real cell aspect down to `createGlyphCanvas` via `GLYPH_CHART_TARGET_DEFAULTS[target].cellAspect` (overridable per call with `options.cellAspect`) — `arcRadii` is the ONLY reader of `canvas.cellAspect` anywhere in the render path (grepped `packages/glyphcss/src/render/canvas/`; pinned by `arcShape.test.ts`'s byte-identity sweep over every non-arc mark type), so this changes nothing else. `web: 0.5859375` = Glyph Mono's own measured advance/line-height (`fontTools` on `glyph-mono.woff2`, 1200/2048 em) at the chart `<pre>`'s `line-height: 1`; `terminal`/`chat`: `0.5` (a typical terminal cell's ratio; `chat`'s is a documented GUESS, since a chat client's own fenced-code font is outside this package's control). Measured on a 96×32 web pie: the pre-fix default (`cellAspect: 0.5`) drew a disc **17.2% wider than tall** on Glyph Mono's real glass; the target's own aspect now measures **within 1%** of a true circle (`arcShape.test.ts`'s "P1-1" suite). Diameter is `min(plotRows, availableCols * cellAspect) * GLYPH_CHART_ARC_FILL` (`GLYPH_CHART_ARC_FILL = 0.8`, exported from `paint.ts`), centred in the plot, never touching its edge. `arc`'s `options.labels: "callout" | "legend-only"` (default `"callout"`) draws a leader line from each slice whose own angular span clears an 8° minimum, out to a `name · NN%` label beside the disc (left half left, right half right; same-side labels sort by angle/row and push apart by one row on collision, dropping with `label-dropped` when a side runs out); `"legend-only"` paints just the disc — `availableCols` drops a `min(GLYPH_CHART_ARC_CALLOUT_GUTTER_COLS, floor(plotCols / 4))`-wide strip per side only for `"callout"` (the cap only ever binds under 96 plot columns; a tall/square grid otherwise traded away most of the disc's own row diameter for a flat column reservation — measured at 40×40, 63% of the disc's rows), so `"legend-only"`'s disc pays no gutter tax. The legend row is unaffected either way (it carries the swatches; callouts carry the pointers). Full derivation, the rejected `plotCols / cellAspect` formula, and the callout geometry: `docs/design/charts.md`'s own "Arc shape and callouts".

**Labels** use `glyphChartLabelLayout`, including band/time ticks: fold through `canvas.text` and abbreviate within a slot/viewport — a NUMERIC label (an axis tick's own formatted value, or any label the caller marks `numeric`) tries SI abbreviation and then is DROPPED, never truncated with an ellipsis, since cutting characters off a formatted number produces a different, plausible, wrong one; a category label still elides with `…`/`...`. Crowded bands retain every kth label. Axis tick REQUESTS are derived from the space actually available (label width × count that fits), not a flat over-request greedily thinned back down; a bar/rect chart's zero baseline and a log axis's decade ticks are prioritised so collision-thinning can never drop them, and an axis never shows the identical label text twice in a row (a duplicate is dropped with a ledger entry, favouring the earlier, distinct one). ASCII is 7-bit throughout: `-`, budgeted three-character `...`, folded titles/text/ticks; every chart string is painted through `canvas.text`, never direct grid writes. Width/height must be positive integers (`bad-size` before layout, including page/CLI fractions).

**Axes**: `spec.axes?.{x,y}: { ticks?, tickMarks?, title?, titleAt?, grid?, color?, format? }`. `tickMarks` (default `true`) draws the axis per-cell instead of one plain rule: y gets `┤` at each tick row and `│` elsewhere, x gets `┴` at each tick column and `─` elsewhere, `└` at the corner — all four reused directly from the box tier's own JUNCTION table (never a parallel glyph set), which is what gives `ascii` its own tick glyph for free (its junction table already collapses every multi-stem entry to `+`). `tickMarks: false` reverts that axis to the original plain `canvas.line()` sweep, byte-identical to the feature not existing. `ticks` is a REQUESTED count fed straight to `scale.ticks(n)`, replacing the auto-fitted budget outright; the existing collision/stride thinning still runs underneath it, so an oversized request still degrades to what fits rather than overlapping. **The AUTO row budget (no explicit `ticks`) always reflects the true row-INTERVAL count** (`bottom - top`, never `+ 1` — the off-by-one used to over-ask d3 by exactly one tick, which also defeated the stride-thinning below by matching its own overshoot) **and shrinks further until the scale's own `ticks(n)` already map to rows clearing the minimum spacing on their own**, re-asking for a coarser count exactly like `axes.*.ticks` would rather than letting the flat collision loop drop an arbitrary interior rung — a kept numeric ladder is therefore always an evenly-spaced subsequence, never a collision-thinned hole (CHARTS-RESEARCH B3). **The overshoot-stride sample (when d3 hands back more ticks than fit) is phase-anchored at the ZERO tick when one exists, or the domain-MINIMUM tick otherwise** — never at raw index 0, which is the domain's cell-ascending order and for a y-axis (row = larger-value-is-smaller-row) is therefore the domain MAXIMUM, so an index-0-anchored stride worked backward from the top and left the always-kept zero baseline landing off-stride at whatever offset that produced (a final-gate-2 review finding: the Area preset's kept ladder at heights 22-24 was `9,7,5,3,1,0`, gaps `2,2,2,2,1`, not arithmetic). Index/integer data (every value on that axis a whole number) never shows a fractional tick (`0.5`, `1.5`, …) even when d3's own "nice" ladder for a small domain reaches for half-steps. `title` defaults to the axis channel's own field name when it's a plain string field (an accessor/literal-array channel has no name to show) **and there's genuine room for it — rows>=20 for the x title, cols>=60 for the y title, and the field name longer than two characters** (a default used to cost a whole row/column on every chart with a named field, which is exactly the regime the tick ladder above breaks in; B4) — an explicit `title` (including `""` to suppress) always shows regardless of size. The x title is centred under its own tick-label row, the y title sits top-left above the axis (a rotated column of glyphs has no character-grid analogue) — both are the resolved defaults of **`axes.x.titleAt: "start" | "center" | "end"`** (default `"center"`, byte-identical when absent) and **`axes.y.titleAt: "top" | "bottom"`** (default `"top"`): `"start"`/`"end"` left/right-align the x title at the plot's own edge instead of centring it, and `"bottom"` moves the y title below the plot at column 0, on its own row exactly like the x title's — sharing that row with the x title when it fits to the LEFT of it, else claiming a second row and logging `axis-title-stacked`. Applies to an explicit title and the automatic field-name default alike; a value outside its own axis's vocabulary (each axis has its own — `"top"` is not valid for `axes.x.titleAt`) rejects with `bad-axis-title-at`. `grid` (default `false`) paints faint `┈`/`┊` gridlines (`.` on ascii) at tick positions, behind every mark and axis. **`format`** (`GlyphChartTickFormat`, `tickFormat.ts`) overrides a tick's own label: a named PRESET (a bare string, `"si"`, or `{ preset, ...params }` for one that takes them, e.g. `{ preset: "currency", symbol: "$" }`) — the ONLY shapes `renderGlyphChartJson`/the CLI/the JSON schema accept, since a function has no JSON representation — or, TS/JS callers only, a raw callback `(value, index, ticks) => string` called per tick with its raw scale value, its own index, and the full pre-thinning tick array. `"auto"`/omitting `format` is today's behaviour (d3's multi-scale time format / the existing SI-or-plain numeric ladder / the band category string), returned as a no-op by `resolveGlyphChartTickFormat` so the default path never re-derives it and stays byte-identical. Every preset lives in ONE exported table, `GLYPH_CHART_TICK_FORMAT_PRESETS` (`number`, `si`, `compact`, `integer`, `percent`, `currency`, `decimals`, `scientific`, `date`, `year`, `month`, `day`, `time`, `template`), which `schema.ts`'s tick-format schema and `validate.ts`'s `bad-tick-format` rule both derive from rather than keeping a parallel list. A formatted numeric label that overflows still follows the existing abbreviate-or-drop policy — a preset's own `siFallback` (when it declares one) is tried first, never a generic reparse of the DISPLAY text (which a symbol/comma-formatted string no longer round-trips through `Number()`), and otherwise the label DROPS, never truncates into a shorter-but-wrong number; a CALLBACK's output is always treated as a category label (elided with `…`) since its text is opaque to the library. Applies to axis ticks only — never an arc's own callout percentage or a funnel's value·percent label, both of which format independently.

**Colours**: `spec.axes.color?: string` (canonical `#rrggbb`) sets BOTH axes' line, tick marks, tick labels, title, and grid; `spec.axes.{x,y}.color` overrides it per axis. With colour on and no colour given, axes default to a muted mid grey (`GLYPH_CHART_AXIS_DEFAULT_COLOR`, `"#7a7f8a"`) instead of the reader's full-brightness foreground, so data marks read brighter than the frame; `color: "none"` and any non-canonical hex reject with `bad-axis-color`. Every mark's `options.color?: string | string[]` overrides its palette colour AND legend swatch — a single hex for every one of that mark's own series, or an array assigned per series in series order (cycling if shorter; a longer array logs `mark-color-unused`). `arc`: per slice. `cell`: the ramp's ink colour, or a diverging domain's `[losses, gains]`. `sankey`: per source node. `funnel`: per stage. Invalid values reject with `bad-mark-color`. `renderGlyphChart(..., { color: "none" })` drops every one of these exactly as it always dropped the palette — text-only output is byte-identical to before this option existed.

**Validation/schema**: tagged errors and repair hints use `GLYPH_CHART_VALIDATION_RULES`. Runtime and JSON Schema share vocabularies and date syntax; real Ajv (charts devDependency only) compares verdicts over shared fixtures/designed-bad specs. **Sankey and funnel** are non-cartesian, plumbed exactly like `arc` (excluded from the x/y scales, from `layoutGlyphChart`'s cartesian gutter, from `transform` — neither has an x/y scale for one to act on, so a `transform` on either rejects with `bad-options` rather than being ignored). `glyphChartSankey(data, { source, target, value, name?, color? })` groups into `ChartSeries` one entry per SOURCE node and lays out node columns by DEPTH (`d3-sankey`); a column too deep to fit the plot width even at the minimum node width (3 cells) FOLDS the deepest columns onto the last one that fits (`sankey-columns-folded`) rather than walking a box past the plot rect — the fit check uses the layout's own FLOOR gap (1 cell, what the defensive final shrink loop already accepts), never the 3-cell PREFERRED spacing the reflow above reclaims toward, since checking against the preferred spacing folded columns the layout could actually place (measured: HEAD silenced more links than no fold in 1,344 of 1,992 swept column/width configurations and fewer in 0 before this fix). Row height is ∝ throughput under ONE GLOBAL rows-per-unit rate — sized to the tightest column so no column ever overflows — never an independent per-column normalisation; this is monotone WITHIN A MEASURED BOUND, never absolutely proportional: the ±1-row cumulative rounding nested across a node's own column split and then its bands' own split is real, but `ensureMinimumHeights`'s reclaim loop (repeatedly decrementing the SAME tall entry, once per near-zero flow in that column needing a floor-of-1 bump) and `ensureFoldStubVisible`'s steal can each cost a further row — a value of 150 can draw fewer rows than a 130 elsewhere by as much as 2 (measured over 60 seeded random DAGs at five sizes, both node heights and band row-ranges, source and target sides; a prior "just never two or more" claim was false, disproved at deficit 2 — `docs/design/charts.md` has the counterexamples). A column with more positive-value nodes than it has rows keeps the `capacity` BIGGEST values at exactly 1 row each (the only layout that seats every survivor) and drops the rest, reported via `sankey-nodes-dropped` — deciding this BY VALUE, never by an artifact of the rate's own cumulative-rounding order, is what makes "the biggest values keep their row" true. A flow whose share would round to zero rows folds into one `(other)` band for that source, iterating to a FIXED POINT (never a single re-run — a re-split can itself hand a different survivor 0 rows) so every kept band has >= 1 row and every folded flow is named in `sankey-folded-flows`; the fold bucket's own node id is suffixed (`(other) (2)`, …) whenever a REAL node in the graph is already named `"(other)"`, so the fold can never route onto that real node's own box and silently merge the two (`uniqueSankeyFoldName`). A converged `(other)` bucket that itself still rounds to 0 steals one row from its source's tallest kept band, since an invisible fold stub defeats the reason it exists — and when even that has no spare row anywhere (measured on 2,028 of 6,400 swept fold configurations), `sankey-folded-flows`' own `detail.stubVisible: false` says so explicitly rather than leaving a reader to notice the missing band unaided. Stub rows on each node side are allocated in TARGET-COLUMN ORDER leaving a node (SOURCE-column order entering one), so non-crossing bands land on disjoint cells by construction. Each band of k rows is PAINTED as k parallel single-cell-wide routes through the cell canvas's own edge/route/`resolveJunctions()` contract (`docs/design/canvas.md`'s "Junctions") — `k = max(sourceHeight, targetHeight)`, the shorter end's last row absorbing the extras (a taper, the common case, not an edge case) — each reserving a column within an INTERVAL-COLOURED ribbon (`assignSankeyLanes`): two bands share a ribbon slot only when their vertical extents never overlap, so two overlapping crossing bands always land on different columns. A row's own first and last cell (touching its source/target border) are claimed with ABSOLUTE priority, ahead of every other cell, which is what guarantees every band reaches both its own borders regardless of any other band's transit crossing through — the property the design exists for. `report.routeConflicts` is not fully empty in practice — real cell-sharing between genuinely crossing bands, not an artefact of routes that could have been registered to avoid it (measured: 8,657 conflicts over 600 seeded-DAG renders, of which `parallel` is a minority (1,114) against `corner` (5,626) and `multi` (1,917); `docs/design/charts.md` has the full breakdown) — and every conflict cell always paints a real contending band's own colour, never a blank or foreign one, so a band never loses a whole run to it — only ever the exact cells another band's own route also claims. What it CAN cost is a band's own visible CONTIGUITY: `sankey-band-broken` reports, per band, the longest single interior gap in its own painted run when a crossing band's genuine claim splits it (never the quantity, which stays exact at every border). A gap too narrow for the packed ribbon width degrades by wrapping (`sankey-crossings-merged`, naming the actual bent-BAND count sharing the gap alongside the packed-vs-available COLUMN counts — the two are never the same number, and the message never calls the column count a flow count). A skip-level band (its target sits two-plus columns past its source) routes its pass-through at a ROW proven clear of every intermediate node's own box (never through one — asserted internally); if no such row exists anywhere in the plot it falls back to the top row, a documented residual. A non-terminal node whose inflow and outflow disagree gets `sankey-imbalance`. A nonpositive value, or a missing source/target/value channel, rejects with `sankey-bad-value` (a non-finite value in the DATA itself rejects earlier and generically with `non-finite-data`; only an accessor-computed non-finite value reaches `sankey-bad-value`); a channel resolving to `undefined`/`null`/`""`/a plain object (a typo'd field name, or genuinely unusable data) rejects with `sankey-missing-channel` rather than a misleading `sankey-cycle` or a node literally named `undefined`/`"[object Object]"`; a genuine cycle rejects with `sankey-cycle` (a runtime-only tagged code, like `mixed-x-scale` — no declarative schema clause can prove a graph acyclic). A node box under 3 rows tall skips its own label (`label-dropped`) rather than overwriting its border — a 2-row box's only two rows ARE the border. Folding node columns also names every LINK it silences (both endpoints now sharing a column) in `sankey-columns-folded`'s own detail, not just a column count. `glyphChartFunnel(data, { stage, value, name?, color? })` (or a bare `number[]`, index-stage shorthand) keys each STAGE by its own row, never by name (two stages sharing a label, e.g. two "Retry" steps, are still two rows) and gives every stage an EQUAL row band; only the CENTRED bar's WIDTH is ∝ value/max — never an equal-step trapezoid. More stages than the plot has rows FOLDS the tail into one "other (k more)" stage (at the largest folded value, keeping the monotone shape plausible) rather than dropping it silently past the row budget (`funnel-folded-stages`). A negative value rejects with `funnel-bad-value` (structurally, for the literal `number[]` shorthand; at resolve time otherwise, mirroring `sankey-bad-value`'s own split); an all-zero funnel draws nothing (`empty-total` — the code is shared with `arc`'s own empty pie, `ledgerEmptyTotal(subject)` keeping each its own wording); a nonpositive first-stage value omits every percentage rather than printing a fabricated `0%`, logging `funnel-bad-reference` once. A stage exceeding the one above it renders in place and logs `funnel-not-monotone`; a proportional width under one cell draws a one-cell stub and logs `funnel-thin-stage`. The value·percent label tries a plain, exact, comma-grouped format first, then a 3-significant-digit SI abbreviation, then drops with `label-dropped` — never the 6-significant-digit default SI form, which routinely made the abbreviation LONGER than the plain number it replaced. Both marks fill through `seriesShade(tier, styleIndex)` via `canvas.text` (the region-mark rule), so `braille`/`blocks` paint the same whole-cell glyph bar/rect do. Funnel's legend defaults OFF (its stage labels already carry identity); an explicit `legend: true` still lists the stages. Rationale and measured widths: `docs/design/charts.md`.

## Diagrams (`@glyphcss/diagrams`)

Pure async graph-to-cell rendering over the public canvas: `GlyphGraph` + Mermaid `flowchart`/`graph` or JSON adapters → `measureGlyphGraph` → `reserveGlyphGraphPorts` → async `layoutGlyphGraph` (dagre) → `routeGlyphGraphEdges` (Manhattan A*) → fresh-canvas paint. Node/edge/group ids are canonicalized before Dagre 3 layout in cell units (returned x/y are centres); both side capacities are finalized before port offsets, at least `2N + 1`, then reserved slots are assigned by the laid-out endpoint order. Reserved escape lanes and node/parallel-route clearance are one cell. Non-endpoint boxes never contain transit. Junction resolution and node fills precede target-border arrowheads; labels are last, disjoint from nodes/routes/each other except a node's own interior labels. An edge label must be adjacent to its own route or be reported as dropped. Every render uses fresh storage; one-cell box sides use the tier's explicit vertical glyph, avoiding the frozen canvas's degenerate-line/re-routing/revisited-cell limitations. Groups use compound layout where membership is nested/disjoint; unsafe enclosures become explicit member lists. `layoutGlyphGraph`'s `setGraph` call also fixes dagre's `edgesep` at `1` cell — the same integer unit `nodesep`/`ranksep` are in — rather than leaving it at dagre's own pixel-era default of `20`; unset, that default pins a rank's edge-label dummy nodes 20 cells apart transversally, which happens to coincide with TB's own label-width pitch (invisible there) but forces LR siblings (transverse axis = node height, `3`) 45 rows apart instead of ~19 (DIAGNOSIS-diagrams-fanout.md RC1/RC3 — no fixture had two LR siblings in one rank, so this shipped unnoticed). Budgets 9 nodes / 12 edges invoke a bounded sequence: compaction → decoration → duplicates → leaf clusters → split. Compaction is non-semantic (touches spacing, never content), runs in every detail mode including `faithful`, and is gated on `!current.fits` only — the DECORATION rung after it is gated on `!current.okay` (or `detail: "simplified"`), so a diagram that compaction alone already rescues keeps every label/shape it drew (a regression fixed once: the decoration rung used to run unconditionally and threw away exactly what compaction had just saved). It retries a too-large layout at `margin: 0`, then steps `nodesep`/`ranksep` down one unit at a time from the caller's own value to `glyphDiagramCompactionFloor(graph)` = `max(3, N + 1)`, `N` the graph's largest single-side fan-in/out degree (measured: degree 3 needs floor 4, degree 4 needs 5, degree 6 needs 7 — derived from `route.ts`'s port-lane reservation, never a flat constant, and reachable at the library's own `4`/`4` defaults, unlike the superseded fixed floor) — the first candidate that both fits AND routes every edge wins, a merely-fitting one is kept only as a fallback, and `budget-compaction` logs only when a candidate actually engages (RC2 — no fixture rendered at chat's real 72×24 default, so a 4-rank diagram's plain size overflow at that default went straight to `split` with no cheaper rung tried). The pre-compaction overflow/routing-failure report is deferred until AFTER the compaction rung runs, so it is never logged for a diagram that compaction goes on to rescue whole. A layout that still doesn't fit after compaction is reported as `layout-overflow` (the laid-out vs. requested size, `layoutWidth`/`layoutHeight` vs. `requestedWidth`/`requestedHeight` — `split-panel-dropped` shares the `requestedWidth`/`requestedHeight` vocabulary for the same concept), never as a per-edge `routing-attempt` — that code is reserved for a genuine A* failure inside a layout that already fits (RC4). Original lineage survives in `meta`, all split panels in `pages`, and every loss in `report.ledger` — `GlyphDiagramLedgerEntry[]` (`{ code, message, detail? }`), mirroring `@glyphcss/charts`' own shape and `ledger.ts` constructor discipline; `unroutable` describes final output only. The CLI prints each entry's `code`/`message` to stderr; `/diagrams` shows only the diagram, controls, tray and export bar — no ledger readout. The viewport holds only the render; feedback lives on the buttons and in the rail. Targets/options mirror charts, literally now: the bare `renderGlyphDiagram(input)`/`renderGlyphDiagramJson(json)` call (no `options`) defaults to `target: "web"`, exactly like `renderGlyphChart`; text/escaped HTML/ANSI remain separate exits. Validation/schema share `GLYPH_DIAGRAM_VALIDATION_RULES`, each with its own dedicated repair hint (never the generic fallback); full Ajv relational parity requires `GLYPH_DIAGRAM_JSON_SCHEMA_KEYWORDS`. Malformed input JSON is tagged `GLYPH_DIAGRAM_BAD_JSON` at both boundaries (`renderGlyphDiagramJson`, the CLI's `.json` path) via `parseGlyphDiagramJson`, never a bare native `SyntaxError` with no `code`. `engine: "elk"` rejects with `GLYPH_DIAGRAM_ELK_NOT_INSTALLED` at `layoutGlyphGraph` itself, not a generic `bad-options`; `./elk` is reserved with the same code and the root never imports elkjs. The Mermaid adapter's inert-directive allowlist (`classDef`, `class`, `style`, `click`, `linkStyle`, `%%` comments) is parsed as data, never executed; `-. text .->` edge-text and `|label|` spans are protected from statement-splitting like quoted labels, so a decoded entity's own `;` (e.g. inside `&nbsp;`) can't truncate a statement. Label decoding is one left-to-right scan of the original text: an HTML entity always wins over Mermaid quote-escape interpretation at that position, and its decoded output is never re-scanned — the order that keeps a round-tripped `\\server\share`-style label intact. `glyphcss diagram` and `/diagrams` use this same pipeline and the shared instrument shell; no orbit (a diagram has no camera). The whole workbench state shares via `?d=`, the same envelope `/charts` uses — see "## Charts"' URL-state clause and `docs/design/diagrams.md`'s own "URL state". The page's Graph panel has a third "Table" tab beside Mermaid/JSON — a nodes table (id, label, kind) and an edges table (from, to, label); a node's `shape`/`group` and an edge's `id`/`style`/`priority` aren't exposed there but ride through untouched, since switching tabs only REFRESHES the newly-shown text from whichever source is currently authoritative, never steals authority itself (only an actual edit does), the same rule that already let JSON-only fields survive a round trip through Mermaid. The table-authoritative graph likewise carries the source's own `groups` and `direction` verbatim beside `nodes`/`edges` (`diagramsWorkbenchState.ts`'s `tableGraph`) — editing one cell on a grouped preset (Subgraph, the CrewAI-style crew) used to rebuild `{ nodes, edges, direction: "TB" }` with no `groups` at all, replacing the render with an `unknown-group` error and silently resetting LR to TB. Details and current verification limits: `docs/design/diagrams.md`.

## Maps (`@glyphcss/maps`)

Pipeline: `source → sample → field → classify → bands → compile`. Everything public speaks lat/lng (`GlyphMapView = { center: [lon, lat], span, cols, rows }`, aspect-locked). Rotation and projection units are degrees (`glyphMapFromD3Raw` converts d3 radians and swaps to the package's `(Y, X)` world order).

- **Projections** are vertex transforms (`{ id, project, unproject, domain, exaggeration }`) plus optional CAPABILITIES — `visible(world, depthOf)` and `cameraForCenter`/`centerForCamera` (globe only). **Every projection-specific branch in the widget keys on capability presence, never on `projection.id`.** "Crop, don't clamp": `project()` returns `NaN` outside the valid window. `exaggeration` is READABLE (`1` = true scale) because it is a TERRAIN concept and `project` is the package's ONE elevation conversion: a TRUE-METRE quantity (a structure's height) reaches that axis through `glyphMapTrueScaleElevation(metres, projection)`, and nothing else can recover the factor — a sheet's `X`/`Y` are degrees and the globe's are Earth radii, so no probe of `project` says how much of its `Z` was exaggeration. Shared world frame: `X` north, `Y` east; `glyphMapGlobe` is the textbook right-handed sphere, pinned by `chirality.test.ts` against glyphcss's real camera. `website/scripts/bake-globe.mjs`'s own sphere negates `Y` (a known, unfixed mirror; `parity.test.ts` documents the exact sign flip).
- **Tiles** — `GlyphMapGeoTile` is vertex-centered `(cols+1) × (rows+1)` elevation, projected client-side, split at the antimeridian before projecting, baked as int16 `.bin` under a `version: 2` manifest (z0–z4 global plus a curated overlay, 358 files / 11.8 MB, COMMITTED under `website/public/data/geo-tiles/` because nothing bakes at deploy time and `/maps` mounts no widget at all without it; `--fixture` for the vendored parity fixture). `glyphMapCuratedProvider` overlays deeper curated levels (Switzerland z5–z7) that degrade to ancestors, exposing `resolveTile` so siblings dedupe. Vector tiles use the SAME equal-angle quadtree addressing; `glyphMapTargetLOD` keys LOD on degrees-per-cell, never `camera.zoom`, and keeps the DEEPEST level when none is fine enough, so a shallower pyramid (borders stop at a curated z4 while terrain reaches z7) stops sharpening, never stops drawing. A tile-sweep's visibility test samples the tile's own bounds AND the VIEWPORT's own unprojected points (`viewportGeoSamples`) — never a single point: a 22.5° tile straddles a 3° viewport whenever that point lands within a viewport-width of a tile edge, and a nonzero `tilt` makes the visible window asymmetric (it reaches much further toward the horizon), so no box centred on `view.center` describes it.
- **Relief mesh** — `glyphMapPolygons(tile, projection, { resolution, colorSample, elevationBias })`; resolution is resolved per pyramid LEVEL (never per tile — cracks). Three tiers per raster layer: target LOD, a coarser fallback mounted first, and a permanent floor (capped to 32 quads/axis unless it is the target). Never a blank hole while panning. **A tier that is not the target LOD is a BACKSTOP and is mounted SUNK by `GLYPH_MAP_RELIEF_BACKSTOP_SINK_M` (20,000 m, via `elevationBias`), so it can never occlude the target tier.** All three tiers are opaque meshes in ONE scene — glyphcss's `occlusionPriority` orders layers, not meshes inside the base grid — and a coarse quad is not merely a blurrier fine one: its chord interpolates linearly across up to ~11 degrees, so where it straddles a coast it sits kilometres ABOVE the fine tier's sea floor, wins the shared depth test over open ocean and paints it in the colour of a block that is mostly land. That is the reported "the sea is basically GREEN" on `/maps`, measured over the Peru-Chile trench at 486 of 4,462 sea cells in a land band against 16 for the target tier alone; with the sink the combined render is cell-for-cell identical to the target tier alone at every view measured. The sink is a BOUND, not a tuning — it exceeds Earth's entire solid-surface relief (~19,784 m), which bounds how far any coarse chord can rise above a finer sample of the same field — and it is in METRES so it is exaggeration-invariant. Raising the floor's own resolution is NOT a fix (231 stolen cells even at its finest 2-degree quads), and neither is a colour rule: no single colour per 11-degree quad is right, so `corner-mean` merely trades sea-painted-as-land for land-painted-as-sea. `elevationBias` never touches the elevation `color` is handed. Gate: `widget.backstopOcclusion.test.ts`. **A quad's COLOUR elevation is the MEDIAN OF THE SURFACE it covers — the level that halves the AREA of the tile's own full-resolution bilinear surface over the quad's block (`colorSample: "surface-median"`, the default), not the mean of its 4 corners and not the median of the SAMPLES it covers.** Colour fidelity still does not degrade with mesh resolution (a coarsened quad reads the finer terrain it stands in for, not its own chord), and the guarantee is now exact at every block size because it is a median's defining property rather than a claim about counts: a band that less than half the covered surface occupies cannot contain the level that halves it. Both rejected rules failed on real data. The 4-corner MEAN averages deep ocean with high land and falls below sea level, painting bathymetric blue over land (the floor tier's quad over Bogotá averaged −155 m on terrain that is 379/441 samples above sea level, Quito's −718 m). The SAMPLE median, which shipped next, was defended with a guarantee stated for `n >> 1` ("more than half the covered samples at or above sea level ⇒ the sample at `n >> 1` is too") that is FALSE at the resolution a reader looks at: `reliefFractionForLevel` is 1 for every span the target tier draws at, so the block is the quad's own 4 corners and the statistic is a 3-of-4 vote blind to magnitude — reported live as Buenos Aires' city centre painted as river, where the z4 quad reads (nw −1, ne −1, sw +12, se −1) and 72.6% of the surface between those corners is above sea level (2,756 base cells OSM calls land painted as water, 1,673 visible, with a straight quad edge through Palermo). The area median's cost was measured and accepted rather than discovered: it paints MORE water overall, because the surface between a lone high sample and its low neighbours really is mostly low — 56 of 16,200 quads flip land→water on Buenos Aires' own z4 tile (14 the other way), 96 on Amsterdam's (39 the other way), and 4 quads of the Bogotá fixture (real cliffs into the Peru-Chile trench, e.g. corners 212/426/**−3046**/81, where the terrain steps and the interpolant ramps). It reads the BILINEAR patch, not the two triangles glyphcss actually fills: the fan diagonal is an artefact of the fill order and would make the answer depend on it (the same Buenos Aires corners are 42.6% above sea level split nw–se and 85.2% split sw–ne, bracketing the bilinear's 72.6%). Exact along a row (the surface is linear in `u`, so a row's heights are uniform between its edge heights) and discretized only across rows, at `SURFACE_MEDIAN_STRIPS` (8) or more per block; the median of that mixture is solved in closed form, not searched. Cost, real z4 tile: target tier 4.2 → 6.2 ms/tile, and the work is now proportional to the tile's own cells rather than the quad count, so the strip count is divided among a coarse block's cell rows (32-quad floor tier 3.3 ms instead of 8.2). Point-sampling the quad centre was measured and is WORSE than the mean (it lands in rivers/inlets). Below-zero DRY LAND is left alone and is not a defect: 138 of 187 z4 samples around Amsterdam are genuinely below 0 m (polders, the IJsselmeer bed), mean, median and area all agree there, and no per-quad statistic separates a polder from a lake bed at ~13 km per sample — band 0 means "below the datum", the OSM water layer is the only real water mask, and no band was added. `colorSample: "corner-mean"` is required by, and used only by, the `heatmap` layer, which keys a `Map` on that exact float to recover per-quad density. Gates: `mesh.seaLevelBand.test.ts` (the area invariant, both directions, at every rung of the ladder), `mesh.surfaceMedian.test.ts` (four quads no two candidate statistics agree on) and `widget.reliefSurfaceBand.test.ts` (the reported cells, rendered), against the vendored real-ETOPO1 `fixtures/sea-level-band.json` (`bake-geo-tiles.mjs --fixture`).
- **Widget** — `createGlyphMap(host, opts)` owns one `createGlyphScene` (`map.scene` is the escape hatch), tile cache/diff/in-flight guard/180ms gesture-gated debounce, and one `requestAnimationFrame` motion loop (inertia, `flyTo`, `setProjection` blends) issuing at most one render per displayed frame — input handlers update state synchronously and only the render is deferred. **EVERY SCENE WRITE GOES BEFORE THAT FRAME'S `scene.rerender()`, AND NO INPUT HANDLER MAY WRITE TO THE SCENE AT ALL** — `rerender()` supersedes a microtask render armed ahead of it (it bumps `renderGeneration`), so a write before it is free and the identical write after it arms a second full render nothing can cancel, on the same task's own microtask checkpoint. The near-side sweep is therefore split: `syncNearSideDom` (marker/symbol `opacity`/`visibility`) is what a pointer handler runs, and the geometry half (a `fill-extrusion`'s far-side wall cull, which calls `setPolygons`) runs only immediately before a render — from the motion frame, and from the `rerender` on the `map.scene` proxy, so an out-of-band repaint between two pointer events still gets the cull for the camera it is repainting. Getting this wrong is not a small tax: with buildings mounted the page rendered the whole scene once per FRAME extra and once per POINTER EVENT extra, measured at street level in Zürich as 1.72 renders/frame walking (38.5 fps) and 2.98 dragging (11.8 fps), against 0.87 and 1.00 (58.7 and 28.8 fps) once ordered. Gates: `widget.motion.test.ts`, `widget.extrusionWalls.test.ts`. **A SWEEP THAT RESOLVES THE SAME TILE OBJECTS DOES NOT REBUILD a point (`symbol`/`circle`) layer, and a rebuild that does happen measures the grid BEFORE it touches the DOM and creates every label already at `opacity: 0`.** The three are one rule — a label the declutter arbiter has not ruled on is not a label the reader may see. Without them the 180 ms debounce tore down and re-created every hotspot after every gesture (measured `+4298 -4298` on a 40 px pan that fetched no tile), `sync()` then forced two synchronous layouts PER RECORD, and the first of those resolved the fresh elements at the CSS default `opacity: 1` — so hiding them was a change between two resolved styles and a consumer's `transition: opacity` (which `/maps` sets) faded every place name on Earth across the map for ~120 ms. The DOM is correct at every frame boundary throughout, so only a screencast sees it. `reprojectGeometry()` forces the rebuild, because a projection change moves every anchor. Gate: `widget.symbolRebuildFlash.test.ts`. Sheet projections **cover, not contain** (`getMaxSpan()`, pan clamp to a fixed point); an explicit `maxSpan` opts out. The widget remembers which `cameraForCenter` preimage an unclamped orbit drag is on. **`map.idle()`** resolves when the widget is quiescent BY ITS OWN ACCOUNT — no armed `scheduleTileUpdate` debounce, no dispatched or queued layer-runtime sweep, no pending ground-change re-plant, no owed motion frame, no `flyTo` or `setProjection` blend (`widgetBusy`, gated clause-by-clause in `widget.idle.test.ts`). All of that work is fire-and-forget internally, so before this there was no completion signal at all and a caller reading the settled picture — an export, a screenshot, a test — could only guess a duration. It does NOT time out (a widget that never goes quiet is a real hang) and resolves immediately on a destroyed map. **`setLayerSource(id, source)`** replaces a MOUNTED vector-source layer's data in place — `line`, `fill`, `fill-extrusion`, `symbol`, `circle`, `heatmap`; a `RangeError` naming the id for `raster`/`contour` (field sources), `background` and `model`. It is the ONE primitive a live feed needs, and it is IDLE-NEUTRAL: the rebuild it dispatches goes through the same `trackUpdate` counter `addLayer`'s does, so `setLayerSource(id, next); await idle()` resolves with the new features on screen and `idle()` keeps its exact meaning. There is deliberately no `refreshMs` — counted in `widgetBusy()` a repeating timer makes `idle()` never resolve, and excluded it is state `idle()` hides, which none of its five clauses does; the interval, abort, backoff, visibility gate and per-service rate-limit policy belong to the consumer (`website/src/components/MapsWorkbench/mapsLiveRefresh.ts` is the reference one). A `symbol`/`circle` layer RECONCILES rather than rebuilding when the incoming features carry unique `id`s: survivors move through the hotspot's own `setAt` (the call `syncGround` already uses), departures are removed, arrivals created, arbiter once — measured on the real page at 384 markers, a refresh is +0/-0 node churn and 5.7-8.4 ms against +384/-384 and 6.8-9.8 ms for the keyless rebuild and 14.8-15.8 ms for a `removeLayer`+`addLayer`. Ids absent or non-unique keeps the pre-existing rebuild exactly. Attribution needs no machinery: `getAttributions()` derives from the mounted layers and a collection carries its own credit, so a feed's credit appears and withdraws with its data. `destroy()` now disposes `feature`-kind runtimes too (it skipped the kind entirely, leaking every hotspot and both registry entries). Gate: `widget.liveSource.test.ts`.
- **Camera pitch (`tilt`)** — `tilt` pitches the camera ABOUT THE SURFACE POINT UNDER THE VIEW CENTRE with the pivot distance equal to the camera's altitude (Google Earth / Cesium), so `map.project(getView().center)` lands at the CENTRE of the grid at every pitch and every span, and the two feels fall out of ONE rule with no threshold: zoomed out the pivot is far below the camera relative to the view, so pitching swings the globe and the limb enters tangentially; zoomed in the pivot is directly beneath, so pitching reads as raising your head off the ground (what makes 3D buildings legible). Under the ORTHOGRAPHIC camera the pivot's distance along the view axis is unobservable (`project` is `R·(v − target)`, so a shift along the axis moves depth by a constant and col/row by nothing), so the model reduces EXACTLY to `camera.target = projection.project(lon, lat, 0)` — what a SHEET has always done, so one implementation serves both and the sheet pose is byte-identical (`rotX`/`rotY`/`target`/`zoom` pinned exactly). An orbit `tilt` still ADDS to `cameraForCenter`'s pitch (default `0`; a sheet's `tilt` IS `camera.rotX`, default `40`); only the pivot changed. `applyDragState` re-anchors the pivot on the centre the drag produced and subtracts the APPLIED pitch before `centerForCamera`. This replaced a model that swung the camera about the GLOBE'S CENTRE with `target: [0,0,0]`, which held the NUMBER in `view.center` stable while the PICTURE was `tilt` degrees of latitude away — measured at `tilt: 40` on 140x63: row 11.9 of 63 at span 140, −33.3 at 40, −827.9 at 3, −23,405 at 0.11 — and which six defects on this branch traced to. **`getMaxTilt()`** is the ceiling `setTilt` clamps to: the HORIZON ANGLE at the view's own scale, `asin(R / (R + h))` capped at `GLYPH_MAP_MAX_TILT` (85), where `R = |proj.project(lon, lat, 0)|` (the same origin-centred sphere `glyphMapGlobe.visible` already assumes) and `h` is the frame's world half-height `(rows·cellHeight/2)/zoom` — the host's rendered pixel height over `zoom`, so the ceiling is invariant to `cols`/`rows`/cell size exactly as `camera.zoom` is. `h` is the one modelling choice: an orthographic camera has no altitude, so the view supplies the only length it has. It gives ~21° at a 360° span (where 80° aims past the limb at empty space), ~50° at 40°, and the 85° cap by city scale; a SHEET has no limb so its ceiling is the cap at every span (capability, never `proj.id`). The clamp is non-destructive — the request is remembered, `getTilt()` reports the APPLIED pitch. Gates: `widget.tiltPivot.test.ts` (pivot at four spans, both signs, through-pole drag, sheet byte-parity, and the ceiling re-derived independently through `map.unproject`). **The GESTURE is Ctrl+drag / right-button drag, vertical, `GLYPH_MAP_TILT_DRAG_DEG_PER_PX` (0.5, MapLibre's own rate)** — `controls.tilt` (default `true`) is its own opt-out beside `drag`/`wheel`, plain drag is untouched, `contextmenu` is suppressed over the host while it is enabled, and the gesture emits no `click` and no inertia. It goes through `applyTiltState` (the state half split out of `setTilt`) plus `markMotionDirty()`, so it shares the ONE motion loop — never a second render path — and it accumulates from the APPLIED pitch, not the request, so it has no dead travel against a lowered ceiling while the remembered request still survives a zoom out and back. Gate: `widget.tiltGesture.test.ts`. The gesture's HORIZONTAL axis is `bearing` (below); one `controls.tilt` flag opts out of the whole stroke, because it is one press.
- **Camera bearing (`bearing`)** — the compass heading, degrees, that points UP on screen (`0` = north up, `90` = east up, i.e. the picture turns CCW as the number grows — MapLibre's convention; `setBearing`/`getBearing`, reported normalized to `[0, 360)`). It is **rotation about the SURFACE NORMAL AT THE PIVOT** — the same point `tilt` pitches about — NOT a roll about the view axis: the two are identical at zero pitch and diverge exactly where this exists, because a roll TIPS THE HORIZON on a pitched camera and no map product does that. Composition, in glyphcss's axis-swapped c-frame, is `M = E · Rot(uc, −bearing)` with `E = RotX(camera.rotX)·RotZ(camera.rotY)` and `uc` the pivot's local up (asked of the projection via `localUpDirection`, never hardcoded, so a `glyphMapFromD3Raw` projection and a `setProjection` blend both work). Right-multiplication is what keeps the horizon level — `up` is the rotation's own axis, so `M·uc = E·uc` for every bearing — and where the pivot is the view centre `E0·uc = ẑ`, so the whole thing reads `RotX(tilt)·RotZ(−b)·RotX(trueRotX)·RotZ(rotY)`: navigate, turn, pitch (the MapLibre/Cesium camera). It rides on `GlyphCamera.mat`/`useMat` (public, honoured by `project()`), so `rotX`/`rotY` keep their meanings underneath and `centerForCamera` still inverts the centre. **At bearing 0 NO matrix is installed** (`useMat` false, `mat` null) and render/`project`/`unproject`/`getMaxSpan`/`getMaxTilt` are bit-identical — gated three ways (a fresh map, an explicit `bearing: 0`, and one that went to 137 and back). Three things it touches: `applyDragState`'s ORBIT branch rotates the pixel delta by `+bearing` first (`bearingDragDelta`) or a turned map pans sideways — the sheet branch must NOT, since `screenToWorldDelta` probes the live camera and is already bearing-aware; `glyphMapHeadlightDirection` is NOT bearing-invariant after all (a normal-axis turn genuinely moves the view axis, unlike the roll the audit assumed), so the headlight reads `(mat[7], mat[6], mat[8])` when a matrix is installed, which reduces algebraically to the Euler formula at 0; and the SHEET cover clamp DOES under-cover — the visible window is a rotated rect whose world-axis reach is `w|cos b| + h|sin b|` (worst at 45°), measured as a viewport corner falling off the map, so `spanCoverLimit`/`clampWorldToCover` take that AABB, with bearing 0 keeping the original expressions verbatim (`(a/b)/c ≠ a/(b·c)`). **The GESTURE is the horizontal axis of the same Ctrl+drag / right-drag stroke, `GLYPH_MAP_BEARING_DRAG_DEG_PER_PX` (0.8, MapLibre's own rate); drag RIGHT INCREASES the bearing**, turning the picture anti-clockwise, so the NEAR ground — the lower half of a pitched picture, the half the hand is on — follows the hand, and the Dock's `Bearing °` slider moves the map the same way the drag does (the opposite sign shipped first and was reported backwards). Both axes are live in one stroke (no axis lock), `controls.tilt` opts out of both, no inertia, same one motion loop. **`temporalBlend` is the one known hole and it is in glyphcss, not here**: `rasterize.ts`'s TAA history camera rebuilds from `rotX`/`rotY` and drops `mat`/`useMat`, so a maps scene opting into `temporalBlend` would reproject against an unrotated frame — `@glyphcss/maps` never sets it, so nothing ships broken. Gate: `widget.bearing.test.ts` (the discriminator is up-at-the-pivot invariant while the heading turns, at pitch).
- **Touch gestures** — Google Maps' vocabulary on MapLibre's thresholds, because Google publishes the SET (Android/iOS SDK docs, quoted in `docs/design/maps.md`) and not one number behind it. One finger pans (unchanged); two fingers **pinch** to zoom (ratio 1:1, anchored on the midpoint), **twist** to turn (1:1 degrees, `bearing` DECREASES as the picture turns clockwise with the fingers), and **drag together vertically** to pitch (`GLYPH_MAP_TILT_DRAG_DEG_PER_PX`, the SAME 0.5 the Ctrl+drag stroke uses, UP = more pitch); a **double-tap** zooms in one level about the tapped point, a **two-finger tap** one level out, and a **double-tap held and dragged** is the one-handed zoom (`GLYPH_MAP_TAP_DRAG_ZOOM_LEVELS_PER_PX` = 1/128, DOWN = in, entered on the widget's existing 3px `didDrag` tolerance rather than MapLibre's first-pixel rule). **DISAMBIGUATION IS THE WHOLE FEATURE**, and it is MapLibre's arbitration, not a tuning: **pan + pinch + twist COMPOSE** (three components of one similarity transform of the finger pair, each with its own activation threshold) while **the PITCH is EXCLUSIVE and latched ONCE** — a two-finger drag recognised as a pitch stays one however far the fingers later spread, and one ruled out can never become one. Recognition needs all four of: the fingers landed SIDE BY SIDE (`sideBySide`, checked at the second `pointerdown` — stacked fingers make "both moved down" and "the fingers closed" the same pixels), both travelled `GLYPH_MAP_TOUCH_TILT_THRESHOLD_PX` (2), both more vertical than horizontal, both the same way; one finger may lead for at most `GLYPH_MAP_TOUCH_SINGLE_TOUCH_GRACE_MS` (100) before the gesture is ruled pinch/twist. The two activation thresholds are deliberately NOT pixel counts — `GLYPH_MAP_TOUCH_ZOOM_THRESHOLD_LEVELS` (0.1 zoom levels = a 7.2% RATIO of finger separation, so a wide and a narrow grip are the same gesture) and `GLYPH_MAP_TOUCH_ROTATE_THRESHOLD_PX` (25 px of ARC along the finger circle, measured against the SMALLEST spacing so far, so a closing pinch does not make turning easier: 28.6 degrees at a 100px grip, 7.2 at 400px). Neither protects a PERFECT gesture (the geometry does); they exist for the sloppy one, and the gate drives a pinch with 8 degrees of incidental turn and a twist with 5% of incidental spread. **NOTHING IS MEASURED FROM AN INCOHERENT PAIR** — a Pointer Event carries ONE finger, so the pair right after any single event holds one live position and one stale one, a configuration the fingers were never in. Measuring it is not merely imprecise, it INVENTS motion: 80px apart sliding 8px the same way reads as 72px apart for one event, 0.152 zoom levels, past the 0.1 threshold. The spurious halves telescope to nothing until something REFUSES one, and `clampViewToCover` at the maximum span refuses exactly the first, so a pure two-finger pan walked the span 360°→324° per stroke and a constant-distance 50° twist 360°→326.27° (both measured; the same class of defect as the undecided-pair one, and the fix is one rule for the WHOLE gesture rather than two patches). A pair is measured only once every finger has reported since the last measured sample, or once `GLYPH_MAP_TOUCH_SINGLE_TOUCH_GRACE_MS` says a silent finger is genuinely AT REST (a thumb anchoring a pinch emits no `pointermove` at all — without that clause the gesture would run at one increment per grace window). The grace also decides the pitch: `firstMoveAtA`/`firstMoveAtB` are stamped from the RAW event, ahead of the coherence gate, so two fingers whose starts are further apart than the window are never one two-finger drag — the same rule, not a second check. The event that RESOLVES the mode still applies nothing and re-bases (a 5px reference error measured at 5.38/6.15/6.92px through 1.08x/1.23x/1.38x). **THE SPAN IS AN ABSOLUTE FUNCTION OF THE GRIP**, `zoomBaseSpan * zoomBaseDist / dist` from the grip that crossed the threshold — never a product of per-event factors, which banks a clamped increment and never returns it (a wobble at the maximum span ratcheted 360°→337.5°). `applyTouchTransform(spanFactor, bearingDelta, from, to)` is the ONE write and does all three components with ONE anchor re-pin, through `clampViewToCover`/`syncCameraToView`, `applyBearingState` and `applyDragState`, repainting via `markMotionDirty()` — one motion loop, no scene write from an input handler. **THE RE-PIN IS A SECANT ITERATION, NOT A FIXED-GAIN ONE**: `applyDragState` converts pixels at the VIEW CENTRE's rate (`degPerPx = 1/camera.zoom`) and the anchor is not at the view centre, so on a globe at latitude 80 the same ask moves the anchor ~`1/cos 80` = 5.8x too far — feeding the raw residual back DIVERGES, and the old "stopped improving" bail then fired on the next pass (measured drift after a corner double-tap: 10.9px at lat 46, 178px at lat 80, 63.8px under a 60° pitch; more passes alone still leave 93px at lat 80). Each pass now divides the ask by the gain the last one actually bought and stops at `GLYPH_MAP_TOUCH_ANCHOR_STOP_PX` (0.005), reaching ≤0.002px in four or five passes; a pan the cover clamp REFUSES buys nothing and that, not a non-improving residual, ends the loop. **AND IT CANNOT END WORSE THAN ITS OWN BEST POINT**: some views admit no local model at all (a corner double-tap at latitude 88, where the grid corner is 119° of longitude away and the zoom throws it off the grid entirely) and there the iteration wanders however it steps, so every ask is accumulated since the last improvement and undone at the end — exact in the orbit branch, where `rotX`/`rotY` are additive and `degPerPx` is constant for the loop. Swept over 147 globe views (5 latitudes × 3 tilts × 4 spans × 4 tap points): the old loop left 81 past 0.005px, worst 574.6px; this one leaves 6, worst 548.5px, and every one of the six is better than the old value at the same view. **`pointercancel` IS NOT A RELEASE** — its own handler drops the contact, ends the pair without tap recognition and disarms both tap recognisers, because a cancelled press used to be recognised (two stationary fingers plus a cancel zoomed out a level; a cancelled press armed a double-tap the next real press completed). **NO NEW `controls` FLAG**: the three that exist are CAPABILITIES, so `wheel` is zoom (notches, pinch, both tap zooms AND the one-handed double-tap-drag, which is established even under `drag: false` and emits no `click` there), `tilt` is orient (the mouse stroke's two axes, the two-finger pitch, the twist) and `drag` is pan — under `drag: false` a pinch still zooms, about the CENTRE. `createGlyphMap` sets `touch-action: none` on the host (restoring the caller's inline value on `destroy()`) but ONLY when one of the three is live, since an inert map that still blocks the page's own scrolling is a hole in the article it sits in; `beginTwoFinger` refuses outright while `walk` is non-null. A third contact is ignored, and `handBackToLoneFinger` is called from every release that takes the count to ONE, not only from the end of the pair — otherwise a pinch that gained and lost a third finger stranded the survivor. Gate: `widget.touchGestures.test.ts` (48 cases, thirteen mutation checks recorded in the design note; the anchor cases now cover the GLOBE at latitude 46, latitude 80 and under a 60° pitch, for both the double-tap and the pinch — they exercised sheets ONLY before, which is why the orbit branch shipped with 178px of drift).
- **Projection transitions** — `setProjection(target, { durationMs })` blends via `glyphMapProjectionTransition` (plain lerp / scale-normalized lerp / spherical-cap unwrap, chosen by capability, anchored on the view centre) and schedules zoom on log-linear apparent size, never a lerp. Endpoint framings are assigned VERBATIM at `t <= 0`/`t >= 1` (`a + (b − a)·1` is not `b`), each endpoint's pitch is clamped to its OWN ceiling, and the applied pitch rides in the framing so a mid-flight drag subtracts back out exactly what was added. Gates: `widget.transitionContinuity.test.ts`, `widget.transitionAnchor.test.ts`.
- **Camera-following key light (`keyLight`)** — `GlyphMapOptions.keyLight` / `handle.setKeyLight`/`getKeyLight` pick who aims the scene's key light: `"fixed"` (the default — the widget never writes `direction`, byte-identical to before this option existed) or `"headlight"`, which points it along the camera's OWN view axis and rewrites it whenever the camera moves. `glyphMapHeadlightDirection(rotXDeg, rotYDeg)` is that vector, `n = (sin rotX cos rotY, sin rotX sin rotY, cos rotX)` — an orthographic camera's projected depth is LINEAR in the world point, so the direction that increases it fastest (i.e. where the camera is) is exactly that functional's gradient, which is also the same `n` `glyphMapGlobe.cameraForCenter` inverts; glyphcss's `direction` points from the surface TOWARD the light, so `+n` is the sign and a headlight at the framing for `(lon, lat)` equals the SUN direction for a subsolar point there (both proven in `widget.headlight.test.ts`, one against the real `createGlyphOrthographicCamera`'s depth). Like the sun it writes `direction` ONLY — `intensity`/`color` stay the consumer's — and **the sun outranks it**: a real terminator is a statement about the world, a headlight one about the viewer, so `keyLightDirection()` is `sunDirection() ?? headlight`. `getKeyLightDirection()` reports whichever owner is live (or `null`), and is the ONE call a consumer composing its own `directionalLight` write should read. This is what makes "everything lit, like a globo terráqueo" reachable: the whole visible face is lit with no terminator anywhere, while Lambert still varies per face so TERRAIN RELIEF survives — the alternative, pure ambient, also removes the terminator but gives every face the same shade and renders the map as flat paint (rendered, not argued: one distinct colour across the entire disc, and the relief clause of the test goes red on it). `applyKeyLight` is called ONLY immediately before a synchronous `scene.rerender()` (construction, `setView`, `setTilt`, `resize`, the one motion-loop render, the projection-transition frame) and no-ops when the direction is unchanged: `scene.setOptions` invalidates glyphcss's shading cache and schedules a MICROTASK render, so writing it from an input handler instead would buy a whole extra grid render per pointer event — exactly the discarded work the widget's single motion loop exists to remove. **Measured** (`bench/maps-render`, spans, 1440x900, 140x63, same build with `mapKeyLightForSunMode` pinned to `"fixed"` as the baseline): renders/frame stays exactly `1.00` on every scenario, confirming the write-then-render discipline buys no extra render; a pure zoom is FREE (wheel base-raster 3.33 -> 3.28 ms, inside noise — a zoom does not rotate the camera, so the equality check no-ops and the shade cache survives); the price is paid only where the camera actually TURNS, and it is large — orbit base-raster 9.11 -> 16.52 ms (55.9 -> 42.9 fps), drag 9.10 -> 17.63 ms (54.4 -> 40.5 fps), flyto 5.08 -> 6.86 ms. That is inherent, not a wiring defect: glyphcss's per-triangle shade cache is built to survive a moving camera under a STATIC light, and a light bolted to the camera invalidates it every frame, re-lighting all 65,312 polygons. It is partly self-funding — an evenly lit globe has longer same-colour runs, so commit-write drops (orbit 2.21 -> 1.53 ms, wheel 1.19 -> 0.35 ms) and flyto/wheel end up FASTER overall (73.9 -> 77.4 and 93.8 -> 112 fps). A user dragging a heavy globe has `interactiveDownscale` (`/maps`' "Drag density") as the existing lever; no angular quantization of the direction is shipped, because it would save least exactly when the camera moves fastest. `/maps`' "Full" sun button is the reference consumer — `mapKeyLightForSunMode` turns it into `"headlight"` on an ORBIT projection only (a sheet's faces all point roughly `+Z`, so it has hillshading, never a dark hemisphere, and aiming its light down the view axis would only take away the Azimuth/Elev control that does real work there), and the Dock dims Azimuth/Elev with a reason in exactly the cases something else owns the direction, which reduces to `isOrbitProjectionId(projectionId)` in every sun mode.
- **Real-sun lighting** — `sun.ts` is the pure, clock-free solar math (`glyphMapSubsolarPoint(date)`, NOAA's formulation INCLUDING the equation of time — worth ±16 min ≈ ±4° of longitude, so dropping it is a visible error; verified against the published equinox/solstice declinations, both EoT extremes and a published subsolar point). `GlyphMapOptions.sun` / `handle.setSun`/`getSun`/`getSunDirection`/`getSubsolarPoint` and a `"sun"` event drive three modes: `"off"` (the default — no light write, no timer, no hook, byte-identical to before), `"realtime"` (re-resolved on the widget's own `setInterval` at `GLYPH_MAP_SUN_TICK_MS` = 30 s, so the terminator keeps advancing at 0.25°/min; snapped immediately on entering the mode, cleared in `destroy()`), and `"manual"` (pinned to one instant, no timer). **Two mechanisms, chosen by projection CAPABILITY, never `projection.id`**: an ORBIT projection gets a real `directionalLight.direction` = the outward unit vector at the subsolar point (`normalize(project(subLon, subLat, 0))` — glyphcss's source-vector convention), and Lambert draws the terminator, so no cell hook is installed there at all; a SHEET has one normal everywhere and cannot express a terminator with a directional light, so it gets a per-cell day/night term (`stampGlyphMapNight`) through the SAME single composed `transformCells` hook `line`/`contour` use, stamped BEFORE the strokes so a border stays legible at night. The sheet term darkens COLOUR only (never the glyph, which carries terrain shape) and so is invisible under `useColors: false`. Darkness is quantized to `GLYPH_MAP_NIGHT_LEVELS` (4) purely for cost: a continuous ramp gave almost every cell its own colour and destroyed span-run merging — measured 1,679 spans / 9.40 ms per render at 160×64 on the worst case (whole world, equinox, where the polar rows sit inside the twilight band all the way around) against 123 spans / 1.00 ms with no sun; 4 levels is 604 spans / 3.32 ms. The widget only writes `direction`; `intensity`/`color` stay the consumer's, and `/maps`' own `buildMapLighting` reads `getKeyLightDirection()` (not `getSunDirection()` — that answers `null` while a headlight owns the light, so the page would clobber it) fresh at write time so page and widget can never disagree.
- **Cast shadows (`shadow`)** — `GlyphMapOptions.shadow` / `handle.setShadow`/`getShadow` (a `GlyphMapShadowOptions` = `{ color?, opacity?, lift? }`, or `null`). OFF by default and byte-identical there — no `shadow` key reaches `createGlyphScene` at all, and the bench's fidelity digest for the default page is unchanged by the feature (`c619778796…` for shadows off, shadows on with no caster mounted, and no token at all). What the widget adds on top of glyphcss's shadow map is the three things a caller here cannot supply. (1) WHO: `GLYPH_MAP_SHADOW_CASTERS` = `fill-extrusion` + `model`, `GLYPH_MAP_SHADOW_RECEIVERS` = those two PLUS `raster` + `fill` + `heatmap`, set as per-mesh `castShadow`/`receiveShadow` UNCONDITIONALLY at mount (glyphcss reads them only inside a pass carrying `scene.shadow`, and `isDetailMesh` ignores them, so they are inert while shadows are off — which is what makes the toggle ONE `setOptions` rather than a remount of every mesh). The sets OVERLAP, which is what makes a building shadow the building next to it; they were disjoint at first, and that made the case a reader notices first in a city impossible by construction. What made the overlap safe is not a tuning but glyphcss's derived, slope-scaled acne guard (see "Shadows"): the error is a function of the shadow map's own texels, so it cannot be expressed as the world-unit `lift` this package has no scale to supply. TERRAIN still never casts — the shadow volume is fitted to ALL casters and a raster layer keeps a global floor tier mounted, so 256 texels would span the Earth. (2) The BIAS: `GLYPH_MAP_SHADOW_LIFT` stays `0`, now because the guard is already correct and `lift` is only an EXTRA absolute length — glyphcss's own `0.05` is 5% of the globe's radius (318 km) and erases every shadow (gated: handing `lift: 0.05` through changes not one cell), and any nonzero `b` erases every caster standing less than `b / sin(altitude)` above its receiver, i.e. the short buildings first and worst at a LOW sun. (3) The DIRECTION is NOT an option: shadows fall along the scene's own `directionalLight.direction`, which is whatever `getKeyLightDirection()` reports, so one vector lights the scene and casts its shadows. **A `keyLight: "headlight"` is therefore incompatible with visible shadows, exactly and unavoidably**: a headlight is the camera's view axis, and an orthographic camera's screen position is the component PERPENDICULAR to that axis, so displacing a caster along it moves its shadow zero columns and zero rows — every shadow lands in its own caster's cells (measured: 27 surviving fringe cells against 535 under a fixed light). `/maps` opened on a globe with Sun "Full", which is a headlight, and so showed no shadow anywhere; `mapKeyLightForSunMode(mode, projection, shadows)` now drops the headlight whenever shadows are on and the Dock un-dims Azimuth/Elev in that one case (`mapDirectionLocked`). Shadows are NOT base-grid only: glyphcss builds one shadow map per frame from every caster in the SCENE (see "Shadows"), so a layer separated by its own `density`, `renderMode` or `glyphPalette` casts and receives like any other. That is what `/maps`' OSM card needs — it gives every row its own density and no master at all (a `symbol`/`circle` row gets no density control, since nothing reads one for it), so a reader who moves any row past 1 separates the buildings that cast AND the landuse that receives, and the toggle used to go silently inert (measured on the reported link's own `osmDensity: 2.9`: 4,469 changed cells now, exactly 0 before). What a stamped `line`/`contour` still cannot do is RECEIVE — a stroke's colour is written flat into the cell after shading (`grid.color[idx] = color`), so a road is never darkened by the building beside it; that is a known, documented inconsistency, not a tuning. Measured (`bench/maps-render`, spans, 1440x900, 140x63, `--demo-layer fill-extrusion`): a flat +2.5 to +3.0 ms per render — orbit 19.60 → 22.06, drag 21.54 → 24.04, wheel 4.58 → 7.53, flyto 9.39 → 12.27 — so it costs most where the frame was cheapest (wheel +64%, orbit +13%). Making the casters receive as well is inside that measurement's noise (989 polygons / 845 caster polygons at 140x63: 0.29 ms shadows off, 0.74-0.81 ms ground-receives-only, 0.75-0.86 ms casters-receive-too). Solid down to ~10 degrees of sun altitude; below that the shadow dithers and by ~5 degrees it is a stipple that loses about half its cells, on a lit/shadowed contrast that is by then near-invisible anyway. Gate: `widget.shadow.test.ts`. Full record: `docs/design/maps.md`.
- **Street-level walk (`setWalk`/`getWalk`)** — a GATED mode: a positioned PERSPECTIVE camera at eye height (1.7 m), walked with WASD/arrows (`GLYPH_MAP_WALK_SPEED_M_PER_S` 6, Shift x3) and aimed by POINTER-LOCK MOUSELOOK. That speed is deliberately NOT anatomical — walking is ~1.4 m/s and shipping it read as glacial, because a first-person camera has none of the peripheral flow or body sense that makes 1.4 m/s feel like walking to a body doing it, leaving how fast the scene changes as the only motion cue; through a 56 deg lens at a horizon of a few hundred metres that is nearly nothing, so this sits where games settled (Half-Life 3.3, Minecraft 4.3) and is honest about being a CAMERA speed, not a gait. OFF by default and byte-identical there — no perspective camera is constructed and every branch is guarded on it. Almost nothing is new, because the pose is the EXISTING orbit camera read at its limit: `tilt` pitches about the surface point with a ceiling of `asin(R/(R+h))` that opens to 90° as the altitude goes to zero, so `GLYPH_MAP_WALK_HORIZON_TILT_DEG` (90) looks dead ahead and `tiltRequest`/`appliedTilt` IS the walker's pitch (clamped to a NECK, ±`maxPitch` 84° — the parthenon's own `6..174` read from the same horizontal, and what it protects is the YAW AXIS, not the picture); `bearing` IS the heading and keeps the horizon LEVEL by construction; `view.center` IS where they stand; `view.span` DESCRIBES the horizon footprint (`glyphMapWalkSpan`) so tile LOD, the URL codec and every readout keep working, and the wheel is a no-op rather than a repurposed FOV control. What IS new is the POSITION (an orthographic camera has no eye) and the LENS: `perspective = 5000·near`, `zoom = 25·W/(tan(fov/2)·P)`, and the eye sits `P/BASE_TILE` behind `target` — `BASE_TILE` PROBED off the live camera's affine `eyeDepth`, never assumed. **The lens and the pose are ONE thing** and both defects the first cut shipped came from treating them as two. (a) `P` is in the map's own units, so it is 3.9e-4 CSS px at the default entry — measured through the real `project()` that IS exactly 70° of horizontal FOV and a 0.5 m near plane, and the parthenon's literal `perspective: 1000` substituted in gives 0.02° and clips the planet (a world unit here is an Earth RADIUS). What carries over from `parthenon.astro` is the invariant, not the constant: solving `zoom` from the rendered width holds the FOV exactly at every width, and a `ResizeObserver` held only for the duration of a walk re-applies it — `/maps` never calls `map.resize()`, so at a third of the width the FOV was 26.3° where 70 was asked for. (b) The eye sits 50 m BEHIND `target`, so `applyBearingState` must RE-POSE while walking, not just install the bearing matrix: turning the head used to orbit the eye on that 50 m circle (3.49 m per 4°, 70.7 m per quarter turn) while `view.center` stayed put. Steering is the parthenon's control model whole — pointer lock acquired from `pointerdown` NEVER `click` (a per-frame-rewritten `<pre>` detaches the mousedown target, so `click` never fires), `GLYPH_MAP_WALK_FOV_DEG` is 56 (the parthenon's own focal length): 70 shipped first and read as "the buildings are not straight", but the camera measured innocent — a world vertical projects with `dcol` 0.000 at the centre AND both edges at every bearing, the axis is level to two thousandths of a row, the picture is isotropic to 0.18% — so what was being seen is a rectilinear projection's own `1/cos` edge magnification, 1.2208x at 70 against 1.1126x at 56. `GLYPH_MAP_WALK_LOOK_DEG_PER_PX` 0.15 (`createGlyphFirstPersonControls`' own default, not the map's 0.8/0.5 direct-manipulation drag rates), and drag-to-look at 0.24 for pointers that cannot lock. `createGlyphFirstPersonControls` is NOT reused: its step is a flat world-XY translate at a fixed `groundZ`, where this is a geodesic on a sphere with a per-frame terrain re-sample and a heading about the pivot's local up. TRUE metres (eye height, near plane) convert through `glyphMapTrueScaleElevation`, the same exemption an extrusion's height takes; the walker stands on `groundElevationSampler`'s terrain. **`glyphMapGlobe.visible()` is NOT generalised** — it is derived for the orthographic camera and reports the ground one metre in front of a walker invisible, and its consumers (tile sweep, `unprojectSphere`, wall culling, markers) would all fail together. That local horizon is ONE predicate — `nearSideVisible` — and EVERY point consumer goes through it: `project()`, stroke run clipping, `unprojectSphere`, marker and point-feature hotspot sync, and a `fill-extrusion`'s wall cull. It used to be `project()`'s alone, on a measurement taken at LEVEL pitch, and the other four kept asking `glyphMapGlobe.visible()` — which is not merely redundant under the walk camera, it is WRONG, and it blanked the frame the moment the reader looked up. That test takes `axial = depthOf(world) - depthOf(origin)`, accepts `axial >= 0`, and otherwise asks whether the point is outside the silhouette CYLINDER of radius `radius` about the view axis — both halves wanting the ORTHOGRAPHIC camera's depth, the raw rotated `z` in the same WORLD units as `|world|`. A CSS-perspective camera's `project()[2]` is `r_z * BASE_TILE - distance`, 50x that, and its eye is ON the sphere, so `axial` at pitch `p` is `-BASE_TILE * sin(p)`: measured through the real camera for the pavement 80 m ahead, `+1.744` at 2 deg DOWN, `-6.3e-4` level, `-8.8e-2` at a tenth of a degree UP, `-4.36` at 5 deg — i.e. five degrees of looking up puts the ground under the walker's feet four and a third EARTH RADII off the view axis, and every consumer rejects everything at once. Measured: a 300 m block 80 m ahead painted 4,900 cells at 140x63 up to `+0.01` deg and 0 from `+0.1` deg (a wall survives while ANY corner passes, and at level pitch only its 300 m top corners did); a ground-level `line` 30 m ahead has no such margin — `|world|` is exactly `radius` at the datum — so roads were already dark at the DEFAULT entry pitch. The same expression is wrong the other way too: looking DOWN it accepts every distance, so a block six horizons away painted 24 cells at 10 deg of down pitch. Road ribbons are out of scope; the ground between the buildings is flat. **Buildings are SOLID** (`walkCollision.ts`): only `fill-extrusion` footprints, never a `fill` (a park or a lake stays walkable) and never a slope. The STEP is tested, not the position, and a blocked one SLIDES — the tangential component of the step survives, which is what makes a corridor walkable where a halt-on-contact model glues the reader to every wall they brush (measured: 30 of 52 m of tangential intent kept). A `GLYPH_MAP_WALK_BODY_RADIUS_M` of 0.3 m stops the BODY at the wall rather than the eye inside its face, and is deliberately under a real shoulder width so a `2 * radius` gap keeps every visibly walkable alley walkable. Distances are taken in a LOCAL METRIC frame at the walker (a degree of longitude is 0.68 of a degree of latitude at Zürich), footprints are `[outer, ...holes]` with an even-odd test over every ring (a courtyard is open ground), and a step longer than a radius is SUBDIVIDED so a stalled frame cannot tunnel. The index is a metre-sized lon/lat bucket grid (`GLYPH_MAP_WALK_COLLISION_CELL_M` 32) rebuilt LAZILY from ONE invalidation site — `createMeshFeatureRuntime`'s `build`, which every path that gives a layer features goes through, dispose's own `rebuild([])` included — so a query touches one bucket and a map that never walks constructs no index at all; measured on the 63k-polygon Zürich walk scene it is FREE (47.6/47.6 fps with, 48.3/45.5 without — the run-to-run spread is bigger than the difference). **The walker is never trapped**, by two rules that are both load-bearing: a step STARTING with the walker's point inside a footprint is unconditional (including further IN — the off-centre case a "reduces penetration" rule alone refuses), and otherwise any step that REDUCES penetration is allowed (the walker standing in the body-radius shell of a wall that just streamed in). - **The walk SKY (`sky.ts`)** — a walker gets a sky, and it is REAL GEOMETRY: an inward hemisphere added as an ordinary opaque mesh at `GLYPH_MAP_SKY_RADIUS_FRACTION` (0.98) x `far`, so the renderer projects it like the terrain, anything nearer occludes it and there is no camera math anywhere (`website/src/pages/examples/parthenon.astro`'s own model; its CLOUDS are deliberately not taken). Mounted on entering walk, disposed on leaving, `sky: false` opts out and is byte-identical to a build without it (gated on glyphcss's `__glyphPerf.polys` seam, because an inward dome is BACK-FACING from outside and a leaked one paints nothing). Ordinary base-grid mesh with no `density`/`mode`/`glyphPalette`/`ambientIntensity` and no `castShadow`/`receiveShadow`, so it separates nothing, cannot switch on `computeOcclusionIds` (+10.4 ms/frame for one separated layer) and is invisible to the tile sweep and `getAttributions()`. **Lambert never touches it**: an inward dome's normals face the viewer, so the colour comes from a MESH-TARGETED appearance program over the dome's own handle (`glyphMapSkyEffect`, requirement `worldPosition`) - not the parthenon's distance-from-origin test, which cannot work here because a map's origin is the Earth's centre. Solid-mode only (mesh targeting reads `winnerMesh`), so the dome is simply not mounted in another mode. Colour: `glyphMapSkyPalette(altitude)` blends night -> dusk -> day anchors across the civil-twilight band and the first 25 degrees, warm at the horizon and blue at the zenith, quantized to `GLYPH_MAP_SKY_BANDS` (32) for the same span-run reason `stampGlyphMapNight` quantizes darkness (measured: +1,903 painted cells for +26 spans, 835 -> 861). - **Layers** — `background`, `raster`, `line`, `contour`, `fill`, `fill-extrusion`, `symbol`, `circle`, `glyph`, `heatmap`, `model`. Mesh-backed layers forward `density`, `renderMode` and `glyphPalette` to glyphcss's per-mesh options (edge modes mount `transparent`); a `raster` layer additionally takes an elevation WINDOW (`minElevation`/`maxElevation`, metres, either end omitted = unbounded and byte-identical) — terrain outside it is **CLAMPED to the window edge, not cropped**, so `minElevation: 0` draws the land and replaces the seabed with a smooth plane at sea level. It clamps PER VERTEX, in `glyphMapPolygons` and in `glyphMapGeoTileElevationAt` alike — a ground reading that interpolated the raw field and clamped afterwards is a different function across any quad that STRADDLES a bound (measured: +2,000 m of drawn surface against an answer of 0, i.e. 48 km at `exaggeration: 24`, which buried a draped road entirely). That is a deliberate exception to "crop, don't clamp", and it is the tier ladder that forces it: a dropped quad is a HOLE, each of the three tiers resolves the window against its OWN quad grid, and the backstop simply fills what the target tier opened — measured on the real ETOPO1 pyramid, a cropped floor of 0 painted 641 of 1,752 Mediterranean sea cells in a land band against the target tier's own 150 (and 344 of 2,932 against 13 over the Peru-Chile trench), i.e. "the sea is basically GREEN" reintroduced at its original magnitude, plus 200 coastal land cells lost. `GLYPH_MAP_RELIEF_BACKSTOP_SINK_M` cannot answer it — the sink ORDERS two surfaces where both exist and says nothing about what shows through a gap in one. A clamp has no hole, and wherever every sample a tier covers is out of window every tier's surface is the SAME constant plane, so no coarse chord can rise above a finer one. It moves POSITION only, per VERTEX (so `colorSample` never enters it and a coast still slopes): a quad's colour reads the terrain's own unwindowed statistic exactly as `elevationBias` does, so the sea keeps its bathymetric band and only its floor goes — clamping the colour too would hand `etopo1V1`'s band 0 the value 0 and paint every ocean in the lowest LAND colour. Every tier takes it, and so does `groundElevationSampler`, since what is planted on the terrain must stand on the surface actually DRAWN; a `contour` is NOT windowed by it (it marches the mosaic's own vertex grids and carries its own window). ## No per-frame DOM mutation

**Each render cycle writes each `<pre>` exactly once** — the base `<pre>` plus one write (and one `transform`) per detail layer. No cell-by-cell patching, no double writes. Hotspots update via one inline-style assignment each. Controls mutate a single camera state object; the boundary is camera event → state → rasterise → one string.

Render-path cost reductions that keep output byte-identical (details and measurements in `docs/design/performance.md`):

- **Cull runs** — `cullChunks` (`buildGlyphPolygonCullChunks`, 48-polygon runs with AABB + normal cone) let the solid rasterizer skip whole runs pre-projection. A box not wholly in front of the near plane is always accepted; nothing is ever reordered (draw order resolves coplanar ties). Back-face rejection derives its orientation sign from the camera by probing, and self-disables for non-affine (perspective) cameras.
- **Empty-coverage skip** in `scanFillTriangle`, hoisted below the shading block on purpose (`litCache` bucket order is colour-visible).
- **Projection memoization** on exact input equality (`resolveProjectionMetrics`, `rotateVec3Voxcss`).
- **Indexed vertex projection** — `render/vertexIndex.ts` projects one DISTINCT world position per pass, not one per vertex OCCURRENCE. Positions are keyed on their IEEE-754 BIT PATTERN (so `+0` and `-0` never merge); nothing is reused across passes (a generation bump, so a detail grid can never read the base grid's coordinates); the camera's own returned tuple is stored by reference, never copied into a pre-shaped row; and the index is built on the SECOND render of a polygon array and declined outright for an array that shares nothing. Invalidation is the polygon array's identity, the same invariant `cullChunkCache` runs on.
- **`fillDepthTri` samples `ceil(min)..floor(max)`** — the tight integer-sample bounds `scanFillTriangle` has always used; the wider form only sampled integers in order to reject them.
- **Depth before texture in `scanFillTriangle`** — a fragment that loses the depth test never pays a texel lookup. Alpha rejection stays AHEAD of the depth WRITE: a transparent texel must not occlude.
- **`interactiveDownscale`** — render at `1/n` while a control drags; controls signal via `scene.setInteracting`. Mirrored on React/Vue/custom elements. It divides `options.cols`/`rows` IN PLACE, so `getOptions()` reports the coarser RENDER grid for the gesture's duration — right for anything measured in rasterized cells, wrong for a DOM OVERLAY, whose CSS pixel size the downscale does not touch. **`scene.getBaseResolution()`** is the pair with the downscale not applied, equal to `getOptions()`'s at rest and the only way to recover it mid-gesture; `@glyphcss/maps`' `symbol` labels are the consumer. Gates: `createGlyphScene.baseResolution.test.ts`, `widget.symbolDownscale.test.ts`.
- **`createGlyphSurfaceAtlasWebGpuSession`** — browser-only WebGPU presentation companion on an adjacent canvas; never touches the `<pre>`; no CPU fallback; React/Vue re-export the factory only.

## Numeric conventions

Native glyphcss/voxcss surface; the `*/three` subpaths convert internally.

- **Rotation units: degrees.** `rotX`, `rotY` on cameras and `rotation` on meshes are degrees (XYZ Euler). `rotX=65, rotY=45` is the classic isometric-ish viewpoint. No radians.
- **Camera `zoom`: absolute, CSS pixels per world unit.** `zoom=50` maps one world unit to 50 CSS px (voxcss/polycss author at `BASE_TILE=50` and apply `scale(zoom / BASE_TILE)`). Not a viewport fraction.
- **Perspective `distance`: default `0`.** A CSS-pixel pull-back under the default CSS-perspective projection; world-unit pinhole semantics only in legacy `perspective: 0` mode.
- **Directional light `direction`: source-vector convention.** Unit vector from the surface toward the light. Up-right-forward lights faces whose normals point up-right-forward.
- **Depth: larger = nearer** everywhere (`fillDepthTri`, `CellGrid.depth`, camera `.project()[2]`).

## Cross-package discipline

The React and Vue packages are mirror images. **Any public API change in one must land in the other in the same PR.** Same names, arguments, defaults, and return shapes (allowing refs vs reactives, `useEffect` vs `watchEffect`). A `packages/glyphcss` or `packages/core` public-surface change updates both bindings in the same PR.

Before opening a PR:

- [ ] If I touched a React component/hook, the Vue composable/component matches.

## Iterating on the system

The design described here is *current*, not frozen. Rules for evolving it:

- **AGENTS.md is the canonical reference.** Edit it directly; `CLAUDE.md` is a symlink.
- **Architectural changes require user approval.** Dropping or adding a render mode, renaming a public convention, changing what JS is allowed in the render path — propose, don't decide. The user is the architect.
- **Same-PR sync.** Any PR that adds, removes, or materially changes a render mode, naming rule, or cross-package contract updates `AGENTS.md` (contract) and `docs/design/` (rationale) in the same PR.
- **Don't append-only.** Prune content that no longer reflects the codebase, here and in `docs/design/`. A dropped mode loses its table row; a renamed hook is updated in place.

## Backward compatibility

- **No BC shims.** Clean breaks only. No re-export aliases, no `@deprecated` wrappers. Callers update.
- Applies across the monorepo — published packages move together.

## Tests & build

- Refactors keep all tests passing. Don't delete or weaken assertions to make a refactor go through.
- A renamed export's tests rename their imports — no alias kept to satisfy them.
- `pnpm test` runs the full suite across every test-bearing package.
- **`pnpm build` is mandatory before opening a PR.** Vitest doesn't catch DTS/declaration build failures. Run `pnpm test && pnpm build` as a unit; either failing is "not ready."
- **CI enforces both gates** (`.github/workflows/ci.yml`: `pnpm test` + `pnpm build:packages` + `pnpm build:website`). Don't merge with red CI. The test step sets `NPM_CONFIG_WORKSPACE_CONCURRENCY: 1` — one package's vitest at a time. pnpm's default of 4 put 12 forks on a 4-vCPU runner, and vitest's largest-file-first ordering landed `@glyphcss/maps`' two biggest integration files inside that window every run; that, not any test's waiting, is what timed out three of them on correct work. vitest cannot see across packages, so no `maxWorkers`/`pool` setting can fix it. Local `pnpm test` is unaffected.
- A guarantee with no failing test is not a guarantee: byte-identity claims, no-op claims, and "degrades, never throws" claims each get a test that goes red when the property is removed.
- **Settle on the component's own idle signal, never on the wall clock.** A test that mounts a `createGlyphMap` awaits **`map.idle()`** — armed tile-sweep debounce, in-flight or queued layer updates, the ground-change re-plant, motion frames, `flyTo`, `setProjection` blend, all quiescent — before reading a frame. `setTimeout(…, N)` in a test body is legitimate only when `N` is the quantity UNDER test (a paced loader, the sun tick), and then the test says so; a stability poll ("the same frame three times") is the same guess wearing a coat. **A probe of a MOVING camera is a pose, not an instant** — a flight's or a projection blend's progress is a function of real time, so "180 ms into a 400 ms flight" is a race a loaded machine wins: advance the widget's own frames until the pose is reached, measure the destination rather than assuming it, and assert the premise (the flight has not settled) instead of hoping for it. `vi.waitFor` takes an explicit `{ timeout }` sized for a runner several times slower than a laptop — its 1,000 ms default is not that. A test whose remaining cost is real work declares its budget inline (`}, 30_000)`) with one line naming the work; `@glyphcss/maps`' package floor is 30 s (`vitest.config.ts`). `map.idle()` deliberately does NOT time out: a widget that never goes quiet is a real hang, and reporting it as a settle is the same lie a fixed sleep tells. Migration is unfinished — 45 of `@glyphcss/maps`' `widget.*` test files still contain a `setTimeout` (some legitimately), and 69 of its 83 `vi.waitFor` calls still ride the 1,000 ms default; convert the ones you touch.

## Style / process

- No time estimates in planning docs. This is agentic engineering, not team scheduling.
- Prune superseded content from long planning docs as you go — don't just append.
- No half-finished features, no speculative abstractions, no defensive code for cases that can't happen.
- Comments explain *why* (a constraint, a browser quirk, a non-local invariant), never *what*.
