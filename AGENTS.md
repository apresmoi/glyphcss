It states the current design and the rules we work under; if a request conflicts with one of them, push back before doing it.

Design rationale, measurements, and per-feature deep dives live in `docs/design/*.md` (index at the end). ## What this repo is

`glyphcss` is an ASCII polygon-mesh renderer for the DOM. It projects 3D meshes to 2D and rasterises them as monospace text inside a single `<pre>` element. No WebGL, no canvas-per-frame, no per-polygon DOM nodes.

Originally forked from polycss (a CSS-based polygon paint engine). The mesh math, OBJ/glTF/GLB parsers, scene composition tree, camera math, and input controls carried over intact. The paint backend is entirely new: the rasteriser walks all polygons, fills a `cols × rows` character grid, and writes one text string to `<pre>.textContent`.

Monorepo layout (pnpm workspaces):

| Package | npm name | Role |
|---|---|---|
| `packages/core` | `@glyphcss/core` | Pure math: Vec3, Polygon, scene, camera, mesh ops, parsers. Zero browser globals. (`project()`/`math/projection.ts` was removed with no BC shim — use each camera's own `.project()`.) |
| `packages/glyphcss` | `glyphcss` | Vanilla renderer + custom elements (`<glyph-scene>`, etc.). Owns the ASCII rasteriser, custom element definitions, and imperative API. |
| `packages/react` | `@glyphcss/react` | React components + hooks. Thin wrapper over core + glyphcss. |
| `packages/vue` | `@glyphcss/vue` | Vue 3 mirror of the React package. |
| `packages/compile` | `@glyphcss/compile` | Build-time static compiler: 3D mesh → static `<pre>` ASCII. Vite plugin, CLI, Node API. Node-only (fs); reuses `compileScene` (pure) from glyphcss. |
| `packages/effects` | `@glyphcss/effects` | Framework-agnostic spatial effect definitions and stock surface/scene effects. Depends on glyphcss's generic effect protocol; never owns the renderer or animation clock. |
| `packages/maps` | `@glyphcss/maps` | Geographic data → glyphcss. Raster `source → sample → classify → compile` pipeline, projections, relief meshes, TopoJSON/PMTiles/MVT providers, and `createGlyphMap` (the interactive widget with the full layer vocabulary). Root entry is pure/browser-safe; `@glyphcss/maps/node` carries fs-backed readers (never `gdal-async`). |
| `packages/fonts` | `@glyphcss/fonts` | Font/text → extruded polygon meshes. Emits Z-up meshes (world Z = letter height, Y = letter width, X = extrusion depth). A camera viewing flat unrotated text needs `rotX: 90`; `website/src/components/WordArtWorkbench` is the reference consumer. Authors UVs on every polygon (planar caps, strip walls). |
| `website` | `@glyphcss/website` | Astro + Starlight docs site. Not published. |

Public API is **mirrored** across React and Vue. Adding a hook on one side without the matching composable on the other is not acceptable (see "Cross-package discipline").

### Three-like parity surface

The native API keeps glyphcss/voxcss conventions. For Three.js ports, explicit `*/three` subpaths exist:

- `@glyphcss/core/three` — pure Three-like math wrappers and transforms.
- `glyphcss/three` — the core Three-like surface plus `compileScene` and geometry helpers.
- `@glyphcss/react/three` and `@glyphcss/vue/three` — mirrored `GlyphThreePerspectiveCamera`, `GlyphThreeOrthographicCamera`, `GlyphThreeMesh`.

These subpaths use Three-compatible names and units (`Vector3`, `Euler`, `Object3D`, `PerspectiveCamera`, `OrthographicCamera`, `DirectionalLight`, `AmbientLight`; radians; Y-up; Three frustum semantics). They are adapters, not a Three.js dependency. Geometry converts to native coordinates via `transformPolygonsToGlyph` with the Y-up → Z-up axis map `[x, -z, y]` so winding and Lambert lighting stay right-handed. `DirectionalLight.toGlyphDirectionalLight()` converts Three's `target → position` vector into the native source-vector convention.

## Rendering model

**One render pass → one `<pre>.textContent` assignment.** On every camera or scene change the rasteriser walks all mounted meshes in scene order, projects vertices through the camera, fills a `cols × rows` grid (per-cell depth test, glyph picked by render mode), joins the cells into one string, and writes it exactly once. No per-polygon DOM, no CSS `matrix3d`.

**Post-rasterize cell hook.** A scene's optional `transformCells(grid, layer?)` runs after rasterization and depth testing but before stringification. It receives a `CellGrid` (in solid mode with requirement-gated `shade`/`worldPosition`/`normal`/`surfaceUv` buffers; `NaN` = unavailable) and a `GlyphTransformCellsLayer` (`{ detail, mesh?, density?, viewport?, cellToSceneGrid }`) identifying which output grid it was handed; the hook must tolerate `undefined` for the second argument. Still one write per `<pre>`.

**Per-cell textures.** A polygon carrying `uvs` + `texture` (and a sampler for that key) is sampled PER CELL in solid mode: the texel multiplies the cell colour AND folds its luminance into the `intensity` that picks the glyph, so a texture reads as character variety and survives `useColors: false`. `Polygon.textureWrap` is honoured per cell (`repeat` / `mirrored-repeat` / default `clamp-to-edge`), so a face's UVs can carry a real TILE COUNT and one small image tiles across it — `@glyphcss/maps`' building facades are the consumer, and it is the difference between 1 image and 101. A triangle CLIPPED against the near plane rebuilds its sampler context from the clipped UVs, so a textured surface the eye straddles (the road you are standing on) keeps its texture instead of falling back to flat colour. `scene.setTextureSamplers(map | null)` supplies decoded pixels directly, keyed like a `texture` URL and merged over anything the scene decoded itself — the path for a PROCEDURAL texture, with no fetch, no canvas, and therefore no browser requirement.

**Semantic output.** `scene.getGlyphSemanticCellFrame()` is an immutable base-grid snapshot of the depth-winning polygon → surface → instance → class lineage, derived from the rasterized winner buffer (never a second projection); `null` in visible mode; detail-layer cells excluded. The model-control tensor is a 17-channel NCHW keyframe (23 in temporal form); missing UVs are `NaN` in raw frames and zero + `surface-uv-valid = 0` in tensors.

**Retained Glyph Effects.** `scene.addEffectLayer(definition, options)` mounts ordered scene-root appearance programs with no extra DOM. The first geometry render retains an immutable `CellGrid` per output; changing `params`/opacity/blend/order/enabled recomposes from those grids without re-projecting. `params` has stable identity and schedules a coalesced transaction. Effects run before `transformCells`. With no effect and no hook, the direct renderer is byte-identical and allocates nothing extra. Compositor supports `over`/`replace`, `"surfaces"`/`"viewport"`/mesh-handle(s) targets, and the requested inputs `baseColor`, `baseShade`, `depth`, `normal`, `worldPosition`, `objectPosition`, `objectExit`, `uv0`. Hard requirements are solid-mode-only; `optionalRequirements` and `dynamicRequirements(params)` degrade in wireframe/voxel. Scene-image sampling, scratch buffers, and static export of a mounted effect reject explicitly.

**Per-object targeting.** A `GlyphMeshHandle` or array target normalizes at mount to an immutable id set (`setOptions` with a different set throws — remove and re-add). Mechanism is per-cell `targetCoverage` from `CellGrid.winnerMesh` (solid-only; elsewhere the layer is inactive, never a throw). Later scene-wide layers composite over targeted ones by design. React/Vue diff array targets by id set.

**`program` / `colorProgram`.** Opaque definition-owned payloads on `GlyphEffectDefinitionLayerOptions`, forwarded unchanged, validated once at mount via the definition's `validateProgram`/`validateColorProgram`, immutable after mount (imperative `setOptions` throws; wrappers forward at creation only). glyphcss never interprets them — `@glyphcss/effects` depends on `glyphcss`, never the reverse.

**Stock effects (`@glyphcss/effects`).** Matrix rain, flow text, scan, wipe, scramble, glitch, noise dissolve, ripple, field synth; `GlyphRamps`. Package owns no clock — apps drive `time`. Field-synth is the large one: up to `SYNTH_VOICES = 9` voices (`fieldN`/`waveN`/`freqN`/`ampN`/`angleN`/`originU/V/WN`/`dutyN`/`phaseN`/`iterN`), three voice layers, `combine` incl. categorical `argmax`, `space: "auto" | "surface" | "scene" | "object"`, `subcellRes: "1x1" | "2x4" | "ink"`, `render: "paint" | "carve" | "xray"`, SDF voices (`gyroid`/`menger`/`sierpinski`, `step` wave), sphere tracing for qualifying SDF programs, and a public field-program IR (`buildGlyphFieldProgram`, `validateGlyphFieldProgram`, `evaluateGlyphFieldProgram`, `marchGlyphField`, `integrateGlyphField`, `glyphFieldStepCount`). Every `validateParams` throw carries a rule id from `GLYPH_FIELD_SYNTH_VALIDATION_RULES`. Schema key families are append-only (the `/synth` URL codec decodes positionally). The `/synth` website page is the front-end. Full semantics: `docs/design/effects.md`.

### Per-mesh detail layers

By default every mesh renders into the shared base `<pre>`. A mesh pops into **its own silhouette-fitted, CSS-translated `<pre>`** when it declares any of: `density` (multiplier, isotropic) or `fontSize`/`lineHeight`; `transparent: true` (x-ray: neither occludes nor is occluded); a `mode` that genuinely differs from the scene's; `glyphPalette` (solid ramp only); `ambientIntensity`. Browser-only; works with every camera; detail grids clamp to the viewport. This is a per-mesh property on the flat mesh list, not a group concept. Each distinct mode is a full extra rasterizer pass — reach for it per layer, not per mesh.

- **`detailGroup`** — detail meshes naming the same string share ONE `<pre>`/pass/occlusion id (removes the inter-mesh seam at shared edges). Never separates a mesh by itself. Members must agree on every layer-level option or a `RangeError` names the group and field. `@glyphcss/maps` groups raster tiles per tier.
- **Cross-layer occlusion** — opaque meshes occlude across `<pre>`s via a shared id-map built at the scene's supersample resolution (`computeOcclusionIds`); detail layers render at `supersample: 1` and sample it. A sub-cell depth-gradient refinement closes the ownership-vs-coverage seam; it is skipped when any group sets `occlusionPriority`/`occlusionContourPx`. Textured polygons claim only opaque texels (alpha-aware). Self-disables at zero cost when no opaque detail mesh exists.
- **Claim shaping** (solid, opaque meshes only): `occlusionPriority` (class beats depth), `occlusionClaim: "alpha" | "geometry"`, `occlusionContourPx` (coverage-aware claim with a screen-px margin, expensive — fine raster for every group whenever any group sets it).
- **Cross-scene occlusion** — producer `getOpaqueCoverage()` → consumer `setForeignOcclusion(coverage | null)`; solid-mode only; a plain-mesh producer needs `trackOpaqueCoverage: true`.
- **Meshless viewport overlays** — `scene.setViewportOverlayDensities([...])` adds transparent full-viewport output grids at `density×` resolution, painted only by `transformCells` (`layer.viewport === true`), each carrying its own geometry depth pass. `@glyphcss/maps` stroke layers with `density !== 1` are the consumer.

All of these mirror on React/Vue `<GlyphMesh>`/`<GlyphScene>` and the custom elements (kebab-case attributes); scene-handle methods need no wrapper. **Static compile takes a flat polygon list and cannot represent detail layers.** Details and measurements: `docs/design/detail-layers.md`.

### Render modes

| Mode | How cells are filled |
|---|---|
| `wireframe` | Polygon edges rasterised as ASCII rules; glyph weight scales with edge prominence |
| `solid` | Filled cells; glyph picked from a `CharRamp` by Lambert-shaded intensity |
| `voxel` | Cube-aligned geometry; face normals drive glyph selection |
| `ink` | Silhouette + crease outline only; oriented glyph (`_ / \| \ - ‾ ▏ ▕`) traces the smoothed contour tangent |

All four are runtime modes. Scene options layered on top, each a documented no-op outside its listed modes:

- **`glyphPalette`** — named solid ramps; `"dense"` is printable-ASCII-only by design for sub-2px cells and ASCII-only outputs. Do not add Unicode to it.
- **`charMode: "ascii" | "braille" | "halfblock" | "quadrant"`** — braille is wireframe-only (2×4 dot mask); halfblock/quadrant are solid-only two-colour-per-cell encoders (`encodeGlyphBuffersDual`), no-ops with `transformCells`, `temporalBlend`, or `solidWeightRamp`. Reachable from `compileScene`/`GlyphSceneStatic`.
- **`wireframeJunctions`** — ascii-wireframe-only box-drawing resolve pass for joints. Runtime-only.
- **`solidWeightRamp`** — `(glyph, weight)` steps from `calibrateWeightedGlyphRamp`, replaces the solid ramp and adds `font-weight` to spans (bold never changes monospace advance). Reachable from `compileScene`.
- **`hiddenLines: "show" | "hide"`** — wireframe uses a slope-scaled depth bias against a surface prepass (bias 0.03, slope 0.5, internal); `ink` uses an identity-based test (`buildInkOcclusionMap`, own-neighbourhood exemption) — never a flat bias, which fails across world scales. No-op in solid. Reachable from `compileScene`.
- **`colorTolerance`** (0–765 redmean) — merges same-glyph runs within a colour distance; one `colorRunExtends` backs all four coalescers. Composes with TAA; no-op under semantic output. Forwarded by `compileScene`; not by the export builders.
- **`colorEncoding: "spans" | "atlas"` + `atlasPalette` + `fontAtlas`** — atlas encodes `(glyph, palette slot)` as PUA code points against a checked-in COLR/CPAL font (`GLYPH_FONT_ATLAS` 212 glyphs/30 slots, `GLYPH_FONT_ATLAS_ASCII` 94/68); zero spans. Library default is `"spans"`; the website defaults to `"atlas"` via `CSS.supports("font-palette", "--x")`. Palettes are median-cut quantized and causally pooled per scene with a transaction latch; readiness needs a real COLR paint probe AND `font-palette` support; the per-`<pre>` `font-family` pin follows the encoding a frame actually produced; out-of-atlas glyphs latch the scene to spans until a relevant `setOptions`. `fontAtlas` is fixed at creation. Compiled output must include the CSS itself (`loadGlyphAtlasFontFaceCss`, `buildGlyphAtlasFontPaletteValuesCss`). Breaks find-in-page; accepted.

Rationale, constants, and measurements for every option: `docs/design/render-modes.md`.

### Shadows

Opt-in: set `shadow: GlyphShadowOptions` on the scene, then `castShadow`/`receiveShadow` per mesh (both default false; `GlyphGround` defaults `receiveShadow`). Shadow-map technique, so self-shadowing is free.

| Option | Type | Default | Description |
|---|---|---|---|
| `shadow.color` | `string` | `"#000000"` | Shadow tint hex color |
| `shadow.opacity` | `number` | `0.25` | Darkness 0..1 toward `color` |
| `shadow.lift` | `number` | `0.05` | EXTRA absolute-world-length depth bias, on top of the derived acne guard below. `0` is a valid and often correct answer |
| `shadow.maxExtend` | `number` | `2000` | **Declared but never read.** The light-space volume is fitted to the AABB of the caster vertices themselves (`buildShadowMap`), so this option has no effect on any render; the type and the `shadow-max-extend` attribute still accept it. Removing it is a public break and has not been taken. |

That volume's PAD is relative to the caster extent, not a fixed world length: 256 texels are divided across it, so an absolute term sets a smallest scene the shadow map can resolve at all.

**The caster set is the SCENE's, not the pass's.** A frame rasterizes the base grid plus one grid per detail layer, and the shadow map used to be built from whichever polygons the pass in hand held — so a mesh that separated for a reason with nothing to do with shadows (`density`, a private `mode`, `glyphPalette`, `ambientIntensity`, `transparent`) silently stopped casting, and one that separated stopped receiving. `castShadow` meshes are now collected once across every mesh in the scene (`GlyphShadowCasters`) and the built map is shared across the frame's passes through a `GlyphShadowMapCache` holder, so one light gives one light-space volume to all of them: a detail layer casts onto the base grid, the base grid casts into a detail layer, and two detail layers cast onto each other. A detail pass's `receiveShadow` is read PER MEMBER, not off the group's shared transform — it changes shading, not how the group rasterizes, so a `detailGroup` may legitimately hold a receiver beside a non-receiver. Both are supplied only when `scene.shadow` is set and something actually casts, so the shadows-off path is byte-identical and allocates nothing. Gate: `@glyphcss/maps`' `widget.shadowDensity.test.ts` (casting out of a detail layer and receiving into one are separate clauses, so neither can hide behind the other).

**A `transformCells` stamp cannot receive.** The shadow term is consumed inside `scanFillTriangle` when a cell's final colour is computed, and no per-cell occlusion fraction survives into `CellGrid` — the requirement-gated `shade` buffer is the LIGHT term, not the shadow one. Anything painted by the hook instead of by geometry (`@glyphcss/maps`' `line` and `contour` layers) therefore keeps its flat colour under a shadow that darkens the surface around it.

**The acne guard is derived, slope-scaled and internal** (`SHADOW_SLOPE_BIAS_TEXELS` = `1.25`, `rasterize.ts`). Self-shadow acne here is a POSITION quantization artefact, not a depth-precision one — the buffer is `Float64Array`; a receiver reads the map at `tu = lu | 0`, i.e. up to one full texel away in each light-space axis, so its own depth is compared against a copy of itself taken from up to `|dd/du| + |dd/dv|` away. One texel of each is the exact bound, so `1.0` is the smallest guard that provably closes it; measured, a lone self-receiving box goes from 450 of 450 lit roof cells claimed at `0` (`floor`, not `round`, makes the error systematic — it darkens almost uniformly rather than speckling) to 0 at `1.0`, and the first real shadow loss is at `1.5` (a 4 m building inside a 1.8 km caster AABB). `1.25` sits between the two bounds. `lift` stays the caller's own EXTRA absolute term; its `0.05` default is a room-scale assumption (`@glyphcss/maps` sets `0` because a map has no absolute length to offer, see its own section).

### Hotspots

3D anchors → positioned 2D hitboxes. The rasteriser projects `Hotspot.at` and returns a `HotspotCell` (col, row, depth, visible); the consumer positions its own `<div>`. The rasteriser never emits the DOM node.

The injected `.glyph-hotspot` rule defaults to `user-select: none` (`-webkit-user-select: none`), same as `.glyph-output` and for the same reason — the hotspot div sits `pointer-events: all` above the drag surface, so without this a drag on a hotspot's label selects its text instead of orbiting the camera. `.glyph-hotspot.glyph-selectable` re-enables `user-select: text`, mirroring `.glyph-output.glyph-selectable`. `pointer-events: all` is unchanged — hotspots must stay clickable; only selection was the defect.

## Compilation (static & interactive)

`rasterize` is pure, so a scene renders at build time or on the server; the render *is text*.

- **`compileScene(opts)`** (`glyphcss`, pure) — polygons + camera + options → `<pre>` string, byte-identical to the runtime render for the same inputs. Foundation for every adapter.
- **`@glyphcss/compile`** — Node adapters: `loadMeshFromFile`, `compileFile`, Vite plugin (`?glyph`), CLI (`glyphcss`), `compileInteractive`. `writeGlyphControlMaps` defaults to the frozen `glyph-control-export/v1` contract; `appearanceRgb: "albedo-and-target"` opts into `v2`.
- **`GlyphSceneStatic`** (React + Vue) — SSR/SSG `<pre>`, no client runtime.
- **`buildGlyphFramesExport`** — turntable of `frameCount` full renders cycled by a pure-CSS `steps()` animation. Payload grows linearly with frames.
- **`buildGlyphInteractiveExport` / `glyphCodepenPrefill`** — self-contained CDN snippet; declared `interactions` drive both the wired control and the decimation budget; optional `effect: { id, params, blend?, timeScale? }` mounts a **stock** `@glyphcss/effects` layer from the CDN. The export path for a moving-camera or volumetric/carve/xray effect scene.
- **`buildGlyphFieldSynthStaticExport`** (`@glyphcss/effects`) — effect-only, static-camera field-synth scene → inlined-JS pen with zero runtime imports; verified byte-exact against the real renderer. Rejects `space: "object"`, carve/xray, `program`, and 3D-only voice params; `isGlyphFieldSynthStaticExportSupported(params)` is the matching predicate for UIs.

Mounted effects are otherwise runtime-only (no `compileScene`/frame-roll evaluation). Trade-offs and reject rules: `docs/design/compile.md`.

## Maps (`@glyphcss/maps`)

Pipeline: `source → sample → field → classify → bands → compile`. Everything public speaks lat/lng (`GlyphMapView = { center: [lon, lat], span, cols, rows }`, aspect-locked). Rotation and projection units are degrees (`glyphMapFromD3Raw` converts d3 radians and swaps to the package's `(Y, X)` world order).

- **Projections** are vertex transforms (`{ id, project, unproject, domain, exaggeration }`) plus optional CAPABILITIES — `visible(world, depthOf)` and `cameraForCenter`/`centerForCamera` (globe only). **Every projection-specific branch in the widget keys on capability presence, never on `projection.id`.** "Crop, don't clamp": `project()` returns `NaN` outside the valid window. `exaggeration` is READABLE (`1` = true scale) because it is a TERRAIN concept and `project` is the package's ONE elevation conversion: a TRUE-METRE quantity (a structure's height) reaches that axis through `glyphMapTrueScaleElevation(metres, projection)`, and nothing else can recover the factor — a sheet's `X`/`Y` are degrees and the globe's are Earth radii, so no probe of `project` says how much of its `Z` was exaggeration. Shared world frame: `X` north, `Y` east; `glyphMapGlobe` is the textbook right-handed sphere, pinned by `chirality.test.ts` against glyphcss's real camera. `website/scripts/bake-globe.mjs`'s own sphere negates `Y` (a known, unfixed mirror; `parity.test.ts` documents the exact sign flip).
- **Tiles** — `GlyphMapGeoTile` is vertex-centered `(cols+1) × (rows+1)` elevation, projected client-side, split at the antimeridian before projecting, baked as int16 `.bin` under a `version: 2` manifest (z0–z4 global, gitignored; `--fixture` for the vendored parity fixture). `glyphMapCuratedProvider` overlays deeper curated levels (Switzerland z5–z7) that degrade to ancestors, exposing `resolveTile` so siblings dedupe. Vector tiles use the SAME equal-angle quadtree addressing; `glyphMapTargetLOD` keys LOD on degrees-per-cell, never `camera.zoom`, and keeps the DEEPEST level when none is fine enough, so a shallower pyramid (borders stop at a curated z4 while terrain reaches z7) stops sharpening, never stops drawing. A tile-sweep's visibility test samples the tile's own bounds AND the VIEWPORT's own unprojected points (`viewportGeoSamples`) — never a single point: a 22.5° tile straddles a 3° viewport whenever that point lands within a viewport-width of a tile edge, and a nonzero `tilt` makes the visible window asymmetric (it reaches much further toward the horizon), so no box centred on `view.center` describes it.
- **Relief mesh** — `glyphMapPolygons(tile, projection, { resolution, colorSample, elevationBias })`; resolution is resolved per pyramid LEVEL (never per tile — cracks). Three tiers per raster layer: target LOD, a coarser fallback mounted first, and a permanent floor (capped to 32 quads/axis unless it is the target). Never a blank hole while panning. **A tier that is not the target LOD is a BACKSTOP and is mounted SUNK by `GLYPH_MAP_RELIEF_BACKSTOP_SINK_M` (20,000 m, via `elevationBias`), so it can never occlude the target tier.** All three tiers are opaque meshes in ONE scene — glyphcss's `occlusionPriority` orders layers, not meshes inside the base grid — and a coarse quad is not merely a blurrier fine one: its chord interpolates linearly across up to ~11 degrees, so where it straddles a coast it sits kilometres ABOVE the fine tier's sea floor, wins the shared depth test over open ocean and paints it in the colour of a block that is mostly land. That is the reported "the sea is basically GREEN" on `/maps`, measured over the Peru-Chile trench at 486 of 4,462 sea cells in a land band against 16 for the target tier alone; with the sink the combined render is cell-for-cell identical to the target tier alone at every view measured. The sink is a BOUND, not a tuning — it exceeds Earth's entire solid-surface relief (~19,784 m), which bounds how far any coarse chord can rise above a finer sample of the same field — and it is in METRES so it is exaggeration-invariant. Raising the floor's own resolution is NOT a fix (231 stolen cells even at its finest 2-degree quads), and neither is a colour rule: no single colour per 11-degree quad is right, so `corner-mean` merely trades sea-painted-as-land for land-painted-as-sea. `elevationBias` never touches the elevation `color` is handed. Gate: `widget.backstopOcclusion.test.ts`. **A quad's COLOUR elevation is the MEDIAN of the tile's own full-resolution vertices over the block the quad covers (`colorSample: "median"`, the default), not the mean of its 4 corners** — so colour fidelity does not degrade with mesh resolution, and a quad straddling a coastline can never be classified into a band the terrain's majority doesn't hold. The mean could: it averages deep ocean with high land and falls below sea level, painting bathymetric blue over land (measured on the real ETOPO1 pyramid — the floor tier's quad over Bogotá averaged −155 m across corners on terrain that is 379/441 samples above sea level, Quito's −718 m; 41 of 163 majority-land floor quads worldwide were painted as water). The median's guarantee is exact, not statistical: more than half the covered samples at or above sea level ⇒ the sample at `n >> 1` is too. Point-sampling the quad centre was measured and is WORSE than the mean (it lands in rivers/inlets). `colorSample: "corner-mean"` is required by, and used only by, the `heatmap` layer, which keys a `Map` on that exact float to recover per-quad density. Gate: `mesh.seaLevelBand.test.ts` against the vendored real-ETOPO1 `fixtures/sea-level-band.json` (`bake-geo-tiles.mjs --fixture`).
- **Widget** — `createGlyphMap(host, opts)` owns one `createGlyphScene` (`map.scene` is the escape hatch), tile cache/diff/in-flight guard/180ms gesture-gated debounce, and one `requestAnimationFrame` motion loop (inertia, `flyTo`, `setProjection` blends) issuing at most one render per displayed frame — input handlers update state synchronously and only the render is deferred. Sheet projections **cover, not contain** (`getMaxSpan()`, pan clamp to a fixed point); an explicit `maxSpan` opts out. The widget remembers which `cameraForCenter` preimage an unclamped orbit drag is on.
- **Camera pitch (`tilt`)** — `tilt` pitches the camera ABOUT THE SURFACE POINT UNDER THE VIEW CENTRE with the pivot distance equal to the camera's altitude (Google Earth / Cesium), so `map.project(getView().center)` lands at the CENTRE of the grid at every pitch and every span, and the two feels fall out of ONE rule with no threshold: zoomed out the pivot is far below the camera relative to the view, so pitching swings the globe and the limb enters tangentially; zoomed in the pivot is directly beneath, so pitching reads as raising your head off the ground (what makes 3D buildings legible). Under the ORTHOGRAPHIC camera the pivot's distance along the view axis is unobservable (`project` is `R·(v − target)`, so a shift along the axis moves depth by a constant and col/row by nothing), so the model reduces EXACTLY to `camera.target = projection.project(lon, lat, 0)` — what a SHEET has always done, so one implementation serves both and the sheet pose is byte-identical (`rotX`/`rotY`/`target`/`zoom` pinned exactly). An orbit `tilt` still ADDS to `cameraForCenter`'s pitch (default `0`; a sheet's `tilt` IS `camera.rotX`, default `40`); only the pivot changed. `applyDragState` re-anchors the pivot on the centre the drag produced and subtracts the APPLIED pitch before `centerForCamera`. This replaced a model that swung the camera about the GLOBE'S CENTRE with `target: [0,0,0]`, which held the NUMBER in `view.center` stable while the PICTURE was `tilt` degrees of latitude away — measured at `tilt: 40` on 140x63: row 11.9 of 63 at span 140, −33.3 at 40, −827.9 at 3, −23,405 at 0.11 — and which six defects on this branch traced to. **`getMaxTilt()`** is the ceiling `setTilt` clamps to: the HORIZON ANGLE at the view's own scale, `asin(R / (R + h))` capped at `GLYPH_MAP_MAX_TILT` (85), where `R = |proj.project(lon, lat, 0)|` (the same origin-centred sphere `glyphMapGlobe.visible` already assumes) and `h` is the frame's world half-height `(rows·cellHeight/2)/zoom` — the host's rendered pixel height over `zoom`, so the ceiling is invariant to `cols`/`rows`/cell size exactly as `camera.zoom` is. `h` is the one modelling choice: an orthographic camera has no altitude, so the view supplies the only length it has. It gives ~21° at a 360° span (where 80° aims past the limb at empty space), ~50° at 40°, and the 85° cap by city scale; a SHEET has no limb so its ceiling is the cap at every span (capability, never `proj.id`). The clamp is non-destructive — the request is remembered, `getTilt()` reports the APPLIED pitch. Gates: `widget.tiltPivot.test.ts` (pivot at four spans, both signs, through-pole drag, sheet byte-parity, and the ceiling re-derived independently through `map.unproject`). **The GESTURE is Ctrl+drag / right-button drag, vertical, `GLYPH_MAP_TILT_DRAG_DEG_PER_PX` (0.5, MapLibre's own rate)** — `controls.tilt` (default `true`) is its own opt-out beside `drag`/`wheel`, plain drag is untouched, `contextmenu` is suppressed over the host while it is enabled, and the gesture emits no `click` and no inertia. It goes through `applyTiltState` (the state half split out of `setTilt`) plus `markMotionDirty()`, so it shares the ONE motion loop — never a second render path — and it accumulates from the APPLIED pitch, not the request, so it has no dead travel against a lowered ceiling while the remembered request still survives a zoom out and back. Gate: `widget.tiltGesture.test.ts`. The gesture's HORIZONTAL axis is `bearing` (below); one `controls.tilt` flag opts out of the whole stroke, because it is one press.
- **Camera bearing (`bearing`)** — the compass heading, degrees, that points UP on screen (`0` = north up, `90` = east up, i.e. the picture turns CCW as the number grows — MapLibre's convention; `setBearing`/`getBearing`, reported normalized to `[0, 360)`). It is **rotation about the SURFACE NORMAL AT THE PIVOT** — the same point `tilt` pitches about — NOT a roll about the view axis: the two are identical at zero pitch and diverge exactly where this exists, because a roll TIPS THE HORIZON on a pitched camera and no map product does that. Composition, in glyphcss's axis-swapped c-frame, is `M = E · Rot(uc, −bearing)` with `E = RotX(camera.rotX)·RotZ(camera.rotY)` and `uc` the pivot's local up (asked of the projection via `localUpDirection`, never hardcoded, so a `glyphMapFromD3Raw` projection and a `setProjection` blend both work). Right-multiplication is what keeps the horizon level — `up` is the rotation's own axis, so `M·uc = E·uc` for every bearing — and where the pivot is the view centre `E0·uc = ẑ`, so the whole thing reads `RotX(tilt)·RotZ(−b)·RotX(trueRotX)·RotZ(rotY)`: navigate, turn, pitch (the MapLibre/Cesium camera). It rides on `GlyphCamera.mat`/`useMat` (public, honoured by `project()`), so `rotX`/`rotY` keep their meanings underneath and `centerForCamera` still inverts the centre. **At bearing 0 NO matrix is installed** (`useMat` false, `mat` null) and render/`project`/`unproject`/`getMaxSpan`/`getMaxTilt` are bit-identical — gated three ways (a fresh map, an explicit `bearing: 0`, and one that went to 137 and back). Three things it touches: `applyDragState`'s ORBIT branch rotates the pixel delta by `+bearing` first (`bearingDragDelta`) or a turned map pans sideways — the sheet branch must NOT, since `screenToWorldDelta` probes the live camera and is already bearing-aware; `glyphMapHeadlightDirection` is NOT bearing-invariant after all (a normal-axis turn genuinely moves the view axis, unlike the roll the audit assumed), so the headlight reads `(mat[7], mat[6], mat[8])` when a matrix is installed, which reduces algebraically to the Euler formula at 0; and the SHEET cover clamp DOES under-cover — the visible window is a rotated rect whose world-axis reach is `w|cos b| + h|sin b|` (worst at 45°), measured as a viewport corner falling off the map, so `spanCoverLimit`/`clampWorldToCover` take that AABB, with bearing 0 keeping the original expressions verbatim (`(a/b)/c ≠ a/(b·c)`). **The GESTURE is the horizontal axis of the same Ctrl+drag / right-drag stroke, `GLYPH_MAP_BEARING_DRAG_DEG_PER_PX` (0.8, MapLibre's own rate); drag RIGHT INCREASES the bearing**, turning the picture anti-clockwise, so the NEAR ground — the lower half of a pitched picture, the half the hand is on — follows the hand, and the Dock's `Bearing °` slider moves the map the same way the drag does (the opposite sign shipped first and was reported backwards). Both axes are live in one stroke (no axis lock), `controls.tilt` opts out of both, no inertia, same one motion loop. **`temporalBlend` is the one known hole and it is in glyphcss, not here**: `rasterize.ts`'s TAA history camera rebuilds from `rotX`/`rotY` and drops `mat`/`useMat`, so a maps scene opting into `temporalBlend` would reproject against an unrotated frame — `@glyphcss/maps` never sets it, so nothing ships broken. Gate: `widget.bearing.test.ts` (the discriminator is up-at-the-pivot invariant while the heading turns, at pitch).
- **Projection transitions** — `setProjection(target, { durationMs })` blends via `glyphMapProjectionTransition` (plain lerp / scale-normalized lerp / spherical-cap unwrap, chosen by capability, anchored on the view centre) and schedules zoom on log-linear apparent size, never a lerp. Endpoint framings are assigned VERBATIM at `t <= 0`/`t >= 1` (`a + (b − a)·1` is not `b`), each endpoint's pitch is clamped to its OWN ceiling, and the applied pitch rides in the framing so a mid-flight drag subtracts back out exactly what was added. Gates: `widget.transitionContinuity.test.ts`, `widget.transitionAnchor.test.ts`.
- **Camera-following key light (`keyLight`)** — `GlyphMapOptions.keyLight` / `handle.setKeyLight`/`getKeyLight` pick who aims the scene's key light: `"fixed"` (the default — the widget never writes `direction`, byte-identical to before this option existed) or `"headlight"`, which points it along the camera's OWN view axis and rewrites it whenever the camera moves. `glyphMapHeadlightDirection(rotXDeg, rotYDeg)` is that vector, `n = (sin rotX cos rotY, sin rotX sin rotY, cos rotX)` — an orthographic camera's projected depth is LINEAR in the world point, so the direction that increases it fastest (i.e. where the camera is) is exactly that functional's gradient, which is also the same `n` `glyphMapGlobe.cameraForCenter` inverts; glyphcss's `direction` points from the surface TOWARD the light, so `+n` is the sign and a headlight at the framing for `(lon, lat)` equals the SUN direction for a subsolar point there (both proven in `widget.headlight.test.ts`, one against the real `createGlyphOrthographicCamera`'s depth). Like the sun it writes `direction` ONLY — `intensity`/`color` stay the consumer's — and **the sun outranks it**: a real terminator is a statement about the world, a headlight one about the viewer, so `keyLightDirection()` is `sunDirection() ?? headlight`. `getKeyLightDirection()` reports whichever owner is live (or `null`), and is the ONE call a consumer composing its own `directionalLight` write should read. This is what makes "everything lit, like a globo terráqueo" reachable: the whole visible face is lit with no terminator anywhere, while Lambert still varies per face so TERRAIN RELIEF survives — the alternative, pure ambient, also removes the terminator but gives every face the same shade and renders the map as flat paint (rendered, not argued: one distinct colour across the entire disc, and the relief clause of the test goes red on it). `applyKeyLight` is called ONLY immediately before a synchronous `scene.rerender()` (construction, `setView`, `setTilt`, `resize`, the one motion-loop render, the projection-transition frame) and no-ops when the direction is unchanged: `scene.setOptions` invalidates glyphcss's shading cache and schedules a MICROTASK render, so writing it from an input handler instead would buy a whole extra grid render per pointer event — exactly the discarded work the widget's single motion loop exists to remove. **Measured** (`bench/maps-render`, spans, 1440x900, 140x63, same build with `mapKeyLightForSunMode` pinned to `"fixed"` as the baseline): renders/frame stays exactly `1.00` on every scenario, confirming the write-then-render discipline buys no extra render; a pure zoom is FREE (wheel base-raster 3.33 -> 3.28 ms, inside noise — a zoom does not rotate the camera, so the equality check no-ops and the shade cache survives); the price is paid only where the camera actually TURNS, and it is large — orbit base-raster 9.11 -> 16.52 ms (55.9 -> 42.9 fps), drag 9.10 -> 17.63 ms (54.4 -> 40.5 fps), flyto 5.08 -> 6.86 ms. That is inherent, not a wiring defect: glyphcss's per-triangle shade cache is built to survive a moving camera under a STATIC light, and a light bolted to the camera invalidates it every frame, re-lighting all 65,312 polygons. It is partly self-funding — an evenly lit globe has longer same-colour runs, so commit-write drops (orbit 2.21 -> 1.53 ms, wheel 1.19 -> 0.35 ms) and flyto/wheel end up FASTER overall (73.9 -> 77.4 and 93.8 -> 112 fps). A user dragging a heavy globe has `interactiveDownscale` (`/maps`' "Drag density") as the existing lever; no angular quantization of the direction is shipped, because it would save least exactly when the camera moves fastest. `/maps`' "Full" sun button is the reference consumer — `mapKeyLightForSunMode` turns it into `"headlight"` on an ORBIT projection only (a sheet's faces all point roughly `+Z`, so it has hillshading, never a dark hemisphere, and aiming its light down the view axis would only take away the Azimuth/Elev control that does real work there), and the Dock dims Azimuth/Elev with a reason in exactly the cases something else owns the direction, which reduces to `isOrbitProjectionId(projectionId)` in every sun mode.
- **Real-sun lighting** — `sun.ts` is the pure, clock-free solar math (`glyphMapSubsolarPoint(date)`, NOAA's formulation INCLUDING the equation of time — worth ±16 min ≈ ±4° of longitude, so dropping it is a visible error; verified against the published equinox/solstice declinations, both EoT extremes and a published subsolar point). `GlyphMapOptions.sun` / `handle.setSun`/`getSun`/`getSunDirection`/`getSubsolarPoint` and a `"sun"` event drive three modes: `"off"` (the default — no light write, no timer, no hook, byte-identical to before), `"realtime"` (re-resolved on the widget's own `setInterval` at `GLYPH_MAP_SUN_TICK_MS` = 30 s, so the terminator keeps advancing at 0.25°/min; snapped immediately on entering the mode, cleared in `destroy()`), and `"manual"` (pinned to one instant, no timer). **Two mechanisms, chosen by projection CAPABILITY, never `projection.id`**: an ORBIT projection gets a real `directionalLight.direction` = the outward unit vector at the subsolar point (`normalize(project(subLon, subLat, 0))` — glyphcss's source-vector convention), and Lambert draws the terminator, so no cell hook is installed there at all; a SHEET has one normal everywhere and cannot express a terminator with a directional light, so it gets a per-cell day/night term (`stampGlyphMapNight`) through the SAME single composed `transformCells` hook `line`/`contour` use, stamped BEFORE the strokes so a border stays legible at night. The sheet term darkens COLOUR only (never the glyph, which carries terrain shape) and so is invisible under `useColors: false`. Darkness is quantized to `GLYPH_MAP_NIGHT_LEVELS` (4) purely for cost: a continuous ramp gave almost every cell its own colour and destroyed span-run merging — measured 1,679 spans / 9.40 ms per render at 160×64 on the worst case (whole world, equinox, where the polar rows sit inside the twilight band all the way around) against 123 spans / 1.00 ms with no sun; 4 levels is 604 spans / 3.32 ms. The widget only writes `direction`; `intensity`/`color` stay the consumer's, and `/maps`' own `buildMapLighting` reads `getKeyLightDirection()` (not `getSunDirection()` — that answers `null` while a headlight owns the light, so the page would clobber it) fresh at write time so page and widget can never disagree.
- **Cast shadows (`shadow`)** — `GlyphMapOptions.shadow` / `handle.setShadow`/`getShadow` (a `GlyphMapShadowOptions` = `{ color?, opacity?, lift? }`, or `null`). OFF by default and byte-identical there — no `shadow` key reaches `createGlyphScene` at all, and the bench's fidelity digest for the default page is unchanged by the feature (`c619778796…` for shadows off, shadows on with no caster mounted, and no token at all). What the widget adds on top of glyphcss's shadow map is the three things a caller here cannot supply. (1) WHO: `GLYPH_MAP_SHADOW_CASTERS` = `fill-extrusion` + `model`, `GLYPH_MAP_SHADOW_RECEIVERS` = those two PLUS `raster` + `fill` + `heatmap`, set as per-mesh `castShadow`/`receiveShadow` UNCONDITIONALLY at mount (glyphcss reads them only inside a pass carrying `scene.shadow`, and `isDetailMesh` ignores them, so they are inert while shadows are off — which is what makes the toggle ONE `setOptions` rather than a remount of every mesh). The sets OVERLAP, which is what makes a building shadow the building next to it; they were disjoint at first, and that made the case a reader notices first in a city impossible by construction. What made the overlap safe is not a tuning but glyphcss's derived, slope-scaled acne guard (see "Shadows"): the error is a function of the shadow map's own texels, so it cannot be expressed as the world-unit `lift` this package has no scale to supply. TERRAIN still never casts — the shadow volume is fitted to ALL casters and a raster layer keeps a global floor tier mounted, so 256 texels would span the Earth. (2) The BIAS: `GLYPH_MAP_SHADOW_LIFT` stays `0`, now because the guard is already correct and `lift` is only an EXTRA absolute length — glyphcss's own `0.05` is 5% of the globe's radius (318 km) and erases every shadow (gated: handing `lift: 0.05` through changes not one cell), and any nonzero `b` erases every caster standing less than `b / sin(altitude)` above its receiver, i.e. the short buildings first and worst at a LOW sun. (3) The DIRECTION is NOT an option: shadows fall along the scene's own `directionalLight.direction`, which is whatever `getKeyLightDirection()` reports, so one vector lights the scene and casts its shadows. **A `keyLight: "headlight"` is therefore incompatible with visible shadows, exactly and unavoidably**: a headlight is the camera's view axis, and an orthographic camera's screen position is the component PERPENDICULAR to that axis, so displacing a caster along it moves its shadow zero columns and zero rows — every shadow lands in its own caster's cells (measured: 27 surviving fringe cells against 535 under a fixed light). `/maps` opened on a globe with Sun "Full", which is a headlight, and so showed no shadow anywhere; `mapKeyLightForSunMode(mode, projection, shadows)` now drops the headlight whenever shadows are on and the Dock un-dims Azimuth/Elev in that one case (`mapDirectionLocked`). Shadows are NOT base-grid only: glyphcss builds one shadow map per frame from every caster in the SCENE (see "Shadows"), so a layer separated by its own `density`, `renderMode` or `glyphPalette` casts and receives like any other. That is what `/maps`' OSM card needs — it gives its whole stack ONE density slider, so a reader who moves it past 1 separates the buildings that cast AND the landuse that receives in the same gesture, and the toggle used to go silently inert (measured on the reported link's own `osmDensity: 2.9`: 4,469 changed cells now, exactly 0 before). What a stamped `line`/`contour` still cannot do is RECEIVE — a stroke's colour is written flat into the cell after shading (`grid.color[idx] = color`), so a road is never darkened by the building beside it; that is a known, documented inconsistency, not a tuning. Measured (`bench/maps-render`, spans, 1440x900, 140x63, `--demo-layer fill-extrusion`): a flat +2.5 to +3.0 ms per render — orbit 19.60 → 22.06, drag 21.54 → 24.04, wheel 4.58 → 7.53, flyto 9.39 → 12.27 — so it costs most where the frame was cheapest (wheel +64%, orbit +13%). Making the casters receive as well is inside that measurement's noise (989 polygons / 845 caster polygons at 140x63: 0.29 ms shadows off, 0.74-0.81 ms ground-receives-only, 0.75-0.86 ms casters-receive-too). Solid down to ~10 degrees of sun altitude; below that the shadow dithers and by ~5 degrees it is a stipple that loses about half its cells, on a lit/shadowed contrast that is by then near-invisible anyway. Gate: `widget.shadow.test.ts`. Full record: `docs/design/maps.md`.
- **Street-level walk (`setWalk`/`getWalk`)** — a GATED mode: a positioned PERSPECTIVE camera at eye height (1.7 m), walked with WASD/arrows (Shift jogs) and aimed by dragging. OFF by default and byte-identical there — no perspective camera is constructed and every branch is guarded on it. Almost nothing is new, because the pose is the EXISTING orbit camera read at its limit: `tilt` pitches about the surface point with a ceiling of `asin(R/(R+h))` that opens to 90° as the altitude goes to zero, so `GLYPH_MAP_WALK_HORIZON_TILT_DEG` (90) looks dead ahead and `tiltRequest`/`appliedTilt` IS the walker's pitch (clamped to a NECK, ±`maxPitch` 55°, not to the horizon ceiling); `bearing` IS the heading and keeps the horizon LEVEL by construction; `view.center` IS where they stand; `view.span` DESCRIBES the horizon footprint (`glyphMapWalkSpan`) so tile LOD, the URL codec and every readout keep working, and the wheel is a no-op rather than a repurposed FOV control. What IS new is the POSITION (an orthographic camera has no eye) and the LENS: `perspective = 5000·near`, `zoom = 25·W/(tan(fov/2)·P)`, and the eye sits `P/BASE_TILE` behind `target` — `BASE_TILE` PROBED off the live camera's affine `eyeDepth`, never assumed. TRUE metres (eye height, near plane) convert through `glyphMapTrueScaleElevation`, the same exemption an extrusion's height takes; the walker stands on `groundElevationSampler`'s terrain. **`glyphMapGlobe.visible()` is NOT generalised** — it is derived for the orthographic camera and reports the ground one metre in front of a walker invisible, and its consumers (tile sweep, `unprojectSphere`, wall culling, markers) would all fail together. Instead the horizon is LOCAL: `GLYPH_MAP_WALK_FAR_M` (400 m), which is the tile budget (4 z14 tiles measured, against 36 for the true 4.65 km horizon and 1,849 at 100 m eye height) AND the aesthetic cap in one number. Three local-horizon branches were built and DROPPED as measurably redundant (`orbitCandidateGeoBounds`, `isBoundsVisible`, `nearSidePredicate`); only `project()`'s is load-bearing. Orbit-only (`setWalk` throws a `RangeError` on a sheet — a sheet's X/Y are degrees and Z Earth radii, so a 20 m building draws 85× too short); `setProjection` LEAVES walk mode; leaving restores `view`/`tiltRequest`/`appliedTilt`/`bearing`/`orbitRotation` verbatim and the orthographic camera object is never written while walking, so the rendered bytes come back exactly. Road ribbons and collision are out of scope; the ground between the buildings is flat. It is a CAMERA mode, not a layer feature: what it renders is whatever is mounted, and the walker's height comes from `groundElevationSampler` (any `raster` layer, finest tier first; the datum with none), so walking a bare ridge is the same code path as walking a street. `/maps`' DOCK View folder is the reference consumer — the Walk row sits under Tilt/Bearing (which it takes over) and is DIMMED WITH ITS REASON on the row, `mapDirectionLocked`'s idiom; the gate (`mapsWalk.ts`) is the globe plus span ≤ `GLYPH_MAP_WALK_MAX_ENTRY_SPAN_DEG` (0.05°) and says nothing about which layers are on — the ALTITUDE is what makes the mode safe, and it holds over terrain identically. Gates: `widget.walk.test.ts`, `mapsWalk.test.ts`, `mapsKit.viewFolder.test.tsx`.
- **Layers** — `background`, `raster`, `line`, `contour`, `fill`, `fill-extrusion`, `symbol`, `circle`, `heatmap`, `model`. Mesh-backed layers forward `density`, `renderMode` and `glyphPalette` to glyphcss's per-mesh options (edge modes mount `transparent`); `fill-extrusion` additionally takes `facade` (window bays across and floor bands up each WALL, from the wall's own metres and the feature's own `heightProperty` — one generated 12x12 tile repeated via `textureWrap`, registered on the scene by the widget itself and never fetched) and `colorVariation` (deterministic per-feature tone around `color`, seeded from the feature's own identity). Both default off and are byte-identical there. They exist because an untextured flat-roofed box is ONE Lambert value per face, so at eye height a block of them is two tones and a wedge; measured on the real 900 m / 3,005-building Zurich scene at 140x63, the facade costs +0.96 ms (3.25 -> 4.21 ms) and turns the solid ramp's per-cell dither into runs (mean run length 1.83 -> 2.99); `line`/`contour`/`symbol`/`circle` carry no `renderMode` or `glyphPalette`. `glyphPalette` is the CHARACTER ramp and composes with — never replaces — a `raster` layer's `colors` (the elevation-band COLOUR ramp). **Both appearance options are FREE when they name what the scene already has**, and for `glyphPalette` that escape lives HERE, not in glyphcss: `glyphMapMeshTransform` compares the layer's ramp against `scene.getOptions().glyphPalette` and does not set the per-mesh option when they agree. It is exact — two EQUAL names always resolve to one ramp — whereas glyphcss cannot compare in general, since an unrecognized name resolves to the default and two DIFFERENT names can mean one ramp. It matters because one opaque separated layer makes `computeOcclusionIds` raster the whole scene per render: measured +10.4 ms/frame, 41.7 → 29.0 fps for a one-quad probe, against a probe on the scene's own ramp that lands in the base pass (`polys 65313`) for free. The scene's ramp is read LIVE at mount; a later `map.scene.setOptions({ glyphPalette })` does not re-evaluate mounted meshes (re-add the layer). `line`/`contour` are stamped post-raster via ONE composed `transformCells` hook into every grid (base, detail, or their own viewport overlay when `density !== 1`). **A `line`'s vertices are DRAPED — projected at the ground elevation under their own lon/lat** (`groundElevationSampler`, read from the mounted `raster` layers' own tiles, finest tier first; `null` and byte-identical to the datum expression when no raster layer is mounted), because everything else in the scene already stands on the exaggerated relief and under a tilt that relief has PARALLAX: at `/maps`' defaults 10 m of ground moves the building on it 16 rows and moved the road beside it zero (400 m moves it ~2,000), so roads and buildings stopped coinciding. The depth test is then the ordinary coplanar-surface allowance and nothing else — the same slope-scaled bias as wireframe HLR, which is real work rather than a formality (the drape reads the tile's FULL-resolution field while the terrain rasterizes from a coarsened quad mesh, so 147 of 650 stamped samples read up to 6.54e-4 behind a real ridge against an allowance reaching 7.18e-3; mutated to 0, all 307 go dark and the border breaks). Two allowances DIED with their premise rather than being tuned down: a flat `0.03` world-unit bias (0.03 earth radii is ~7,960 m of terrain at `exaggeration: 24`, so it forgave Earth's entire relief on every stroke — a 60 m OSM building stands 1.1676e-5 in front of a road under it, 2,570x under the allowance) and `GLYPH_MAP_STROKE_GROUND_MARGIN` (that offset measured per vertex by a SECOND projection at the ground and forgiven — which is exactly the projection the drape now is, so the stamp got 15% cheaper: 2.76 ms against 3.26 ms for 9,600 border vertices at 160x63). A `contour` needs none of it and is byte-identical: it projects no vertex and runs no depth test, sampling per CELL through `unproject` instead — though that inverts at elevation zero and so carries the MIRROR of the same parallax, identified and unfixed (it needs a terrain ray-march, not a sampler). A finer tier landing DOES move a stroke, onto the ground that tier now describes, in the same frame the terrain moves there — `stamp()` re-resolves the sampler per render and holds no snapshot; within one tier the sample is camera-independent, so no pan or orbit can make it shimmer. Gates: `widget.strokeDrape.test.ts`, `stroke.test.ts`, `widget.strokeOcclusion.test.ts`, `widget.tiltedTileCulling.test.ts`. Lines are clipped to the visible hemisphere before stamping; contours sample tile VERTEX grids across a mosaic. A `contour` layer's optional `minElevation`/`maxElevation` (metres, omitted = unbounded and byte-identical) is an elevation WINDOW — two numbers rather than a land/sea mode, so `floor 0` is land, `ceiling 0` sea, `0..2000` the foothills, and no "land" ever has to be defined (the Caspian is simply below the floor). It does BOTH halves, since either alone is a half-fix: a COUNT `levels` is DISTRIBUTED across the window ∩ the mosaic's range (the crowding fix — ETOPO1 spans ~-10,900..+8,300 m, so an unwindowed count spends most of its lines on the abyssal plains), while an explicit array and an `{ interval }`'s absolute multiples are CLIPPED, never renumbered (an interval's lines must stay at fixed elevations or they crawl on every pan); and INK is clipped per cell, because the crossing scan reads a cell's right/down neighbours, so a sea cliff's level crosses BETWEEN an ocean cell and a land cell and inks the ocean one. An empty window renders nothing and never throws, levels stay computed across the WHOLE mosaic (a per-tile window would tear seams), and `getContourFieldRange` keeps reporting the field's DATA range — a UI needs it to bound its own floor/ceiling controls, which is what `/maps`' Contour card does. A `contour` layer's `labels` (default off, byte-identical there — no buffer allocated, no extra pass) prints elevations ON the lines, adapting paper cartography rather than imitating it: INDEX contours only (`labelEvery`, default 5, selected by a level's ordinal on the ABSOLUTE ladder `round(level / step)` via the exported `glyphMapContourIndexLevels`, so an `{ interval }`'s labelled lines stay at fixed elevations and never renumber on a pan); the number sits in a GAP in its own line (`stampGlyphMapContourLabels` restores the pre-ink terrain glyph either side, only for cells this pass inked with THAT label's level, so a crossing contour keeps its ink and the relief is never punched through); placement is CHOSEN — near-horizontal on screen, locally straight across the label's own width, wholly over terrain, clear of the map edge — and arbitrated by the SAME greedy `glyphMapDeclutterLabels` the `symbol` layer uses, now with optional `padX`/`padY` (both default `0`, symbol path untouched) where `padX` doubles as the repetition spacing along one line. Rotated text does not exist on a character grid, so "aligned with the line, top of the number uphill" is DROPPED and its purpose kept by SELECTION instead — ArcGIS's own "Centered horizontal" contour style; the tempting inversion (label where the contour is STEEP, so a horizontal label crosses it in one cell) is wrong because contours are locally parallel, so a vertical-running line's neighbours are separated horizontally and the label ploughs through all of them. Labels inherit the elevation window and the globe horizon from the ink they derive from. Measured incremental cost, real grid shapes, built package: +0.18 ms/stamp at 140x63, +0.48 ms at 283x105 (~1.3-1.9% of the frame the `bench/maps-render` README measures at those sizes). `fill`/`fill-extrusion` normalize ring topology in lon/lat, probe facing with `localUpDirection`, refine faces until the projection is locally affine, and re-cull walls per frame (`glyphMapVectorMesh` + `glyphMapVectorCullWalls`) — never bake a camera verdict into a mesh. **A `fill-extrusion`'s HEIGHT is TRUE METRES and is exempt from the terrain's `exaggeration`, while the GROUND it stands on is not** — the ground a structure stands on is wherever the exaggerated relief puts it, so only what is measured up from that ground is exempt (reversing that buries every extrusion; exempting neither drew a 20 m OSM building 480 m tall at `/maps`' default `exaggeration: 24`). `glyphMapVectorMesh` converts with `glyphMapTrueScaleElevation`, so `GlyphMapVectorWall.elev`/`elevTop` are AXIS elevations (what `glyphMapVectorCullWalls` re-projects — a wall on a mountain reaches the horizon from that mountain's own height, and a genuinely far-side one is still dropped whole), and a stylised skyline is `heightScale` — the same multiply on the same metre count, never a second option. **That ground is the TERRAIN under the footprint, never a feature attribute**: `glyphMapVectorMesh`'s `groundElevation` is called once per polygon GROUP at its outer ring's mean lon/lat (a structure is RIGID — one ground per piece keeps the cap planar, the walls planar quads, and a wall's two elevations the scalars the cull re-projects), and the widget answers it from the SAME `groundElevationSampler` the strokes use, `null` and free with no `raster` layer mounted. What used to be one absolute `base` is now those two quantities: OSM's `min_height` is `baseOffsetProperty`, a STRUCTURE measurement in TRUE metres above the ground with the height's own exemption, not a terrain elevation — fed onto the terrain axis it planted every extrusion at sea level, and a 60 m building over 400 m of ground drew NOT ONE CELL while a road at the same place still drew. A `fill` is deliberately not planted (a flat overlay on the datum, no walls to stand on), and a `fill-extrusion` on a STATIC source is re-planted when the mounted tile set changes (`groundChangeSyncs`; it is never rebuilt by `scheduleTileUpdate`, so a building mounted before its terrain landed would otherwise stay at the datum for the life of the map — the re-probe costs one tile lookup per group, measured 0.013 ms for the vendored Zurich extract's 469 groups, and a rebuild runs only on a real difference). Measured build cost of the planting itself: +0.02 ms on a 2.6 ms rebuild of those 469 groups / 7,768 polygons, and nothing per frame. Terrain, contour and `fill` output are byte-identical, as is an extrusion with no raster layer mounted. Gates: `layers.extrusionHeight.test.ts`, `widget.extrusionGround.test.ts`, `widget.extrusionHorizon.test.ts`. Heatmap relief hugs the mounted terrain. Attribution derives from mounted layers (`getAttributions()`).
- **OpenStreetMap (Protomaps PMTiles)** — `glyphMapPMTilesProvider` is the raw archive reader (WEB MERCATOR `z/x/y`, as PMTiles is) and now also reports the header's own `extent`; `vector/protomaps.ts` is the SCHEMA MAPPING on top of it. The Protomaps basemap's nine source layers (`boundaries`, `buildings`, `earth`, `landcover`, `landuse`, `places`, `pois`, `roads`, `water`) are NOT map layers: `roads` holds motorways, footpaths and railways together and `water` holds rivers as LINES beside lakes as POLYGONS, both discriminated by a plain `kind` (`pmap:kind` on pre-v4 archives — `glyphMapProtomapsKind` reads either). `GLYPH_MAP_PROTOMAPS_LAYERS` is the `(source layer, kind, geometry) -> glyph layer type` table (`roads`/`boundaries` -> `line`, `water`/`landuse`/`earth` -> `fill` plus a `line` row for waterways, `buildings` -> `fill-extrusion` on its real `height`, `places` -> `symbol`, `pois` -> `circle`); `glyphMapProtomapsLayers(extract, opts)` builds them, `opts.kinds` narrows per source layer. **Every name in that table was read out of the vendored archive's own `vector_layers` metadata and tiles (`vector/protomaps.test.ts` re-derives them per run), never from the published schema docs.** An archive is mounted as an EXTRACT (`glyphMapProtomapsExtract` -> one `GlyphMapVectorFeatureCollection` per source layer, `kinds` per layer, `bounds` = the header bbox, `maxTiles` 64), NOT as a mounted provider: PMTiles is Web Mercator while every pyramid the widget sweeps is equal-angle, and at z12 the Zurich fixture sits at Mercator `y = 1434` and equal-angle `y = 1025`, so a sweep would enumerate tiles the archive does not hold and request neither of the two it does. Retiling Mercator onto the equal-angle grid is machinery with no data to justify it — an extract is a handful of tiles at ONE zoom, so there is no LOD ladder to select across. Attribution rides on every collection (`GLYPH_MAP_PROTOMAPS_ATTRIBUTION`, ODbL) and so reaches `getAttributions()` from the mounted layer itself; `widget.osm.test.ts` gates that mounting adds the credit and removing withdraws it. The vendored 150 KB Zurich archive stays a FIXTURE (`pmtiles.fixture.test.ts`, `protomaps.test.ts`, `widget.osm.test.ts`); it is no longer copied into the website.
- **OpenStreetMap (OpenFreeMap, the shipped path)** — `glyphMapOpenFreeMapProvider` mounts <https://tiles.openfreemap.org/planet/latest/{z}/{x}/{y}.pbf> (public, no API key, OpenMapTiles schema, z0-z14) as a real `GlyphMapVectorProvider`, so the widget's own sweep streams the planet on demand. It works because a provider may now declare `tileRange` — `vector/mercator.ts`'s `glyphMapMercatorTileRange` — and `createGlyphMap` keys on that CAPABILITY, never on a provider id, exactly as projections do; a provider that declares nothing keeps this package's equal-angle indexer and is byte-identical. `vector/openmaptiles.ts` is the SECOND schema mapping (`class` not `kind`, `transportation` not `roads`, `waterway` split from `water`, `admin_level` NUMBER not a `kind`, `render_height` not `height`, no landmass polygon at all), deliberately not a generalization of the Protomaps table; `GLYPH_MAP_OPENMAPTILES_LAYERS` + `glyphMapOpenMapTilesLayers(source, opts)` build ready-to-mount layers. Every name in it was read out of the live service's own TileJSON and tiles, vendored at `fixtures/openfreemap/`. A tile that 404s/times out/is undecodable resolves EMPTY, never rejects (one rejection would take down the frame's whole `Promise.all`); `onError` reports it. Volume falls out of `glyphMapMercatorZooms`' `tileResolution` (256, the size the tiles were generalized FOR - the MVT extent 4096 is precision, not detail): 1 tile at a world view, <= 24 at a country or city view, never more than 100 anywhere on the ladder. Attribution (`GLYPH_MAP_OPENFREEMAP_ATTRIBUTION` - OpenStreetMap ODbL, OpenMapTiles, OpenFreeMap) rides the provider into `getAttributions()` like every other credit. `/maps`' OSM card is the reference consumer: it mounts this, its previous extent/coverage/fly-to controls are GONE with the extract that needed them, and it shares in-flight tile requests because each mounted layer sweeps on its own cache.
- **`GlyphMapFeatureFilter`** — `filter?: (feature) => boolean` on every vector-source layer (`line`, `fill`, `fill-extrusion`, `symbol`, `circle`, `heatmap`), applied AFTER `sourceLayer` and instead of it for a static collection (which has no source-layer grouping). Omitted = every feature, byte-identical. A predicate rather than a match spec because pre-splitting the features into one collection per rendered layer is impossible for a PROVIDER source, whose tiles arrive after mount. Four code paths need it and each has its own test (`widget.featureFilter.test.ts`): the `line` runtime's static and provider branches, and `createFeatureLayerRuntime`'s.
- **Vector bake** — Visvalingam-Whyatt over the SHARED arc list (never per feature), antimeridian cut before the Liang-Barsky box clip, 4096-extent delta quantization; simplify the whole level, then clip per tile. Bakers: `bake-geo-tiles.mjs`, `bake-vector-tiles.mjs`, `bake-place-tiles.mjs`. **A LINE and a FILL take different clips and a tile carries both.** `glyphMapClipPolyline` returns OPEN fragments (right for a border, where a cut end must read like an interior point) and `glyphMapClipPolygonGroup` returns CLOSED `[outer, ...holes]` groups (Sutherland-Hodgman, which walks the tile boundary), baked side by side as `lines` and `polygons` — handing the open fragments to earcut fills "fragment plus straight chord", which blanked 57-85% of the cells strictly inside every country spanning more than one tile while single-tile countries stayed perfect. The area path unwraps longitude at the antimeridian instead of cutting (a cut leaves the ring open, and closing that repaints the polar bar the cut exists to prevent) and closes a pole-encircling ring over its own pole. `topology.ts` supplies the grouping; `rings` stays flat and in source order, so every baked `lines` fragment is byte-identical to before.
- **Bench** — `bench/maps-render` drives the real `/maps` page with in-page synthesized input, vsync on, grid shape as a gate, run with `--encoding spans`.

No React/Vue surface yet. Everything above is condensed from `docs/design/maps.md`, which holds every measurement, fixed defect, and rejected alternative — read the relevant section before touching `widget.ts`, `layers.ts`, `transition.ts`, or the bakers.

## No per-frame DOM mutation

**Each render cycle writes each `<pre>` exactly once** — the base `<pre>` plus one write (and one `transform`) per detail layer. No cell-by-cell patching, no double writes. Hotspots update via one inline-style assignment each. Controls mutate a single camera state object; the boundary is camera event → state → rasterise → one string.

Render-path cost reductions that keep output byte-identical (details and measurements in `docs/design/performance.md`):

- **Cull runs** — `cullChunks` (`buildGlyphPolygonCullChunks`, 48-polygon runs with AABB + normal cone) let the solid rasterizer skip whole runs pre-projection. A box not wholly in front of the near plane is always accepted; nothing is ever reordered (draw order resolves coplanar ties). Back-face rejection derives its orientation sign from the camera by probing, and self-disables for non-affine (perspective) cameras.
- **Empty-coverage skip** in `scanFillTriangle`, hoisted below the shading block on purpose (`litCache` bucket order is colour-visible).
- **Projection memoization** on exact input equality (`resolveProjectionMetrics`, `rotateVec3Voxcss`).
- **`interactiveDownscale`** — render at `1/n` while a control drags; controls signal via `scene.setInteracting`. Mirrored on React/Vue/custom elements.
- **`createGlyphSurfaceAtlasWebGpuSession`** — browser-only WebGPU presentation companion on an adjacent canvas; never touches the `<pre>`; no CPU fallback; React/Vue re-export the factory only.

## Numeric conventions

Native glyphcss/voxcss surface; the `*/three` subpaths convert internally.

- **Rotation units: degrees.** `rotX`, `rotY` on cameras and `rotation` on meshes are degrees (XYZ Euler). `rotX=65, rotY=45` is the classic isometric-ish viewpoint. No radians.
- **Camera `zoom`: absolute, CSS pixels per world unit.** `zoom=50` maps one world unit to 50 CSS px (voxcss/polycss author at `BASE_TILE=50` and apply `scale(zoom / BASE_TILE)`). Not a viewport fraction.
- **Perspective `distance`: default `0`.** A CSS-pixel pull-back under the default CSS-perspective projection; world-unit pinhole semantics only in legacy `perspective: 0` mode.
- **Directional light `direction`: source-vector convention.** Unit vector from the surface toward the light. Up-right-forward lights faces whose normals point up-right-forward.
- **Depth: larger = nearer** everywhere (`fillDepthTri`, `CellGrid.depth`, camera `.project()[2]`).

## Cross-package discipline

The React and Vue packages are mirror images. **Any public API change in one must land in the other in the same PR.** Same names, arguments, defaults, and return shapes (allowing refs vs reactives, `useEffect` vs `watchEffect`). A `packages/glyphcss` or `packages/core` public-surface change updates both bindings in the same PR.

Before opening a PR:

- [ ] If I touched a React component/hook, the Vue composable/component matches.
- [ ] If I touched a Vue component/composable, the React component/hook matches.
- [ ] If I added an option to a `glyphcss` factory, both bindings expose it.
- [ ] If I renamed a `core` export, every package that imports it is updated.
- [ ] Website docs (`website/src/content/docs/**`) and READMEs reflect any user-visible change.
- [ ] If I changed a render mode, naming convention, or the DOM-mutation rules, `AGENTS.md` reflects the new state in this same PR.
- [ ] Rationale and measurements went into `docs/design/<topic>.md`, not here; this file is still under 400 lines.

## Iterating on the system

The design described here is *current*, not frozen. Rules for evolving it:

- **AGENTS.md is the canonical reference.** Edit it directly; `CLAUDE.md` is a symlink.
- **Architectural changes require user approval.** Dropping or adding a render mode, renaming a public convention, changing what JS is allowed in the render path — propose, don't decide. The user is the architect.
- **Same-PR sync.** Any PR that adds, removes, or materially changes a render mode, naming rule, or cross-package contract updates `AGENTS.md` (contract) and `docs/design/` (rationale) in the same PR.
- **Don't append-only.** Prune content that no longer reflects the codebase, here and in `docs/design/`. A dropped mode loses its table row; a renamed hook is updated in place.

## Backward compatibility

- **No BC shims.** Clean breaks only. No re-export aliases, no `@deprecated` wrappers. Callers update.
- Applies across the monorepo — published packages move together.

## Commits & PRs

- Conventional commits format. Single-line subject. No body unless genuinely useful.
- **NO `Co-Authored-By: Claude` trailer.**
- **NO "🤖 Generated with Claude Code" footer in PR bodies, commit messages, issue comments, or anywhere else.**
- Never amend commits. New follow-up commits only (pre-commit failures: fix and create a new commit).
- Don't auto-push subagent exploration branches — local commits only. The user pushes.
- `main` is **not** branch-protected (the `Publish packages` workflow pushes the release commit + tag directly). Use PRs for feature work by convention.
- **Release = one click.** Run `Publish packages` (Actions → "Run workflow", `patch`/`minor`/`major`, or `gh workflow run publish-packages.yml -f bump=patch`). It bumps every package in lockstep, builds, publishes, and tags `v<X.Y.Z>` on `main`.

## Tests & build

- Refactors keep all tests passing. Don't delete or weaken assertions to make a refactor go through.
- A renamed export's tests rename their imports — no alias kept to satisfy them.
- `pnpm test` runs the full suite across every test-bearing package.
- **`pnpm build` is mandatory before opening a PR.** Vitest doesn't catch DTS/declaration build failures. Run `pnpm test && pnpm build` as a unit; either failing is "not ready."
- **CI enforces both gates** (`.github/workflows/ci.yml`: `pnpm test` + `pnpm build:packages` + `pnpm build:website`). Don't merge with red CI.
- A guarantee with no failing test is not a guarantee: byte-identity claims, no-op claims, and "degrades, never throws" claims each get a test that goes red when the property is removed.

## Style / process

- No time estimates in planning docs. This is agentic engineering, not team scheduling.
- Prune superseded content from long planning docs as you go — don't just append.
- No half-finished features, no speculative abstractions, no defensive code for cases that can't happen.
- Comments explain *why* (a constraint, a browser quirk, a non-local invariant), never *what*.
