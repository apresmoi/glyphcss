# Glyphcss — agent guide

This file is the single source of truth for AI coding agents (Claude Code, Cursor, etc.). `CLAUDE.md` is a symlink to this file — **always edit `AGENTS.md`, never `CLAUDE.md`**. The constraints below describe the current design and the rules we work under; if a request conflicts with one of them, push back before doing it.

## What this repo is

`glyphcss` is an ASCII polygon-mesh renderer for the DOM. It projects 3D meshes to 2D and rasterises them as monospace text inside a single `<pre>` element. No WebGL, no canvas-per-frame, no per-polygon DOM nodes.

Originally forked from polycss (a CSS-based polygon paint engine). The mesh math, OBJ/glTF/GLB parsers, scene composition tree, camera math, and input controls carried over intact. The paint backend is entirely new: instead of emitting one CSS-transformed DOM leaf per polygon, the rasteriser walks all polygons, fills a `cols × rows` character grid, and writes one text string to `<pre>.textContent`.

Monorepo layout (pnpm workspaces):

| Package | npm name | Role |
|---|---|---|
| `packages/core` | `@glyphcss/core` | Pure math: Vec3, Polygon, scene, camera, mesh ops, parsers. Zero browser globals. (Removed public export, no BC shim: `project()`/`math/projection.ts` — a dead helper with a different axis convention than the real camera; use each surface's own camera `.project()` method instead.) |
| `packages/glyphcss` | `glyphcss` | Vanilla renderer + custom elements (`<glyph-scene>`, etc.). Owns the ASCII rasteriser, custom element definitions, and imperative API. |
| `packages/react` | `@glyphcss/react` | React components + hooks. Thin wrapper over core + glyphcss. |
| `packages/vue` | `@glyphcss/vue` | Vue 3 mirror of the React package. |
| `packages/compile` | `@glyphcss/compile` | Build-time static compiler: 3D mesh → static `<pre>` ASCII. Vite plugin, CLI, Node API. Node-only (fs); reuses `compileScene` (pure) from glyphcss. |
| `packages/effects` | `@glyphcss/effects` | Framework-agnostic spatial effect definitions and stock surface/scene effects. Depends on glyphcss's generic effect protocol; never owns the renderer or animation clock. |
| `packages/fonts` | `@glyphcss/fonts` | Framework-agnostic font/text → extruded polygon-mesh generation. Emits Z-up meshes: world Z = letter height (`+Z` = up, matching every native primitive's `+Z (top)` convention), world Y = letter width, world X = extrusion depth (see `extrude.ts`'s `toWorld`). A camera viewing a flat, unrotated text mesh needs `rotX: 90` (not the default `rotX: 0`) so that vertical axis reads on screen — the word-art page (`website/src/components/WordArtWorkbench`) is the reference consumer. |
| `website` | `@glyphcss/website` | Astro + Starlight docs site. Not published. |

Public API is **mirrored** across React and Vue. Adding a hook on one side without adding the matching composable on the other is not acceptable (see "Cross-package discipline" below).

### Three-like parity surface

The native glyphcss API keeps glyphcss/voxcss conventions. For agent-friendly Three.js ports, the monorepo also exposes explicit `*/three` subpaths:

- `@glyphcss/core/three` — pure Three-like math wrappers and transforms.
- `glyphcss/three` — the core Three-like surface plus `compileScene` and geometry helpers for vanilla/static usage.
- `@glyphcss/react/three` and `@glyphcss/vue/three` — mirrored framework components: `GlyphThreePerspectiveCamera`, `GlyphThreeOrthographicCamera`, and `GlyphThreeMesh`.

These subpaths intentionally use Three-compatible public names and units: `Vector3`, `Euler`, `Object3D`, `PerspectiveCamera`, `OrthographicCamera`, `DirectionalLight`, `AmbientLight`, radians for object rotations, Y-up authoring coordinates, and Three camera frustum semantics. They are adapters over glyphcss, not a Three.js runtime dependency. Geometry authored in that surface is converted to native glyphcss coordinates with `transformPolygonsToGlyph`; the Y-up → Z-up axis map is `[x, -z, y]` so winding and Lambert lighting stay right-handed. Three-like lights preserve color and intensity; `DirectionalLight.toGlyphDirectionalLight()` converts Three's `target → position` source vector into glyphcss's native directional-light convention.

## Rendering model

**One render pass → one `<pre>.textContent` assignment.** On every camera or scene state change, the rasteriser:

1. Walks all mounted meshes in scene order.
2. Transforms polygon vertices through the camera matrix to get 2D projected positions.
3. Fills a `cols × rows` character grid: depth-tests overlapping polygons, picks a glyph per cell based on the render mode.
4. Joins all cells into a single string and writes it to `<pre>.textContent` exactly once.

There are no per-polygon DOM elements. There is no CSS `matrix3d`. The base `<pre>` is the render surface for all shared-resolution meshes.

**Post-rasterize cell effects.** A scene's optional `transformCells` hook runs after rasterization and depth testing but before the final grid is stringified. It receives a `CellGrid` and may change cell characters or colors without adding DOM nodes or extra writes. In solid mode, requirement-gated optional buffers expose the final shaded scalar (`shade`), depth-winning world position (`worldPosition`), geometric face normal (`normal`), and authored perspective-correct UV (`surfaceUv`). Empty or unavailable vector/UV cells contain `NaN`. Under supersampling, world position, normal, and UV come from the same covered subcell nearest the output-cell center; shade is box-filtered with uncovered samples contributing zero. The hook remains inside the render pass: the transformed grid is still joined once and written to the `<pre>` exactly once.

When semantic output is active, `scene.getGlyphSemanticCellFrame()` exposes an immutable, last-committed **base-grid** snapshot of depth-winning polygon → surface → instance → class lineage. It is derived from that same rasterized winner buffer, never from visible glyphs and never by a second projection; it is `null` in visible mode. Detail-layer cells are deliberately excluded because they have their own grids and no base-cell address. Control-frame capture also retains separately addressable `albedoRgb` (texture × authored base-color factor) and `targetRgb` (that albedo under the per-cell ambient/key Lambert and direct-only shadow policy) from the same winning subcell; these are not inferred from presentation spans.

The fixed model-control tensor is a 17-channel NCHW keyframe: visible glyph, semantic glyph/color, depth, normal, world position, surface UV, explicit surface-UV validity, coverage, and Lambert shade. Its temporal form prepends six warp/validity/disocclusion/confidence channels for a total width of 23. Raw control frames continue to preserve unavailable authored UVs as `NaN`; tensor UV value planes use zero only together with `surface-uv-valid = 0`, so a missing mapping never aliases a legitimate authored `(0, 0)` corner.

**Retained Glyph Effects.** `scene.addEffectLayer()` mounts ordered, scene-root appearance programs without adding output elements. The first geometry render retains an immutable `CellGrid` for the base `<pre>` and every detail `<pre>`; changing `layer.params`, opacity, blend, order, or enabled state then recomposes and safely encodes those retained grids without transforming or projecting the mesh again. The handle's flat `params` object has stable identity, validates known string keys, accepts Anime.js/private symbol metadata, and automatically schedules a coalesced effect transaction. Generic effects run before the legacy `transformCells` escape hatch. An effect-only transaction stages every affected string before assigning each `<pre>` at most once. With no mounted effect and no hook, the original direct renderer remains byte-identical and does not allocate retained effect frames.

The current generic compositor supports `over`/`replace`, `"surfaces"`/`"viewport"`/mesh-handle targets, canonical base-grid affines across detail densities, and the `baseColor`, `baseShade`, `depth`, `normal`, `worldPosition`, `objectPosition`, `objectExit`, and `uv0` requested inputs. Hard surface requirements are solid-mode-only; `optionalRequirements` retain those inputs in solid mode but allow a program-defined fallback in wireframe/voxel modes. Scene-image sampling, program scratch buffers, surface-key/UV-footprint inputs, and static compile/export evaluation of a mounted effect are not implemented yet and reject explicitly (field-synth's own static exporter is a separate, explicitly-scoped path — see "Compilation" below).

**Per-object effect targeting.** `target` on `addEffectLayer` accepts `"surfaces"` (default, scene-wide), `"viewport"`, a single `GlyphMeshHandle`, or a `readonly GlyphMeshHandle[]` — a layer applies only to the mesh(es) named. A handle/array target normalizes at mount to a canonical, immutable `Set` of mesh ids (module-level monotonic counter, never aliasing across scenes); `setOptions` with an equivalent set is a no-op, a genuinely different set throws (live retargeting is out of scope — remove and re-add the layer instead), and plain `"surfaces"`/`"viewport"` retargeting is unaffected and stays freely mutable. The mechanism is `targetCoverage`, not emission-zeroing: a targeted layer's per-cell `targetCoverage` is `0` on any cell whose depth-winning mesh is not in the target set, base coverage otherwise — zeroing the program's own output instead would ERASE the base on non-targeted cells under `blend: "replace"` at opacity 1, since `inputWeight` is itself derived from `targetCoverage`. The depth-winning mesh id is a solid-mode-only per-cell buffer (`CellGrid.winnerMesh`) retained alongside the existing shade/world-position/normal buffers; outside solid mode no winner data exists, so a mesh-targeted layer degrades to fully inactive (never a throw), and a removed/disposed mesh's id simply matches no cell, same degradation. It is never a `GlyphEffectRequirement` — a program cannot request it — but as of the Phase 2 P1 fix below it IS surfaced read-only on `GlyphEffectFrameView.winnerMesh` (populated whenever `objectExit` retention is active, which every carve layer already sets, or a layer is mesh-targeted): a volumetric subcell program needs exact mesh-identity equality between neighboring cells, which `objectPosition`/`normal` alone can't express for two coplanar, same-normal meshes. Occlusion-blanked cells (winner `-1`) are never in any target set. Each per-mesh detail layer (its own `<pre>`) carries its own real winner-mesh id, so targeting applies per output grid — a layer can target only a detail mesh, only the shared base grid's meshes, or both. A later scene-wide layer still composites OVER a targeted layer's output, including painting into carve holes — that is global ordering working as designed, not a bug. React/Vue `<GlyphEffectLayer target>` and `<glyph-effect-layer>` all forward `GlyphMeshHandle`/array targets; the React/Vue wrappers diff a mesh-array `target` prop by its canonical id set (not `Object.is`), so a fresh `[a, b]` array built every render is a no-op instead of a spurious `setOptions` call. `@glyphcss/effects` supplies Matrix rain, flow text, scan, wipe, scramble, glitch, noise dissolve, ripple, and **field synth** as reusable definitions. `field-synth` is a small composable synth — up to nine oscillators (`fieldN` × `waveN`: radial/linearX/linearY/diagonal/angular/spiral/noise/linearZ/gyroid/menger/sierpinski × sin/triangle/saw/square/step, each with `freqN`/`speedN`/`ampN`), combined (`add`/`multiply`/`max`/`min`/`difference`/`argmax`) into one scalar field mapped to a glyph ramp + color, over `space` — for emergent moiré/interference patterns. Every voice except `noise` and the SDF family (`gyroid`/`menger`/`sierpinski`, added in slice 2 — see below) is a 1D wave sampled along a scalar projection of the plane, so it is CONSTANT along its own level sets (parallel lines for linearX, circles for radial, rays for angular, spirals for spiral) and its terrain is ruled or revolved for those voices — genuine 2D relief from them only appears through `combine`. The SDF family breaks that invariant on its own: `gyroid`/`menger`/`sierpinski` are inherently volumetric implicit surfaces, not a 1D wave along any scalar projection, so a single SDF voice already carries genuine 2D/3D relief with no `combine` needed. Each voice additionally carries `angleN` (degrees; rotates that voice's sampling frame about its own origin, turning the three fixed linear fields into one steerable plane wave — radial is invariant to it) and `originUN`/`originVN` (an offset from the global origin in the same normalized domain units, so two radial voices can sit on DIFFERENT centres, which is the classic interference figure and was unreachable at any voice count while the centre was shared). `combine: "argmax"` is CATEGORICAL rather than value-folding: it reports WHICH voice won, giving each region one flat level (and, with `voiceColors`, the winning voice's own colour) instead of a value that keeps varying inside the region. That is what makes hard-edged tilings reachable — three plane waves 60° apart under argmax produce the rhombille/cube tessellation, which no value-combining op can express. `combineSynth` degrades argmax to `max` when called pairwise; the winning identity is resolved by `evaluateVoices`, which sees the whole stack at once and is the single evaluator the ramp, the 2x4 subcell probes and the ink gradient probes all share. `ampN` is a MIX WEIGHT (blends the result toward `combine(result, voiceN)` per voice, not a signal gain), so low amp gently mixes instead of `multiply` collapsing to flat; `amp 0` skips the voice. `lit` (0..1) modulates output color by the surface Lambert shade so lighting reads through the texture. `voiceColors` blends each active voice's `colorN` by its contribution (per-voice color composition); off keeps the `color`/`colorB`/`gradient` value-gradient. `subcellRes` selects how the scalar field becomes glyphs: `"1x1"` indexes the ramp by level (one glyph per cell), `"2x4"` thresholds eight subcells into a Braille dot mask, and `"ink"` CONTOURS the field instead of shading it — `inkLevels` cuts the amplitude axis into that many evenly spaced levels (`n / (levels + 1)`, so neither extreme gets a degenerate line) and a cell inks where any level falls BETWEEN it and a neighbour, which is what makes a continuous line rather than a scatter of near-level marks. The stroke is oriented perpendicular to the local gradient into the same four 45° buckets the geometry `ink` render mode uses. Like that mode it draws ONLY lines: plateaus and interiors stay empty, and a square wave's flat crest needs no special case because its step is an abrupt gradient the crossing test already sees. `"ink"` ignores the ramp (like `"2x4"`), gives inked cells full coverage rather than level-scaled coverage (half a contour lies below a level and would otherwise be nearly invisible), and emits plain-ASCII strokes because box-drawing glyphs are missing from common monospace faces and would desync the character grid. A contour of an oscillating field is inherently dense — a `freq 6` voice crosses a level on most cells at 32×12 — so legibility comes from fewer `inkLevels`, not from a higher one. `@glyphcss/effects` also exports `GlyphRamps` (named character-sets: Fade/Blocks/Shades/Dots/Binary/ASCII/Hatch/Stars/Digital). The **`/synth` website page** is the front-end: dual-sidebar modular synth — voice cards (add/remove, live per-voice previews that stay static until hovered, a color swatch, icon multi-toggles, per-voice mix) grouped into collapsible per-layer `LayerGroup`s (blend mode, mix, threshold, invert) in the voice sidebar; Stage/Mix/Output/Lighting Dock; a `Mapping` dropdown is the SOLE 2D/3D control (`space` itself — the earlier separate 2D/3D toggle was removed as a duplicate) and, once a volumetric stage is active, an optional camera auto-orbit is available; a live preset gallery including a `pyramid` stage and three volumetric presets (Sierpinski pyramid, Breathing gyroid, Menger (cssGraphics)) — full patch persisted to the URL through a two-tier repair gate: an ordered predicate → reset-keys table repairs known-invalid combinations (e.g. a stale `carve` + `subcellRes: "2x4"` URL), falling back to a full effect-param reset (preserving valid non-effect state like shape/camera/lighting) when a validator has no matching table row, so a crafted or legacy URL always hydrates to a working page instead of throwing. For surfaces it gives each face a local 0..1 UV so patterns map per-face. For flow-text/scan, `space: "auto"` (their default) resolves authored UVs first and then generated world-surface coordinates; `space: "surface"` forces the generated orientation-aware mapping, while `space: "scene"` uses projected scene coordinates. `space: "object"` stops painting the pattern per-face and instead treats it as a field filling the mesh's own pre-transform 3D volume, sampled from the retained `objectPosition` cell field (interleaved x/y/z, requirement-gated exactly like `worldPosition`/`normal` — allocated only when a mounted effect's `requirements`/`optionalRequirements` asks for it). `objectPosition` is recovered by carrying each polygon's PRE-transform vertices alongside its baked world vertices (`Polygon.objectVertices`, set by `applyTransform` in `createGlyphScene.ts`) and barycentric-interpolating those with the SAME weights used for `worldPosition` — cheaper and exact under non-uniform scale, unlike inverting a per-mesh matrix. Matrix rain has a natural 3D form and uses this volumetric formulation directly (lanes indexed by the two mesh-local axes perpendicular to `direction`, phase along the third), so a cap cell and an adjacent wall cell read the same underlying `(x, y, z)` at their shared edge and the same strands continue across the seam — this is why matrix rain (unlike flow-text/scan) defaults to `space: "object"` rather than `"auto"`. `scan`/`flow-text` have no 3D form of their own, so `space: "object"` gives them a triplanar fallback instead: each cell projects onto whichever of the three axis-aligned planes its face normal most faces, blended by `normalize(|normal|^4)` (`4` is the seam-vs-mush knob — the conventional triplanar starting point). `objectPosition` only exists in solid mode (hard surface requirements are solid-mode-only); `space: "object"` degrades to the same generated-surface/scene fallback `"surface"` already uses in wireframe/voxel modes, never a silent empty render. `scale` means a 3D field frequency under `"object"`, not a 2D UV-domain frequency — a value tuned for `"auto"`/`"surface"` does not carry over 1:1, which is why a saved matrix-rain preset that tuned `scale` under the old `"auto"` default should pin `space: "auto"` explicitly if it needs to keep its old look. Matrix rain's volumetric lane assignment (`objectVolumetricAlongLane`) hashes each cell's `objectPosition` into an integer lane per `Math.floor` bucket; because the supersampled solid rasterizer picks that position from the nearest COVERED subcell to a cell's screen-space center (see "Per-mesh detail layers" above), which subcell wins can flip to a different point — sometimes a different face — as a mesh rotates, even one frame to the next with the effect clock paused. A hard bucket boundary would turn that small sample jump into a swap to an unrelated `hash2` bucket (a strand popping in/out); `objectVolumetricAlongLane` instead fades a cell's coverage out (`edgeFade`, `OBJECT_LANE_EDGE_MARGIN = 0.18` of a lane's width on either side of its boundary) as the sample nears a lane boundary, so a boundary crossing reads as a graceful fade rather than a pop. `@glyphcss/fonts` authors UVs on every emitted polygon unconditionally, not only when a face carries a texture — front/back caps get a planar mapping normalized to the whole word's type-plane bounds (the glyph's own 2D authoring space, computed before any mesh `rotation` is applied), and side walls get a strip mapping (`u` = fractional arc-length position around the glyph contour, `v` = fractional extrusion depth). Because those UVs are fixed in mesh-local space, `space: "auto"` resolves the authored-UV path for text by default, so Matrix/flow/scan patterns stay locked to and turn with the letterform surface instead of the generated world-surface fallback, which is anchored to world space and would otherwise slide underneath a rotating mesh. On generated surface coordinates, `down` is world `-Z` projected into each geometric face's tangent plane; coplanar polygons agree, differently oriented polygons derive different downhill directions, and a plane perpendicular to that vector gets a deterministic pseudo-random in-plane fallback. That `down` (vertical) axis is quadratic in the face normal, so it is already invariant to the normal's dominant-axis sign canonicalization; the derived `right` (horizontal) axis is `down × normal` — linear in the normal — and is explicitly counter-signed against that same canonicalization so it shares the same invariance, instead of flipping independently every time a rotating mesh's normal crosses the canonicalization boundary. This keeps a spinning mesh's generated-surface flow direction (matrix rain, flow-text, scan) continuous through a rotation: `right`/`left` no longer reverses out of step with `down`/`up` mid-spin. The only remaining discontinuity is the documented pseudo-random fallback itself, which fires only at the exact instant a face passes through perpendicular to `-Z` (no direction is more "down" than another there) — a single, expected re-pick, not a run of spurious flips. Generated Matrix rain fits each quantized coplanar surface basis to projected glyph-cell space, orthogonalizes its visible flow and lane vectors, and evaluates both sparse trail membership and glyph phase in that same face-local field. The word therefore shares the strand's direction and projected-cell velocity on sheared or foreshortened faces, remains ordered when a periodic strand wraps, and does not mutate in place while its mask moves separately. Active rain cells have full logical coverage; sparsity comes from lane selection and trail length, not fractional tail coverage that the compositor would dither into broken strands. Matrix also supports original surface colors or a configurable monochrome color; in monochrome each strand lights a bright `headColor` head and fades its tail toward black (still modulated by surface shade) for the classic head-to-tail falling-code gradient. The package owns no clock. Applications animate explicit parameters such as `time` directly or through Anime.js. React and Vue mirror the scene-root `<GlyphEffectLayer>` wrapper, and custom HTML configures `<glyph-effect-layer>` through JavaScript properties/`configure()` because executable definitions are values, not JSON attributes. `ANIMATIONS.md` records both this implemented slice and the richer approved graph/sampling architecture that remains.

**Volumetric effect inputs (`objectExit`) and `dynamicRequirements`.** `objectExit` (requirement) is the interleaved x/y/z **object-space exit point** of the view ray through the depth-winning mesh — the farthest intersection of that same mesh along the cell's ray, in the mesh's pre-transform coordinates, same NaN-for-unavailable contract as `worldPosition`/`objectPosition`. There is no separate ray buffer: an effect derives one as `normalize(objectExit − objectPosition)`, both endpoints barycentrically interpolated from `Polygon.objectVertices` (the same no-matrix-inverse discipline `objectPosition` established), so a grazing-silhouette cell where entry and exit coincide yields a degenerate ray an effect must treat as "no volume." Producing it needs a **second sweep**: the per-cell solid-pass winner is only final after the last polygon and back faces are culled before scan-fill, so a farthest-of-winning-mesh value can't come from the main pass. The sweep runs a farthest-depth rasterizer (mirroring `fillDepthTri`'s nearest-depth one, clipping near-plane-straddling triangles rather than skipping them — a perspective camera near or inside the mesh is the marquee case) restricted per cell to whichever mesh actually won there, via a polygon→mesh winner buffer (`winnerMeshBuf`) retained in visible mode specifically for this — distinct from the semantic-output-only, polygon-indexed `winnerPolygonBuf`. It runs once per output that retains effect inputs (the base `<pre>` and each per-mesh detail `<pre>`) at that pass's own supersample resolution, downsampled by the same nearest-covered-subcell selection `worldPosition`/`normal` use. **Convex-exact, concave-approximate**: for a convex mesh entry→exit is the exact solid chord; a concave mesh's segment may bridge void gaps (a documented approximation — the fix needs per-cell hit lists / depth peeling, future work). **Carved holes show the page background, never farther scene geometry** — anything behind the host mesh already lost the per-cell depth test before effects run, including cross-`<pre>`: a hole in a detail layer does not reveal base-grid geometry sitting behind it, because the occlusion id-map already blanked those base cells at rasterize time.

Because a static per-program `requirements` array would make every mounted patch — including plain 2D ones — pay for the second sweep, the generic effect protocol (`GlyphEffectDefinition`/`GlyphEffectProgram`, packages/glyphcss/src/api/effects.ts) gains an optional `dynamicRequirements(params): readonly GlyphEffectRequirement[]` hook, merged with the static `requirements`/`optionalRequirements` arrays and re-evaluated whenever a coalesced params transaction changes the hook's own result (a requirement-set change additionally invalidates retained inputs, not just recomposes). `dynamicRequirements` is optional-shaped like `optionalRequirements` — it degrades in wireframe/voxel modes rather than throwing, since the hook can't see the render mode. A requirement it returns that isn't in `SUPPORTED_REQUIREMENTS` still throws at mount, same as a static one. A dynamic input the *current live params* don't ask for reads as `undefined` on the frame view rather than erroring — worth stating explicitly (a Phase-1 reviewer note): a program must guard a dynamic buffer's presence itself, the same discipline `optionalRequirements` fallbacks already need. Field-synth's own hook returns `["objectPosition"]` when `params.space === "object"` and adds `"objectExit"` only when `params.render === "carve"`, so a plain 2D or non-carve volumetric patch never pays for the exit sweep.

**Field-synth's volumetric branch.** Under `space: "object"` with `objectPosition` retained, `fieldSynth` (unlike `matrixRain`/`scan`/`flowText` above) takes its own distinct branch: `(x, y, z) = objectPosition · scale` (matrix rain's precedent — `scale` is a 3D field frequency under `"object"`, not the 2D UV frequency `"auto"`/`"surface"` use). The 2D branch is separate code, not `z = 0` through one shared formula: `linearZ` (new field, appended to `SYNTH_FIELDS`) exists only in 3D; `diagonal` is `(x+y+z)/√3` in the volumetric branch vs. the untouched `(x+y)/√2` in 2D (changing the 2D constant would break existing presets like Zebra/Lattice); `noise` becomes a 4D hash (`synthNoise4(x·freq, y·freq, z·freq, time·speed)` — the 2D path's third `synthNoise3` axis is already time, so volumetric noise needs a fourth axis or it freezes); `angular`/`spiral` stay evaluated in the XY plane with `z` ignored (documented scope limit); `radial` is spherical distance from the voice origin. Voice origins gain `originW1..9` (default 0, 3D-only); `angleN` keeps its 2D meaning (rotation about Z). Every voice also gains `duty1..9` (default 0.5, the square wave's high fraction; other wave kinds ignore it) and `phase1..9` (default 0 cycles, added to every wave/field kind's argument) — `phase` exists because linear fields ignore the voice origin entirely (only `angle ≠ 0` and the radial/angular/spiral centers read it), so a middle-third selector needs `wave: square, duty: 1/3, phase: -1/3` rather than an origin shift. `subcellRes: "2x4"`/`"ink"` finite-difference the volumetric coordinate the same local-affine way the 2D generated-surface path already does; under `render: "carve"` both are rejected outright (see Carve, below).

**Voice layers.** `layer1..9` (default 1, integer 1..3) opts a voice into one of three groups, each with its own `layerCombineL` (intra-layer fold, default = the patch-level `combine`), `layerThresholdOnL`/`layerThresholdL` (default off / 0, range −3..3 — an add-fold of three amp-1 voices spans ±3), `layerInvertL` (default off), and `layerBlendL` (`add`/`multiply`/`max`/`min`/`difference`, default `multiply`) + `layerAmpL` (0..1 mix weight, default 1) for how the layer's shaped output enters the cross-layer fold. Layers exist because no flat combine of separable (per-axis-projected) voices can express a per-scale membership rule like Menger's ("hole ⇔ at least two axes are in their middle third at that same scale") — the fix is a threshold *per scale* before scales combine, i.e. a layer with its own shaping stage; Cantor-dust-style per-axis rules remain reachable in the flat fold once voices are 3D and `duty` exists. A thresholded layer's folded value maps to **±1, not {0, 1}** — the downstream `clamp01(bias + gain·v·0.5)` mapping (default bias 0.5) is calibrated for a ±1 signal, and a {0, 1} indicator can never reach the ramp's empty end. An empty layer (no active voices) is skipped in the cross-layer fold exactly like an amp-0 voice is skipped in the intra-layer fold — otherwise it folds to 0 and the default multiply-blend annihilates the stack. **Backward compatibility is structural**: every voice on layer 1 with threshold/invert off and amp 1 is a single-layer stack whose output is exactly the pre-layers flat fold, so existing patches/presets/URLs are unchanged without migration. `combine: "argmax"` stays categorical and single-layer only — `validateParams` rejects a patch where argmax is the **effective** combine (its layer override, else the patch-level default) of any *populated* layer in a multi-layer stack; a multi-layer patch whose every populated layer overrides to a value op is valid regardless of the patch-level `combine`, which is then dead metadata by design. `voiceColors` still blends across all active voices regardless of layer — layers have no color model of their own.

**Carve mode.** `render: "paint" | "carve"` (default `"paint"`) is field-synth's raymarched hollow-interior mode. Carve requires the volumetric branch (`space: "object"`, `objectPosition` + `objectExit` retained); in wireframe/voxel modes it degrades to paint like every other optional-requirement fallback. `subcellRes: "2x4"`/`"ink"` are legal under carve — see "Volumetric subcell modes" below — only xray still rejects them (`"xray-subcell-unsupported"`); the plain `"1x1"` path described here is carve's shading-only mode. Per covered cell it calls the public `marchGlyphField` (see below) over `objectPosition → objectExit` with the compiled field program as sampler. `marchSteps` (default 48, max 256) is a *minimum*, raised per cell to `ceil(2·chordLength·f_finest)` (the Nyquist floor below which thin walls render as shimmering false holes) — a measured 120×48-grid, depth-2-Menger, half-covered scene stays around 3ms/`evaluate()` call at the default (`bench/carve-march.md`). `f_finest` is duty-aware and the depth-3 recipe ships as a preset — see "Authoring tier" below for both. A sample counts solid when the same `clamp01(bias + gain·v·0.5)` mapping the ramp uses is `> 0` — no separate iso parameter. **Emission is at the raw guaranteed-solid march sample, not an interpolated hit position**: the marcher's secant refinement is exact for an affine field, but every voice/layer boundary in a hard-thresholded field (a square wave, any layer threshold) has a plateau at 0 under that same clamp mapping, so an interpolated position can land on the plateau's edge and resample non-solid. `FieldMarchHit.sampleX/Y/Z`/`sampleDistance` are the raw sample that actually triggered the hit and are guaranteed to resample `> 0`; carve emits at that point (the paint pipeline's ramp glyph, `lit`/shade, `voiceColors`, gradient) and multiplies color by `exp(−marchFade · sampleDistance)` — `sampleDistance`, not the chord-normalized `t`, so two cells with different chord lengths shade an interior wall identically instead of painting a spurious silhouette-tracking gradient. At `sampleDistance = 0` (surface-solid cell) the factor is exactly 1, so an everywhere-solid carve is byte-identical to paint on the same scene. A cell with no solid sample along the chord emits nothing — ordinary compositor semantics: `blend: "replace"` at opacity 1 composes holes to page background (the intended look, and what carve should be mounted with); `over` lets the base surface show through holes; `replace` at opacity < 1 Bayer-dithers the base back into them.

**Xray mode.** `render: "xray"` (appended to the render enum, slice 2) is field-synth's transmittance mode: the same volumetric branch as carve, but instead of a first-hit march it integrates density along the whole chord and reports how much of it a viewer sees through, rather than where it first stops. Per covered cell, density per sample is the same `clamp01(bias + gain·v·0.5)` mapping paint/carve use; transmittance `T = exp(−xrayGain · ∫ d dt)` (the integral in absolute domain units, via the public integrator below); brightness `B = 1 − T`. `xrayGain` is its OWN param (appended, default 4, min 0, max 16) — not `marchFade`: at `marchFade`'s default 1 a fully solid unit chord only reaches B ≈ 0.63 and typical preset domains never saturate, and `0` means opposite things in the two modes (no fade in carve, invisible in xray). **Coverage is forced to 1** for any cell with `B ≥ 1/255` regardless of the resolved color's alpha (the `subcellRes: "ink"` full-coverage precedent — fractional coverage would dither the transmittance look into noise); a cell under that threshold emits nothing. `lit` still modulates by surface shade; `voiceColors` is inert (and hidden in the UI) since a transmittance integral has no per-voice winner. A degenerate chord (no finite exit, zero length) emits nothing — deliberately different from carve's paint-at-entry fallback, since a full-strength rim ring around a transmittance volume would contradict the mode. **Uniform step count per `evaluate()` pass**: carve tolerates a per-cell step-count `ceil` flip (a sub-step shift in where the hit lands), but an integral does not — a ±1-2 step difference between neighboring cells can read up to ~20% apart in brightness, visible as per-cell speckle. Xray therefore computes ONE step count for the whole pass, from the MAX chord over every covered cell, and integrates every cell at that count; carve keeps its own per-cell count, unchanged. **A zero-mean oscillating field reads as fog under xray** — it integrates to roughly `bias` per unit length, so structure only shows once a voice is shaped near-binary first (the `Breathing gyroid` preset thresholds its layer for exactly this reason); a MIP/max-density accumulation mode is a recorded future option, out of scope for this slice. Validation mirrors carve's `space: "object"` requirement (same rejected-value error codes), but stays `subcellRes: "1x1"` only — unlike carve, which also accepts `"2x4"`/`"ink"` (see "Volumetric subcell modes" below) — since an accumulated transmittance integral has no per-cell hit point for either neighbor probe to read; xray degrades to paint in wireframe/voxel exactly like carve; `dynamicRequirements` returns `objectExit` whenever `render` is `carve` OR `xray`, so a plain paint patch never pays for the exit sweep.

**SDF voice family.** `gyroid`, `menger`, `sierpinski` (appended to `SYNTH_FIELDS` after `linearZ`, slice 2) take a dedicated branch in `sampleFieldVoice`, like `noise` — and, unlike every other field, they read the voice **origin** (`originU/V/W`) as a pre-evaluation TRANSLATION of the sampled point, the opposite of every linear field's convention (which ignores origin entirely) and of radial/angular/spiral (which read origin only as a distance-from-center anchor): without translating the sample itself an SDF voice has no way to align to its host mesh, and `phase` is not a substitute — `phase` for an SDF voice is instead an ISO-LEVEL offset that erodes or dilates the solid, never a translation. `freq` is the lattice scale, applied ONCE to the translated sample; the shipped wave projection `t = raw·freq − time·speed + phase` every other field uses is NOT reused here (freq would apply a second time, doubling shell density to freq²) — SDF voices route through their own `t = raw − time·speed + phase`. `gyroid` is a 2π-normalized smooth implicit (`sin(2πx)cos(2πy) + sin(2πy)cos(2πz) + sin(2πz)cos(2πx)`, so `freq` means cycles-per-domain-unit like every other voice) used directly as the wave argument — its sign means "which labyrinth half," not inside/outside solid. `menger`/`sierpinski` are the signed distance to the **depth-`iter` box/tetra union** — an EXACT union distance via a pruned recursive descent of the same kept-child tree the digit-rule membership test walks (menger: 20-of-27 axis-aligned kept subcubes per level; sierpinski: 4-of-8 kept octants per level, the corner-tetra rule), not a Lipschitz-bound distance estimator: a true limit-set SDF is positive almost everywhere (the limit set has measure zero) and would carve to nothing. A parent box's own SDF is a valid lower bound for every descendant's, so the descent prunes any child whose bounding-box distance already exceeds the best union distance found so far. The cell convention is the unit cube `[0,1]³`, matching the recipe presets and the `pyramid` stage's own authoring window; the 2D branch evaluates at `z = 0` (a documented slice). `iter1..9` (integer 1..4, default 3, menger/sierpinski only, knob hidden otherwise) is capped at 4 because carve/xray's march resolution caps at 256 steps: menger `iter` 4 needs ~162 steps on a unit chord and fits, `iter` 5 needs ~486 and would render guaranteed false holes. The shared Nyquist step floor (below) reads each voice's own **effective finest frequency**, not the raw `freq`: `freq·3^iter` for menger, `freq·2^iter` for sierpinski, `freq·2` for gyroid, `freq` for everything else — a menger/sierpinski voice at `iter ≥ 3` is therefore expensive to march/integrate at full resolution (recorded reviewer P2); turn on `interactiveDownscale` while dragging camera controls on an `iter ≥ 3` menger/sierpinski patch. `step` (appended to `SYNTH_WAVES`) is a non-periodic waveform — `+1` when its argument is `≥ 0`, else `−1` (duty ignored, no cycle to shape) — legal on every field (a `linearX` + `step` voice is a half-space), and every SDF preset depends on this exact line: inside the solid `sdf < 0` → `raw > 0` → `t > 0` → `step = +1` → density `> 0.5` at the default bias → solid. The static exporter ports all three SDF fields and `step` through its own IR runtime with real-renderer parity — they export in the 2D branch like any other field/wave.

**The field program IR.** The internal evaluation form — an array of layers, each an array of voice records, plus per-layer combine/threshold/invert/blend/amp, no fixed length anywhere — is public as the field program IR, the seam a future field-authoritative primitive or spectral-analysis mode plugs into without touching the schema. `@glyphcss/effects` exports the types (`GlyphFieldProgram`, `GlyphFieldLayer`, `GlyphFieldVoice`, `GlyphFieldSampler`, `GlyphFieldEvalResult`, `GlyphFieldMarchOptions`, `GlyphFieldMarchHit`, `GlyphFieldMarchMiss`, `GlyphFieldMarchResult`), the evaluator `evaluateGlyphFieldProgram(program, x, y, z, time)`, and the sampler-agnostic marcher `marchGlyphField(entry, exit, sampler, opts)` where `sampler` is any `(x, y, z, t) => number` — carve calls it with the field-program sampler, but the marcher itself knows nothing about voices. `marchGlyphField` returns a first hit and cannot express an accumulated quantity; its sibling **`integrateGlyphField(entry, exit, sampler, opts) → { sum, steps, chordLength }`** (slice 2) is equally sampler-agnostic and drives xray's transmittance integral. Both share one exported step-count floor, **`glyphFieldStepCount(chordLength, opts)`** — `max(minSteps, min(cap, ceil(2·chordLength·finestFreq)))` — so carve and xray can never disagree about how finely a chord is resolved; `integrateGlyphField`'s quadrature is midpoint, not endpoint: `steps` samples at `t_i = (i + ½)/steps · chordLength`, weighted by `Δt = chordLength/steps`, with a non-finite sample contributing 0 — no endpoint double-counting. Field-synth's own params→IR compile (`stock.ts`) is one caller among others a hand-built program could replace.

**Preset named exports.** Alongside `GlyphFieldSynthEffect.presets`, four presets are individually exported by object identity for a consumer that needs to key off a SPECIFIC preset rather than a name string: `GlyphCubeTilesPreset`, `GlyphSierpinskiPyramidPreset`, `GlyphBreathingGyroidPreset`, `GlyphCssGraphicsMengerPreset` — the `/synth` page's per-preset stage-hint table (below) is the reference consumer, keyed by object identity so renaming a preset's display name can't silently drop its hint. (A later preset cull removed five other identity-exported presets — `GlyphMengerSpongePreset`, `GlyphGyroidXrayPreset`, `GlyphMengerSdfPreset`, `GlyphSierpinskiSdfPreset`, `GlyphMengerFlowPreset` — along with three more that were never identity-exported — "SDF bloom", "Iridescent sponge", "Iridescent shell"; `GlyphBreathingGyroidPreset`/`GlyphCssGraphicsMengerPreset` now inline the recipes those removed presets used to spread from, byte-identical to before.)

**`GLYPH_FIELD_SYNTH_VALIDATION_RULES`.** Every `validateParams` throw site in field-synth tags its thrown error with a stable rule id from this exported array (typed `GlyphFieldSynthValidationRuleId`; the error itself is typed `GlyphFieldSynthValidationError` with a `.code` field): `"empty-glyphs"`, `"non-positive-scale"`, `"multi-layer-argmax"`, `"carve-requires-object-space"` (covers both `render: "carve"` and `render: "xray"`), `"xray-subcell-unsupported"` (xray-only — see "Volumetric subcell modes" below for why carve no longer shares this rejection). This replaces a hand-maintained mirror list that could silently drift out of sync: a consumer (the `/synth` URL repair table) asserts every exported id is covered by its own repair rows, so a validator added here without a matching repair-table entry fails a real cross-package test instead of rotting quietly.

**Volumetric subcell modes (carve only).** `render: "carve"` + `subcellRes: "ink"` or `"2x4"` are legal (xray still rejects both, tagged `"xray-subcell-unsupported"` — an accumulated transmittance integral has no per-cell hit point for either neighbor probe to read).

*Ink-over-carve* contours the march's hit/hole boundary instead of shading every hit cell (outline sponges). The carve evaluate pass allocates per-evaluate local buffers — `hitState` (OUT / HOLE / HIT; OUT collapses "no geometry" and "geometry from a mesh outside this layer's target set", since both discard identically — the compositor's own `targetCoverage` weighting already discards whatever an OUT cell emits, regardless of which sub-case it is), `hitDistance` (the hit's `sampleDistance`, absolute domain units from the TRUE entry — its known consequence is a contour break across an entry-surface crease, accepted), and the hit's resolved color — fills them in the march loop, then a second pass resolves ink from those buffers alone (no re-march). New param `inkSpacing` (domain units, default 0.25, min 0.05, max 4, appended after every existing key) is an ABSOLUTE contour spacing, not a fraction of the observed depth range (that would make contours crawl frame-to-frame under orbit and degenerate on a flat wall); `inkLevels` is a documented no-op under carve-ink (2D `subcellRes: "ink"` keeps it). Inking rules: (a) `hitState` differs between any of a cell's 4 neighbors, OR two same-state HIT neighbors carry a DIFFERENT winner mesh id (`GlyphEffectFrameView.winnerMesh`, both ids known — Phase 2 P1 fix: `hitState` alone can't tell two coplanar, same-normal, globally-targeted meshes apart, so a contour previously bridged straight across that seam instead of rimming it) → rim, always inked, on BOTH sides of the boundary (a hole/OUT cell touching a hit is rimmed too, so it can borrow a color); (b)/(c) for a cell whose every neighbor shares both its state AND its winner mesh, a multiple of `inkSpacing` between two hit depths (contour) or too great a depth jump (interior edge) — contours never cross a hit/non-hit OR winner-mesh boundary, since both are already rule (a). Orientation: rim cells use the screen-space gradient of a mask that reads 0 for a non-HIT neighbor OR a HIT neighbor on a different winner mesh (a depth gradient is undefined against either — the naive fallback renders every rim cell as `-`); contour/edge cells use the depth gradient (both neighbors are real hits on the SAME mesh there). Both quantize through the same exported 4-bucket `inkGlyphForField` the 2D ink path uses. Non-inked cells emit nothing; inked cells get full (non-level-scaled) coverage; color is the cell's own hit color, or — for a rim cell with no hit of its own — its nearest inked hit neighbor's color, else the layer's base color.

*Braille-over-carve* (`subcellRes: "2x4"`) marches 8 sub-rays per covered cell, one per Braille dot position, sharing ONE step count sized from the longest of the 8 (+ the cell's own) chords (xray's own "uniform step count" rationale, applied per-cell). Sub-ray entry/exit endpoints interpolate the cell's own chord with its neighbors' via the same edge-mirrored gradient probe style the file already uses elsewhere, gated by STRICT neighbor eligibility: a neighbor participates only if its own entry AND exit are finite, it is in-target, it carries the SAME winner mesh id as this cell (`GlyphEffectFrameView.winnerMesh`, both ids known — Phase 2 P1 fix: an agreeing normal alone previously let a same-normal neighbor on a genuinely DIFFERENT mesh through, interpolating a dot's endpoint off the near mesh's own surface toward the far mesh's unrelated position), AND its geometric face normal agrees with this cell's (dot > 0.9, which independently catches the crease-edge case — two faces of the SAME mesh with disagreeing normals) — an ineligible axis's gradient defaults to 0, collapsing that axis's sub-rays to the cell's own center chord. One color per cell: the center sub-ray's hit color if it hit, else the first hitting sub-ray's (dot-scan order), else no emission.

**Sphere tracing for carve (qualifying SDF programs only).** `buildGlyphFieldDistanceOracle(program, { bias, gain }, time)` builds a per-voice signed-distance oracle — `D(p) = max_i D_i(p)`, `D_i(p) = (sdf_i(freq_i·R_i(p − o_i)) − c_i) / freq_i` (÷`freq_i` converts the freq-scaled SDF back to domain-unit distance; measured 2.9× overshoot at freq 3 without it) — or returns `null` when the compiled program doesn't qualify; carve marches with `marchGlyphFieldSphere` (the fixed marcher's public sibling) instead of the fixed grid whenever the oracle is non-null, and stays byte-identical to before when it's `null`. Qualifying is conservative, every condition normative: exactly one populated layer, `combine: "min"` (an intersection of ±1 solids — distance to it is the MAX of member distances, not `min`: an executed counter-case shows min-of-distances terminating inside the union where the solid test says empty), `thresholdOn` off, every active voice `menger`/`sierpinski` with `wave: "step"` and `amp === 1` (`gyroid` excluded — its implicit is not a genuine distance), `invert` allowed (negates the whole fold symmetrically, still distance-true), and `bias`/`gain` in the step-selective regime `bias + gain/2 > 0 && bias − gain/2 ≤ 0` (outside it the ±1 field is all-solid or all-empty, so the tracer's target iso isn't the one the solid test reads). The marcher steps by `SPHERE_MARCH_SAFETY · D` (0.9) and, on a sign change, overshoots `SPHERE_MARCH_OVERSHOOT_EPSILON` further into the solid and confirms with the REAL sampler before emitting — `marchField`'s own raw-sample plateau discipline, so a hit never lands on a hard-thresholded field's own zero plateau. **Stall/step-cap-pressure fallback** (amended after measurement): naive distance-stepping alone stalls approaching an off-ray feature on dense recursive fractals — measured 17% of fixed-step's hits lost to cap exhaustion at iter 3. `SPHERE_MARCH_STALL_STEPS` (8) consecutive advances below `SPHERE_MARCH_STALL_ADVANCE`, or the last step of the `SPHERE_MARCH_MAX_STEPS` (64) budget, falls back to a fixed-step scan of the remaining segment — but on the SAME absolute grid a plain fixed-step call over the FULL original chord would use (`fieldStepCount` applied to the full chord length, at the caller's own `steps`/`maxSteps`/`finestFreq`), not a freshly-derived grid for the shorter remaining segment: re-deriving the step count for a shorter segment shifts the Nyquist phase and can legitimately skip a thin feature the full-chord grid's own sample offsets would have caught, so "same per-cell step density" has to mean the same grid phase, not just the same step count, for the hit-set superset guarantee to hold by construction (measured at the time, against two now-removed presets — "Menger SDF"/"Sierpinski SDF", see below — 218/218 and 153/153 fixed-step hits recovered, vs. 182/218 and 127/153 pre-fallback). The equivalence bar: (a) sphere hit set ⊇ fixed-step hit set (restored by the fallback, strict); (b) identical ramp glyph on every shared hit, fallback-produced included — the invariant that actually holds everywhere; (c) sphere's hit distance ≤ fixed-step's and within one fixed step, but ONLY for PURE distance-stepping hits — a fallback hit is a separate `marchField` call over its own independently-quantized remaining sub-segment with no such guarantee relative to the full-chord fixed-step call (measured up to ~0.13 domain units apart on that same fixture). The linear-voice recipe presets (Menger/Sierpinski-membership style) are recipe-based and can never qualify for this path — only a genuine SDF voice (`menger`/`sierpinski`, `wave: "step"`) does. The two presets that originally exercised this — "Menger SDF"/"Sierpinski SDF" (one SDF voice each, carve, iter 3) — and the only other sphere-tracing-qualifying preset, "SDF bloom" (an animated variant of "Menger SDF"), were all three removed in a later preset cull (see "Preset named exports" above); no shipped preset currently exercises the SDF voice family or sphere tracing, though the mechanism remains fully implemented and tested. Measured speedup at the time: ~1.8-1.9× vs. fixed-step on the pinned half-covered 120×48 iter-3 scene (the design's drafted ≥2× floor assumed no stalls; the honest floor accounting for the fallback's own cost is lower, revised to ≥1.5×, which this cleared).

**Authoring tier: 9 voices, duty-aware Nyquist floor, program builder, program-as-data.** `SYNTH_VOICES` is 9 (bumped from 6); voices 7-9's key families are appended at the schema TAIL, never interleaved into the original `voice1..6` blocks — append-only ordering is load-bearing for the `/synth` URL codec's positional decode. The module-load schema guard now checks every one of the 14 per-voice key families (was 7 of 14), so a future voice bump can't ship with half its keys unchecked. The website imports `SYNTH_VOICES` directly instead of an independent `MAX_VOICES = 6` duplicate; voice Add caps at 9, layers stay 1..3. `voiceColorsAll`'s baked snapshot size changes with `SYNTH_VOICES` (re-pinned deliberately); render byte-identity holds regardless, since amp-0 voices are skipped in every fold and the exporter filters them the same way.

`effectiveVoiceFinestFreq` (the shared Nyquist step-count floor's per-voice input) is duty-aware for `square`-wave voices: `freq / min(duty, 1 − duty)` (two samples per narrowest band), replacing the old one-sample-per-band `2·freq` convention (at `duty = 0.5` the floor doubles — `freq → 2·freq` — a one-to-two-samples-per-band convention change, not an identity; no shipped preset's floor binds either way). `step` is non-periodic and unaffected; `sin`/`triangle`/`saw` keep plain `freq`. No shipped preset's floor changes (no shipped preset's finest voice bound the old formula); only patches with `chord · f_eff > marchSteps / 2` — the previously under-sampled class the fix targets — change. This makes the depth-3 Menger recipe safe: its finest band (1/27) now needs 94 steps, well inside the 256 cap (VOLUMETRIC-2.md's "depth-3 needs ≥~281 steps, out of v1's envelope" rationale used the un-fixed formula and was wrong by 3×, corrected here and in `bench/carve-march.md`). The depth-3 recipe no longer ships as its own preset (a later preset cull removed the standalone "Menger sponge" preset that used to carry it, though `GlyphCssGraphicsMengerPreset` still inlines the exact same recipe — see "Preset named exports" above); the gating remains as an EMPIRICAL hit-set-equality check against a 256-step ground-truth march on the acceptance scene, kept alive as a standalone params fixture in stock.test.ts — not formula trust, since no frequency bound can guarantee a thresholded multi-layer fold doesn't produce a wall thinner than its voices' nominal frequency implies.

`buildGlyphFieldProgram({ domain, layers: [{ combine?, threshold?, invert?, blend?, mix?, voices: [{ field, wave, freq, … }] }] })` (public, `@glyphcss/effects`) fills every IR default — including `sourceIndex`, numbered in flat authoring order, exactly mirroring field-synth's own flat-schema→IR compile — from the pleasant `voices: [...]` authoring surface; there is no `"inherit"` combine value (that's relative to a patch-level `combine` a hand-built program has no equivalent of), so `combine` defaults to `"multiply"` instead. `validateGlyphFieldProgram(program)` shape-validates an arbitrary value (layers/voices/origin fields/enum membership) before it reaches `evaluateFieldProgram`'s unguarded per-voice/per-layer dereferences, throwing a descriptive `TypeError` on the first structural problem rather than repairing or coercing.

**Program-as-data.** A `program?: unknown` option on `GlyphEffectDefinitionLayerOptions` (packages/glyphcss) carries an opaque, definition-owned program payload — glyphcss never imports or interprets it (the dependency points the other way: `@glyphcss/effects` depends on `glyphcss`, never the reverse) — forwarded unchanged onto `GlyphEffectEvaluateContext.program` and, when a definition supplies a `validateProgram(program)` hook (field-synth's own delegates to `validateGlyphFieldProgram`), validated once at MOUNT, not on every params transaction. Immutable after mount: the imperative handle's `setOptions` throws on a genuinely different `program` value (remove and re-add the layer to change it), mirroring mesh-handle `target`'s own immutable-after-mount rule; the React/Vue wrappers and `<glyph-effect-layer>` instead forward it ONLY at creation and silently no-op a later prop/config change, since neither diffs it on every render. When `program` is present, field-synth ignores its flat voice/layer params as the field definition (`params` still governs space/render/march/output mapping); `voiceColors` colors and the carve/xray finest-frequency both read from the PROGRAM's own voices, not the ignored flat params, and the `argmax` winner-color lookup is bounds-checked regardless of `sourceIndex` (previously a `sourceIndex ≥` palette length TypeErrored inside the render pass). `buildGlyphFieldSynthStaticExport` rejects a `program` option explicitly, before the flat-param merge/bake, through the same centralized reject gate `space: "object"`/carve/xray already use — an unbounded program-as-data payload has no schema this baked coordinate-table/affine-fit exporter can serialize. Not URL-persistable; the `/synth` page (API-tier only) never sets it.

### Per-mesh detail layers

By default every mesh renders into that one shared base `<pre>`. A mesh can opt into **its own resolution** — set `density` (a multiplier: `density: 3` → 3× the scene's glyph resolution, cell = base ÷ density, isotropic, same on-screen size) or the low-level `fontSize` / `lineHeight` (which override `density`). Such a mesh "pops out" into its **own silhouette-fitted, CSS-translated `<pre>`** rendered at that cell size — so a hero mesh carries far more detail while the rest of the scene stays cheap in the shared grid. Browser-only (needs layout to measure cells); works with any camera (ortho / perspective / FPV) — detail meshes render **in place** (real world positions, scaled zoom, offset projection center), and the detail grid is clamped to the viewport so a camera near/inside a mesh can't blow up the render. This is **not** a group/tree concept — it's a per-mesh property on the flat mesh list.

`transparent: true` (default `false` = opaque) makes a mesh see-through (x-ray): it neither occludes nor is occluded. Because a mesh in the shared `<pre>` always occludes (one depth buffer), declaring `transparent` also pops the mesh into its own `<pre>` — separation happens for custom cell metrics **or** transparency.

**Cross-layer occlusion.** Opaque meshes occlude each other across `<pre>` layers via a shared camera-depth pass: `computeOcclusionIds` rasterises all opaque geometry into one id-map (nearest layer per cell), and each layer's `rasterize` blanks cells a *different* layer owns (a layer never occludes itself). Integrated into `rasterize` (an `occlusion` `OcclusionMap` input) so it works for plain text **and** colored spans, and self-disables (zero cost) when no opaque detail mesh exists. Within the shared `<pre>`, meshes occlude each other for free via the normal per-cell depth buffer. The occlusion id-map is built at the **scene's supersample** resolution (same offset-scaling wrapper `rasterizeSolid` uses), so the world's supersampled silhouette and its id-map hole coincide subcell-for-subcell — no 1-cell seam at the world/entity boundary. **Detail layers still render at `supersample: 1`** (already high-res; coverage AA buys little and costs a full extra pass) and sample the supersampled id-map via an `×ss` cell affine. Both world-hole and detail-fill clip to the same id-map footprint, so they coincide (no black-hole, no seam). No-op when `supersample: 1` (id-map = output resolution, byte-identical to the non-supersampled path).

These options mirror across React/Vue `<GlyphMesh>` and the `<glyph-mesh>` custom element (`density`, `font-size`, `line-height`, `transparent`). **Static compile (`compileScene`, `GlyphSceneStatic`, the CLI/Vite plugin) and the interactive/CodePen export take a flat polygon list — they cannot represent per-mesh detail layers**, so per-mesh density/transparent is a runtime-only feature there (the gallery's scene-wide "Density" slider drives the render font-size instead, which *does* export).

### Render modes

| Mode | How cells are filled |
|---|---|
| `wireframe` | Polygon edges rasterised as ASCII rules; glyph weight scales with edge prominence |
| `solid` | Filled cells; glyph picked from a `CharRamp` by Lambert-shaded intensity |
| `voxel` | Cube-aligned geometry; face normals drive glyph selection |
| `ink` | Silhouette + crease outline only (interior empty); oriented glyph (`_ / \| \ - ‾ ▏ ▕`) traces the smoothed contour tangent |

`mode: "ink"` detects silhouette edges (adjacent triangles' front/back-facing sign flips, same screen-space convention `solid` mode's backface cull uses — view-dependent, correct under both ortho and perspective) and crease edges (dihedral angle beyond a fixed 35° threshold, always drawn independent of view), plus boundary edges on open meshes; an edge is only ever drawn when at least one adjacent triangle is front-facing. Kept edges are chained into a per-vertex screen-space tangent field via central differencing (most-anti-parallel neighbor pair at a junction), then smoothed with two passes of sign-aligned neighbor averaging — this is what turns per-triangle-edge stair-stepping into a tangent that reads as continuous along a sphere/torus silhouette. The smoothed tangent quantizes into four 45°-wide direction buckets (horizontal / `\` / vertical / `/`); the horizontal bucket further picks `‾`/`-`/`_` from the cell's fractional vertical position, and the vertical bucket mirrors that onto the column axis, picking `▏`/`|`/`▕` (LEFT ONE EIGHTH BLOCK / VERTICAL LINE / RIGHT ONE EIGHTH BLOCK — verified font-distinct, not invented) from the cell's fractional horizontal position; without this a stroke could wander within a cell while its glyph stayed fixed, reading as head-on wobble. The diagonal buckets (`\`/`/`) do not get sub-cell discrimination — no monospace font renders an offset diagonal variant, and a diagonal stroke already spans its cell corner-to-corner. Interior cells stay empty by design — hatching/texture fills are future effect-layer work, not baked into this mode. `charMode` and `wireframeJunctions` are wireframe-path-only concerns and are documented no-ops in `ink` (it always renders its own fixed oriented-glyph set as plain ASCII, independent of `glyphPalette` too). `hiddenLines: "hide"` IS wired in `ink` — see below. `ink` is a runtime-only render mode for now, same as `wireframe`/`solid`/`voxel`.

When two kept edges of EQUAL `rank` contest the same cell — the reported case being an extruded letter's own front-face silhouette and a farther extrusion side wall, both `rank: 1` — the winner is the NEARER one (camera-space depth, same "larger = nearer" convention `fillDepthTri` uses), not whichever segment happened to rasterize last. This is unconditional, not gated behind `hiddenLines` (which only drops an edge that fails a depth test along its ENTIRE length; two visible, un-hidden edges can still tie for a cell, and that's what this resolves). Depth is the same per-vertex `camera.project` result already computed for screen position, cached alongside it — no second projection pass — and lerped along each segment exactly like its tangent/color. Because this only changes which already-kept, already-visible stroke wins a contested cell, it cannot blank a cell the way the two per-sample hidden-line attempts recorded in `research/contour-first-text/decisions.md` did; the convex-mesh regression suite (cube, icosahedron, sphere subdiv 2 and 3) confirms identical inked-cell counts before and after.

`charMode: "ascii" | "braille" | "halfblock" | "quadrant"` (scene option, default `"ascii"`) selects the character encoding used for rasterized output. `"ascii"` is the rule-glyph encoding above. `"braille"` (`wireframe`-only) packs a 2×4 subcell dot-coverage grid into each output cell as Unicode Braille Patterns (`U+2800`..`U+28FF`), giving up to 8 independent sub-cell "pixels" per glyph — visibly smoother diagonal/curved edges than a single ASCII rule glyph per cell. It runs the same `transformCells` post-rasterize hook as the ASCII path. `charMode: "braille"` is a documented no-op in `solid`/`voxel`/`ink` modes — braille dot coverage is binary and cannot carry a Lambert shade ramp, a voxel face-normal glyph, or ink's oriented direction glyph, so those modes always render ASCII regardless of this option.

`charMode: "halfblock"` (`solid`-mode-only) is the mirror trade-off: braille buys SHAPE resolution at one color per cell; halfblock buys COLOR resolution at coarse (block) shape — exactly where solid mode's shade ramp already loses per-subcell color by averaging supersampled subcells into one glyph. It reuses that same supersample pass (internally forcing an even supersample of at least 2 when the scene didn't already request one) and independently averages the TOP half and BOTTOM half of each cell's subcells, then picks a glyph from the resulting per-cell decision table: neither half covered → a bare space with no color and no background (a cell with no geometry never paints an opaque rectangle); both halves covered with the SAME resolved color → `█` (full block) with just `color` set, no `background-color` — cheaper markup, and the cell merges into a same-color run exactly like the ASCII solid path; both halves covered with DIFFERENT colors → `▀` with `color` = the top subcell's color and `background-color` = the bottom subcell's color; only one half covered → `▀` (top) or `▄` (bottom) with that half's color as `color` and no background, so the uncovered half shows the page/`<pre>` background instead of a painted rectangle. A run only merges consecutive cells when BOTH colors match (`encodeGlyphBuffersDual` in `render/cells.ts`, a sibling encoder to the single-color `encodeGlyphBuffers` — it does not extend the shared `CellGrid` contract, so the `transformCells` hook and the generic effect compositor stay exactly one-color-per-cell). `charMode: "halfblock"` is a documented no-op outside `solid` mode, and also a no-op alongside a `transformCells` hook or active `temporalBlend` reprojection — both already expect and produce the existing one-color-per-cell grid, and halfblock's two-color split has no equivalent there.

`charMode: "quadrant"` (`solid`-mode-only) generalizes `"halfblock"` from a 1×2 (top/bottom) subcell split to a full 2×2 split, buying BOTH shape and color resolution at the same two-colors-per-cell markup cost — half-block's `▀`/`▄` are two of the 16 masks this mode picks from (space, `▘▝▖▗▀▄▌▐▚▞█`, and the four three-quadrant glyphs `▛▜▙▟`, covering every possible binary 2×2 coverage pattern exactly, with no approximation). It shares halfblock's eligibility rule and forced even supersample (`≥2` in both axes, so each output cell splits into four TL/TR/BL/BR subcell regions), and the same never-paint-an-empty-region discipline. Per cell: no region covered → a bare space, no color, no background. 1-3 regions covered → the exact coverage-mask glyph (14 distinct partial silhouettes vs. halfblock's fixed top/bottom split — the shape win) with ONE coverage-weighted average color across the covered regions and no `background-color` (a background would have to paint an uncovered region, which this mode — like halfblock — never does); distinct true colors among the covered regions collapse into that single average. All 4 regions covered → the color win over plain solid-mode averaging: same resolved color on all four → `█` with just `color` set (the halfblock-style cheapest-markup case); otherwise the 4 regions split into a "high"/"low" luminance group by comparison against their mean (deterministic, not real k-means clustering) and render as the matching two-tone mask with `color` = the high group's average and `background-color` = the low group's — a genuine two-color split of the whole cell, since full coverage is the only state where a background can never touch an uncovered region. A degenerate split (every region on the same side of the mean) falls back to the same-color `█` case. What's lost vs. per-subcell-exact color: a partially-covered cell with more than one true subcell color still collapses to one average; a fully-covered cell with more than two true colors collapses to whichever two-group luminance split the mean threshold produces, not a globally optimal partition. Same `encodeGlyphBuffersDual` two-color encoder halfblock uses — `CellGrid`/`transformCells`/the generic effect compositor stay untouched.

Both `"halfblock"` and `"quadrant"` are documented no-ops outside `solid` mode, and no-ops alongside a `transformCells` hook or active `temporalBlend` reprojection — both already expect and produce the existing one-color-per-cell grid, and neither's two-color split has an equivalent there. Both are also no-ops alongside `solidWeightRamp` (neither's two-color-per-cell encoding has a font-weight span). Mirrored as `char-mode` on `<glyph-scene>` and `charMode` on the React/Vue `<GlyphScene>`. `charMode` is also reachable from the static path — `compileScene` and `GlyphSceneStatic` (React + Vue) accept and forward it, so braille/halfblock/quadrant output can be baked at build time, not just rendered at runtime.

`wireframeJunctions: boolean` (scene option, default `false`) is a `charMode: "ascii"`-only refinement, orthogonal to `charMode` itself: the default per-cell wireframe glyph is picked independently per edge (weight tier → random glyph from the active palette), so two edges meeting in one cell — a corner, a T-junction, a crossing — render whichever edge rasterized last, which visibly breaks at joints. When `true`, a second pass runs over the finished wireframe stamp: every near-axis-aligned edge accumulates which of a cell's four sides (N/E/S/W) carry a line into a per-cell mask, and any cell with a non-zero mask renders from the fixed `┌┐└┘├┤┬┴┼─│` box-drawing set keyed by that mask instead of the random pick — so a joint resolves to ONE glyph consistent with every edge touching it. An edge counts as "near-axis-aligned" when its two projected endpoints round to the same output row (near-horizontal) or the same output column (near-vertical) — under half a cell of perpendicular drift across the edge's whole screen-space length; this scales with edge length instead of a fixed angle constant. A diagonal-dominant edge contributes nothing to the mask, so its cells keep the existing slope-glyph behavior unchanged. It is a pure post-rasterize resolve pass over the same stamp (no geometry-pass change) and runs the same `transformCells` hook as the untouched path; `false` (the default) keeps `rasterize` byte-identical. Mirrored as `wireframe-junctions` on `<glyph-scene>` and `wireframeJunctions` on the React/Vue `<GlyphScene>`. Unlike `charMode`, it is runtime-only — `compileScene`/`GlyphSceneStatic` do not expose it.

`solidWeightRamp: { glyph: string; weight: number }[]` (scene option, `solid`-mode-only, default `undefined`/off) is a second density axis for solid-mode shading: CSS `font-weight`. A weighted ramp is a sequence of `(glyph, weight)` steps ordered darkest → densest by MEASURED ink coverage — `@glyphcss/effects`'s `calibrateWeightedGlyphRamp` crosses a glyph pool against candidate `font-weight` values through the same real-canvas measurement `calibrateGlyphRamp` uses, so this is never a hand-authored table. It cannot be expressed as the existing plain ramp string (`glyphPalette`'s `.solid: string[]`), since a plain ramp has no weight dimension — so it is its own option, and when set it REPLACES `glyphPalette`'s solid ramp entirely for that render (both the glyph sequence AND the weight lookup come from the steps). This is safe because bold measurably does NOT change monospace advance width in every tested stack (Menlo, Courier New, Monaco, Andale Mono, the gallery's `ui-monospace, "JetBrains Mono", "SF Mono", "Menlo", monospace` stack — including for a browser-SYNTHESIZED bold when a font lacks a real bold face), so a weight-bearing span can never desync the character grid; `encodeGlyphBuffers` starts a new run on a weight change alongside color, landing `font-weight` in the same `<span style="...">`. Measured payoff (Menlo, 10-glyph pool): glyph-only ramp reaches 10 steps / coverage 0.3295; the weighted ramp reaches 15 steps / coverage 0.4508 — more distinguishable shading buckets and a darker dark-end than glyph shape alone reaches. `undefined` (the default) keeps `rasterize` byte-identical — the per-cell `weight` buffer (`CellGrid.weight?: Uint16Array`, `0` = no override) is never allocated or written. Documented no-op outside `solid` mode, under `charMode: "halfblock"` or `"quadrant"` (both two-color-per-cell encoders have no font-weight span either), and during active `temporalBlend` reprojection (which blends the ramp index continuously across frames and has no notion of a parallel weight lookup) — same precedent as `charMode: "halfblock"`'s own no-op list. The `transformCells` hook and `rasterizeToCells`'s `CellGrid` both carry the live `weight` buffer when the option is active, so an effect can read or rewrite it like `color`. Mirrored as a `solidWeightRamp` JS property on `<glyph-scene>` (not an attribute — the ramp is data, the same "JS property, not attribute" rule `sceneManifest`/`dictionary` use) and `solidWeightRamp` on the React/Vue `<GlyphScene>`. Also reachable from the static path — `compileScene` accepts and forwards it (plain step data, no browser/canvas dependency at compile time, exactly like `charMode`), so a weighted-ramp render can be baked at build time too.

`hiddenLines: "show" | "hide"` (scene option, default `"show"`) is hidden-line removal for the `wireframe` render path, including `charMode: "braille"`. The wireframe path otherwise has no depth reference at all: edges rasterize in mesh/array order, and `drawLineToStamp` resolves a contested cell by edge WEIGHT (`if (stamp[idx] < val)`), not by which edge is actually nearer the camera — so a mesh's back side can paint its extrusion side walls over a front face, braille strokes from a farther stroke can bleed into a nearer one's dot pattern, and a darker `sideColor` edge can overwrite a brighter front-face color. `"hide"` depth-tests every wireframe stroke sample (per-cell for ASCII, per-cell for braille too — measured 777 vs 786 inked cells for 25% more cost at per-subcell resolution, not worth it) against a solid surface prepass — the same triangle-depth rasterizer `computeOcclusionIds`/cross-layer occlusion uses — with a slope-scaled depth bias: `allowed = bias + slopeScale * |local screen-space depth gradient|` (the standard shadow-map slope-scaled-bias technique). The gradient term is load-bearing, not cosmetic: a FLAT bias (`slopeScale = 0`) regresses every convex mesh at every magnitude tried (cube -11..-32, icosahedron -5..-44, sphere -12..-158 inked cells vs. ground truth), because a smooth surface's own silhouette lies ON the contour it outlines and needs an allowance proportional to the local depth gradient, not a constant one; `slopeScale ~0.5` converges within ~0-4% of analytic ground truth (cube 115→115, icosahedron 177→173-175, sphere 431→426-430) and is the shipped internal constant (bias 0.03, not a public option). Documented no-op in `solid` mode (already depth-buffered per cell via the normal scan-fill depth test).

`ink` also wires `hiddenLines: "hide"`, but with an IDENTITY-based occlusion test, not the wireframe margin-based one reused as-is. Two earlier bias-based attempts (flat, then slope-scaled, applied per-sample and then per-edge) both fought SELF-occlusion — a sphere's silhouette lies ON the sphere, so the surface occludes its own outline, and any margin large enough to prevent that ate 38-46% of the silhouette anyway (recorded as ruled-out attempts in `research/contour-first-text/decisions.md`). The fix excludes the caster from its own test, the same principle as shadow-map self-shadow exclusion: `buildInkOcclusionMap` rasterizes every ink triangle into a depth+id buffer (id = triangle index, reusing `fillDepthTri`, the same rasterizer `computeOcclusionIds` uses), and each kept silhouette/crease edge carries its own local vertex-topology neighborhood (`edgeOwnFaceIds` — the triangles touching either endpoint, one vertex-ring hop out) as an exemption set. A stroke sample is hidden only when a DIFFERENT, non-exempt triangle wins that cell and is nearer by more than a residual `depthGradient`-scaled allowance (the same screen-space depth-slope probe wireframe HLR uses, needed only to absorb the tiny chord-vs-curve discretization noise between a fine mesh's neighboring facets — not a self-occlusion margin, since identity already handles that). A flat constant residual was tried and rejected: it rescued one world scale and regressed a 10x-larger sphere in the same projection by up to -60%, reproducing the original failure one scale away — the gradient term is load-bearing because it scales with the mesh's own local screen-space depth variation. `INK_HLR_RING = 1` / `INK_HLR_SLOPE_SCALE = 2.5` are the smallest combination measured to hold cube/icosahedron/sphere (subdiv 2 and 3) to exactly 0 delta across five world-scale/projection combinations; because self-occlusion is handled by identity rather than margin, the test runs per-SAMPLE (not per-edge), so a wall edge only partly behind a cap now hides just the covered portion instead of the old rule's all-or-nothing whole segment. On the motivating extruded-text repro (`Glyph\nCSS`, depth 80, curveSteps 4, turn -38 tilt 0.2) this takes inked cells from 1152 (show) to 914 (hide, -20.7%), with the interior cross-letter/side-wall clutter visibly reduced — the previous per-edge design only reached -1.9% on the same repro. Mirrored as `hidden-lines` on `<glyph-scene>` and `hiddenLines` on the React/Vue `<GlyphScene>`. Unlike `wireframeJunctions`, it IS exposed by `compileScene`/`GlyphSceneStatic` — like `charMode`, it's a pure function of geometry + camera, and it fixes a genuine occlusion defect a static bake shouldn't reproduce.

`colorTolerance: number` (scene option, default `0` = off, byte-identical) merges adjacent same-glyph cells into one `<span>` while their colors stay within this redmean colour distance of a held run **anchor** — spans are what gate frame rate for colored output, and this directly minimizes span count for a given colour error. Range is `0`–`765`, not `0`–`255` (black↔white is 764.83 under redmean); the public surface validates at that layer — `NaN`/negative degrades to `0`, `+Infinity` merges every same-glyph run in a row. It is a **lever, not a flat multiplier**: `bench/color-tolerance.md`'s reproducible six-preset table (`node bench/color-tolerance.mjs`, matched to ~8 mean redmean error) measures a 1.2x–9.1x reduction in spans from unquantized to the best merge policy — Aurora 1.2x, Lava 1.3x, Nebula 1.5x, Menger 2.9x, Breathing gyroid 9.1x; Cube tiles (already flat, an `argmax` tiling) gains nothing at 1.0x, on purpose, and does not regress. An earlier hand-measured 1.6x–31x figure from a different, non-reproducible rig is superseded by this table — do not cite it. Flat, hard-edged output (per-face colour, carved solids) wins enormously; smooth noisy fields win modestly because their spans are dominated by genuine per-cell variation no merge policy can invent coherence around. Monotonicity (raising tolerance never raises span count) holds on every shipped preset measured but is **not a general guarantee** — greedy re-anchoring admits local non-monotonicity (a larger tolerance can let an early run swallow one more cell, moving the next anchor to a strictly worse centre for what follows); worst magnitude observed at grid scale is +5.4%. One exported comparison test, `colorRunExtends` (`packages/glyphcss/src/render/cells.ts`), backs all four coalescers glyphcss can emit colour from so they can't drift out of sync: `encodeGlyphBuffers` (single colour), `encodeGlyphBuffersDual` (`charMode: "halfblock"`/`"quadrant"`'s two independent channels, where a run requires *both* foreground and background to match), and `rasterize.ts`'s two DUPLICATE coalescers — `solidBufToString`'s unsafe branch (the common no-`transformCells` solid/ink/braille render path) and `stampToGlyphs` (the plain-`charMode: "ascii"` wireframe/voxel no-hook path) — neither of which calls `encodeGlyphBuffers` and would otherwise silently lack the feature. Routing either unsafe path through `encodeGlyphBuffers` itself was measured and rejected: its per-cell `assertGlyph`/`assertColor` validation costs ~90-100% more time per call at ~86k cells. Composes normally under active `temporalBlend` reprojection (a pure post-hoc merge over the same one-colour-per-cell grid TAA already produces — no structural conflict) and is a documented no-op under `glyphOutput: "semantic"` (semantic colours are exact class identifiers, not shaded appearance, so merging them would corrupt the lineage `scene.getGlyphSemanticCellFrame()` reads). Mirrored as `color-tolerance` on `<glyph-scene>` and `colorTolerance` on the React/Vue `<GlyphScene>`, and forwarded by `compileScene`/`GlyphSceneStatic` — like `charMode`/`hiddenLines`/`solidWeightRamp`, it is a pure function of geometry + camera reproducible at build time, though mechanically it alone operates on the already-rasterized cell grid rather than changing rasterization itself. None of the four reach `buildGlyphFramesExport`, `buildGlyphInteractiveExport`, or `buildGlyphFieldSynthStaticExport` — a `colorTolerance` set through the `/synth` page's UI persists to the URL but is silently dropped by that page's CodePen export.

### Shadows

Shadows are opt-in per mesh. To enable them, set `shadow: GlyphShadowOptions` on the scene (undefined by default = no shadows). Then flag individual meshes with `castShadow` (default false) and/or `receiveShadow` (default false). A mesh that is both cast and receive self-shadows — this is free because glyphcss uses a **shadow-map** technique (render depth from the light, compare per cell) rather than polycss's analytic SVG projection. `GlyphGround` defaults `receiveShadow=true`, `castShadow=false`.

| Option | Type | Default | Description |
|---|---|---|---|
| `shadow.color` | `string` | `"#000000"` | Shadow tint hex color |
| `shadow.opacity` | `number` | `0.25` | Darkness 0..1 toward `color` |
| `shadow.lift` | `number` | `0.05` | Depth bias — prevents self-shadow acne on flat lit surfaces |
| `shadow.maxExtend` | `number` | `2000` | Half-extent of the light-space projection volume |

### Hotspots

Hotspots are 3D anchors that produce positioned 2D hitboxes in the consumer's DOM. The rasteriser projects each `Hotspot.at` point through the camera and returns a `HotspotCell` (col, row, depth, visible). Consumers absolute-position a `<div>` at the cell — the rasteriser only computes the position; it does not emit the DOM node.

## Compilation (static & interactive)

Because `rasterize` is pure (geometry + camera → string), a scene can be rendered **at build time / on the server**, not just in the browser. This is glyphcss's static story — the render *is text*, so it inlines into HTML with no runtime.

- **`compileScene(opts)`** (in `glyphcss`, pure) — polygons + camera + options → the `<pre>` string. **Byte-identical to the runtime render** for the same inputs; same defaults as `createGlyphScene`. The foundation for every adapter.
- **`@glyphcss/compile`** — Node adapters around `compileScene`: `loadMeshFromFile`, `compileFile`, a **Vite plugin** (`import x from "./m.glb?glyph&…"` → baked `<pre>`), a **CLI** (`glyphcss`), and `compileInteractive`.
- **Control-map export compatibility** — `writeGlyphControlMaps` defaults to the frozen `glyph-control-export/v1` directory and manifest contract. B44 appearance controls are opt-in only through `appearanceRgb: "albedo-and-target"`; that writes separately hashed `albedo-rgb-u32` and `target-rgb-u32` maps under the distinct `glyph-control-export/v2` manifest contract. Default exports never gain those files or a schema-version change.
- **`GlyphSceneStatic`** (React + Vue) — SSR/SSG component that renders the compiled `<pre>` with no client runtime (mirror of each other; static counterpart to `GlyphScene`).
- **Frame-roll export** — `buildGlyphFramesExport(polygons, { frameCount, durationSec, rotX, rotY, zoom, … })` (pure, browser-safe, in `glyphcss`): bakes a turntable of `frameCount` full `compileScene` renders, stacks them in one `<pre>`, and cycles them with a pure-CSS `steps()` animation — **zero runtime JS**, faithful per-face color, instant paint. Trade-offs: discrete angles (smoothness ∝ `frameCount`), fixed resolution, and payload grows **linearly** with `frameCount` (a colored frame costs several KB gzipped even after cross-frame color-class dedupe) — good for a handful of frames, not for a long or continuous loop.
- **Interactive export** — `buildGlyphInteractiveExport(polygons, { interactions })` (pure, browser-safe, in `glyphcss`): the declared interactions (`orbit`/`zoom`/`pan`/`fpv`) drive **both** the wired control (only that one is imported → the snippet tree-shakes) **and** the decimation budget (`decimatePolygons` — coarser for orbit, finer when `zoom`/`fpv` let the camera approach). Output is a self-contained CDN+inlined-mesh snippet; `glyphCodepenPrefill` turns it into a CodePen POST (the gallery's "CodePen" button). Less declared interactivity = less mesh + less runtime shipped. An optional `effect: { id, params, blend?, timeScale? }` mounts a live **stock** `@glyphcss/effects` layer: the snippet adds a second `import { getGlyphEffect } from "https://esm.sh/@glyphcss/effects@<ver>?deps=glyphcss@<ver>"` (same `<ver>` as the glyphcss import; `?deps` dedupes the shared glyphcss module instance), resolves the effect by id at runtime (`glyphcss` itself never imports `@glyphcss/effects` — that dependency only points one way), calls `scene.addEffectLayer(...)` after the scene/controls are wired, and — when `timeScale > 0` — appends a small `requestAnimationFrame` loop driving `params.time`. This is the export for a **moving-camera or multi-effect** scene (the gallery's "CodePen" button); it ships the glyphcss + effects runtime from the CDN.
- **Static effect export (field-synth)** — `buildGlyphFieldSynthStaticExport(polygons, { params, blend, loopSeconds, cols, rows, … })` (pure, browser-safe, in `@glyphcss/effects` — not `glyphcss`, since it needs a stock effect's own math): for an **effect-only, static-camera** scene (fixed mesh + camera, only the field-synth texture animating over `time`), bakes the static base grid plus each covered cell's resolved field-synth domain coordinate **once**, reusing glyphcss's real rasterizer + effect-input machinery, then ships a tiny hand-written vanilla-JS field-synth evaluator that recomputes the pattern every `requestAnimationFrame` — **zero imports, zero CDN, zero `glyphcss`/`@glyphcss/*` at runtime**. Fixed payload regardless of loop length and continuously smooth, unlike a frame-roll export whose payload grows with frame count; see `bench/static-effect-export.md` for the size/quality trade-off that motivated shipping this over more prebaked frames. Always reads the layer's **real** `blend` (`over` vs `replace`), never the effect definition's `defaultBlend` UI metadata. Field-synth only today — the `/synth` page's export button is the reference caller; a future effect id needs its own exported coordinate resolver (mirroring `fieldSynthCoordinate`) plus a hand-written inlined-JS port of its per-cell math, since there's no way to ship an arbitrary `GlyphEffectProgram.evaluate()` without shipping glyphcss's effect runtime alongside it. Two further bakes shrink this for the common flat-surface case (the `/synth` page's default fullscreen plane): when every covered cell's per-cell domain coordinate fits an AFFINE function of grid `(col,row)` within a tight residual (a least-squares fit checked against every cell, not just on average, so a genuinely curved surface can't be mis-fit) AND, evaluated through the real field program, never flips a cell's actual ramp index, argmax winner, `subcellRes: "2x4"` dot mask, or `"ink"` crossing/stroke bucket relative to the true coordinate — a residual bound alone can't rule that out, since the fit's own least-squares solve leaves numerical noise (~1e-8, not real curvature) even on an exactly-affine surface, and `Math.floor` (every duty/threshold discontinuity) has no continuity guarantee at an exact boundary a symmetric setup can legitimately land several cells on — the per-cell coordinate table (and, for `subcellRes: "2x4"`/`"ink"`, the coordinate GRADIENT table those need) is replaced with 6 fitted scalars and a one-line runtime formula (the gradient too, since a truly affine coordinate's gradient is exactly the fit's own slope); curved/projected surfaces (cube, sphere, …), and flat surfaces whose fit would flip a decision (an argmax lattice, a hard threshold), fail that check and keep the table — baked at full float64 precision, like the `cx`/`cy` field-recentering origins radial/angular/spiral fields read, since any of them can feed the same discontinuity-sensitive math. Separately, when the effect covers every grid cell with `blend:"replace"` at opacity 1 (the base contributes provably zero weight to every composited cell), the baked base glyph/color grid is skipped too. `subcellRes: "1x1"` (the ramp path), `"2x4"` (braille dot mask), and `"ink"` (contour) all export, verified byte-exact against the real `createGlyphScene` renderer, not a second compositor implementation.

**Volumetric field-synth (`space: "object"`) and `render: "carve"`/`"xray"` reject explicitly** from `buildGlyphFieldSynthStaticExport`, each checked before the generic `space` reject so the thrown error names the actual mistake — a per-cell-per-frame march (carve/xray) is a different export design than this bake's affine-fit/coordinate-table strategy, not planned. An active voice (`ampN > 0`) with `fieldN: "linearZ"` or a nonzero `originWN` also rejects explicitly, worded separately from the generic `space` reject — both are otherwise 3D-only semantics with no meaning in the 2D branch this exporter ports, and a precise per-field error beats folding that into the `space` reject when the likely mistake is forgetting to also flip `space` to `"object"`. That `originWN` reject is EXEMPTED for an active SDF voice (`gyroid`/`menger`/`sierpinski`): the SDF family genuinely reads `originW` even in the 2D branch (its translation contract, see above), so a nonzero `originWN` on one of those fields is ported and exported normally, not rejected; every other field still ignores `originW` in 2D and the reject stands for them. `gyroid`/`menger`/`sierpinski` and the `step` wave otherwise export normally in the 2D branch, at real-renderer exact parity, like every other field/wave. `isGlyphFieldSynthStaticExportSupported(params)` is the pure predicate mirroring the exporter's own reject rules — merges `params` over defaults and returns whether `buildGlyphFieldSynthStaticExport` would accept them, so a UI gates its export button on this instead of duplicating the reject list; the `/synth` page's CodePen-export gate is the reference caller. The **interactive/CodePen exporter is the export path for a volumetric or carve/xray patch** — it mounts the live effect runtime from the CDN, so it evaluates the real 3D branch/march every frame instead of baking a static approximation.

Dynamic Glyph Effect layers are otherwise runtime-only: `compileScene`/`GlyphSceneStatic` and the frame-roll export do not serialize or evaluate a mounted effect. Two paths do carry a live effect: the **interactive/CodePen exporter** mounts a **stock** effect by id from the `@glyphcss/effects` CDN (a custom `defineGlyphEffect` can't cross the CDN boundary), and **`buildGlyphFieldSynthStaticExport`** bakes an effect-only, static-camera field-synth scene into a self-contained inlined-JS pen. Neither generalizes to a moving camera plus effect, arbitrary effects in a static bake, or geometry animation.

## No per-frame DOM mutation

The invariant we hold: **each render cycle writes each `<pre>` exactly once** — the base `<pre>` plus one write per per-mesh detail layer (and one `transform` per detail layer for positioning). Cell-by-cell DOM patching, or multiple writes to the same `<pre>` per cycle, are not acceptable.

Hotspot positions update via a single inline-style assignment per hotspot element, not via DOM rebuild.

Controls (orbit, map, first-person) mutate a single camera state object; the rasteriser reads that object when it renders. The JS ↔ DOM boundary is: camera event → update camera state object → rasterise → write one string.

**Interactive LOD.** Cost scales ~quadratically with scene-wide density (font ÷ d → cells × d²), so a tiny cell (high density / small font) can blow the frame budget while dragging (Script + browser Layout/Paint of a huge `<pre>`; colored output's `innerHTML` spans add ParseHTML/Style/Paint on top). The `interactiveDownscale` scene option (default `1` = off) renders at `1/n` resolution *while a control is actively dragging* and restores full detail on release — same on-screen size (camera `zoom` unchanged; bigger cell → fewer cells), just coarser mid-gesture. All three controls signal this automatically via the shared listener registry (`emitInteraction` → `scene.setInteracting`); consumers can call `scene.setInteracting(active)` for custom interaction sources. Mirrored across React/Vue `<GlyphScene interactiveDownscale>` and `<glyph-scene interactive-downscale>`.

**GPU temporal presentation companion.** `createGlyphSurfaceAtlasWebGpuSession`
is a browser-only, imperative image-generation companion, not a glyph render
mode. It keeps surface-addressed RGB/confidence state private on WebGPU,
reprojects stable surfaces from exact control frames, and presents the
immediate RGB result through one persistent adjacent canvas. It never changes,
reads, or replaces the scene's `<pre>`, and has no CPU/WASM presentation
fallback. `readback()`, `checkpoint()`, and optional presentation capture are
explicit untimed integrity boundaries. Device loss and destruction invalidate
the whole session. React and Vue mirror the factory and types as re-exports;
there is no framework component because the session is not scene ownership.
The additive diagnostic `submitProfiled()` follows the same internal submit
path and reports CPU routing, upload, dispatch encoding, render encoding,
canvas-submit, and GPU-completion milestones plus optional WebGPU
`timestamp-query` compute/render durations; normal `submit()` does not allocate
profiling resources.

## Naming

Every public export gets a `Glyph` prefix. Exceptions are generic math/geometry types (`Vec2`, `Vec3`, `Polygon`, `TextureTriangle`) and the explicit `*/three` compatibility subpaths, where Three-compatible names are the point of the API. React/Vue components in those subpaths still use the `GlyphThree` prefix.

- **Hooks/composables:** `useGlyphCamera`, `useGlyphMesh`, `useGlyphSceneContext`, `useGlyphAnimation`.
- **Components:** `GlyphScene`, `GlyphSceneStatic` (SSR/build-time `<pre>`, no runtime), `GlyphEffectLayer`, `GlyphPerspectiveCamera`, `GlyphOrthographicCamera`, `GlyphOrbitControls`, `GlyphMapControls`, `GlyphFirstPersonControls`, `GlyphAxesHelper`, `GlyphDirectionalLightHelper`, `GlyphThreePerspectiveCamera`, `GlyphThreeOrthographicCamera`, `GlyphThreeMesh`.

## Numeric conventions

These conventions are the native glyphcss/voxcss surface. The `*/three` subpaths are the exception: they use Three.js units and frames, then convert internally.

- **Rotation units: degrees.** `rotX`, `rotY` on cameras and the `rotation` prop on meshes are all in degrees (XYZ Euler). `rotX=65, rotY=45` is the classic isometric-ish viewpoint. Do not use radians — the asciss-lineage radian convention has been replaced.
- **Camera `zoom`: absolute, CSS pixels per world unit.** `zoom=50` means one world unit maps to 50 CSS px. This matches voxcss/polycss's public camera API; internally those engines author geometry at `BASE_TILE=50` and apply `scale(zoom / BASE_TILE)`. This is not a fraction of the viewport.
- **Perspective `distance`: default `0`.** With the default CSS-perspective projection, `distance` is a CSS-pixel pull-back matching voxcss/polycss. In legacy `perspective: 0` mode only, it keeps the old world-unit pinhole semantics.
- **Directional light `direction`: source-vector convention.** `GlyphDirectionalLight.direction` is the unit vector from the shaded surface toward the distant light source, matching polycss/voxcss. A vector pointing up-right-forward lights faces whose outward normals point up-right-forward.

## Cross-package discipline

The React and Vue packages are mirror images. **Any public API change in one must land in the other in the same PR.** Same names, same arguments, same defaults, same return shapes (allowing for idiomatic differences — refs vs reactives, `useEffect` vs `watchEffect`).

When you change `packages/glyphcss` or `packages/core` in a way that affects the public surface (new option, renamed export, changed default), the React and Vue bindings update in the same PR. Don't ship a glyphcss change that leaves the bindings stale.

Before opening a PR:

- [ ] If I touched a React component/hook, the Vue composable/component matches.
- [ ] If I touched a Vue component/composable, the React component/hook matches.
- [ ] If I added an option to a `glyphcss` factory, both bindings expose it.
- [ ] If I renamed a `core` export, every package that imports it is updated.
- [ ] Website docs (`website/src/content/docs/**`) and READMEs reflect any user-visible change.
- [ ] If I changed a render mode, naming convention, or the DOM-mutation rules, `AGENTS.md` reflects the new state in this same PR.

## Iterating on the system

The rendering model, naming conventions, and cross-package contracts described in this document are the *current* design — not frozen. Render modes can be added or removed, the public API will keep evolving. The rules for evolving them:

- **AGENTS.md is the canonical reference.** Edit it directly; `CLAUDE.md` is just a symlink that exists so Claude Code finds the same content.
- **Architectural changes require user approval.** Dropping a render mode, adding a new one, renaming a public-facing convention, changing what JS is allowed in the render path — propose, don't decide. The user (human) is the architect.
- **Same-PR sync.** Any PR that adds, removes, or materially changes a render mode, naming rule, or cross-package contract must update `AGENTS.md` in the same PR. An API change that lands without an AGENTS.md update is an incomplete change.
- **Don't append-only.** Prune content that no longer reflects the codebase. If a mode is dropped, remove its row from the table. If a hook is renamed, update the naming section in place — don't list the old name "for reference".

## Backward compatibility

- **No BC shims.** Clean breaks only. No re-export aliases for renamed symbols. No `@deprecated` wrappers. If the API changes, callers update.
- This applies across the multi-package monorepo — published packages move together.

## Commits & PRs

- Conventional commits format. Single-line subject. No body unless genuinely useful.
- **NO `Co-Authored-By: Claude` trailer.**
- **NO "🤖 Generated with Claude Code" footer in PR bodies, commit messages, issue comments, or anywhere else.**
- Never amend commits. New follow-up commits only. (Pre-commit hook failures: fix and create a new commit, don't `--amend`.)
- Don't auto-push subagent exploration branches — local commits only. The user pushes when ready.
- `main` is **not** branch-protected (so the `Publish packages` workflow can push the release commit + tag directly, like voxcss). Still use PRs for feature work by convention — but it's not enforced, and direct pushes to `main` are allowed.
- **Release = one click.** Run the `Publish packages` workflow (Actions tab → "Run workflow", choose `patch`/`minor`/`major`, or `gh workflow run publish-packages.yml -f bump=patch`). It bumps every package in lockstep, builds, publishes to npm, and commits + tags `v<X.Y.Z>` back to `main`.

## Tests & build

- Refactors must keep all tests passing. Don't delete or weaken assertions to make a refactor go through.
- If a renamed export still has tests for the old name, rename the test imports — don't keep the old export as an alias just to satisfy them.
- `pnpm test` runs the full suite across every test-bearing package.
- **`pnpm build` is mandatory before opening a PR.** Vitest doesn't catch DTS / declaration build failures (tsup runs strict type-checking that vitest's transient TS pass doesn't enforce). A green test run with a red build is a real failure mode. Run `pnpm test && pnpm build` as a unit; treat either failing as "not ready."
- **CI enforces both gates.** `.github/workflows/ci.yml` runs `pnpm test` + `pnpm build:packages` + `pnpm build:website` on every PR against `main` and on every push to `main`. Don't merge with red CI.

## Style / process

- No time estimates in planning docs ("2 days", "1 hour" etc.). This is agentic engineering, not human team scheduling.
- Prune superseded content from long planning docs as you go — don't just append.
- No half-finished features, no speculative abstractions, no defensive code for cases that can't happen.
- No comments explaining *what* code does — the code already says that. Comments are for *why*: a non-obvious constraint, a workaround for a specific browser quirk, an invariant that isn't visible locally.
